差分隐私部分建议设计为一个运行在可信本机的**隐私发布子系统**。它负责决定哪些信息可以离开本机、采用什么随机机制、消耗多少隐私预算，以及网络故障后如何恢复。

本地前导网络负责计算，隐私发布子系统负责发布。两者之间设置明确接口：前导网络产生的原始激活只能进入本地发布服务，不能直接交给网络传输层。

以下是完整的目标架构描述。当前项目已有拆分推理和裁剪基础，但 Gaussian 机制、组合会计、持久预算账本与正式发布事务仍待实现；下文不代表系统已经具备差分隐私保证。

**一、明确保护目标与信任边界**

首先确定保护对象。建议第一阶段保护“单条用户输入的内容”，采用 **prompt replacement 邻接关系**：在预先声明的输入域中，将一条完整 prompt 替换为另一条 prompt，云端观察到的输出分布变化受到限制。

对于任意相邻输入 \(x\sim x'\) 和可观测事件集合 \(S\)，要求发布机制满足：

\[
\Pr[M(x)\in S]
\leq
e^\varepsilon\Pr[M(x')\in S]+\delta
\]

其中，\(\varepsilon\) 和 \(\delta\) 描述所声明邻接关系下的隐私损失。它们不表示“绝对保密程度”，\(\delta\) 也不能直接解释成某次请求泄密的概率。

第一阶段需要明确以下边界：

- **可信本机**保存原始输入、tokenizer、本地前导网络、本地 KV、原始激活、随机化机制和预算账本。
- **云端**能够观察收到的激活载荷、允许公开的元数据、请求次数及协议行为，并可能尝试反演输入。
- **网络攻击者**主要由认证和 TLS 应对；TLS 不阻止云服务提供方分析已经收到的数据。
- **身份、是否发起会话等信息**如果被列为公开元数据，就不属于当前保证的保护对象。不能据此声称保护用户参与情况或隐藏通信存在性。

机制证明可以针对预先定义的观察模型成立。面对恶意云端返回异常结果，本地还必须进行协议校验；不能允许云端通过返回指令改变本地模型、扩大发布范围或关闭隐私机制。

**二、整体架构与主要数据流**

建议按以下顺序组织：

```text
用户输入
   ↓
可信本地：Tokenizer / Embedding / 前 K 层 / 本地 KV
   ↓
原始激活，仅保留在本地
   ↓
PrivacyReleaseService：唯一隐私发布入口
   ├─ 解析并校验已批准的 PrivacyProfile
   ├─ 校验公开形状、模型清单和协议元数据
   ├─ 计算本次发布的隐私费用上界
   ├─ 原子检查并预留预算
   ├─ 对完整发布向量进行裁剪和随机化
   ├─ 持久化唯一载荷及发布记录
   └─ 持久标记可能出站后，允许发送
   ↓
认证传输层
   ↓
云端后段计算
   ↓
返回 token / 结果及步骤回执
   ↓
本地核对回执、更新执行状态
   ├─ 满足批准的结束条件：结束会话
   └─ 继续生成：产生新激活，再次进入隐私发布服务
```

这里最重要的控制关系是：**传输层只能发送发布服务已经批准并持久绑定的载荷**。它不能接收任意原始激活，也不能在隐私服务不可用时自行降级。

工程上可以使用仅在发布服务内部构造的 `PreparedRelease` 对象，将载荷引用、预算记录和摘要一起交给传输层。还需要限制其他网络出口，避免调用方绕过门面后直接上传数据。

**三、PrivacyProfile：将隐私承诺写成不可变合同**

`PrivacyProfile` 应是经过独立审查、批准和版本管理的合同。Planner 可以请求某个 profile，自进化模块可以在批准集合内提出配置建议，但都不能临时修改其数学含义。

合同至少包含以下内容：

| 字段组 | 必要内容 |
|---|---|
| 保护定义 | 保护单位、邻接关系、允许输入域、观察者与信任假设 |
| 发布范围 | 发布张量、公开元数据、prefill/decode 行为、允许的输出通道 |
| 数值约束 | 公开形状、裁剪范数、敏感度界、数据类型和编码方式 |
| 随机机制 | 机制名称、版本、校准方法、噪声参数及实现版本 |
| 组合规则 | 会计方法、参数网格、目标 \(\delta\)、允许累计预算 |
| 交互协议 | 最大发布次数、停止规则、重试规则、异常处理 |
| 身份绑定 | 保护主体映射、账户范围、模型 manifest 和策略版本 |
| 生命周期 | 批准状态、生效时间、撤销条件、兼容性要求 |

profile 一旦用于发布，其内容不能原地修改。参数变化应形成新版本，并重新检查与历史消费的组合关系。

新建一个 profile 名称不意味着获得新预算。系统必须根据同一保护主体和同一保护目标，处理跨 profile 的累计消费。

**四、先约束完整通信记录，再讨论张量加噪**

云端观察到的内容包括：

```text
激活数值
张量形状
attention mask
位置与偏移信息
包大小
请求次数
停止行为
错误分支
重试行为
通信时间
```

如果这些信息直接依赖私有输入，单独扰动激活数值不足以支撑“完整会话满足 DP”的声明。

建议第一阶段采用公开固定协议：

1. 输入限制在明确的允许域内，使用公开长度上限和批准的 padding 方案。
2. 外发形状、mask 和位置字段按固定协议生成，不直接暴露真实输入长度。
3. 不发送原始 token ID、私有长度或由私有内容产生的调试信息。
4. 首先验证单次发布，再扩展到预先限定次数的交互。
5. 停止和错误处理必须纳入观察范围。

尤其需要检查现有拆分协议中的 `position_offset`、真实长度和 mask。它们在无隐私基线中可能是合理字段，但不能未经分析直接沿用于 DP profile。

如果停止条件仅由已发布结果、云端返回结果和公开配置决定，可以在相应假设下分析为公开历史的后处理。若本地根据原始输入决定提前停止、改变请求频率或返回不同错误，则需要额外处理。

通信时间如果不在本阶段保证中，必须明确排除；如果声称覆盖，则需要进一步设计调度、填充和异常行为，不能仅依靠固定张量形状。

**五、发布机制：完整向量裁剪与 Gaussian 随机化**

建议先采用便于核查的 Gaussian 基线。

设一次发布的完整激活展平为：

\[
h(x)\in\mathbb{R}^{d}
\]

对整个向量做全局 L2 裁剪：

\[
\bar h(x)
=
h(x)\min\left(1,\frac{C}{\|h(x)\|_2}\right)
\]

因此，对任意两个允许输入：

\[
\|\bar h(x)-\bar h(x')\|_2\leq 2C
\]

在上述 replacement 定义下，可以使用保守敏感度界：

\[
\Delta_2\leq 2C
\]

随后发布：

\[
Y=\bar h(x)+Z,
\qquad
Z\sim\mathcal N(0,s^2I_d)
\]

这里的 \(s\) 是每坐标噪声标准差，不能和未定义的 noise multiplier 混用。

需要特别明确：

- 裁剪对象是**一次完整发布向量**。
- 对每个 token 分别裁剪后一起发布，需要重新分析整体敏感度。
- 不能把 replacement 的 \(2C\) 直接换成 \(C\)。
- 不能用 `sigma = 1 / epsilon` 代替敏感度与噪声校准。
- 降维、压缩或坐标变换应明确发生在裁剪之前还是之后，并分析相应影响。
- 有限精度采样、随机源和数值异常属于实现审查范围，理想实数 Gaussian 公式不会自动证明具体代码正确。

建议采用固定版本、经过核查的解析 Gaussian 校准实现。统计检验可以检查分布和实现错误，但仅凭“噪声看起来像正态分布”不能证明 DP。

**六、组合会计：每次新增信息发布都计入同一账本**

自回归推理的下一次本地激活通常仍依赖原始输入或本地 KV，因此属于新的私有查询。

以下情况均需判断是否新增消费：

- prefill 激活发布；
- 后续每个 decode 激活发布；
- 同一输入重新生成新的噪声载荷；
- 用户重复提交相同或相关请求；
- 跨会话再次使用同一保护主体的数据；
- 将依赖私有输入的去噪结果或经验摘要重新外发。

对具有敏感度 \(\Delta_t\)、噪声标准差 \(s_t\) 的 Gaussian 发布，在适用条件下，其 \(\alpha\) 阶 RDP 上界为：

\[
\rho_t(\alpha)
=
\frac{\alpha\Delta_t^2}{2s_t^2}
\]

多次发布可组合为：

\[
\rho_{\mathrm{total}}(\alpha)
\leq
\sum_t\rho_t(\alpha)
\]

再转换为给定 \(\delta_{\mathrm{target}}\) 下的一个有效上界：

\[
\varepsilon_{\mathrm{total}}
\leq
\inf_{\alpha>1}
\left[
\rho_{\mathrm{total}}(\alpha)
+
\frac{\ln(1/\delta_{\mathrm{target}})}{\alpha-1}
\right]
\]

实现时可固定一组 \(\alpha\) 阶数，保存累计 RDP 向量，并采用保守舍入。

预算预留前，应计算：

```text
已有消费 + 尚未解除的预留 + 本次费用
                  ↓
转换为目标 δ 下的 ε 上界
                  ↓
是否仍满足账户上限
```

不能只分别检查每个请求的 \(\varepsilon\)，也不能在使用 RDP 时，把累计预算简单实现成未经定义的“余额减一”。

第一阶段建议固定机制参数和最大发布次数。根据私有激活动态降低噪声、修改预算或改变停止规则，需要额外理论支持，不应混入初版。

**七、预算账户：认证用户与保护主体需要分别建模**

账户不能仅使用请求体中的 `ownerId`。调用者可以随意更换的字段不能决定预算归属。

建议区分：

- `principalId`：当前经过认证、发起调用的身份；
- `privacyAccountId`：用于累计隐私损失的账户；
- `protectedSubjectRef`：实际被保护的人、记录或输入贡献范围；
- `compositionScope`：哪些发布需要组合。

如果多个登录账户能够访问同一人的私有数据，仅按登录用户分别记账可能漏计。因此，账户映射必须由可信策略确定，不能由调用方自报。

会话结束、应用重启、profile 更名、模型更新和图版本回滚，都不能清除已有消费。

如果产品使用“预算窗口”，需要解释窗口的隐私语义。自然日过去并不会让攻击者忘记昨天看到的信息，因此不能通过每日清零就宣称获得了新的全生命周期预算。

**八、PrivacyReleaseService：唯一发布编排服务**

发布服务承担事务编排，不应同时承担模型推理、HTTP 实现和数学库实现。

建议依赖以下端口：

| 端口或组件 | 职责 |
|---|---|
| `ProfileRegistry` | 读取已批准、不可变的隐私合同 |
| `BudgetStore` | 原子预留、查询和持久记录累计消费 |
| `PrivacyAccountant` | 计算费用与组合上界 |
| `PrivacyMechanism` | 执行合同规定的裁剪和随机化 |
| `PayloadVault` | 受控保存唯一载荷与摘要 |
| `ReleaseOutbox` | 管理待发送、可能已发送和回执状态 |
| `RemoteTransport` | 发送批准载荷、查询远端步骤回执 |
| `AuditSink` | 保存不含敏感正文的审计事件 |

建议发布请求包含：

```text
releaseId
privacyAccountRef
authenticatedPrincipalRef
profileDigest
manifestDigest
sessionId
requestId
step
phase
activationRef
publicProtocolVersion
```

原始激活通过本地受控引用传入。profile、身份、会计费用和协议字段均由服务核验，不能相信调用方提供的“已扣费”“已匿名”标记。

**九、发布事务状态与严格执行顺序**

建议采用以下状态：

```text
不存在发布记录
      ↓
RESERVED
预算已原子预留
      ↓
PREPARED
唯一随机化载荷已持久绑定
      ↓
MAYBE_SENT
发送资格和可能出站状态已持久化
      ↓
ACKED
收到并核验远端回执
```

执行顺序必须是：

1. 核验身份、profile、manifest、会话和公开协议。
2. 在事务中检查 `releaseId` 是否已存在。
3. 对新发布计算费用，原子检查并预留预算。
4. 在本地执行裁剪与随机化。
5. 将唯一载荷、摘要和机制身份持久化，转入 `PREPARED`。
6. 持久写入 `MAYBE_SENT`，随后才允许网络发送。
7. 收到有效回执后转入 `ACKED`。

`releaseId` 应具有唯一约束。同一标识重复提交时，必须核对请求绑定信息；内容冲突则拒绝，不能覆盖旧记录。

如果账本和载荷存储位于不同系统，需要定义明确的准备协议。只有预算记录有效、载荷确已持久保存且摘要一致时，才能进入可发送状态。任意一边失败都不能放行网络输出。

**十、重试、超时和崩溃恢复**

隐私发布不能依赖网络提供“恰好发送一次”。网络可能丢失回执，也可能重复交付，系统必须接受这种现实。

关键规则如下：

| 故障位置 | 处理方式 |
|---|---|
| 预算预留前失败 | 不发送，未产生本次预留 |
| 预算已预留、载荷尚未持久化时崩溃 | 初版保守保留费用，禁止该标识重新采样 |
| 载荷已持久化、尚未发送 | 可恢复同一载荷，按明确流程继续 |
| 已进入可能出站状态但超时 | 保留消费，先查询远端回执 |
| 回执确认该步骤已完成 | 使用原回执继续，不再次推进云端 KV |
| 远端状态不明 | 保守失败或按协议重发原载荷，不能重采噪 |
| 原载荷丢失或损坏 | 拒绝恢复发送，不能生成新载荷冒充原发布 |
| 账本损坏或无法写入 | 关闭发布，不能创建空账本继续运行 |

重发完全相同的随机化载荷，本身不会增加一个独立随机样本；但次数、时序等协议行为仍需符合已声明范围。

如果重新采样：

\[
Y_1=\bar h(x)+Z_1,\qquad
Y_2=\bar h(x)+Z_2
\]

云端获得了两个独立观察，因此必须作为两次发布进行会计，不能沿用一个旧收据。

**十一、隐私事务与拆分模型 KV 事务分离**

两类事务解决不同问题：

- 隐私事务保证发布被正确记账，并绑定唯一随机载荷。
- 模型会话事务保证同一个步骤不会重复推进 KV、重复采样 token 或发生乱序执行。

两者通过以下身份关联：

```text
认证身份
sessionId
requestId
step
manifestDigest
releaseId
payloadDigest
```

云端应在会话锁或等价串行控制下：

1. 检查请求身份、步骤与载荷摘要。
2. 已完成的相同请求返回原始回执。
3. 相同请求标识但摘要不同则拒绝。
4. 新步骤执行后段计算。
5. 将后段 KV 更新、生成 token、步骤号和回执作为一个逻辑提交。
6. 无法确定提交结果时，使会话进入明确失败状态，避免继续使用不一致 KV。

本地在回执身份校验通过后，才提交对应的输出与下一步推进。若恢复所需的本地 KV 或待处理状态丢失，初版应终止旧会话，而不是假装可以继续。

新会话可以重新开始，但此前消费继续保留，新发布继续计费。

**十二、输入异常、取消和输出处理**

输入验证也可能形成侧信道。例如，云端能通过是否发起请求判断某个私有条件是否成立。

因此需要事先选择并写清：

- 哪些输入属于允许域；
- 输入拒绝是否属于公开行为；
- 哪些错误可能被云端观察；
- 是否需要统一响应、固定调度或其他处理。

不能把只适用于“合法输入域内”的证明扩展为任意输入的完整行为保证。

取消操作同样不能自动退款。取消前已经发送或可能发送的载荷仍保留消费；只有经过严格定义、可以证明未被观察的取消协议，才可能释放未使用预留。

云端对已发布载荷进行计算，通常属于该载荷的后处理。但是，本地如果再次读取原始输入进行去噪、生成解释或抽象经验，然后把结果发送出去，就形成了新的信息通道，需要单独分析。

**十三、审计、存储和跨模块权限**

审计建议记录：

```text
发布身份与账户引用
profile / manifest 摘要
机制与会计版本
公开形状及协议版本
费用上界与累计消费
载荷摘要
状态迁移
回执与故障类别
```

审计日志不应包含原始 prompt、原始激活、噪声种子或能够还原原载荷的调试信息。持久化随机载荷仍需加密、访问控制和保留期管理。

载荷过期后可以清理，但应保留足以阻止旧 `releaseId` 被重新采样或重新使用的记录。删除载荷不意味着删除消费。

与其他模块的权限关系应明确：

- **Planner**提出质量和资源需求，不直接更改隐私预算。
- **Runtime**提供真实身份、执行授权和批准的配置绑定。
- **前导网络**提供待发布的本地激活。
- **隐私发布服务**独立判断是否可以外发。
- **自进化模块**只能提出经过评测的配置或结构候选，不能自行批准新的隐私机制。
- **版本回滚**不回滚隐私账本，也不恢复已经消耗的预算。

经验摘要、技能内容和训练数据如果包含私有轨迹，不能因为被抽象过就认为自动获得 DP。它们需要单独的数据授权与保护定义。

**十四、实施顺序与验收标准**

建议分四步实施。

第一步，完成单次发布原型：冻结邻接、允许域、完整发布向量、公开协议和机制版本，验证全局裁剪、敏感度及 Gaussian 校准。

第二步，完成持久事务：实现预算预留、唯一载荷、发送状态和恢复机制，重点验证并发、重试、磁盘故障与进程崩溃。

第三步，接入固定次数的拆分会话：对 prefill、decode、停止、长度、错误和跨会话消费进行统一分析，确认没有独立于批准机制的私有旁路。

第四步，开展质量与系统评估：

| 验收维度 | 重点检查 |
|---|---|
| 数学与数值 | 邻接、敏感度、校准、组合条件、有限精度 |
| 发布事务 | 原子预留、唯一载荷、未知出站、幂等恢复 |
| 模型会话 | 步骤一致、重复请求、KV 提交、重启失效 |
| 任务效用 | 完成率、答案质量、不同输入长度和任务类型 |
| 经验攻击 | token/实体恢复、激活反演及辅助信息条件 |
| 系统成本 | TTFT、TPOT、上下行字节、内存和持久化开销 |
| 长期运行 | 跨会话累计、profile 切换、版本回滚与账本保留 |

攻击实验用于衡量指定条件下的经验风险，不能替代机制证明；形式化机制正确也不意味着任务效用一定可接受。只有定义、实现、完整协议和事务行为都通过核查后，才应启用对应的正式 DP profile。
