## 实际持久化顺序

1. NodeRunner 先在 ExecutionValueStore 保存 prepared WAL 和 PREPARED NodeExecutionRecord，再装配上下文并调用 Adapter。prepared 不是成功 Receipt，更不是“副作用未发生”的证明。
2. 返回值经过输出合同及审计，引用/正文进入各自受控仓库；不可变 committed Receipt 先提交，随后 NodeExecutionRecord 进入 COMMITTED。这里的 ValueStore、审计、记忆、Provenance 不是同一个事务。
3. Native Scheduler wrapper 将 step.succeeded 与 Run 快照在 Workflow SQLite 的一个事务提交，flush Identity outbox，将 Attempt/StepExecution 标为 succeeded。
4. 图提交节点结果并 yield node_completed；Runtime 追加成功 Trace、Provenance 引用，将完成投影持久化到 Run。超步结束才清空 active 列表。
5. superstep_completed 调用 ACGStatePersistence.save_checkpoint：独立 Checkpoint SQLite BEGIN IMMEDIATE + 版本 CAS 提交新正文；之后才更新 Workflow Run 的 checkpointId。既有 after_checkpoint hook 精确处于两个数据库提交之间。

不存在 Workflow/Checkpoint/Identity/ValueStore 的联合原子事务。恢复只承认各自已经提交、能相互解释的事实。

自动确认条件：

- promoted checkpoint 正文与原 Handoff/staged 来源一致；新恢复点的 Graph/Run/Permit/generation、内容派生 ID 和版本通过原有 head validator。

- 仅支持无控制、无循环、无 review/skip/黑板/辩论状态的已结算 DAG 超步。依赖闭合使用已编译包的完整 edges；不新建拓扑编译器。
- promoted 已完成前缀的结果、上下文、记忆、Trace、摘要及 Provenance 引用不得变化。

- ValueStore 输出/上下文必须与封存 Provenance checksum 一致；引用归属复用现有 validate_state_references。
- 全部执行 operation 必须有可解释的 WAL/Receipt。未知 prepared、无 NodeExecutionRecord、未投影成功或其他不完整状态拒绝自动对账。

## 失败、审核与显式重试

仅“发生异常”不足以证明外部副作用未发生。本轮正向重试采用真实 AgentInvocationAdapter 的解析失败路径：B 节点已有调度、Attempt、StepExecution 和 prepared WAL，但 Agent 尚未调用。Adapter 在其服务端解析失败分支给出 not_invoked 标记；NodeRunner 将现有 NodeExecutionRecord 标为 FAILED/AGENT_NOT_IN_SCOPE。普通 Agent 异常即使有同名 code，也不会默认得到该标记。

B 首次失败后经过现有 Planner wait 与 Review 拒绝，进入 FAILED；显式 operator prepare_single_step_retry 是后续独立操作。既有 Review 拒绝路径缺少立即 flush Identity outbox，会导致下一步 retry 看到非 FAILED Identity，本轮补齐这条生命周期接缝。

Permit 图的 retry 只允许同 Run，保留 GraphVersion/Permit/generation、已完成引用及通信预算。原审核屏障只有已有拒绝 Trace 能证明已解决时才清除其 planner marker，不清除节点审核合同。原 Retry 规则分配新 AttemptId/StepExecutionId，写入正常新 checkpoint，再交回同一个 Native Scheduler。旧 Attempt/StepExecution 不改写，旧终态 NodeExecutionRecord 不能被迟到成功升级。

这不是通用外部副作用补偿：已进入 Agent 后异常/失联但无结算证据，仍然保留 prepared 并阻止自动重试；不能用 retryable=True、清空 Attempt 或新 Key 证明安全。

## 进程实验与失败反例

所有实验使用真实临时 SQLite、正式 S02 接受→物化→激活→B1 Handoff→Permit 链及原 Native Scheduler，不依赖 LLM 生成指定图。

- 独立 spawn 子进程执行 B，把模拟外部副作用写入独立文件；Checkpoint 提交、Run 未确认时直接 `os._exit(71)`。不是 Python 异常模拟死亡。新 Runtime 对账后仅调用 C/D，外部文件中的 B 恰好一条，A/B 均不重跑；旧 Run 快照保存被拒绝。
- 另一子进程写入外部副作用后、结果结算前 `os._exit(72)`：prepared/不明操作保留，新 Runtime 拒绝自动恢复，没有后续 Agent 调用。
- 删除 B 的独立执行记录、损坏 checkpoint、撤权、取消、对账计算期间新增操作员输入，均拒绝确认，不覆盖新的操作员数据。
- B 真实 Adapter 解析失败→Planner wait→Review 拒绝→原 Retry authority→新 Runtime；B/C/D 成功，A 不重跑，新旧 Attempt/StepExecution 区分，旧终态 NodeExecutionRecord 迟到提交拒绝。撤权变体阻止下一次外部调用。

开发期先固定了缺少 reconcile API 的失败测试（真实子进程已到达故障切口），再实现对账。正向重试先复现了遗留 planner marker 拒绝与 Identity 尚未同步 FAILED 的两处接缝，均在原恢复/审核边界做最小修复。另有夹具 Planner 在任务耗尽时仍建议 continue，合法进入 WAITING_REVIEW；新夹具改为按真实 remaining_step_ids 提议 complete，没有修改生产预算、deadline 或放宽断言。

## 自动恢复与介入边界

| 状态 | 行为 |
|---|---|
| 完成事实已投影、收据/Identity/Provenance 齐全，只有 checkpointId 未确认 | 自动对账，可再调度后继。 |
| 无新头且证据完整 | 幂等返回；不重新执行已完成工作。 |
| 可信 Adapter 已证明未调用，Identity 已结算失败 | 可经既有审核/显式重试；不自动发新 Permit。 |
| prepared 但无法证明副作用结算 | 拒绝自动重试，需要外部结算证据/人工介入。 |
| 缺失或损坏证据、来源漂移、撤权、取消、控制图/未解决审核 | 保守拒绝，不回退旧头。 |
| Receipt 已提交但 node_completed/Trace 尚未投影，或 Retry checkpoint 准备本身中断 | 当前自动对账不涵盖，需要独立证据流程，不能据此重跑。 |
