# PR-S03-02B2｜Execution Permit Authority 实施记录

日期：2026-10-19

状态：实现完成，等待独立验收；工作区未提交。

## 范围

在 S03-02A/B1 的显式激活与 `STATE_PREPARED` Handoff 之上增加 opt-in Execution Permit Authority。Permit 只在服务端从持久化 Handoff、已接受 Graph Revision、当前权限、Frozen Run/Checkpoint 和 Identity 来源重新验证后签发。客户端只传 `handoff_id` 与幂等键，不能传 candidate package、checkpoint 内容、attempt 身份或执行授权。

新增 `ExecutionPermitRecord`，以 `PREPARING → ISSUED` 表示跨 Workflow、Checkpoint、Identity 三个持久化边界的可恢复交接；只有 Workflow SQLite 中的 `ISSUED` Record、正式 Run Permit 投影和 promoted checkpoint 身份在同一最终事务中一致时，执行入口才接受 Permit。相同键重放返回历史 Receipt；同一 Handoff 使用其他键或同键绑定不同来源时拒绝。Runtime 装配不运行 DDL，Permit Store Schema 只能通过显式管理升级接口建立。

交接顺序为：复验 B1 候选及来源 → Workflow 写入 `PREPARING` → Checkpoint 按来源版本 CAS 提升并绑定 Permit/attempt generation → Identity 以独立幂等事件更新同一个 Run 的图与 TaskPlan → 再验 Workflow、权限和外部提升 → 单个 Workflow 事务将 Permit 与 Run 投影一并置为 `ISSUED`。跨库步骤不声称联合原子；任何中断保留 `PREPARING`，同一幂等键可在新 Runtime 实例中重驱动。失败的来源变化不会生成可调度 Permit。

`ACGNodeRunner` 的新图 receipt key 含有 attempt generation，使新 GraphVersion 的 attempt 不会复用旧图完成收据。执行入口在资源分配前、分配后及 NodeRunner 调用前复核当前 Permit、Mission 权限、激活头、Identity 投影和取消/终态；授权失效会阻止新节点派发。资源要求只从激活包的 Binding Manifest 派生，不作资源预留；调度前会与包复核，避免普通 Run 写入降低候选节点能力要求。可信 Recovery 可调整非权威 `agentRole` 排序偏好，能力与其余执行约束仍须匹配编译包。

## 2. 真实权威链与签发线性化点

`WorkflowRuntime.issue_execution_permit` → `ExecutionPermitAuthority.issue`（`runtime/execution_permit.py:66`）：只接受 handoff ID 与原 Key；读取 `STATE_PREPARED`，取得 Run 进程锁与 OS 文件锁。首次请求调用 B1 `_validated_candidate`，比较完整 Handoff，再在 Workflow 事务登记 PREPARING。

`_reconcile`（同文件 :164）顺序为：读取/校验 staged 正文 → 判断两库已晋升情况 → 必要时 B1 来源重验 → Workflow Fence → Checkpoint `save_promoted` → Identity 专用投影 → 校验两库结果 → Workflow 最终事务内再验 → `_issue` CAS 与 Run Permit/Checkpoint 投影一起提交。

**签发线性化点是 Workflow 最终事务 COMMIT**，不是 Checkpoint 或 Identity 晋升成功。`execution_permit_store.py:96` 只允许未变的 PREPARING 转 ISSUED；`planning_commit_store.py:65` 的事务包装在异常时回滚。表对 permit ID、Key、Handoff、Activation 建立唯一约束（`execution_permit_store.py:11`），行正文、索引和 checksum 在读取时对表。Runtime 装配不执行 Permit DDL；本轮只在临时 SQLite 显式升级测试 Schema。

PREPARING 不能调度。历史同 Key 的 IDEMPOTENT_REPLAY 只报告历史事实；派发仍重新查询 ISSUED、正式 Activation 链、当前 Mission 接受头和权限，不把 Receipt 当执行许可。新 Key 不能绕过旧 PREPARING。

## 3. 执行许可与恢复点

当前入口为 `_claim_acg_execution`（`workflow_runtime.py:1131`）：OS Run Fence 覆盖执行槽认领至执行结束，持久 Head 存在而 Authority 缺失时拒绝。`validate_activation_run`（`graph_activation_store.py:77`）校验正式 Head、Activation、Materialization、完整包、Run 投影和 Permit 链；普通 Store 写入也经过此校验。

READY decorator 在 Binder 前、分配后、Identity 事件持久化后和 NodeRunner 前调用权限校验（`acg_execution.py:589,669,760,765`）。ResourceBinder 仍负责真实资源选择；compiled binding requirements 在入口与包比较，Run 字典不能降低能力合同。候选窗口、模型、Receipt 都没有资源选择或 Permit 签发权。

本轮新增 `_assert_recovery_head`（`execution_permit.py:409`）：不可变 promoted checkpoint 必须与 staged/Handoff 逐字段一致，版本必须等于 Permit 初始版本；当前最新 Checkpoint 必须由 Run 确认，且 Run/Graph/Version/Permit/Generation 全部一致。后续正常执行 checkpoint 允许版本增长，但必须符合现有 `state_persistence.py` 的内容派生 ID，不能用“永远等于签发时版本”阻断正常 B/C/D 执行。该 ID 是完整性校验，不是签名，也不抵御拥有数据库任意写权限者同时重算全部内容与索引。

## 6. Attempt、副作用与 Native Scheduler 证据

Scheduler 为带 generation 的执行按 `{generation,run,step,attempt,loop}` 确定性生成 Attempt ID（`acg_execution.py:603` 附近）；NodeRunner 的 commit ID 包含 generation（`node_runner.py:1104`）。Identity Attempt/StepExecution 和资源绑定在调用前对表，不允许当前节点借用 A 的 Task 身份。

真实临时 SQLite + 原 Native Scheduler 测试执行 A 后交接 v2，签发本身不调用 Agent；继续执行 B/C/D，完成记录处于当前 generation，A 不重新调用。新增 transport retry 成功分支实际调用顺序为 B、B、C、D，Agent 成功列表严格为 A、B、C、D；撤权分支仅第一次 B 进入 Adapter 后报告 transport 错误，第二次调用被挡，只有 prepared WAL，无成功收据。调用前 cancel、Identity 漂移、Head 损坏和 Run binding 改变也被挡。

授权证明截止于**单机 Runtime 调用 Adapter 的入口**：guard 与调用之间没有新增 await，异步上下文装配/事件/重试等待之后会重验。但 Principal 数据库、Checkpoint、Identity、Workflow 没有联合 CAS；其他线程仍可能在最后一次读取后修改外库。已经进入的 Agent/Tool/远端 Adapter 可以内部 await；本轮不能证明其内部后续每个外部副作用都在当前授权下，也不能中止已发生的远端副作用。不得把本报告用作跨机器执行许可验收。

## 失败、审核与显式重试

仅“发生异常”不足以证明外部副作用未发生。本轮正向重试采用真实 AgentInvocationAdapter 的解析失败路径：B 节点已有调度、Attempt、StepExecution 和 prepared WAL，但 Agent 尚未调用。Adapter 在其服务端解析失败分支给出 not_invoked 标记；NodeRunner 将现有 NodeExecutionRecord 标为 FAILED/AGENT_NOT_IN_SCOPE。普通 Agent 异常即使有同名 code，也不会默认得到该标记。

B 首次失败后经过现有 Planner wait 与 Review 拒绝，进入 FAILED；显式 operator prepare_single_step_retry 是后续独立操作。既有 Review 拒绝路径缺少立即 flush Identity outbox，会导致下一步 retry 看到非 FAILED Identity，本轮补齐这条生命周期接缝。

Permit 图的 retry 只允许同 Run，保留 GraphVersion/Permit/generation、已完成引用及通信预算。原审核屏障只有已有拒绝 Trace 能证明已解决时才清除其 planner marker，不清除节点审核合同。原 Retry 规则分配新 AttemptId/StepExecutionId，写入正常新 checkpoint，再交回同一个 Native Scheduler。旧 Attempt/StepExecution 不改写，旧终态 NodeExecutionRecord 不能被迟到成功升级。

这不是通用外部副作用补偿：已进入 Agent 后异常/失联但无结算证据，仍然保留 prepared 并阻止自动重试；不能用 retryable=True、清空 Attempt 或新 Key 证明安全。
