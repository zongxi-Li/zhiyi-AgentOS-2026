# AgentOS 架构设计

## 分层原则

AgentOS 的核心定位是运行时内核，不承载任何具体行业 Agent 的硬编码实现。

- `agentOS/`：核心运行时。分三层：**顶层 Interface/Abstract**（agents、skills、adapters、governance、communication、memory、recovery 等抽象定义）、**Core Runtime 实现**（`core/` 子包：ACG 引擎、执行适配器、认知规划器、低熵通信实现、治理实现、工作流编排）、**基础设施**（`infrastructure/` 和 `stores/` 的具体存储/适配器实现）。
- `agent/`：应用服务层。负责 FastAPI 入口、业务编排、兼容旧接口、加载启用哪些领域 Pack。LLM 网关和 RAG 检索的实现也在此层。
- `agent/packs/`：领域能力包。法律、教育、编程、写作等具体 Agent、Skill、Workflow、Prompt 和领域数据。
- `agentOS/knowledge/`：知识库服务抽象（向量存储接口、检索器接口）。
- `agentOS/llm/`：LLM 网关服务抽象（Provider Interface、Router Interface）。

> **注**：L4 文档中原始设计的 `knowledge/`、`llm/`、`shared/` 作为独立服务目录，实际实现中：
> - `llm/` 和 `knowledge/` 的 **Interface 层**在 `agentOS/llm/` 和 `agentOS/knowledge/` 下；
> - 具体 RAG 实现（文档解析、分块、检索）在 `agent/app/rag/`；
> - 具体 LLM Provider 实现（DeepSeek、Qwen）在 `agent/app/llm/`；
> - `shared/` 未单独建立，共享类型和工具分散在各模块中。

核心规则：

1. `agentOS/src/agentos/core` 不允许直接 import 任何具体领域 Pack。
2. `agentOS/src/agentos/agents` 只保留通用 Agent Interface 和 Registry。
3. 具体领域 Agent 通过 Pack Manifest 和 Pack Registry 注入运行时。
4. 新增行业能力时，只新增 `agent/packs/<pack_id>/`，不修改 AgentOS Core。
5. Core 面向 Interface 编程，应用层负责选择 Adapter 和 Pack。

## 架构演进：设计 vs 实际实现

原始架构设计偏向扁平 Interface 定义层，实际实现演进为 **"Interface 层(顶层) + Implementation 层(core/子包)"** 的双层结构。

### 双层结构模式

| 模块 | 顶层（Interface） | core/ 子包（Implementation） |
|---|---|---|
| **governance** | `agentos/governance/` 4 个空占位文件 | `core/governance/` TraceStore / CheckpointStore / ReviewManager / WorkflowEvaluator |
| **communication** | `agentos/communication/` 3 个空占位文件 | `core/communication/` ContextAssembler / ContextPack / ProvenanceLedger |
| **models** | `agentos/domain/` dataclass 版本 | `core/models/types.py` Pydantic v2 版本（核心运行时使用） |
| **recovery** | `agentos/recovery/` 3 个空占位文件 | 恢复逻辑内嵌在 `core/governance/checkpoint.py` 和 `core/runtime.py` |

### 设计文档未覆盖的重大子系统

以下子系统在实际实现中存在，但原始架构设计未描述：

#### 1. ACG 动态群体智能引擎 (`core/acg/`)

统一计算图模型，是整个动态异构群体智能架构的核心数据结构和执行载体。

- **7 种节点类型**：StepNode / AgentNode / SkillNode / MemoryNode / EvidenceNode / ControlNode (START/END/IF/LOOP/PARALLEL/CONSENSUS)
- **统一边模型**：ACGEdge 支持 DEPENDENCY / COMMUNICATION / CONTROL_FLOW / EXECUTION / WRITE / READ / SUPPORT
- **图算法**：环检测(Kahn)、拓扑排序、悬空依赖检测、就绪集计算（并行调度核心）
- **升格机制**：`promote_workflow_to_acg()` 将线性 WorkflowDefinition 升格为带认知节点的 ACGBlueprint

#### 2. 执行适配器层 (`core/execution/`)

- **ExecutionAdapter 协议**：`start(task, run, workflow)` + `apply_review(decision)`
- **ACGExecutor**：基于就绪集的并行步骤调度引擎，集成低熵通信（ContextAssembler），支持人审中断和故障注入/自愈
- **FaultInjector**：可控故障注入（TIMEOUT / CRASH / EMPTY_EVIDENCE），用于验证自愈能力

#### 3. 认知规划引擎 (`core/planning/`)

实现"静态优选，动态补位"策略：

```
IntentParser（意图解析）
  ├── LLM 结构化 JSON 解析路径
  └── 关键词确定性启发式 fallback
       ↓
TemplateMatcher（模板匹配）
  └── domain 一级索引 + intent 二级索引 + n-gram Dice 相似度
       ├── 命中 → promote_workflow_to_acg() → ACGBlueprint
       └── 未命中 ↓
CognitiveRouter（认知路由）
  └── 多维效用评分 + 临时角色生成
       ↓
ACGBuilder（动态 ACG 构造）
  └── 语义画像 → 物化 ACGBlueprint（含 PARALLEL/CONSENSUS 控制节点）
```

### 顶层 agentOS/ 与 core/ 职责划分

- **顶层 `agentos/` 目录**：存放 Abstract Interface / Base Class / Protocol / Registry 等可被外部直接引用的抽象定义

- **`infrastructure/`、`recovery/`、`communication/`（顶层）、`governance/`（顶层）**：当前为预留占位，未来作为 Interface 注册入口，实现逐步向 core/ 收敛
