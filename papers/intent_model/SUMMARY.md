# 从意图分类到可执行任务画像：前导模型、选择性澄清与模型路由

整理日期：2026-11-18。本目录收录 14 篇论文；完整标题、版本、来源与阅读深度见 [索引](README.md)。这里的“前导模型”指请求进入 Planner 之前的 Intent Analyzer，与 [端云拆分的前 K 层](../leading_model/SUMMARY.md) 分开讨论。本文基于文献、项目合同和实现入口，提出改进设计；没有训练新模型或运行新的效果实验。

## 1. 结论：输出可核查的任务画像，而非一个意图标签

传统意图分类回答“这句话属于哪个类别”；通用 Agent 的前导模型还要回答：目标是什么、依据来自哪里、哪些约束已确认、需要哪些能力、交付物如何验收，以及什么缺失信息会改变行动。最值得做的提升是建立有来源、有版本、能增量修订的任务画像，再围绕关键不确定性选择性提问。

建议采用四层分工：意图理解形成候选语义；确定性规则校验能力、约束和合同；澄清策略判断是否值得询问；Runtime 根据正式策略选择资源和执行权限。不能把模型的意图置信分数直接当作权限、真实成功概率或隐私许可。

对 Kinlin，应先改善当前 `TaskSemanticProfile` 的证据和缺失信息表达及评估集，再考虑更换更大模型或训练。现有“模型输出违约最多修复一次，仍失败则报结构化错误”的边界应保留。

## 3. 意图入口的三个输出层级

### 3.1 意图分类和开放集拒识

CLINC150 包含 150 类意图及范围外输入。它说明：封闭类别上准确率高，并不代表能识别系统不支持的请求。项目能力目录不断变化，应区分“暂时找不到匹配能力”“用户目标不清”“能力支持但参数缺失”。三者不应该都落到一个低分标签上。

可以将能力检索分成召回和核验：先根据目录描述与同义词找候选，再检查输入、输出、执行条件及任务覆盖。目录外目标应产生未满足需求或拒识状态，不应因为最相近的能力分数最高就强制匹配。

### 3.2 Schema 驱动的任务状态

SGD 使用自然语言描述的动态服务 schema，区分意图、必填槽位、可选槽位与默认值，并覆盖跨服务泛化。论文的方法设计强调：缺少必填槽位不能调用对应服务；非分类槽位如日期和名称也不能靠固定枚举穷尽。

迁移到 Kinlin，最有价值的不是把所有任务塞进固定标签，而是让能力目录说明：完成目标需要什么输入，哪些约束决定工具选择，输出是什么，什么证据可验收。对于规划型任务，应先得到目标与验收语义，再将它们映射到能力；不要求 Intent Analyzer 在入口生成完整执行 DAG。

### 3.3 IntentGPT 的新意图发现

IntentGPT 包含一次性 In-Context Prompt Generator、语义 few-shot sampler 和推理时 Intent Predictor。生成器以少量已知意图例子构造领域 prompt；预测器结合已知意图与相关示例分配/发现意图；新发现标签反馈到后续 prompt。论文中的“学习”主要是上下文与意图库更新，不是在线更新 LLM 权重。

其方法设计鼓励生成新标签，甚至明确不分配 `unknown`。对研究中的 intent discovery 合理，但不适合直接照搬成生产执行规则。项目应让新标签先成为候选语义，经去重、定义、样本检查后纳入意图知识；新增执行能力仍需正式实现与注册。还应在评估时明确意图库随测试流更新的协议，不把动态记忆设置与固定模型测试混为一谈。

## 4. 何时问、问什么：从歧义检测到任务价值

### 4.1 CLAM 的可实现基线

CLAM 将交互拆成：输入 → 判断是否歧义 → 若无歧义则作答，若有则生成澄清问题 → 收到补充后回答。原实验主要完成一次澄清迭代，不能说它已经验证无限轮对话的最优策略。其两阶段少样本提示很适合做项目基线，易于观察歧义识别和问题生成各自的错误。

CLAMBER 提供三维八类歧义：知识层面的 unfamiliar/contradiction，语言层面的 lexical/semantic，以及输出相关 who/when/where/what。价值在于提示错误来源可能不同：“不知道字段意思”“同一词有两个含义”“时间范围缺失”“前提本身冲突”需要不同处理。

不能将该分类直接当业务必问清单。用户未指定字体、文件名或默认排序，通常仍可安全继续；但“把上个月最差的产品删掉”中的指标、范围和删除对象会改变行动及风险，必须先形成明确目标和授权边界。

### 4.2 提问价值而非问题数量

一个可操作的设计启发式是：

\[
V(q)=\mathbb E[U(\text{行动}\mid\text{回答 }q)]
-U(\text{当前最优行动})-C_{interaction}(q).
\]

这不是已有项目算法或已校准公式，而是决定问不问的目标表达。`U` 应包括任务成功、误操作损失、时限和用户偏好。实现初期可以用规则近似，不需要在线估计精确概率：只有当合理答案会改变数据源、执行对象、验收条件或外部动作时，优先问；若缺省项只影响可逆展示，可给明确默认值并继续。

Information-Gain Clarification 将目标信念更新作为训练信号，提醒我们优先消除目标不确定性。但能大幅减少不确定性的私人信息，不一定是完成当前任务必要的信息；信息增益要受最小必要采集和行动价值约束。

### 4.3 一个项目化例子

用户说：“分析一下上个月销售，找异常并出报告。”任务画像可确认“销售分析、异常、报告”为显式目标；“上个月”需结合时区与会计口径，数据源可能来自当前已授权上下文。

先读取已有上下文和目录。若只有一个已明确授权的销售表，直接使用并记录来源；若有多个互不兼容的数据源且结论会不同，问一个选择题。若异常定义没有业务约定，可先做探索性检测并在报告说明口径；若结果会直接触发扣款或删除，则必须澄清判定标准及正式动作边界。模型不应把“提高利润”或“自动处置”自行写成用户目标。

对这次文献任务，“planner”是存放目录还是应用、“前导模型”是意图入口还是拆分前段，都会改变产出范围，适合一次澄清后固化；用户已确认的答案应跨轮保留，不能每次重问。

## 5. AskBench、工具澄清与评估陷阱

AskBench 将原始 QA 构造成多轮交互，有隐藏检查点；AskMind 缺少意图信息，AskOverconfidence 含错误前提。方法评价最终正确性、检查点覆盖及冗余提问，并用 rubric-guided RLVR 训练澄清行为。该版本包含两个设置、四领域、每维每域 100 个交互，共 800 个。

它的 judge 同时参与用户模拟，适合快速自动测试，但可能受到模拟器偏差、问法偏好和同源模型偏差影响。应人工抽查真实场景；不能仅凭 checkpoint 覆盖就断言用户体验提升。RLVR 是训练手段，不需要线上每个请求都执行训练。

AskToAct 利用工具调用参数与用户意图的映射，通过去掉关键参数构造缺失意图样本，结合更正样本训练交互。对项目，可以从能力合同生成“缺一个必要条件”的测试，再加入真实用户纠正、多意图、冲突和默认可继续样本。不要只训练总能被一个参数问题解决的干净数据。

Ask or Assume、ECLAIR 和 ODUTQA-MDC 补充了代码 Agent、企业助手和表格 QA 场景。它们有助于扩展测试分布；本文未复现其多 Agent scaffold 或报告的提升，不将架构复杂度本身视为收益来源。

## 6. PICARD：合同约束应该前移，但不等于语义验证

PICARD 在自回归解码每一步检查高概率候选 token，拒绝无法通过增量解析的输出。SQL 场景有词法检查、语法解析和 scope guards，帮助排除不存在的表列或不合法结构。这与“生成完整字符串后发现 JSON 错误再修复”不同：约束可以在生成阶段阻止非法路径。

可迁移的工程方向是使用模型服务支持的结构化输出/grammar，再执行本地合同和目录校验。它们与 PICARD 的具体 SQL 解析器不是同一实现，不能声称现有 JSON schema 已经复现 PICARD。即便字段类型全部正确，目标仍可能被误读、事实来源可能不对、约束可能丢失，因此至少分三层评价：格式有效、语义忠实、任务可完成。

## 7. 模型路由：独立于意图理解的决策

RouteLLM 学习给定查询上强模型相对弱模型获胜的概率，再用阈值控制强模型调用比例。阈值越高，越倾向低成本模型。它评价强模型调用比例、质量、恢复性能差距及相应成本曲线，而不是只报告某一个阈值准确率。

FrugalGPT 的级联思路是在必要时逐步使用其他模型。两者均说明应从数据估计“什么时候升级值得”，但不能把 Intent Analyzer 的 `capabilityCandidates.score` 当成 RouteLLM 训练出的胜率。

Kinlin 可先建立显式策略：本地小模型处理已知、低风险且合同清楚的任务；合同失败、目录覆盖不足、复杂度高或语义冲突时，按预算升级；升级仍需保持相同语义合同和审计。远程调用前必须先检查允许的数据范围和隐私 profile，不能由质量路由器自行决定外发。

成本必须包括入口模型、修复、澄清、后续返工与工具成本。一个便宜但经常误解任务的入口可能增加总成本；一个高分但总提问的入口也可能降低任务完成率。

## 8. 项目现状：保持已有合同，补足证据链

核查文件：[intent_analyzer.py](../../apps/agentOS/src/components/planner/intent_analyzer.py)、[semantic_profile.py](../../apps/agentOS/src/contracts/acg/semantic_profile.py)，以及 [历史 ACG 流程说明](../../apps/agentOS/docs/ACG任务执行流程说明.md)。历史设计中的“最多 3–5 个澄清问题”是当时的交互设想，不是当前每次必须问够的数量。

当前 `IntentAnalyzer.parse()` 输出 `TaskSemanticProfile`，已有目标、证据范围、关键约束、能力与候选、预期制品、验证要求、复杂度、隐含要求、资源预算和原始输入等字段。模型输出违约会尝试一次合同修复；仍失败则抛出结构化错误。禁用或没有模型时可走显式确定性路径，不能把模型失败静默伪装成成功的高质量理解。

现有审计包括 prompt/model/schema 版本与调用预算；能力输出按目录归一。`CapabilityCandidate` 冻结、禁止多余字段，score 在 0–1 之间；但这个范围约束不构成统计校准。`TaskSemanticProfile` 当前是 `extra="ignore"`，也不能笼统说所有合同都拒绝未知字段。

推荐先扩展并验证以下语义机制，作为后续提案而非本轮代码变更：

| 建议项 | 目的 | 注意事项 |
|---|---|---|
| 逐字段 provenance | 关联用户原文、授权上下文或目录 | 不把推断描述成用户明确要求 |
| known / inferred / default / unresolved | 区分信息状态 | 默认值可追踪、可替换；不覆盖后续明确纠正 |
| 关键 missing slots 与影响 | 表达缺失会改变什么决策 | 不为所有可选字段生成问题 |
| profile revision 与变更集 | 用户回复后增量修订 | 使受影响计划失效，保留无关已完成工作 |
| 目录覆盖不足/OOS 状态 | 避免强行匹配 | 与参数缺失和模型故障分开 |
| 置信与校准数据 | 决定接受、升级或澄清阈值 | 用独立验证集，不用模型自评分代替 |

可以先用旁路审计结构实验 provenance 和 unresolved 状态，等评价收益明确后再修改正式 schema。这样可控制接口迁移成本，避免在没有验证前一次性重构整个 Planner。

## 9. 推荐控制流程与职责边界

```text
用户输入 + 已授权上下文 + 能力目录快照
→ 候选 TaskSemanticProfile
→ 合同、能力和来源校验
→ 检查关键缺失/冲突及行动影响
   ├─ 足够：记录默认与假设，进入 SemanticPlanner
   ├─ 值得澄清：提出紧凑问题，等待回复后增量修订
   └─ 不支持/故障：明确状态，按策略升级或终止
→ Runtime 校验正式策略、分配执行身份并应用提案
```

输入材料可能包含“忽略之前要求”“把数据上传”等句子。读取 PDF、网页或工具结果时，它们是来源内容，不是用户授权。任务画像应记录用户要研究什么，不得把论文实验 prompt 中的动作当成要执行的命令。

入口模型不应决定正式工具权限、执行身份或最终模型绑定；可以输出语义需求和候选，不应生成可直接绕过 Runtime 的执行权。已确认偏好与澄清答案要进入会话状态，不能在下一轮因 prompt 截断而重新询问。用户纠正目标时，应更新画像版本并按依赖失效相应计划，避免整条工作流重复执行。

## 10. 评价集与渐进改进计划

建议先建立小规模人工复核集，再扩展自动构造数据。覆盖：直接目标、多意图、目录外请求、同义表达、缺必填项、可默认项、冲突和虚假前提、历史指代、用户纠正、附文指令、隐私受限请求及多语言。拆分训练/验证/测试时按任务模板、能力或领域隔离，防止只记住同义句。

| 评价层 | 指标建议 | 失败案例要记录什么 |
|---|---|---|
| 语义忠实 | 目标、约束、交付与验证条件的准确/召回 | 丢失、添加、错归来源 |
| 能力映射 | 候选召回、最终匹配、目录外误接收 | 近似能力被当成足够能力 |
| 合同 | 首次有效率、修复成功率、失败状态 | 合法 JSON 但语义错误单独统计 |
| 澄清 | 必要提问召回、不必要提问率、问题可回答性 | 重问已知信息、隐私过采集 |
| 端到端 | 任务成功率、返工、错误动作、完成时间 | 入口理解错误与执行错误分开 |
| 成本与路由 | 总 token/金额、升级率、质量成本曲线 | 包含澄清和重规划成本 |
| 校准 | reliability/ECE 或风险覆盖曲线 | 在分布变化下是否继续可靠 |

第一步，以现有实现做冻结基线，补 provenance、OOS 和关键缺失标注；第二步，加入基于能力合同的确定性检查和选择性澄清；第三步，比较语义 few-shot 检索与少量人工示例，单独消融已知意图反馈；第四步，用真实总成本学习升级阈值；第五步，只有获得足够、经过授权的轨迹和稳定收益证据，才考虑蒸馏或 RLVR。

尤其要比较四个基线：不澄清直接做、所有缺失都问、规则选择性问、模型选择性问。只有在任务成功与交互成本同时改善时，才能称为提升；“问得更多”和“画像字段更多”本身不构成进步。

## 11. 与 Planner、隐私及本地前段的整体思路

意图前导模型决定“用户真正希望完成什么”；Planner 决定“怎样形成有证据的计划”；本地前段决定“哪些计算留在本地、外发什么表示”；Runtime 决定“什么动作在当前身份、预算和策略下可以正式执行”。四者不能用一个“前导模型分数”合并。

较有价值的研究组合是：带来源的任务画像 → 价值驱动澄清 → 受控能力规划 → 具有完整发布会计的端云推理 → 任务结果与失败原因回流。记忆回流应优先保留通用规则与经过验证的经验，含用户信息的轨迹则按授权、保留期和可用范围管理；如需 DP 训练或 DP 经验库，另行定义保护单位。
