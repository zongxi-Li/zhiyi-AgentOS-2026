# 从表格问答到经验驱动的自适应规划：方法、实现与 Kinlin AgentOS 的落地思路

研究整理日期：2026-11-18。核心材料为用户提供的 MAPLE、MACT、Table-Critic、TALON 和 Deep Tabular Research（DTR）。本目录另收集了 39 篇相关论文，共 44 份 PDF。完整书目、原始链接与阅读深度见 [README](README.md)，检索记录见 [citations/search-results.json](citations/search-results.json)。

## 摘要

这些工作的共同问题是：语言模型面对复杂表格时，容易把数据理解、任务规划、数值计算和答案验证混在一次生成中，导致早期错误沿后续步骤传播。解决路径逐渐从“把问题拆开”发展为“执行一小步、获得反馈、检查证据、局部修复、积累经验”。真正值得迁移到通用 Planner 的，是这种有状态、有证据和有边界的闭环，而不是机械增加 Agent 数量。

综合五篇核心论文，比较合理的工程组合是：以 MACT 的在线规划作为控制骨架，以 TALON 的按需数据访问控制上下文，以 Table-Critic 的首错定位控制修复范围，以 MAPLE 的结构化记忆支持跨任务复用，再借鉴 DTR 的操作依赖图和执行统计选择候选路径。本文将论文原有方法、公开代码中核对到的细节，以及针对 Kinlin 的设计建议分开说明；本文没有运行这些模型的复现实验。

## 2. 五篇核心工作的分工

| 工作 | 主要瓶颈 | 控制循环 | 持久经验 | 最适合借鉴的部分 |
|---|---|---|---|---|
| MAPLE | 单次推理无验证，完成后丢弃经验 | Solver → Checker → Reflector → Solver | Archiver 维护结构化记忆及连接 | 验证反馈、经验归档、记忆去重 |
| MACT | 规划和计算能力难以由一个模型同时承担 | 规划动作 → 工具/代码 → 观察 → 下一动作 | 主要是任务内历史 | 语义规划与工具执行分工 |
| Table-Critic | 中间步骤出错后不断传播 | Judge → Critic → Refiner，成功后 Curator | 按错误类型组织的模板树 | 定位首错、保留前缀、修复后缀 |
| TALON | 长表无法完整进入上下文，检索又会漏证据 | Planner ↔ Tool，Critic 处理循环和代码异常 | 不以跨任务记忆为核心 | Schema 先行、受控探索、类型清洗 |
| DTR | 不规则层级表格和长程分析的操作顺序不稳定 | 结构建模 → 操作映射 → 路径选择 → 执行反馈 | 路径统计与抽象经验 | 宏观路径规划、结构前置条件 |

这里有两个容易混淆的概念。第一，多个角色可以共享同一个模型权重，角色数不等于部署的模型数。第二，memory 可以指单次任务内的工作状态，也可以指跨任务经验库，两者的保留期、可信度和检索方式不同。

## 3. MAPLE：把验证、反思和记忆接成闭环

来源：[论文](MAPLE.pdf)，§3、附录 B/C/F；[官方仓库](https://github.com/bettyandv/MAPLE-table-reasoning)。

### 3.1 四个角色与实际动作形式

Solver 读取表格、问题、动作历史、剩余尝试次数和记忆，选择继续操作表格还是提交答案。继续操作时输出新的 Markdown 中间表，并用 `<NOT_READY>` 表示尚未结束；直接回答时以 `<NOT_CHANGED>` 表示表格不变。附录 F 的输出包含 `thought`、`action`、`intermediate_table` 和 `answer`。

因此，MAPLE 原论文的 Solver 不能直接等同于一个真实运行 Pandas 的执行器：其中不少中间表操作由模型生成文本完成。将它用于业务数据时，可保留其反馈结构，把过滤、排序、分组和计算下沉到确定性工具中。这是本文建议的工程改造，并非原论文已经实现的特性。

Checker 分别评价答案类型、格式和证据落地，每项 0～2 分，总分 6 分。算法 1 在得到满分时接受答案，否则调用 Reflector。Checker 是模型验证机制，其高分不构成数学上的答案正确性证明。

Reflector 接收原表、问题、推理轨迹、候选答案和检查反馈，输出错误诊断与改进计划；反馈写入工作记忆，供下一次 Solver 尝试使用。比起笼统要求“再检查一遍”，它把错误位置、错误原因与下一步动作联系起来。

Archiver 则在任务之外提炼经验。一个记忆条目包含问题类型、操作需求、正确/错误步骤、错误原因、关键词、标签等。运行时检索相关条目，维护时检索邻近条目，决定是否建立连接、更新元数据或新增记忆。

### 3.2 记忆演化及需要核对的复现细节

论文算法 2 用邻居密度过滤重复记忆：当近邻数不足阈值时才考虑新增；随后决定是否加强连接和更新邻居元数据。附录 E.3 的比较实验使用距离/相似度阈值 δ=0.7，并比较不演化、总是演化、固定间隔演化和模型选择演化。距离的具体定义依赖实现，不能把 0.7 直接当作所有向量库通用的余弦相似度阈值。

公开 README 的运行流程是 `run_batch.py` 产生多轮推理结果，`run_memory.py` 建立记忆，`mem_to_solver.py` 将检索记忆附加到后续输入。实际核对的 `run_memory.py` 第 58 行读取 `ground_truth`，后续把它作为 `correct_answer` 传入归档流程；代码第 82 行使用 `len(neighbours) <= 3` 的条件。这与论文算法中抽象的 `|N| < k_min` 应分别记录，复现时不能只凭概念描述设置参数。

这意味着上线系统不能假定每次任务结束都有标准答案。需要分别支持“已由执行结果或人工确认的经验”“仅由模型自评的暂存经验”，并在评估时固定记忆构建集与测试集。本文没有足够证据判断原实验所有记忆构建样本的隔离方式，不能据此断言存在数据泄漏；正确做法是把它列为复现协议需要核查的项目。

### 3.3 论文结果说明了什么

论文表 2 中，LLaMA3.3-70B 的 WikiTQ 准确率为 74.01%，TabFact 为 90.66%。表 3 的增量消融为 45.58 → 63.81 → 65.91 → 71.09 → 74.01，依次加入 Solver、Checker、Reflector、Archiver。这个实验支持“分步求解、诊断反馈和记忆均有贡献”，但增量是顺序依赖的，不能解释为各模块在任意系统里的固定收益。

对于 Kinlin，优先迁移的应是结构化验证与归档协议，其次才是记忆连接演化。先确保保存的经验可追溯、能区分确认方式，再考虑更复杂的记忆图。

## 4. MACT：在线规划与专门执行器的分工

来源：[论文](MACT_Findings-NAACL2025.pdf)，PDF 第 3～6 页、§3；[出版页](https://aclanthology.org/2025.findings-naacl.54/)；[官方仓库](https://github.com/boschresearch/MACT)。

MACT 由规划 Agent、编码 Agent、工具集和工作状态组成。其重点是每一步基于已经获得的观察决定下一动作，而不是先生成一个固定长计划并盲目完成。

### 4.1 五阶段循环与六种意图

每轮依次执行：生成候选动作、选择动作、选择工具或生成代码、计算观察、更新状态。动作由 `intent + instruction` 构成，六类意图为：

| 意图 | 执行方式 |
|---|---|
| Retrieval | 编码 Agent 生成 Python，读取、过滤或分组表格 |
| Calculation | 优先计算器；无法直接执行表达式时转 Python |
| Search | Wikipedia 搜索，补充外部事实 |
| Read | 从输入提供的文本上下文提取信息 |
| Ask | 调用规划模型自身知识 |
| Finish | 输出最终答案并结束 |

这里的 Search、Read、Ask 具有不同证据来源。业务系统应在观察中保留来源类型，避免把模型内部知识误当作原表中的事实。

### 4.2 多采样与效率捷径

论文默认动作及代码采样数 k=5，规划和编码温度均为 0.6，最大迭代 I=7。开源组合使用 Qwen-2 72B 规划、CodeLLaMA-34B 编码。动作选择以自一致性投票为主。

一个重要细节是：对 Python 类观察，原方法会把规划模型预测的观察与代码执行得到的观察合并投票。因此，不能把 MACT 描述为“所有中间状态都只来自真实工具”。迁移到 Kinlin 时，建议让确定性执行结果成为事实层，模型猜测只作为候选或异常检测信号。

效率模块先生成若干直接推理答案，如果高度一致就跳过完整协作。论文报告最多可减少约 33% 的迭代，但这不等于节省 33% 总费用：捷径判定本身也需要模型调用。论文正文使用“超过 α·k”的表述，同时实验 α=1；严格不等式会使这一条件无法成立。因此实现时需要核对边界比较，不能照抄成不可达分支。

论文表 3 的开源异构组合在 WTQ、TAT、CRT、SciTab 分别报告 72.6、66.2、64.4、59.8。它们用于说明同一实验内分工协作的作用，不与 MAPLE 或 Table-Critic 的不同协议直接比较。

### 4.3 对 Planner 的启发

Planner 产出“做什么、需要什么输入、成功条件是什么”；执行器负责“调用何种工具、生成何种程序、如何实际运行”；真实观察再驱动 Planner 调整。角色边界清晰后，规划模型和编码模型可以分别替换，也可以先使用同一个模型承担两个角色。

## 5. Table-Critic：从首个错误开始修复

来源：[论文](Table-Critic_ACL2025.pdf)，PDF 第 3～6 页、§3；[出版页](https://aclanthology.org/2025.acl-long.853/)；[官方仓库](https://github.com/Peiying-Yu/Table-Critic)。

Table-Critic 默认以 Chain-of-Table 产生初始推理链，然后让 Judge 判断各步错误、定位错误类型并路由模板树；Critic 生成具体批评并返回首个错误步骤 I；Refiner 根据截至 I 的局部链和批评重新构造剩余推理。最终链被 Judge 接受后，Curator 才提炼批评模板。

这里最可迁移的原则是：**保留经确认的有效前缀，避免让错误后缀继续污染修复过程。** 在线性推理链上是修复后缀；在 Kinlin 的任务图中，应转化为修复失败节点及依赖它的后代，独立分支可以复用。

模板树内部节点是较粗的错误类别，叶子保存具体错误与批评模板。更新有两种方式：向现有叶子添加模板，或者扩展树。纵向扩展把过粗叶子拆为更具体类别；横向扩展增加同层的新错误类别。它保存的是可复用的纠错程序知识，不是整张业务表的副本。

实验标准配置从两个模板开始，温度 0.0、最大修复 K=5。收敛分析中另讨论了更长轮数，应与主实验配置区分。表 1 中 Qwen2.5-72B 的 WikiTQ/TabFact 为 77.2/92.6；表 2 还统计错误变正确与正确变错误。后一个指标十分关键：一个不断“反思”的系统也可能破坏正确答案。

工程实现应保留原候选、修复候选与验证结果，只在新证据支持时替换。Curator 依据 Judge 接受而运行，仍需要独立的执行检查或抽样审计，避免把模型误判固化成长期模板。

## 6. TALON：让长表留在工具侧

来源：[论文](TALON_EMNLP2025.pdf)，PDF 第 3～6 页、§3；[出版页](https://aclanthology.org/2025.emnlp-main.1393/)；[官方仓库](https://github.com/Wwestmoon/TALON)。

TALON 不把整表放入 Planner 的上下文。完整数据在 Pandas DataFrame 中，Planner 起初读取列名和类型等 Schema，通过工具逐步获取需要的内容。论文工具涵盖模糊匹配、单元格/行获取、列含义解释、列格式处理，以及 Python 代码生成。正文和图中 `get_row/get_rows` 命名略有不同，实际对接应以所采用版本的工具 Schema 为准。

### 6.1 类型和格式本身也是推理的一部分

例如一列人数为字符串 `"30,000"`，直接比较或生成 SQL 可能得到错误结果。TALON 先理解列语义，再调用格式处理，再执行数值条件筛选。不能只因程序没有报错，就认为数值比较已经正确。

其 Critic 主要处理两类问题：重复调用造成的循环，以及代码执行异常。重复动作会触发重规划，执行错误反馈给 Critic 产生修正版代码并重新执行。这个角色不等同于 MAPLE 的最终答案检查，也不等同于 Table-Critic 的完整推理链批评。

论文默认温度 0.7、Top P=0.95、Top K=5、最大生成 1024 token、自一致性采样 5 次；Planner 最多 10 轮、Critic 最多 3 轮。它允许同工具不同参数并行调用，但存在依赖的调用仍需等待真实结果。

### 6.2 长表结果与成本含义

WTQ-L 包含 341 张长表；BirdQA 有 314 个单表问题，论文报告平均约 44,000 行。表 1 的三模型平均 EM 为 WTQ-L 66.8、BirdQA 71.9。论文给出的平均提升 7.5 和 12.0 是百分点差值，不应转述成相对百分比增幅。

只传 Schema 可以降低输入成本，但不会自动解决证据覆盖问题。例如求全表最大值，不能只对检索返回的前五行计算。应明确区分“帮助理解列和值的样例”和“用于最终计算的完整数据范围”。

## 7. DTR：用结构和执行经验选择宏观路径

来源：[论文](Deep-Tabular-Research_arXiv2026.pdf)，PDF 第 3～7 页、附录 A/C；[arXiv](https://arxiv.org/abs/2603.09151v2)。

DTR 面向合并单元格、双向表头、层级结构和隐含单位等不规则表格，并将分析任务表述为长期交互执行。与只处理规则二维表相比，它需要先知道“某个数值到底属于哪个行列语义范围”。

### 7.1 从元信息图到操作依赖图

第一步提取行列标题、子标题、单位、时间及聚合指示等元信息，构建层级和包含关系图。一个数据单元格可以同时受到行方向和列方向父节点约束，不能简单压成一条标题字符串后丢弃血缘。

第二步从种子操作库中选择 CLEAN、FILTER、GROUP、AGG、JOIN、SORT 等操作，并组织成符合依赖约束的路径。例如按某类产品比较季度总额，必须先明确季度、产品和金额列的含义；筛选发生在聚合之前还是之后，则取决于条件针对原始值还是聚合值。

### 7.2 期望评分与两类经验

论文给出的路径评分为：

```text
E(π) = R_hat(π)
       + α · P(π) · sqrt(log(sum_π' N(π')) / (1 + N(π)))
```

其中 `R_hat` 是路径经验回报，`N` 是执行次数，`P` 是结构合理性先验。选出的路径被实例化为程序，获得执行结果后再更新。实际实现还需要定义冷启动时计数为零的处理、奖励尺度、路径等价判定和统计重置方式；这些不能靠公式自动解决。

执行反馈包含是否成功、耗时和类型一致性，抽象经验则记录可迁移的策略，例如聚合前先清洗单位。论文所谓 “siamese” 在这里指两条互补经验渠道；“parameterized” 主要涉及执行信号和路径统计，不应自动解释成训练了双塔网络或更新了 LLM 权重。

论文使用指数滑动更新 `R_hat ← (1−η)R_hat + ηR`。奖励组合函数、候选路径规模和超参数仍需要复现时具体化。其 UCB 风格表达是路径选择设计，不足以直接推出在任意业务任务中的最优性或标准 bandit regret 保证。

### 7.3 对实验结果的正确解释

DTR-Bench 基于 RealHiTBench 表格构造 500 个场景分析问题，评价准确性、分析深度、可行性和美观等维度。其 Win Rate、Score Rate 与 WikiTQ 的答案 EM 不是同一种量，不能把约 37.5 的 Score Rate 写成“问答准确率 37.5%”后与其他方法比较。RealHiTBench 的问答、分析及可视化任务又使用不同指标。

对 Kinlin 更实用的启发是：先给候选方案添加可执行前置条件，再利用真实运行统计重排方案；在没有可信奖励和足够重复任务之前，不必先实现复杂搜索器。

## 8. 扩展文献如何补全研究脉络

### 8.1 从程序执行到表格状态演化

[Binder](2210.02875_Binder.pdf) 把自然语言模型能力嵌入符号程序，适合学习语言理解与可执行计算的接口；[Dater](2301.13808_Dater.pdf) 强调表证据和问题分解；[ReAcTable](2310.00815_ReAcTable.pdf) 把 ReAct 用于表格问答；[Chain-of-Table](2401.04398_Chain-of-Table.pdf) 则让中间表格随着操作链演化。它们构成了五篇核心工作的直接方法背景。

[TabSQLify](2404.10150_TabSQLify.pdf) 通过 SQL 抽取子表降低问题复杂度；[TableRAG](2410.04739_TableRAG.pdf) 分别检索 Schema 和单元格值，并进行查询扩展。TableRAG 不等于只对检索到的几行作答：检索结果用于帮助程序定位列和值，后续程序仍可访问完整表。它对不同列值去重并设置编码预算，这比无条件嵌入整行更适合大表。

### 8.2 多角色协作与长答案生成

[AutoTQA](2024_AutoTQA.pdf) 已在 2024 年讨论 User、Planner、Engineer、Executor、Critic 协同，并覆盖单表和多表。因此不能因为某篇后续论文声称“首次多 Agent 表问答”，就在综述中无条件复述为领域事实。

[TaPERA](2024_TaPERA.pdf) 用子问题—子答案序列组织内容计划，通过程序取得执行结果，再生成子答案并修订计划。它适合“分析并写出完整解释”的任务，补充了 WikiTQ 短答案设置。[ComInsight](2610.03525_ComInsight.pdf) 进一步围绕可验证原子洞察组织表到报告的证据组合；本次对它以摘要和任务定位为主，不宣称已经核验其全部实现。

### 8.3 表结构、检索和证据充分性

[ST-Raptor](2508.18190_ST-Raptor.pdf) 用 HO-Tree 表达半结构表格，结合结构构建、操作分解和两阶段验证；[系统短文](2602.07034_ST-Raptor-System.pdf) 是同一研究线的另一个版本，44 份 PDF 中包含这两份，不能当作两个独立方法系列。[RealHiTBench](2506.13405_RealHiTBench.pdf) 提供现实层级表格的评测入口。

[TableSeek](2609.34157_TableSeek.pdf) 与 [Semantic-Answerability Gap](2607.17742_Semantic-Answerability-Gap.pdf) 共同提醒：语义相似不代表证据足以回答。系统需要检查命中的数据是否包含目标时间、指标、实体和所需行列绑定，而不是只看向量相似度。

[Data.Readme](2610.25131_Data-Readme.pdf) 离线构建可混淆、可连接和可合并的表关系，在线让 Agent 沿关系导航。它把探索成本从每次问题的一次性扫描，部分转移到可复用的数据目录建设。[Octopus](2601.02304_Octopus.pdf)、[PARTAB](2608.24082_PARTAB.pdf)、[TabScope](2609.03395_TabScope.pdf)、[H2Table](2609.01216_H2Table.pdf) 和 [GRAB](2606.28916_GRAB-Latent-Bridges.pdf) 分别补充多表发现、分区证据、问题自适应范围以及图结构建模的方向，阅读深度见索引。

### 8.4 经验应从答案缓存升级为程序知识

[ReAct](2210.03629_ReAct.pdf) 提供推理与行动交替的基础；[Reflexion](2303.11366_Reflexion.pdf) 保存自然语言反思；[ExpeL](2308.10144_ExpeL.pdf) 从经验抽取可复用指导；[A-MEM](2502.12110_A-MEM.pdf) 组织记忆连接。它们能帮助解释 MAPLE，但不应被当作表格实验的直接证据。

[SkillTGR](2607.22633_SkillTGR.pdf) 将行—列—单元格关系表示成图，使用 Expand、Navigate、Anchor、Cluster、Rank 等操作，随后把成功和失败轨迹都提炼成技能。成功技能包含触发条件、操作模式和约束；失败技能包含错误步骤、根因和规避方法。相比保存具体问答，这更接近可迁移的 Planner 方法库。

[TabClaw](2606.10316_TabClaw.pdf) 展示可编辑计划、执行流、用户偏好和技能演化的结合。[QUIETT](2602.20017_QUIETT.pdf) 提出先独立于评估问题完成一次规范化，再复用规范表：它要求保持信息和行身份，避免每个问题重复清洗。前者更偏交互与经验，后者更偏可复用的数据准备。

[EviDARL](2611.22310_EviDARL.pdf) 是本次检索中较新的直接相关工作：证据构建 Agent 根据 Schema 和代表行生成程序，在完整多表上执行；回答 Agent 依据执行证据推理。证据不足或程序失败时回退到原始表。训练上先 SFT，再交替冻结一个 Agent、优化另一个 Agent，并用 GRPO 学习。其有监督训练阶段使用标准答案，不能把这些训练奖励直接照搬成在线无标签环境的奖励。

## 9. 综合实现：有边界的闭环 Planner

以下为本文提出的工程设计，不是某篇论文的原样复现。

### 9.1 将状态、计划、证据和经验分开保存

```text
用户目标 + 数据目录
        ↓
结构/意图理解 → 语义任务计划 → Runtime 校验与绑定
                      ↑                 ↓
                 局部修订建议 ← 证据检查 ← 工具执行
                      ↑                 ↓
                 错误模式检索     产物与执行观察
                                        ↓
                         经验候选 → 验证 → 长期方法库
```

工作状态负责当前任务，至少包括目标、输入引用、计划版本、已完成节点、证据引用和剩余预算。执行观察保存实际输入/输出产物、工具状态、类型、耗时和错误码。长期经验保存操作模式、前置条件、失败模式和验证状态。完整原始表、长推理文本和可复用方法没有必要全部塞进同一个向量库。

### 9.2 结构化动作和观察

可以采用如下概念结构；字段名称是设计建议，不代表项目中已有相同合同：

```json
{
  "proposal": {
    "objective": "比较各地区同比增速",
    "capability": "table_analysis",
    "preconditions": ["时间列已解析", "金额单位一致", "比较期间明确"],
    "required_evidence": ["本期汇总", "上期汇总", "分母非零检查"],
    "acceptance_criteria": ["结果可追溯到执行产物", "空值与零分母有明确处理"]
  },
  "observation": {
    "status": "succeeded",
    "input_artifact_refs": ["..."],
    "output_artifact_refs": ["..."],
    "validation": {"schema_ok": true, "units_ok": true, "coverage_ok": true},
    "elapsed_ms": 0
  }
}
```

模型提出语义建议，Runtime 分配正式身份、决定权限和资源绑定，并记录观察。观察中的数值来自工具和校验器，不能让模型自行填写成功状态后直接当作事实。

### 9.3 验证层次和修复范围

验证至少分四层：输入与类型校验、工具执行校验、问题语义校验、跨步骤一致性校验。类型校验回答“输出是不是数字”；执行校验回答“代码有没有运行”；语义校验回答“是否比较了正确年份、单位和指标”；一致性校验回答“各子结果能否共同支持最终结论”。

修复先分类。参数错误只改参数；格式错误先清洗；证据不足扩大数据访问；操作顺序错误才修改计划依赖；目标歧义则返回意图澄清。对任务图做影响分析，保留不依赖失败结果的分支，标记下游产物失效。不能将 Table-Critic 的线性后缀重建简单翻译成“整个 ACG 全部重跑”。

### 9.4 一个可实现的运行循环

```python
# 架构伪代码：函数不是当前项目中已经实现的接口。
state = runtime.open_run(goal, input_refs)
while state.budget.remaining():
    context = runtime.read_projection(state)
    experience = memory.retrieve(context, only_applicable=True)
    proposal = planner.propose(context, experience)
    decision = runtime.validate_and_commit(proposal, state.plan_version)
    if decision.needs_clarification:
        return ask_for_missing_intent(decision)
    observation = executor.execute(decision)
    verdict = verifier.check(goal, observation, state.evidence)
    runtime.append_observation(observation, verdict)
    if verdict.goal_satisfied:
        memory.stage_candidate(distill_verified_episode(state))
        return synthesize_from_evidence(state)
    state = runtime.apply_validated_repair(verdict)
return report_partial_result_and_unresolved_evidence(state)
```

预算应同时记录 token、工具次数、重试次数与墙钟时间。循环指纹应结合“计划版本、动作参数、输入产物版本和状态摘要”；仅用工具名判重会误杀合理的重复调用。可以给同一个错误类型设较小的修复上限，耗尽后输出已有证据和未解决项。

### 9.5 经验库的最小可靠形式

先用结构化 JSON/关系表加向量检索即可，不必一开始部署复杂图数据库。推荐条目包含：

| 字段 | 作用 |
|---|---|
| task_pattern / operator_pattern | 描述可复用问题与操作骨架 |
| preconditions / contraindications | 限制适用范围，记录禁用条件 |
| failure_type / repair_strategy | 关联错误模式与局部修复 |
| source_run / evidence_refs | 追溯来源和确认依据 |
| validation_status / validation_method | 区分人工、确定性执行和模型自评 |
| attempts / successes / cost | 支持选择与淘汰 |
| scope / version / expiry | 管理用户范围、Schema 变化和过期 |

检索顺序可先按能力、数据类型和前置条件过滤，再做向量召回，最后按相似度、成功率、成本与新鲜度重排。保存“同比计算前核对单位和期间”比保存“某公司答案为 17.3%”更有迁移价值。成功次数很少时，不能把偶然成功当作高置信度通用技能。

## 10. 对 Kinlin 当前代码边界的映射

本次只阅读以下现有代码并据此提出建议，没有修改业务实现。

| 当前入口 | 已观察到的职责 | 推荐衔接方式 |
|---|---|---|
| `apps/agentOS/src/components/planner/semantic_planner.py` | 生成执行无关的 TaskPlan，调用分解与拓扑校验 | 接入问题分解和候选方法选择，输出语义约束 |
| `apps/agentOS/src/contracts/planner_actions.py` | 只读投影与候选提案；正式身份由 Runtime 分配 | 用 READ 获取证据/状态，用 PROPOSE 提交局部修订 |
| `apps/agentOS/src/runtime/orchestration/planner_bridge.py` | 登记语义任务和基于已有快照应用补丁 | 修复依赖已有计划版本，避免绕过正式登记链路 |

尤其需要遵守现有协议中“候选登记不等于正式应用”的边界。不要让 Reflector 直接写持久化任务、选择执行模型、创建正式资源绑定或替代 Runtime 的授权判定。论文中的 Agent 可以是逻辑角色；在工程中仍应落实到明确的合同和所有权。

可以按四个阶段推进：

1. **证据闭环**：统一工具观察、产物引用和验收结果；先跑通简单表格任务。
2. **局部修复**：实现首错分类、受影响节点计算和基于版本的计划补丁。
3. **经验复用**：从已经验证的运行中提炼方法，加入适用条件、失败模式和去重机制。
4. **候选路径学习**：在重复任务充足后引入 DTR 风格路径统计，比较选择收益和额外成本。

## 11. 如何证明改造有用

先固定模型、数据、工具、预算和评分器，再比较直接回答、单 Agent 工具调用、规划/执行分工、增加验证、增加局部修复、增加记忆、增加路径选择。按顺序加模块之外，还应做去除单模块的消融，避免误把更多 token 带来的收益归因于架构。

任务集应覆盖：规则短表、超长表、层级表、表文混合、多表 Join、数值聚合和图表/报告。通用 Planner 还应加入跨能力任务，验证从表格领域迁移的机制是否仍成立。

至少记录答案 EM/F1 或任务完成率、证据覆盖率、错误修复率、正确结果破坏率、平均及 P95 成本/延迟、重试与循环率、局部重跑节省量。记忆实验要区分冷启动、冻结记忆和在线写入，并按表格或数据来源隔离样本，报告新 Schema 下的表现。没有这些控制，不能仅凭最终准确率宣称系统“持续学习”。

一个小型可审查验收集可以包含 100 个真实任务，按主要错误类型分层，同时保留一个从未用于调参和归档的测试部分；数量仅是工程起点，不构成统计功效保证。对关键准确率给置信区间，对同一批任务采用配对比较，并将超时和失败纳入成本统计。

## 12. 结论与优先级

五篇论文共同推动了一个明确转变：规划不再是生成一段未来步骤，而是维护目标、证据和执行状态，并随环境结果修订行动。最值得优先实现的是 MACT 式语义规划/执行分工、TALON 式受控数据访问，以及 Table-Critic 式局部修复；MAPLE 的记忆应建立在可信轨迹之上，DTR 的路径学习则依赖稳定的奖励与重复任务。

对于 Kinlin，第一项可交付成果应是一个能够解释“本次为什么修复、哪些节点失效、哪些证据支持完成”的 Planner 闭环。经验库和搜索算法随后围绕这个闭环增强，才能让更多 Agent 和更多记忆转化成可验证的收益。
