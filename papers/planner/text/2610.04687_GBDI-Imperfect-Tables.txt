                                                                                        A BSTRACT
                                                     Answering questions over imperfect tables requires handling errors that can affect
                                                     the answer. We investigate two challenges for large language models (LLMs):
                                                     whether error discovery depends on where errors appear in a table, and whether
                                                     providing their locations is sufficient for accurate question answering (QA). Using
                                                     human-reviewed instances from RADAR-T, we conduct controlled studies across
                                                     three LLMs by varying row order and comparing original, error-marked, and
                                                     repaired tables. First, reordering rows changes error discovery even when the table
                                                     contents and gold answer remain unchanged. During direct inspection, LLMs
                                                     are more likely to discover all rows containing relevant errors when these rows
                                                     appear later in the table or are grouped more closely together. Second, providing
                                                     verified error locations alone is insufficient for accurate QA: with code execution,
                                                     accuracy on repaired tables exceeds that on error-marked tables by 39.0–59.1
                                                     percentage points across the three LLMs. As a practical application of these
                                                     findings, we combine error discovery across shuffled table views with explicit
                                                     guidance for verifying and handling the reported errors in a simple workflow,
                                                     Geometry-Balanced Discovery and Intervention (GBDI). On RADAR-T, GBDI
                                                     improves QA accuracy by 3.8–18.5 percentage points over a code-agent baseline
                                                     across five LLMs (paired 95% confidence intervals exclude zero for four), at the
                                                     cost of additional inference. These results highlight the importance of both reliable
                                                     error discovery and effective error handling in QA over imperfect tables. Code is
                                                     available at https://github.com/645-t/GBDI-ICLR-2027.


                                        1       I NTRODUCTION
                                        Tabular data organize records into rows and features into columns, with each cell representing a
                                        feature value whose interpretation depends on the column semantics and data type (Wickham, 2014;
                                        Hulsebos et al., 2019). This structured representation supports data analysis across domains such as
                                        healthcare (Johnson et al., 2023), finance (Chen et al., 2021), and materials design (Choudhary et al.,
                                        2020). Table question answering (TQA) (Pasupat & Liang, 2015; Herzig et al., 2020) enables users to
                                        access and analyze tabular data through natural-language questions, which often involve operations
                                        such as filtering, comparison, and aggregation (Wang et al., 2024; Zhu et al., 2021). Recent methods
                                        use large language models (LLMs) to interpret questions and reason over tables, often with the help
                                        of executable code or explicit table operations (Jiang et al., 2023; Wang et al., 2024; Gao et al., 2023).
                                        Progress in reasoning over a supplied table, however, does not by itself establish reliability when its
                                        contents are imperfect. Real-world tables can contain errors such as missing values and inconsistent
                                        formats (Gu et al., 2025). Understanding how these errors affect LLM-based analysis is therefore
                                        essential for reliable TQA beyond clean inputs.
                                        Answering questions over imperfect tables involves two connected demands: discovering errors that
                                        matter to the question and deciding how to handle them before computing an answer. LLMs can

critique and revise outputs through iterative feedback (Madaan et al., 2023), but reasoning corrections
remain unreliable without external feedback (Huang et al., 2024). Neither result establishes reliable
error handling in tables. In prose, word order contributes directly to meaning; in a table, a value must
be interpreted through its column, its relations to other values, and the requested computation. For
many questions, the displayed order of records is incidental. RADAR shows that data imperfections
substantially degrade LLM-based analysis (Gu et al., 2025), motivating a closer question: where do
these systems struggle—in discovering relevant errors, or in translating their discovery into correct
answers? We investigate two corresponding challenges.
Challenge 1: Discovering Errors. LLMs receive textual table representations as token sequences,
raising the possibility that error discovery depends on presentation order even when that order is
irrelevant to the answer. Prior work shows that semantically equivalent table arrangements can change
final predictions (Liu et al., 2024b; Dong et al., 2026). We ask whether this sensitivity also affects
which errors are discovered before answering. Specifically, can the same errors be overlooked when
their rows appear earlier in the table or farther apart? We call rows containing errors that can affect
the answer critical rows. Reliable systems should discover these rows regardless of their placement
whenever reordering preserves the meaning of the question and gold answer.
Challenge 2: Handling Errors. Discovering an erroneous value does not determine a valid re-
placement or how that value should enter the computation. A correction must be supported by the
available table evidence; when a required value cannot be recovered, the affected record may need
to be excluded under the task rules. An error notification therefore leaves substantive decisions
unresolved. We ask whether explicitly marking the relevant errors is enough to recover accurate
answers, or whether a substantial gap remains between knowing where the errors are and answering
from a table in which they have already been handled.
To investigate these challenges, we conduct two controlled studies on human-reviewed RADAR-T
instances across three systems. The first uses answer-preserving changes in critical-row placement,
holding all row contents, the question, and the gold answer fixed. On 60 instances, we vary where
critical rows appear; on the 59 instances with multiple critical rows, we also vary their spacing at
controlled mean positions. Complete discovery is higher when critical rows are placed near the back
rather than the front. Averaged over the tested mean positions, Wide layouts yield lower complete
discovery rates than Compact layouts. Thus, answer-preserving changes in presentation can change
whether relevant errors are discovered.
The second study compares answers on original tables, tables with verified errors marked, and tables
with reviewed repairs already applied, using 154 reviewed instances. Error-marked inputs yield
smaller and uncertain changes in accuracy, whereas providing repaired tables yields much larger
gains for code-assisted QA. Across the three systems, providing repaired rather than marked tables
raises accuracy by 39.0–59.1 percentage points. Together, the studies reveal both a sensitivity in error
discovery and a substantial difficulty that remains after error locations are supplied.
To illustrate the practical implications of these findings, we combine inspection across shuffled
table views with explicit guidance for verifying and handling reported errors in a simple workflow,
Geometry-Balanced Discovery and Intervention (GBDI). The workflow aggregates candidate errors
from multiple views, checks them against the visible table, and applies supported actions before final
QA. On all 313 RADAR-T instances, GBDI raises observed accuracy over the Code Agent baseline
by 3.8–18.5 percentage points across five systems; paired 95% confidence intervals exclude zero for
four. Separate controls compare shuffled and repeated inspections at the same call budget and vary
intervention guidance while holding the discovery evidence fixed.
Our contributions are:

       • We show that the discovery of question-relevant errors depends on their placement, even
         when row permutations preserve the table contents and gold answer.
       • We distinguish marked inputs from inputs with completed repairs, showing that providing
         error locations without repairs leaves a substantial gap in final QA accuracy.
       • We demonstrate a practical application of these findings through GBDI, a simple workflow
         that combines varied table views with explicit error-handling guidance to improve final QA.

2     P ROBLEM F ORMULATION
Following RADAR (Gu et al., 2025), a base task is a pair (Ts , Q) of a clean source table and a
natural-language question. RADAR introduces one of five artifact types—missing values, bad values,
outliers, formatting errors, and logical inconsistencies—into a table T derived from Ts ; clean variants
omit this perturbation. Each TQA instance is then a triple (T, Q, A), where T is the resulting observed
table and A is the gold answer computed from the corresponding recovered table. The system receives
T and Q and predicts Â, which we evaluate using the RADAR answer-scoring rules.

2.1   C RITICAL C ELLS

For instance i, let Ti denote its observed table and c a cell in it. Let Ei denote the set of cells in Ti
that contain a human-verifiable error, and let Di (Qi ) denote the set of cells whose values can affect
the answer to Qi , for example through filtering, comparison, or aggregation. The set of critical cells
is their intersection:
                                          Ci = Ei ∩ Di (Qi ).                                         (1)
A critical cell is both erroneous and relevant to the current question.
A table may contain errors that do not affect the answer to Qi . These cells belong to Ei but not to Ci .
Conversely, a cell may be relevant to the question but contain no error; such a cell belongs to Di (Qi )
but not to Ci . Our error-discovery analysis focuses on these critical cells and the rows that contain
them.
Because our row-order experiments operate on rows, we also define a critical row as any row
containing at least one critical cell:
                                Ri = {r ∈ Ti : ∃ c ∈ r with c ∈ Ci } .                              (2)
Thus, Ci identifies the error locations that matter for the question, while Ri identifies the rows that
contain them.

2.3   A NSWER -P RESERVING ROW P ERMUTATIONS

To study the effect of row order, let π denote a permutation of the data rows of Ti with the header
fixed. We consider questions that do not refer directly to row positions, such as the first or last row.
Values with semantic meaning, such as dates or ranks, remain attached to their original rows.
Let Answer(Q, T ) denote the gold answer for question Q and observed table T , computed from the
corresponding recovered table. Under these conditions, changing the displayed row order preserves
this gold answer:
                          Answer(Qi , π(Ti )) = Answer(Qi , Ti ) = Ai .                       (4)
The critical cells also remain unchanged; only their displayed row positions change. We can therefore
vary where critical rows appear while holding the underlying data, question, and gold answer fixed.

3     D ISCOVERING E RRORS : G EOMETRIC S ENSITIVITY
Imperfect TQA requires a system to discover the critical rows that contain errors capable of changing
the answer. For questions that do not depend on displayed row order, a row permutation changes
neither the critical-row set nor the gold answer. We test whether systems respect this invariance by
moving the same human-reviewed critical rows through answer-preserving permutations. We vary
two properties of their placement: position and, for instances with multiple critical rows, dispersion.

Position experiment. All 60 instances are used. For each instance, we keep the critical rows
together as a contiguous block and vary their mean position across five bands, q1–q5, from the front
to the back of the table (Figure 1(a)). The remaining rows retain their relative order as the block
moves. We repeat these five placements under three fixed orders of the remaining rows, yielding
60 × 3 × 5 = 900 views per system–mode pair.

Dispersion experiment. The dispersion experiment covers the 59 instances with multiple critical
rows. The remaining instance has a single critical row, for which spacing between critical rows cannot
be measured. For each instance, we construct three fixed orders of the remaining rows and test three
target mean positions: 25%, 50%, and 75%. At each target position and fixed row order, we compare
Compact, Medium, and Wide layouts with increasing spacing between critical rows (Figure 1(b)).
The individual critical-row positions vary across these layouts, while their mean position remains
fixed within each comparison. This gives 59 × 3 × 3 × 3 = 1,593 views per system–mode pair.
The mean realized σ is 0.008, 0.068, and 0.127 for Compact, Medium, and Wide, respectively.
Appendix B.2 describes the placement procedure.

Systems and inference. We evaluate Qwen Plus, MiniMax-M2.5, and GPT-5 Mini using the Direct
and Code Agent modes adapted from RADAR (Gu et al., 2025). In this experiment, both modes
identify rows that may contain errors relevant to the question. Direct reports these rows in one
response. The Code Agent receives the same complete table and question and may inspect the table
with read-only Python, using up to five responses including its final submission.
Figure 2 reports CDR for both experiments and inference modes. Numerical results and uncer-
tainty estimates appear in Appendices C.1 and E. We also evaluate position and dispersion effects
on missingness instances constructed from WikiSQL following the RADAR missingness setting
(Appendix C.3).

4     H ANDLING E RRORS : D ISCOVERY A LONE I S I NSUFFICIENT
Even when relevant errors are discovered, their locations do not specify how they should be handled.
The model must still determine supported corrections or exclusions. We therefore compare error
marking with completed, human-reviewed repairs to examine whether supplying error locations is
sufficient for accurate QA.

4.2                     R ESULTS

Providing repaired rather than error-marked tables raises observed QA accuracy across all three
systems and both inference modes (Figure 4). The increase is particularly pronounced under the
Code Agent: 39.0–59.1 percentage points, with all paired intervals excluding zero. By comparison,
changes from error marking relative to Raw inputs are smaller and statistically uncertain. Detailed
results and paired intervals are reported in Appendix E.3, Table 18.
These results distinguish discovering relevant errors from resolving them for question answering.
Providing reviewed repairs yields higher QA accuracy than providing verified error locations alone,
motivating an explicit intervention stage after discovery.

5                       G EOMETRY-BALANCED D ISCOVERY AND I NTERVENTION
GBDI puts the two findings into practice by combining discovery across shuffled table views with
explicit guidance for verifying and handling candidate errors. We evaluate how view randomization
affects discovery, how intervention guidance affects QA with discovery reports held fixed, and how
the complete workflow performs on final QA.

5.1                     GBDI W ORKFLOW

Multi-view discovery. As shown in Figure 5, GBDI constructs M views by independently sampling
row permutations uniformly, keeping columns and cell values unchanged. Each view is inspected
in a separate Direct context with the same question, prompt, and decoding configuration. Reported
candidate errors are mapped back to the original rows and merged into a single report, termed the
union ledger. We call this discovery procedure Random-M , where M is a hyperparameter set to 5 by
default.

Guided intervention. The Code Agent receives the original table, question, union ledger, and
Intervention Skill: prompt instructions for verifying candidates against the question and visible table
evidence before choosing actions. The Skill provides guidance on value recovery, formatting, and
execution checks. It instructs the agent to use E DIT when the evidence supports a unique correction,
D ROP when a question-relevant row is verified to be unusable and no supported correction is available,
and N O - OP when an intervention is not justified.
The agent applies the selected actions to a working copy and then answers the original question in the
same conversation and Python state. Appendices B and F provide the prompts and implementation
details.

6    R ELATED W ORK
LLMs in TQA. StructGPT retrieves structured information through specialized interfaces, while
Chain-of-Table constructs intermediate tables through successive reasoning operations (Jiang et al.,
2023; Wang et al., 2024). Earlier models use joint text–table representations, cell selection and
aggregation, or execution-oriented pretraining (Herzig et al., 2020; Yin et al., 2020; Liu et al., 2022).
These approaches develop representations or reasoning pipelines for deriving answers from supplied
tables. We study how question-relevant errors are discovered and handled, using RADAR’s Direct and
Code Agent baselines for controlled comparisons within the same systems and inference interfaces.

Robustness for LLMs. General LLM robustness studies examine adversarial prompt perturba-
tions (Zhu et al., 2024) and distractions from irrelevant context (Shi et al., 2023). For TQA, RobuT
evaluates question and table perturbations and uses adversarial data augmentation for model fine-
tuning (Zhao et al., 2023). FREB-TQA tests retrieval and reasoning robustness, including the
placement of answer-containing rows, and investigates fine-tuning on transposed tables (Zhou et al.,
2024). AutoDCWorkflow generates data-cleaning workflows for a specified analysis purpose; its
benchmark evaluates answer, data, and workflow quality (Li et al., 2025). Our controlled studies
examine the discovery and handling of erroneous cells relevant to the question. We build on RADAR’s
imperfect-table setting, which requires supported corrections or record exclusions (Gu et al., 2025),
and distinguish the effects of marking verified errors from those of supplying completed repairs.

Order Sensitivity in LLMs. TableFormer addresses permutation robustness through a pretrained
table–text encoder (Yang et al., 2022). Rethinking Tabular Data Understanding with Large Language
Models (Liu et al., 2024b) examines table structure variations and combines textual and symbolic
reasoning through answer aggregation. Long-context studies examine how evidence position and
spacing affect retrieval and reasoning (Liu et al., 2024a; Tian et al., 2025). The Power of Order (Dong
et al., 2026) evaluates random row and column permutations and introduces a gradient-based attack
that searches for permutations that degrade final-answer alignment. Its objective is to expose answer
failures through adversarial inputs. Our target is the discovery of erroneous cells that matter to a
question: the model must assess both whether a cell value is erroneous and whether that error is
relevant to the requested computation. We measure this discovery explicitly and separately examine
the QA gap between supplied error locations and completed repairs.

7    L IMITATIONS
First, our controlled diagnostics use imperfect tables, where explicit rows and columns support
precise error localization. For the questions studied here, row permutations preserve the gold answer,
enabling controlled tests of error discovery as row placement varies. Extending these diagnostics to
text, images, or multimodal inputs requires definitions of question-relevant errors, answer-preserving
transformations, and supported interventions, as well as reliable evaluation annotations.
Second, our experiments access LLMs through black-box interfaces, so connecting the observed
effects to specific internal representations requires further investigation. Combining the controlled
diagnostics with analyses of internal activations could help explain how models represent error
evidence and use it during discovery, intervention, and answer generation.

8    C ONCLUSION
We investigated error discovery and error handling in LLM-based TQA over imperfect tables. We used
answer-preserving changes in row position and dispersion to probe error discovery under controlled
conditions. Complete discovery is higher for back than front placements and, averaged over the tested
mean positions, for Compact than Wide layouts. Providing verified error locations alone leaves a
substantial QA accuracy gap relative to tables with reviewed repairs already applied. As a practical
application of these findings, GBDI combines discovery across shuffled table views with guidance
for verifying and handling reported errors. It achieves higher observed QA accuracy than both Direct
and Code Agent across all five systems. These findings highlight two complementary challenges:
discovering question-relevant errors and handling them using the available evidence.

This section documents the 154-instance reference introduced in Section 2, including its coverage,
review procedure, and the subsets used in the experiments. The annotations identify the critical cells
Ci , their containing rows Ri , and supported interventions under the definitions in the main text.

A.1   R EFERENCE C OVERAGE

The reference comprises 154 non-clean RADAR-T instances from 34 base tasks and 24 source tables.
It contains 1,162 distinct instance–row critical locations. Each retained annotation identifies the
affected row and records the implicated columns, visible evidence, and an E DIT or D ROP action; an
E DIT also records the supported replacement values.
Of the 154 instances, 141 have nonempty critical-row sets and 13 have empty sets. The table-state
comparison in Section 4 uses all 154 instances. CDR for the multi-view analysis in Section 5 uses
the 141 nonempty sets; the other 13 instances are excluded because complete discovery would be
vacuous. Their false-positive rates are reported separately in Appendix D.5.

A.2   R EVIEW P ROCEDURE

Four paid undergraduate annotators worked in two pairs, reviewing 79 and 75 instances, respectively.
Within each pair, both annotators assessed each instance independently. An additional reviewer, one
of the authors, checked all annotations and adjudicated disagreements.
Reviewers inspected the complete table and question to identify critical cells and supported interven-
tions according to Section 2. The gold answer was used only to check the resulting computation, not
to infer error locations or replacement values.

A.3   G EOMETRY C OHORT

The geometry study in Section 3 uses 60 of the reviewed instances, with 12 from each of the five error
types. Selection requires the answer-preserving row-order assumption and feasible controlled layouts.
The cohort spans 29 base tasks and 21 source tables. All 60 instances have at least one critical
row and enter the position experiment; 59 have multiple critical rows and also enter the dispersion
experiment.
We apply equal quotas across error types and layout feasibility checks using annotation metadata,
without using system outputs. The selected cohort is fixed across systems and inference modes.
For every retained layout, we verify that the rows moved and scored are exactly Ri . Appendix B.2
describes the layout construction.

The protocols below follow the geometry, table-state, and GBDI studies in Sections 3–5. Appendix A

B.1   B ENCHMARK AND S HARED I NFERENCE C ONDITIONS

RADAR-T contains 313 instances from 53 base tasks and 27 source tables (Gu et al., 2025). A base
task specifies a question and source data; instances apply artifact variants at the table-size setting
for the split. The records use example id for instances and task id for base tasks. Constructed
views are repeated layouts of an instance, not independent tasks. The full benchmark is used for
end-to-end QA; the reviewed reference and its geometry subsets are described in Appendix A.
At inference time, each system receives the question, displayed table, condition-specific instructions,
and any evidence generated within that condition. Human annotations are used for offline scoring and
the controlled table-state study, where errors are marked or repaired before inference. No condition
receives the gold answer.

B.2   G EOMETRY D IAGNOSTIC

We adapt the Direct and Code Agent interfaces from RADAR (Gu et al., 2025) to critical-row
discovery. Under Direct, systems read the complete table view and return candidate row IDs in one
response. Code Agent systems receive the same view and objective and may use up to five responses,
including the final candidate submission, with read-only Python inspection. The visible dataframe is
restored after each inspection command, and the task terminates at localization rather than final QA.
Here, localization is the runtime term for critical-row discovery.
Every view preserves row values and multiplicities. The question–table prompt arrangement is fixed
within each comparison. We call a fixed order of the remaining, noncritical rows a background and
reuse it across the compared layouts.

Position. The position experiment uses the 60-instance cohort in Appendix A.3. For each instance
and each of three backgrounds formed by the remaining rows, the same critical-row block is placed
so that its realized µ falls in one of five equal-width bands. The feasible block location is randomized
within the assigned band, subject to preserving critical-row identities, critical-row count, row contents,
question, and prompt template. Each system–mode pair therefore evaluates 60 × 3 × 5 = 900 views.
Complete discovery rate is reported separately for each of the five position bands.

Dispersion. The dispersion cohort excludes the one instance with a single critical row, leaving 59
instances with at least two critical rows. For each instance, three target mean positions µ (25%, 50%,
and 75%) and three backgrounds are crossed with Compact, Medium, and Wide layouts. Critical-row
identities, values, count, µ, question, and the relative order of the remaining rows are held fixed within
each comparison triplet. The construction yields 59 × 3 × 3 × 3 = 1,593 views per system–mode pair.
Compact uses the minimum consecutive critical-row span; Medium uses an intermediate symmetric
span; Wide uses the largest feasible symmetric span within a normalized radius of 0.2. The audit
records realized µ and σ for every constructed view.

B.3   TABLE -S TATE D IAGNOSTIC

The diagnostic in Section 4 compares Raw, Discovery, and Action on the 154 instances in Appendix A,
under both Direct and Code Agent. Raw uses the canonical table. Discovery wraps each reviewed
critical cell value in <<ERROR:...>> while retaining the original value; it does not provide a
replacement or a separate evidence packet. Action starts from the canonical table, applies the
reviewed replacement values for E DIT, and removes rows assigned D ROP. The Discovery instruction
identifies marked cells as verified errors. The Action instruction states that the reviewed errors
relevant to the answer have been repaired. Both notices precede the usual user turn; the system
prompt is unchanged within each inference mode. Raw Direct uses the released RADAR Direct
prompt. Conditions within a mode share the answer scorer and response allowance. Requests for
all three systems and both modes in this diagnostic omit an explicit output-token cap; provider


                                                   17
defaults still apply. Comparisons are paired by instance and clustered by source table for uncertainty
estimation.

B.4   GBDI AND M ATCHED C ONTROLS

GBDI uses the M independently permuted row orders in Section 5.1. We denote these M independent
inspections by Random-M . Repeated-M is the call-matched control: it presents the unchanged
released row order in M independent inspection contexts. Inspection contexts use the same decoding
parameters within a system. Nominations are mapped to the original rows; every valid nomination
and its independent-view support count are retained. The final Code Agent receives the canonical
table, question, evidence ledger, and Intervention Skill. The intervention turn checks visible evidence
and prepares a persistent work df; the same conversation and Python namespace continue to final
QA. The primary configuration is Random-5. Visible evidence, rather than nomination frequency
alone, determines whether an intervention is supported.
The Qwen, GLM, and MiniMax benchmark collections use the same instance–view permutations,
and every view retains all rows. DeepSeek-V4.1-Flash also uses five independently permuted views.
Permutation construction does not use human annotations. The union ledger retains every valid
nomination. A support threshold of at least two is examined separately in the ledger-support sensitivity
analysis; end-to-end QA uses the union ledger.
Within a system, Random-M and Repeated-M share the call allowance, discovery prompt, output
schema, parser, and final QA protocol. The guidance factorial crosses the two view conditions with
Generic/Skill on the same 313 instances for Qwen, GLM, and MiniMax; GPT and DeepSeek-V4.1-
Flash appear only in the complete-system evaluation. Generic specifies general operation boundaries;
Skill adds artifact-specific rules and parsing, validation, and submission guidance. Within each layout,
both guidance conditions receive the same ledger, so only the guidance text changes. The reserved
turn, persistent namespace, and five-response final QA allowance remain fixed.
The blank-ledger diagnostic preserves the canonical table, question, Skill, intervention turn, and final
budget while removing ledger coordinates and observations. It measures the contribution of ledger
availability within the candidate-guided workflow.
