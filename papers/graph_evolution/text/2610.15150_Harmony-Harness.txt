                                         1. Introduction
                                         A deployed LLM agent wraps a base model in a harness: the system prompt, tool set, agent loop,
                                         verification gates, and orchestration that collectively determine how underlying capabilities translate
                                         into task outcomes. Recent work on self-evolving harnesses allows agents to iteratively modify this
                                         infrastructure from execution feedback (Hu et al., 2025a; Zhuge et al., 2024; Zhang et al., 2026b;
                                         Robeyns et al., 2025; Zhang et al., 2026a; Qiu et al., 2025; Lee et al., 2026). Existing approaches,
                                         however, optimize solely around a single scalar objective, such as pass rate on a benchmark. Harness
                                         self-evolution under multiple objectives, in particular with safety treated as an independent
                                         axis rather than folded into the success signal, remains unaddressed.
                                              Extending harness self-evolution from a single objective to multiple objectives is not as simple as
                                         adding another reward signal. The challenge arises from the structure of the Pareto frontier and
                                         the possibility of genuine trade-offs between objectives. Consider functionality and safety. At first
                                         glance, the two appear aligned: a stronger coding agent should ideally produce code that both passes
                                         its tests and resists exploitation. Yet this alignment need not hold throughout the space of possible
                                         harnesses. A harness may improve pass rate by relaxing a verification gate, for example, or improve
                                         security by rejecting behaviors that are nevertheless required for functional correctness. Once such
                                         conflicts emerge, the evolution procedure must explicitly determine how they should be resolved.
                                         Existing formulations handle such tensions poorly: linear scalarization provably misses non-convex
                                         Pareto regions1 regardless of weight choices, and, even where the frontier is convex, it will trade a point
                                         of one objective for a cheaper point of the other; delegating trade-offs to the agent leaves compromises

implicit, unstable, and rarely Pareto-optimal. Constrained optimization (Sinha et al., 2024; Dai et al.,
2024) enforces safety thresholds, but reduces the task to constrained single-objective search rather
than mapping the trade-off surface. Handling multiple objectives thus requires an explicit mechanism
that keeps pressure on both axes. Whether the frontier is actually non-convex is an empirical question:
on the secure-coding benchmarks we study, better scaffolds often improve functionality and security
together (App. G). There, the main value of decomposition is not recovering non-convex regions. It
is objective-directed search pressure: each subproblem keeps pushing whichever objective has the
largest weighted shortfall from the ideal point, so neither objective can regress unnoticed.
    A second limitation of existing harness-evolution methods is structural rather than algorithmic:
they evolve the harness as a monolithic artifact. Each generation rewrites the repository as a single block
against feedback from a single environment; they do not disentangle general harness design from
environment-specific adaptation (Lee et al., 2026; Yin et al., 2025). In practice, many mechanisms
acquired during evolution contain both components. One is a general capability that should transfer
across environments; the other is the environment-specific calibration required to make that capability
effective in a particular setting. For example, constructing and executing code inside a container is a
broadly useful capability, whereas the choice of image, teardown policy, and handling of benchmark-
specific sandbox conventions is environment dependent. Similarly, compressing or truncating tool
outputs is a general mechanism, while deciding which portions can safely be omitted depends strongly
on whether the output is a compiler log, a fuzzer trace, or a test-runner report. Current methods
typically optimize these components jointly against feedback from a single environment. As a result,
transferable design choices and benchmark-specific adaptations receive the same reward signal and
are encoded into the same monolithic harness. We do not expect the boundary between these two
designs to be perfectly discrete; effective capabilities inevitably require some environment-dependent
calibration. Nevertheless, explicitly separating the two creates a more useful abstraction: a general
harness that can transfer across tasks and environments, paired with lightweight environment-specific
components that specialize it to the execution context at hand.
    To address these challenges, we introduce Harmony Harness, a multi-objective harness evolution
framework built on decomposition-based evolutionary optimization (Li & Zhang, 2009). Rather than
collapsing multiple objectives into a single reward, we decompose the objective space using a set of
weight vectors, each defining a scalar subproblem corresponding to a subregion of the Pareto frontier,
and optimize these subproblems jointly within a shared population. This formulation is particularly
well suited to harness evolution. Existing evolutionary systems often require an explicit artifact-level
diversity metric to prevent population collapse (Novikov et al., 2025; Wang et al., 2025); such metrics
(e.g. number of lines of code) are relatively natural for compact artifacts such as a single program, but
become difficult to define meaningfully for repository-scale agent harnesses whose variations span
prompts, control flow, tools, verification logic, and orchestration. Our decomposition instead gives
each subproblem a different objective preference, so selection pressure is diversified by construction,
without requiring a hand-designed structural diversity metric. This does not by itself guarantee
behavioral diversity: when the objectives are positively correlated, or when LLM edits are small and
local, the incumbents need not differ in behavior. We find that standard code-level diversity metrics
capture behavioral diversity only partially for harnesses (appendix). Maintaining a bounded set of
representative solutions also avoids carrying an ever-growing archive of artifacts into the proposer
context, reducing the context and search overhead of evolution.
    We instantiate dual-objective self-evolution in secure code generation, where functionality requires
passing unit tests and security requires neutralizing proof-of-concept exploits. Our findings are: 1)
Limits of Single-Objective Evolution: Optimizing solely for code functionality yields only marginal,
incidental security gains. 2) Suboptimality of Naive Formulations: Naive combinations, such
as weighted-sum scalarization or sequential evolution, stall below the full framework; the margin

2. Related Work
Self-evolving and self-improving agents. A growing body of work lets agents improve from their
own experience via reflection, memory, skill libraries, and workflow updates (Wang et al., 2024;
Shinn et al., 2023; Sun et al., 2023; Zhang et al., 2024; Ou et al., 2025; Zhang et al., 2025b; Hu et al.,
2025b). Voyager (Wang et al., 2024) grows a skill library from iterative code; Reflexion (Shinn et al.,
2023) uses verbal self-critique over failed trajectories; AdaPlanner (Sun et al., 2023) adapts plans from
environmental feedback. Two systems are conceptual predecessors of ours; we borrow ideas from
them, not their algorithms or code. GEPA (Agrawal et al., 2026) performs reflective prompt evolution
over a maintained Pareto frontier of prompts; we lift the idea of a maintained frontier from prompts
to whole harnesses and from task instances to a (functionality, security) objective space. ADAS (Hu
et al., 2025a) has a meta-agent program new agent designs in code, one level up from the prompt;
we share its view of the agent as an editable program, but our search procedure is MOEA/D (Li &
Zhang, 2009) with LLM variation operators (§4.1), not ADAS’s archive-based meta-agent search.
Closest to our code setting, the Darwin Gödel Machine (Zhang et al., 2026b) and meta-harness (Lee
et al., 2026) self-improve a coding agent by a monolithic loop—evolve the agent’s code as one block.
All of these systems (i) optimize a single objective and evaluate only functionality, and (ii) do not
separate reusable from environment-specific components in what is evolved.
    Safety during evolution, and safety as a constraint. SoS (Sinha et al., 2024) jointly evolves
a prompt for utility and safety, but evolves only a single prompt slot; safety gains at one position
can be undone elsewhere. More broadly, multi-objective alignment treats helpfulness/harmlessness
trade-offs as joint reward optimization (Askell et al., 2021; Bai et al., 2022a,b; Ramé et al., 2023; Zhou
et al., 2024), whereas constrained approaches argue safety is better expressed as a hard constraint
than a reward term (Achiam et al., 2017; Dai et al., 2024). Rather than demoting safety to a feasibility
condition on a functionality objective, we keep it as an objective in its own right and search the
frontier by decomposition, lifted from a single prompt to an entire harness.

4. Multi-Objective and Factored Harness Evolution
Given the multi-objective formulation in §3, Harmony Harness evolves a population of repository-
scale agent harnesses toward different regions of the Pareto frontier. The framework combines two
complementary ideas. First, we adapt decomposition-based multi-objective evolution to LLM agent
harnesses: a set of objective preferences defines multiple scalar subproblems, each maintaining an
incumbent harness for a different trade-off between objectives. An LLM proposer generates candidate
harnesses from execution-grounded feedback, and candidates selectively replace incumbents in nearby
subproblems according to their respective objectives. Second, we factorize the variation process to
distinguish reusable harness mechanisms from environment-specific adaptation. General-purpose
and environment-focused modifications are evolved through different operators and dynamically
composed at inference time. Figure 1 illustrates the complete evolution loop.


Search Space: The Harness as the Genome Unlike program-evolution methods that optimize a
compact code artifact, the individual in Harmony Harness is an entire agent harness. We freeze
only a minimal interface required by the evaluator; the remaining harness—including prompts, tools,
skills, control logic, verification mechanisms, and orchestration—constitutes the evolvable genome.
   Concretely, the search space contains three major classes of components, K = {tools, skills, logic},
where logic also covers orchestration. Tools provide executable capabilities available inside the agent
loop, including environment interaction and verification utilities. Skills encode reusable domain
knowledge, such as debugging procedures or repair strategies, that can be retrieved when relevant.
Finally, logic and orchestration determine how these capabilities are used, including the system prompt,
agent loop, verification gates, and workflow connecting individual reasoning and execution stages.

4.1. Multi-Objective Evolution by Decomposition

(1) evolutionary search must maintain sufficient population diversity to avoid premature convergence;
and (2) different harnesses may realize distinct Pareto-optimal trade-offs. We therefore instantiate
harness evolution using a decomposition strategy based on MOEA/D (Li & Zhang, 2009).

Importantly, the scalarization in Eq. 4 is local to a subproblem: Harmony Harness does
not replace the multi-objective problem with one globally authoritative scalar reward. Different
subproblems preserve different objective preferences, so a harness favored by a security-oriented
subproblem need not compete directly with one favored by a functionality-oriented subproblem.

    Objective-induced diversity and bounded proposer context. This decomposition is particularly
well suited to repository-scale harness evolution. Existing evolutionary methods (Novikov et al., 2025;
Wang et al., 2025) often maintain diversity using explicit artifact-level distance measures, which
are more natural when each candidate is a compact program for a single task. For repository-scale
harnesses, however, structural distance is a poor proxy for behavioral diversity: two repositories
may implement nearly identical behavior with very different code organization, while small changes
to a prompt, verification gate, or orchestration rule can substantially alter behavior. Designing a
reliable hand-crafted diversity metric is therefore difficult when candidates vary jointly over prompts,
tools, control flow, verification, and workflow structure. In Harmony Harness, each incumbent
is preserved because it is the best found so far for a distinct objective preference, not because it is
structurally distant under a hand-designed metric. This makes diversity of selection pressure hold by
construction. Diversity of behavior does not follow automatically. It also requires the objectives to trade
off and the LLM operators to make edits that change behavior rather than wording. Measuring this is
itself an open problem for self-coding harnesses. Our offline analysis (App. J) finds that standard
program-diversity metrics (token, line and AST distance, and edit labels) barely track behaviour: code
distance and objective distance are essentially uncorrelated. The metrics also cannot see diversity
that is decided at run time, such as the distinct per-task DAGs planned by the orchestrator. Among
them, AST distance is the most informative, since it ignores cosmetic rewrites. We therefore treat
diversity as something to monitor, not something decomposition guarantees. The population size is
also bounded by the number of subproblems, avoiding an ever-growing archive and reducing the
evolutionary context that must be maintained.

4.2. Factorized Harness Evolution

For a target subproblem 𝑖, the proposer receives a single parent harness, the incumbent 𝐻𝑖 (or a
neighbor when the subproblem stalls), the objective preference 𝝀𝑖 , and the execution feedback E 𝑖

                                                                                                         6
                           Harmony Harness: Multi-Objective Self-Evolution of Agent Harnesses



collected from running that parent. The feedback contains aggregate objective statistics together with
sampled execution artifacts, such as compiler errors, failing tests, and crash traces. Before modifying
the harness, the proposer first diagnoses the observed failures and formulates a concrete hypothesis
for improvement under the current objective preference.
    Why factorize harness evolution? A repository-scale harness contains heterogeneous compo-
nents, including tools, skills, prompts, verification logic, control flow, and orchestration, that play
different roles in agent behavior. An observed failure often suggests a change to only a subset of
these components. Treating the entire repository as a single rewrite target can therefore couple
an intended repair with unrelated changes elsewhere in the harness. More importantly, because
evolutionary feedback is collected from a particular benchmark, unrestricted rewriting does not
explicitly distinguish reusable mechanisms from adaptations that exploit properties specific to the
current benchmark.
    Factorized harness representation. We therefore factorize harness evolution along two comple-
mentary dimensions: component type and adaptation scope. Component factorization localizes an
update to a semantically meaningful part of the harness, while scope factorization provides an explicit
representation for reusable and environment-specific components. This organization serves as an
inductive bias; we do not assume that either decomposition is unique or theoretically exact. Given ex-
ecution feedback E 𝑖 , the proposer first diagnoses the observed failure and formulates an improvement
hypothesis: 𝑑 𝑖 = Q (E 𝑖 ) , ℎ𝑖 = G( 𝑑 𝑖 , 𝝀𝑖 ) , where Q and G denote the diagnosis and hypothesis steps of
the proposer, 𝑑 𝑖 denotes the failure diagnosis, and ℎ𝑖 denotes the proposed improvement hypothesis.
Based on this hypothesis, the proposer selects the component class to modify, 𝑘𝑖 = 𝜋comp ( ℎ𝑖 ) ∈ K ,
where K is the set of component classes defined in §4. The proposer then assigns the scope of the
modification through a component-specific scope assignment R 𝑘𝑖 :

where Σ = {gen, env} . Here, 𝑘𝑖 determines what component to modify, while 𝑠𝑖 determines where
the resulting modification should reside. gen refers to a general harness component, and env means
environment-specific. The corresponding component-scope update is then applied to produce the
child harness of §4.1: 𝐻𝑐 = O𝑘𝑖 ,𝑠𝑖 ( 𝐻𝑖 ; ℎ𝑖 ) . Here, O𝑘𝑖 ,𝑠𝑖 is a factorized variation operator that directly
modifies the harness. The complete operator details are provided in Appendix E. The distinction
in Eq. 7 is operational rather than semantic. In the implementation, components are stored under
explicit general or benchmark-specific scopes. For example, tools and skills may each contain a
general implementation together with benchmark-specific variants. The proposer therefore makes
two decisions when modifying the harness: which component to change, and whether the resulting
change should reside in the general scope or in an environment-specific scope. This assignment is not
fixed and may be revised during evolution.
   Generalization as cross-scope reorganization. The boundary between general and environment-
specific components is itself allowed to evolve. We introduce a dedicated generalize operator
that inspects the current harness organization and reorganizes components across the two scopes
when their existing placement introduces unnecessary specialization. Implementation details for this
operator are provided in Appendix E.3.
    Validation and recovery. Every proposed child is validated before objective evaluation in three
stages. The details are described in Appendix E.5.

5. Experiments
For each benchmark, we partition tasks into evolve, held-out-ID, and held-out-OOD splits. The evolve
split provides the execution feedback used during harness evolution, whereas both held-out splits
remain inaccessible to the proposer and selection procedure. For SecRepoBench, we use 30/30/30
tasks; for BaxBench, we use 28/28/28 tasks and evolve a separate harness population on each
benchmark. We report secure-pass@1, defined as the conjunction of functional and security success,
𝐹 ∧ 𝑆. Unless otherwise specified, both the harness proposer and the underlying task-solving agent
use gemini-3.6-flash. Appendix C describes the benchmarks in detail.


5.1. Main comparison against self-evolution baselines

We first compare six evolution regimes under an identical seed harness and grader. Baseline is
the un-evolved harness. The three meta-harness (Lee et al., 2026) variants are its monolithic
“summarize→rewrite” loop driven by (i) functionality and security, (ii) functionality only, or (iii)
security only. DGM (Zhang et al., 2026b) scalarizes the two objectives into a single reward. HH
(Harmony Harness) is ours. Each method is evolved on the evolve split only and then evaluated,
without further evolution, on both held-out splits. Figure 2 summarizes the outcome per split on the
two benchmarks; the underlying numbers are tabulated in Tables 9 and 10 in Appendix G.

5.2. Cross-benchmark transfer

We evaluate each evolved harness zero-shot on the other benchmark’s search split (Figure 3, Table 12
in App. G); the target benchmark is never seen during evolution. Meta-harness transfers poorly in
both directions: it drops to 39.3 F&S on BaxBench (baseline 42.9) and to 36.7 on SecRepoBench
(baseline 46.7). Harmony Harness improves over the baseline in both directions, reaching 57.1 on
BaxBench (+14.2) and 70.0 on SecRepoBench (+23.3), close to the 76.7 it obtains when evolved
in-domain. We attribute this to the separation between general and benchmark-specific components:
only the general scope is loaded on the target benchmark, so benchmark-specific fixes do not carry
over.

6. Conclusion
Self-evolving agents optimized for a single objective quietly sacrifice the other, and specialize to one
distribution at the expense of safety on others. We recast self-evolution as multi-objective search
over an entire agent harness, with safety kept as a separate axis of evolution rather than a reward
term to be averaged away. In secure code generation—where both objectives are grounded in real
execution—joint, harness-level evolution improves security and functionality together and, with
execution-grounded feedback, generalizes to unseen vulnerabilities, while naive feedback-driven
evolution falls back. The factorized general and environment-specific harness further improves the
in-domain and cross-benchmark generalization.

C. Implementation Details
Benchmarks and Setup. We conduct our main experiments on two complementary secure-code
benchmarks: SecRepoBench (Dilgren et al., 2025) and BaxBench (Vero et al., 2025). SecRepoBench
evaluates repository-level secure code completion in real-world C/C++ projects: given a masked code
region and repository context, an agent must produce a patch that preserves functional correctness
while eliminating a known vulnerability, with both properties verified through execution-based unit
tests and proof-of-concept exploits. BaxBench instead evaluates the generation of complete backend
applications, testing functional behavior with end-to-end test suites and security against executable
attacks. Together, the two benchmarks cover substantially different settings—repository-level program
repair and application-level generation—while exposing the same underlying functionality–security
trade-off. To assess transfer beyond the environments, we additionally evaluate evolved harnesses
on CWEval (Peng et al., 2025), an outcome-driven secure code-generation benchmark that jointly
evaluates functional correctness and vulnerability-specific security using executable tests.


Baselines. Meta-harness (Lee et al., 2026) and DGM (Zhang et al., 2026b) are not reimplementa-
tions: both run from their authors’ released code, with our benchmarks and grader plugged in as the
evaluation.


Repeats and effective denominators. Every reported rate is the mean of three independent runs.
Grading depends on live infrastructure—a task is scored only if its ARVO image pulls and its build
and exploit probe complete—and a small number of tasks intermittently fail for reasons unrelated to
the harness under test (registry pull failures, and timeouts caused by contention on the local CPU
during heavy rebuilds such as ffmpeg). Those tasks are excluded from the run in which they failed,
so the effective denominator of a cell is at most, and occasionally below, the 30 (SecRepoBench) or
28 (BaxBench) tasks in its split; this is why some rates are not integer multiples of 1/30 or 1/28.
Infrastructure failures are independent of the method being evaluated, but they are not independent
across methods.
   Every row in the lower block of Table 2 shares the full configuration’s factored evolving (§4.2)
and dynamic orchestration (§4.3).


D. Details for Decomposition
A linear scalarization, 𝑗 𝜆 𝑖𝑗 𝑓 𝑗 ( 𝐻 ), can recover only supported Pareto-optimal solutions and may
                          Í
therefore miss entire Pareto-optimal regions when the frontier is non-convex. In contrast, the weighted
Tchebycheff formulation does not rely on convexity of the Pareto frontier and can recover solutions in
such regions. This guarantee matters only when the objectives actually trade off. On our benchmarks
the observed fronts are narrow: on the SecRepoBench search split the front holds two non-dominated
harnesses in early generations, and in the last generation one harness is best on both objectives
(Table 13, §G.1). What decomposition still provides there is a search direction: each subproblem
measures progress by its worst weighted shortfall from z∗ , so a child that improves one objective by
giving up the other is not accepted. Moreover, each 𝝀𝑖 defines an independent search direction: no
single scalarization is treated as the global objective, and the population jointly maintains solutions
corresponding to different regions of the frontier.

E. Implementation Details for Factorized Harness Evolution
This appendix provides implementation details for the factorized evolution procedure introduced in
Section 4.2.


Harness Initialization. We initialize evolution from a lightweight but functional base harness 𝐻0 .
The base agent follows a standard ReAct-style interaction loop and provides only a minimal set of
general-purpose tools—including file reading, file writing, and command-line execution—together
with a simple orchestrator for sequencing reasoning, tool use, and execution. This deliberately
modest initialization provides the basic interface required to solve tasks while leaving the agent’s
higher-level tools, control logic, verification mechanisms, and workflow structure to be discovered
through evolution. The initial incumbents of the 𝑁 decomposition subproblems are instantiated from
this base harness.


Harness architecture. The harness is a self-contained Python package. The package itself is the
evolvable genome: the evaluator imports only the AgentHarness entry point, and nothing outside
the package is imported, so every part of the solver can be changed by the evolutionary operators.
That includes the LLM call layer, the tools, the prompts and the control logic (Figure 4).

E.1. Diagnose Execution Feedback

Given the failure diagnosis, the proposer selects one or more component-specific operators and the
scope in which each operator should act. The tool_evolve operator modifies executable tools and
their integration with the agent loop. The skill_evolve operator modifies reusable procedures,
domain knowledge, and skill modules. The logic_evolve operator modifies prompting, reasoning
procedures, verification logic, control flow, and orchestration. Each operator is restricted to its
corresponding portion of the harness rather than being instructed to rewrite the repository as a single
artifact.
    Before every variation step we run a diagnosis on the niche incumbent (diagnose.py). A
proposer session with read-only tools (Read/Glob/Grep, sandboxed away from other runs’ trees
and from the harness’s own notes) is given the subproblem’s weight vector 𝝀𝑖 , the artifact-grounded
failure digest, and the incumbent’s genome: inlined verbatim when it is small (≤ 8K characters)
and otherwise replaced by a file manifest plus the force-inlined entry-point modules (≤ 24K), since
an instruction to read the files is empirically ignored while inlined text cannot be skipped. Three
hard constraints are then stated immediately before the reply schema. (i) A niche lens fixes which

subproblem is the tie broken by the parent’s own worst objective; the same lens builds the digest,
so “what counts as a failure” and “what may be cited” cannot drift apart. (ii) The diagnoses already
issued by sibling subproblems in this generation are shown with the order to pick a different lever,

by scanning backwards for the last JSON object that decodes and carries a schema key (brace-

and alias normalization for synonymous field names; “parsed” and “usable” (can it actually steer
the operator) are recorded as separate columns. On top of that, an evidence-integrity gate validates
artifact_evidence purely on the filesystem: the cited path must exist under this parent’s own
eval-artifact tree, and the quote (≥ 24 characters) must occur verbatim in it after whitespace
normalization. A reply that is unusable, oversized, empty, or that cites unverifiable evidence triggers
one retry whose correction names that specific failure; a chain that came back in an invented
schema triggers a second, chain-only re-ask. If the evidence still does not check out, the plan’s
guidance is suppressed and the operator proceeds unguided rather than being handed unproven
fact — the same end state as an unusable reply, and recorded as such. Everything the diagnosis
touches is pure guidance: it never enters MOEA/D selection, every failure path degrades to the empty
block, and each call leaves a readable scene in the niche’s own directory (diagnose_input.md /
diagnose_output.md / chain.md) plus one line in logs/moead_diagnose.jsonl, so lens,
focus duplication, parse/usable rate, gate firing rate and retry counts are all countable per run.

E.3. Generalization Operator

The operator evolves for dependencies on incidental properties of the evolution environment, such
as hard-coded repository paths, module names, benchmark-specific commands, magic strings, task-
specific instructions, over-tuned thresholds, or parsers that assume a particular repository structure
or test runner. When such behavior is useful only in one environment, it can be localized to the
corresponding environment-specific scope. When the underlying mechanism can be expressed
independently of that environment, the operator may abstract or parameterize it and move the
resulting mechanism into the general scope. Conversely, a component previously placed in the general
scope may be localized if evolution reveals that it relies on benchmark-specific assumptions.
   Thus, generalize does not attempt to recover a theoretically defined partition between general


                                                                                                                 21
                          Harmony Harness: Multi-Objective Self-Evolution of Agent Harnesses



and specialized behavior. Instead, it makes the boundary itself subject to evolutionary reorganization.
   The scoped operators each add capability to the harness. generalize adds none. It changes
only the scope in which existing components are filed. Each invocation audits both partitions of the
harness, the general scope and the benchmark-specific scope, and corrects exactly one misfiled unit.
Which move applies depends on two properties of the unit: the scope in which it currently resides,
and whether the benchmark-specific knowledge it encodes can be recovered at run time.

• Promote (benchmark-specific → general). Condition: a procedure that is general in nature is
  filed under the benchmark-specific scope, so agents deployed on other benchmarks cannot use it.
  Correction: the unit is moved to the general scope. Each benchmark-specific fact it depends on is
  replaced by a step that obtains that fact at run time, so the promoted unit no longer assumes the
  benchmark it was written for.
• Demote (general → benchmark-specific). Condition: a unit in the general scope hard-codes a
  fact that holds only on the current benchmark, and the fact cannot be recovered at run time.
  Correction: the fact is moved to the benchmark-specific scope, where a tunable value becomes
  a per-benchmark configuration override. The general unit then reads the value from that scope
  instead of stating it.
• Derive (remains general). Condition: a unit in the general scope hard-codes a benchmark-specific
  fact that can be recovered at run time. Correction: the unit stays in the general scope and is
  rewritten to obtain the fact at run time, which removes the dependency without adding any
  benchmark-specific state.

Demote and Derive thus address the same symptom, a general unit that encodes benchmark-specific
knowledge, and are distinguished only by whether that knowledge is observable at run time. When it
is, Derive is preferred because it leaves nothing in the benchmark-specific scope.
    Every move is subject to two invariants. (i) Behavioral equivalence on the current benchmark. The
benchmark-specific partition is still loaded on the current benchmark, so a correct reclassification
leaves the search-split score unchanged. Its benefit is observable only on held-out tasks and when
the general partition is evaluated in isolation. (ii) Standalone executability of the general partition.
Loading the general scope alone must still yield a functioning agent, even if it performs worse.

E.5. Validation, Repair, and Rollback

Validation and recovery. After executing the proposed operator sequence, the resulting child enters
a three-stage smoke-test pipeline that progressively checks the integrity of the modified harness. If
any stage fails, the resulting execution trace and error diagnostics are returned to the proposer, which
is given one opportunity to repair the candidate. The complete three-stage validation is then repeated.
A candidate that fails again is rejected, and the working repository is restored to the last valid parent
version. Only candidates that pass all validation stages proceed to the full task-level evaluation used
by MOEA/D.
   No stage calls an LLM or starts a benchmark container, so the whole pipeline takes seconds to a
few minutes per child.
   Stage 1: import and interface validation. The child package is imported, together with
every submodule individually, because deferred imports (e.g. the orchestrator and step registry)
are not covered by importing the entry point. The frozen evaluator interface is then checked: the
AgentHarness class must expose an asynchronous run (or agent loop) method, and its user-prompt
template must still contain the task specification slot.
    Stage 2: offline smoke test and genome self-tests. The harness is instantiated against a stub
environment and must embed a placeholder specification into its messages and parse a canned model
reply into files. The genome’s own _selftest*.py files are then run as subprocesses (timeout
300 s per file). The seed ships a self-test that drives the full tool-calling loop against a scripted stub
model instead of a real LLM. It checks that the tool schemas exposed to the model are well-formed,
that the payloads sent to each vendor have the shape that vendor requires (e.g. every tool use paired
with a tool result), and that the loop terminates within budget and actually modifies the app. Without
this check, a broken tool-calling protocol is swallowed by the agent’s catch-all and scores a whole
generation 0/0.
    Stage 3: static integrity checks. Two AST-only checks cover what the first two stages cannot
execute. First, every named self-test assertion of the parent must still exist in the child. The self-tests
are part of the evolvable genome, and the cheapest way to make a failing self-test pass is to delete
it. Second, a static call-signature check requires every call in the child to bind to the definition it
resolves to, which catches half-edited call sites on branches the smoke test never reaches.
   A child that fails any stage receives one repair attempt with the failing stage’s log; a child that
passes but is byte-identical to its parent is rejected as well.
    This mechanism is particularly important when multiple operators are scheduled for the same
child: sequential editing ensures that each modification is conditioned on the current harness state,
while end-to-end validation verifies that their composition remains executable before the candidate
can affect the evolutionary population.

F.2. Runtime Harness Assembly

Operational factorization of the harness. H gen and H𝑒env are not required to be two standalone
programs or functions. Instead, they correspond to logically distinct regions of the same harness
repository. We bias executable tooling and reusable agent-control mechanisms toward H gen , since
abstractions such as execution, verification, retry, and context management should ideally transfer
across environments. In contrast, retrieved skills and benchmark-specific procedures—including
environment conventions, task-specific recipes, and local execution knowledge—form H𝑒env . Logic
and orchestration may coordinate both components and therefore need not belong exclusively to
either category.
    Because this distinction is inherently semantic rather than syntactic, we do not impose a rigid file-
level partition. Instead, the generalize operator serves as an explicit mechanism for maintaining the
boundary. It audits the current harness for dependencies whose utility arises from incidental properties
of the evolution environment and either rewrites them into environment-agnostic mechanisms or
confines the specialization to environment-specific components. Thus, factorization is enforced
through evolutionary pressure and operator scope rather than through a fixed manually specified
decomposition of the repository.

G.1. Evolving on one objective/distribution degrades safety elsewhere

Before proposing joint evolution, we confirm the problem exists. A harness evolved to maximize its
search-set score (the “baseline-seeded winner”) collapses on held-out data: combined F&S falls to
35.0, below the un-evolved baseline’s 43.3 (Table 14). Qualitatively (§K.7), an agent that only ever

it toward the missing hardening (e.g., a bounds check), because the exploit signal is hidden at solve
time. This is the self-evolution analogue of overfitting: capability specialized to one distribution,
security left behind.

I. Discussion and Limitations
When do the objectives conflict? On SecRepoBench the front is narrow: two non-dominated
harnesses in early generations, and in the last generation one harness that is best on both objectives on
the search split (App. G.1). The decomposition frontier pays off most where security and functionality
genuinely trade off. Establishing such regimes—adversarial or injection tasks, or security fixes that
break legacy tests—is the most important next step.


Reward hacking demands held-out gating. The 100/100/100 artifact (App. K.6) shows that
any acceptance rule reading only training-set feedback is exploitable; any acceptance rule—ours
included—must be validated on held-out safety.


Isolating the factorization. The orchestration toggle (Table 8) and cross-benchmark transfer in both
directions (Table 12) are now measured, and both favor the factored, dynamic harness—most sharply
in transfer, where the monolithic meta-harness lands below the un-evolved baseline on the target
benchmark. The evolution-surface ablation (Table 7) separates the two: tools-only and skills/logic-
only factoring reach 40.0 and 48.3 combined F&S, the two together 58.3, and only adding dynamic
orchestration reaches 76.7—so “factored” and “dynamic” each carry part of the effect and neither
alone accounts for it.

The instrument is deliberately offline and read-only: it reads the genome tree and the logs after the
fact, and by construction cannot feed anything back into selection — the same discipline that applies
to the held-out evaluation.

  Each genome is reduced to three shingle sets, deliberately chosen to disagree with each other:

   • 𝑆tok ( 𝑥 ) — 𝑔sh -grams (𝑔sh = 5, -ngram) over a normalized token stream of every file. Numbers

     two sets only.

K. Calibrating the overfitting gate

K.1. What the gate is

Beyond the mechanical guardrails of §4.2, every admitted child passes through an overfitting gate:
a one-shot LLM judge that sees the parent→child diff 𝛿 together with the injected ## Diagnosis
block, and returns a scalar risk 𝜌 ( 𝛿) ∈ [0, 1] plus a one-line justification naming the mechanism it
believes the edit fits. A child is rejected when 𝜌 ( 𝛿) > 𝜃.
    Two choices matter. First, the judge is deliberately not shown the artifact-grounded failure digest
or the per-task trajectories: conditioned on a real failure, any edit that addresses that failure can be
rationalized as principled, and the judge collapses to accepting everything. Second, the judge emits a
scalar rather than a verdict, so the operating point 𝜃 can be chosen on a calibration curve instead of
being fixed implicitly by the prompt.
   An uncalibrated judge is an assertion. This appendix reports what the gate actually detects,
on overfits whose ground-truth label is known by construction and, for the harder tiers, verified
behaviourally against the eval-only held-out split of §5.1.


K.2. Paired construction

Constructing an “overfit” population and a “general” population separately confounds the label with
edit size, edit style, and topic. We use a paired design instead. We draw 𝑛𝐶 = 5 real admitted children
from completed runs, sampled from distinct generations and distinct MOEA/D weight niches so that
the study does not measure a single lineage, and restrict to the -operator diff mode so that each
child is already a minimal in-place edit with a well-defined diff against its parent. For each such child



                                                                                                      37
                          Harmony Harness: Multi-Objective Self-Evolution of Agent Harnesses



𝐶 and each plant type 𝑞 we form
                                             𝐶𝑞+ = Inject( 𝐶, 𝑞) ,
a copy of 𝐶 carrying exactly one injected overfit and no other change. The judge scores 𝐶 and every
𝐶𝑞+ blind to the label and in randomised order. Because 𝐶 and 𝐶𝑞+ differ only by the injection, detection
is measured against a matched control and significance is assessed with a paired McNemar test rather
than a two-sample comparison. Each condition is judged 3× and scored by majority vote; we report
the vote disagreement rate as a measure of judge stochasticity.


K.3. The plant taxonomy

Table 18 lists the injected edits. They are graded into three tiers of increasing subtlety, plus a control
class. The tiers exist because a judge that fires on Tier 1 and nothing else is a regular expression
with a language model’s latency; locating where detection actually breaks down is the point of the
exercise.
    Tier 1 (lexical) injects specificity that is visible as a literal string in the diff. Tier 2 (structural)
injects specificity that is real but carries no benchmark string — a branch on a feature that only
co-occurs in the evolve split, a constant tuned to it, or a dependence on an incidental convention of
the ARVO harness rather than on the repair task. Tier 3 (semantic) injects a policy that is defensible
in the abstract but true only of the evolve split’s distribution, or that games the scoring rule rather
than the underlying objective; these are the edits a diff-reading judge has the least purchase on.
    The control class, S (suspicious-but-general), is the complement and is required for a meaningful
false-positive rate. Our own champion’s decisive mechanism — a ground-truth build and boot/exploit
probe (§4) — is ARVO-specific in its interface while being entirely general in its mechanism: consult
ground truth rather than adjudicate a patch by reading it. An overfitting gate that rejects that edit
has cost more than it saved, and a false-positive rate measured only on unmodified children would
never reveal it.

K.5. What the gate detects

Ablations. Two variants are run on the same pairs at negligible additional cost.

• Same-model vs. cross-model judge. The default judge shares a model family with the proposer,
  which risks correlated blind spots — an edit the proposer produced because it appeared general is
  an edit the same model is disposed to certify as general. We repeat the study with a judge from a
  different family and report the difference in Tier 3 recall.
• Diagnosis-conditioned vs. diff-only. Supplying the stated hypothesis may help the judge locate
  the intended mechanism, or may supply a ready-made rationalisation. We report both.


Cost. 𝑛𝐶 = 5 parents × 16 conditions × 3 samples = 240 judge calls, plus 𝑛𝐶 × 7 = 35 held-out
evaluations for behavioural verification — together a small fraction of a single evolution run.

Scope. The gate is calibrated against planted overfits, which are by construction the overfits we

K.6. A concrete reward-hacking failure

The clearest evidence that a search-set safety score is not evidence of safety is a variant that achieved
a perfect one. Raw error feedback is identical to the factored-evolving configuration (Table 5) except
in what the proposer may read and when a child is accepted: it receives the grader’s raw error output,
and any child is accepted whose functional pass rate does not decrease. Under that rule the search
reports 100/100/100 on the SecRepoBench search set—every task functional, every exploit blocked,
on the same 30 tasks where the un-evolved harness scores 46.7 combined.
    The score is an artifact. Inspecting the winning harness’s trajectories shows the code it emits is
not secure: the run satisfies the measurement rather than the property the measurement stands for.
Two further observations from our runs separate the ways a search can do this, because they call for
different defenses.


The soft form: writing the search split into the scaffold. Running DGM we repeatedly recovered
children that had simply hardcoded the search split’s crash distribution. One assumes every task is a
CWE-125 out-of-bounds read reached through the UTF-8 decoding branch and routes every repair
through that path; another ships an _OOW_LADDER of fixes that presumes the bug is always an out-
of-bounds write; a third assumes a calloc off-by-one on a UCS-2 buffer. Each is right often enough
on the split it evolved on to be accepted, and each is structurally incapable of transferring—which
is the mechanism behind DGM’s 0% retention in Table 1. We do not see this signature in our own
runs, and we attribute that to the explicit generalize operator of §4.2, whose only job is to find
and dismantle exactly this kind of mechanism—hardcoded crash-type ladders, magic strings, prompt
text naming concrete tasks, over-tuned constants, parsing that assumes one repository’s layout—and
replace it with one that transfers, so that a fix recipe must be stated in terms of the failure digest
rather than in terms of the tasks it was derived from.


The hard form: editing the grader. The stronger failure is available to any harness that can write to
the files that score it. We tested this deliberately, running without the per-evaluation Harbor container
and without the git-backed restore of protected files: the agent goes straight for evaluate.py,
and the run then reports 100% on every axis—not a weak measurement but no measurement at
all. This is not hypothetical for the baselines we compare against: the meta-harness code carries no
hard constraint protecting those files, so nothing inside the harness prevents it, and the protection
has to come from outside the genome. Ours is structural rather than behavioural. Every evaluation
runs in an isolated Harbor container with the network disabled and CPU, memory, and wall-clock
limits; solution/ and the held-out splits are never built into the image; and the files that define
scoring—the evaluator, the task definitions, the tests—are snapshotted before every operator call
and force-restored afterwards, so an edit to them cannot survive into the evaluated child. Note the
asymmetry this draws: no file inside the genome is protected—the proposer may rewrite the whole
harness down to its base class (§4)—while no file that scores the genome is writable at all. That closes
“rewrite the scorer” and “rewrite the tests” as paths entirely, and it is what makes the 100/100/100
above worth reporting: it was produced with all of these defenses in place, so it is a statement about
the acceptance rule, not about the sandbox.

distribution cannot produce.


K.7. Baseline harnesses and a case study

For calibration we run two off-the-shelf agent harnesses on SecRepoBench under identical grading:
SWE-agent (Opus) reaches secure-pass@1 = 0.444 overall (0.267 out-of-distribution), and an evolved
Terminus-2 harness (Gemini) reaches 0.556 (0.433 OOD). Inspecting their trajectories shows why a
general terminal agent underperforms on this precise code-completion task: whole-file replacement
without a mask-region guardrail turns editing fragility into measured capability loss, and the exploit
signal is hidden at solve time, so its feedback-driven iteration idles on exactly the objective that
matters. The evolved champion instead brackets the pipeline with the only available ground truth
(compile + boot), inserts a dedicated per-CWE hardening pass, and keeps a last-known-good snapshot
so a self-review can never break compilability.
