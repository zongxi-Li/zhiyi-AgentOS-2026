# 从运行轨迹到可验证更新：图自进化与迭代优化的机制、证据及实现路线

整理日期：2026-11-18。本文围绕 Kinlin 的 Planner、Runtime 和 Evolution 研究“怎样让后续任务使用更好的图”。本专题收录 **24 篇 PDF，686 页**；[全文索引](README.md)提供原始来源和固定版本，[阅读日志](citations/reading-log.json)区分摘要筛选与方法选读。本文没有复现论文模型，也没有把作者报告的收益当作本项目成果。

核心判断是：图更新的价值应由独立任务上的质量、成本和历史能力保持来证明。记录更多节点、增加反思次数或反复重写工作流，只能说明系统发生了变化。项目最适合先形成“可回放的小补丁—成对比较—正式版本发布”闭环，再扩大搜索空间。

## 1. “图自进化”到底更新什么

当前文献至少涉及五类图，它们的节点、边和正确性条件不同。

| 图的类型 | 节点与边 | 更新目标 | 必须保留的约束 |
|---|---|---|---|
| 执行依赖图 | 步骤；前置条件、数据和控制依赖 | 补验证、调顺序、并行、局部替换 | 类型、权限、终止、输入输出一致性 |
| Agent 通信图 | Agent/消息事件；消息传递 | 减少无效通信，改善协作 | 信息可见性、时间顺序、预算 |
| 经验与知识图 | episode、实体、事实、洞见 | 检索和跨任务复用 | 来源、时间、冲突、撤销与隐私 |
| 技能关系图 | 技能；依赖、相似、组合 | 技能发现和组合 | 版本、接口、关系语义 |
| 搜索血缘图 | 候选工作流版本；生成或融合关系 | 管理探索和复用候选 | 父版本、评测身份、证据可追溯 |

例如，[DAGO](2610.05284_Workflow-Graph-Fusion.pdf)讨论候选工作流的多父融合搜索；这个候选血缘 DAG 不能直接等同于每个工作流内部的执行 DAG。[G-Memory](2506.07398_G-Memory.pdf)组织经验，不能仅凭记忆图变大就断定执行拓扑得到改进。[Skills 综述](../skills_evolution/SUMMARY.md)进一步区分技能分类树和任务特定的技能执行图。

同样需要区分时间尺度。任务内修改用于恢复当前执行，任务间演化产生供未来 Run 使用的版本。两者可以共享诊断证据，却不应共享“直接修改当前运行状态”的权力。一个当前任务里的有效绕行，可能只适用于该环境，尚不足以成为默认流程。

## 2. 经典方法：边、代码、提示词三个搜索空间

### 2.1 GPTSwarm：让通信边成为可优化变量

[GPTSwarm](2402.16823_GPTSwarm.pdf)把语言 Agent 系统表示为可优化图。给定节点和候选连边，边由参数化分布控制；采样图时排除会造成环的边，再执行采样结构，用任务效用更新边参数。其方法包含基于 REINFORCE 的优化思路，也允许通过文本反馈修改节点提示。

这揭示了两个独立变量：节点做什么，以及信息怎样流动。固定节点而优化连边，更容易控制搜索空间；同时优化角色、提示、模型、工具和连边，归因会迅速变难。其“优化”并不必然训练基础 LLM 权重。

Kinlin 可以借鉴显式候选边和合法性校验，但第一阶段无需引入随机拓扑策略。先记录每条依赖为何存在、消耗多少时间、是否提供新证据；只有当稳定轨迹足以判断冗余或缺失依赖时，才尝试边替换。并行增加还需验证工具是否共享可变状态，拓扑无环不能保证执行没有竞争。

### 2.2 ADAS：把完整 Agent 程序当作候选

[ADAS](2408.08435_ADAS.pdf)在代码空间进行 Meta Agent Search：元 Agent 参考历史 archive，生成新的 Agent 实现，执行评测后将结果加入档案，再继续探索。代码可表达循环、分支和新模块，表达力比预先枚举几种拓扑更强。

但可用图灵完备语言表达某个系统，不代表搜索过程能有效找到它，也不代表生成程序适合直接上线。搜索 archive 的作用是保留多样解和失败经验，其成员身份不等于生产批准。对项目而言，可先让生成器输出受限 GraphPatch 合同，以静态检查限定可修改范围；后续即使允许生成代码，也应使用独立构建和执行环境。

### 2.3 AFlow：在完整工作流的搜索树上积累经验

[AFlow](2410.10762_AFlow.pdf)用节点、算子和代码控制流表达工作流，借助 MCTS 变体进行搜索。需要注意：搜索树中的一个节点代表一个完整工作流，而不是工作流中的一步。选择阶段综合表现与探索，LLM 在经验提示下扩展新候选，执行评测，再回传结果。

在所读实现描述中，模型、温度和格式等因素固定，主要搜索提示和控制流。因此，不能把其结论直接推广为“同时搜索所有模型与部署参数都有效”。论文使用 validation/test 划分，并在验证阶段选择高方差样本以改善区分能力；这种方法能节省搜索成本，但项目不能一边反复适应同一批样本，一边仍将它们作为最终独立证据。

可借鉴的是工作流版本作为搜索单位，以及把失败类别、变更理由和评测结果一起归档。项目不必照搬论文的 20%/80% 划分和 seed，而应按任务族、来源和时间防止泄漏。

## 3. 提示优化、动态结构和反思经验

### 3.1 DSPy、TextGrad 与 GEPA 的关系

[DSPy](2310.03714_DSPy.pdf)强调声明式模块和流水线编译，为“固定接口、优化内部指令或示例”提供组织方式；[TextGrad](2406.07496_TextGrad.pdf)用文本反馈传播修改建议。两篇在本轮属于摘要筛选与全文归档，具体优化器选型仍需后续方法和代码核查。

方法选读的 [GEPA](2507.19457_GEPA.pdf)进一步将执行轨迹、评价器的文字反馈和反思结合：优化器选择模块，基于成功与失败轨迹生成提示词变体，通过小批量比较筛选，再在更完整的评测集上更新候选池；其 Pareto 机制保留不同实例上的专长，并可组合不同候选的优势。

GEPA 冻结基础 LLM 权重，变化主要发生于模块提示。文本“梯度”也不是对业务函数求出了可验证的解析导数。尤其要避免术语混用：按实例表现维持的 Pareto 集，不会自动满足业务上质量、时延、费用和风险四维的 Pareto 要求。这些指标需要额外测量和选择规则。

对 Kinlin，最有用的中间资产是结构化诊断卡：失败步骤、错误类型、可核验证据、建议变更位置、预期收益及可能受损任务。诊断卡既能驱动确定性候选，也可作为后续 LLM 反思输入；其内容本身仍是待检验假设。

### 3.2 MaAS 与查询条件化结构

[MaAS](2502.04180_MaAS.pdf)将目标从单一静态工作流转向 query-conditioned agentic supernet，对不同查询采样不同架构和资源配置。本轮摘要支持其“按查询分配计算”的定位；[AutoMaAS](2510.02669_AutoMaAS.pdf)摘要还提出算子生成、融合和淘汰。本文没有据此断言任一算法已找到全局最优结构。

业务上可以先用任务画像决定确定性模板，例如低风险简单任务走短链，证据冲突任务加核查，明确数据依赖的任务才允许并行。与直接训练复杂 supernet 相比，这种基线便于测出动态结构是否真正优于“同预算单 Agent + 工具”。

### 3.3 QueenBee：把反思变成可检验的外部经验

[QueenBee](2606.27492_QueenBee.pdf)以可执行协调程序表达通信，并展开为时间通信 DAG。其 Structural Feedback and Transition Bank，简称 SFT-Bank，保存诊断卡、具有 confirmed/refuted/inconclusive 状态的假设账本及程序档案；这里 SFT 不指监督微调。设计模型保持固定，主要演化的是外部协调程序与经验。

该框架用调度策略在探索、融合和节约成本等动作之间选择。对项目更直接的启发是把“失败解释”与“验证结果”分离：模型说增加验证器可能修复错误，属于 hypothesis；只有独立回放支持后才标为 confirmed。证据不足时保留 inconclusive，防止将一次成功写成普遍经验。

## 4. 经验图如何更新：从堆积到带来源的时间记忆

[G-Memory](2506.07398_G-Memory.pdf)用 interaction、query 和 insight 多层结构连接具体交互与抽象经验。检索可向上寻找洞见，再向下回到支撑轨迹；任务完成后更新。其主要价值在经验组织和跨层召回。它没有免除执行评估，也不应被解释成“所有被检索的经验都促成了成功”。

[Zep](2501.13956_Zep-Temporal-Graph.pdf)将 episode、实体、事实关系和社区用于时间知识图，强调实体消歧、关系去重与双时间信息。相关时间字段让系统区分事实何时有效和何时被系统获知；冲突可通过使旧关系失效保留历史，而不是抹掉旧事实。社区更新采用动态策略，同时仍需要周期性的整体刷新。

项目建议采用 append-only 证据和显式 supersedes/invalidates 关系。对同一事实，需要同时比较来源权威、用户纠正、有效时间与采集时间，不能机械使用“最近写入优先”。技能失效、工具版本变更和用户撤销授权应能沿关联关系使受影响候选进入待复核状态；删除或去标识化原始敏感数据时，也必须检查衍生经验的处理要求。

[MEGA](2608.10504_MEGA-Wisdom-Graph.pdf)提出 Wisdom Graph 和经验检索、组合更新的基础设施思路，选读部分涉及架构契约与经验组织。但文档明确有专有实现细节选择性披露，不能将其当作完整可复现算法，更不能把架构描述当作独立因果证明。可借鉴接口分层，不宜复制未经披露的性能机制。

## 5. 迭代更新的核心难题是选择偏差

如果在同一验证集上试 100 个候选，再报告最好的一个，即便候选真实能力相近，最佳观察值也容易被噪声抬高。[The Winner’s Curse](2610.09239_Winners-Curse.pdf)针对这一选择问题提供研究线索；本文不引用未复核的效应数字。生成器和评价器使用同模型，也可能共享盲点，使“自评变好”偏离真实结果。

方法选读的 [Evidence-Governed Adoption](2611.16378_Evidence-Governed-Adoption.pdf)将“生成”和“采纳”分开。候选冻结后接受新鲜的成对审计：主要目标相对当前 incumbent 判断改进，受保护能力相对版本化 reference 判断非劣。最低改进、非劣容忍度、误差分配和评价器校准均需要明确。其统计结论依赖采样、评价器和检验条件，不是对任意 Agent 的普遍安全证明。

建议采用三个数据角色：development 用于生成和诊断，selection 用于比较候选，confirmatory 用于冻结后的发布决策。一个集合被反复查看并反馈给生成器后，就不再是新的最终审计。跨版本持续更新还需安排审计预算和新任务补充策略，不能无限次重复使用同一份 holdout。

对于成对样本 i，记录 dᵢ = quality(candidate, i) − quality(baseline, i)。报告均值及不确定性，同时记录任务族分层结果。二元成功应分析同任务上的不一致结果；连续分数可采用任务级成对 bootstrap 等方法；相关子任务不能当成独立样本凑数量。涉及多个能力门槛时，按事先约定的检验策略处理多重比较。以上是实现建议，不是当前项目已有统计功能。

成本需要包含整个流程：搜索时的生成与评测、最终推理、重试、工具调用、检索、并行资源和尾延迟。若搜索一次耗费很高，只有未来使用量足以摊薄才值得采用。[Equal-Cost Structure](2609.04217_Equal-Cost-Structure.pdf)在特定模型及 ALFWorld/WebShop 条件下提出同推理成本的负结果；它支持设置强成本匹配基线，不能推广成“多 Agent 永远无效”。

## 7. Kinlin 当前实现：已有受控骨架，尚缺真实闭环

核查依据是本地代码，尤其是 [图演化服务](../../apps/agentOS/src/components/evolution/application/graph.py)、[候选生成器](../../apps/agentOS/src/components/evolution/infrastructure/graph_candidates.py)、[领域校验](../../apps/agentOS/src/components/evolution/domain/graph.py)、[图端口](../../apps/agentOS/src/components/evolution/ports/graph.py)和 [Run 轨迹投影](../../apps/agentOS/src/components/evolution/integration/trajectory.py)。状态按 2026-11-18 代码解释；旧设计文档中的 TODO 不能替代现状核查。

已实现的受限生成器从显式 capability 到已注册 validator 的映射出发，对同图版本的不同 Run 统计重复失败。默认提案证据门槛为 3、最少失败次数为 2；选择重复失败最多的步骤，提出一个 registered_validator_insertion。相同 Run 的多份快照不能充当多个独立证据，历史数据缺少 runId 时才使用 trajectoryId 回退。这是确定性局部候选，不是已训练的任意拓扑搜索器。

GraphEvolutionService 已编排 propose、validate、paired offline evaluate 和 approved publish；检查图、版本、步骤、证据与评测身份，拒绝源 Run/trajectory 与 heldout 样本 ID 的交叉。质量要求不低于 baseline，成本不得超过 baseline × max_cost_ratio，默认 ratio 为 1.0。发布前重新调用受信 evaluator，调用者自带的评测不能取代它。

但生产图快照 validator、真实任务 replay evaluator 和正式 graph version publisher 仍未接通；依赖缺失时抛出 NotImplementedError，没有新增面向产品的图发布 API。publisher 承担真实授权、CAS、正式 TaskPlan/编译和版本发布；approved_by 非空字符串并不等于身份认证。Runtime 的 GraphRevision/GraphPatch 仍是另一套运行时权威，离线候选没有因此获得改 live graph 的权限。

轨迹已可由 Run 投影，包括步骤、引用、调度和 provenance 等信息；当前评分仍侧重完成状态、错误步骤比例，novelty 固定为 0。它们不能替代语义质量与新颖度判定。已有 policy 的原子事务、幂等回执和回滚新版本，是可借鉴的工程机制，但不能据此宣称图发布或技能发布已经完成。ID 不重叠也不足以阻止同一任务换 ID 后泄漏，需要补充 taskFamily、内容血缘和时间隔离。

## 8. 推荐实现：先做一种可信更新，再扩大搜索

第一步完成可复现回放。冻结正式图版本、工具实现、模型版本和任务输入，获取真实输出及验收；非确定性模型用事先规定的重复次数估计波动。对外写入等操作在回放中使用可核查替身，保证 baseline 与 candidate 面对相同环境。否则分数差可能只来自环境变化。

第二步接通 registered_validator_insertion。静态校验要检查依赖、输入输出合同、可见数据、权限、重试和成本上限；插入验证器后，原下游是否确实依赖验证结果也要检查。仅新增一个不影响执行的 validator 节点，可能制造“看起来有验证”的假改进。

第三步建立独立确认和版本发布。候选与依赖 checksum 冻结，绑定评测报告和审批对象；发布前检查 base version，原子写版本、审批、报告和 receipt。回滚产生一个指向已知内容的新版本，保留历史；后续 Run 冻结 graph/skill/model/policy 的完整版本组合。默认成本比例 1.0 若阻挡有价值的验证器，应通过显式质量—成本政策调整，不能绕过现有门槛。

第四步才扩展候选算子：删除冗余步骤、替换提示模板、有限重连，再考虑并行化、模块融合和 query-conditioned 路由。每扩大一种算子，都补对应合法性和回放能力。先同时演化图和技能会使收益难以归因，建议前期固定一方，另一方通过后再研究联合搜索。

最小评估应比较固定图、人工局部补丁、当前确定性生成器，以及预算一致的 LLM 候选生成；按成功、语义质量、成本、p95 延迟、旧能力退化和无效候选率报告结果。同时统计“提出多少、拒绝多少、原因是什么、接受后是否回退”。完整接口和验收顺序见 [联合实现计划](../EVOLUTION_IMPLEMENTATION_PLAN.md)。

现有证据支持以版本、经验和可执行反馈组织迭代，而没有建立“越复杂越好”或“每轮真实能力必然上升”的结论。项目近期可验证的目标，是把一个重复失败诊断转化为一份有独立证据、能正式发布并能回滚的图补丁。
