# 从通信器到论文：初步选题与实验路线

日期：2026-11-24。阶段：选题论证，尚未形成论文结果。

本文以当前仓库的通信实现为依据，提出可验证的研究路线。推荐优先研究**固定协作图下，接收方如何在有限预算中按需获取上游证据**。用户已确认首篇目标为“结合项目，先完成一篇扎实的方法或系统论文”。这份文档是初步定位，不是完整文献综述；具体投稿目标、主要假设与资源规模仍待讨论。

## 1. 先确定论文要回答什么

项目里的“通信器”涉及多智能体之间的上下文和产物流转，研究对象是信息获取、交付与使用。首篇建议面向 LLM 多智能体协作与上下文管理的读者。

推荐问题：

> 在协作图、基础模型和任务保持一致时，接收方依据当前任务与已读证据，逐步选择读取上游产物的字段、子树和页面，能否在减少实际模型输入成本的同时，保持任务成功率与证据完整性？

需要解释的矛盾是：提前给足全部信息可能增加成本和干扰；提前给出的摘要或固定字段又可能遗漏后续推理所需的事实。按需读取有机会缓解这一矛盾，也可能因为检索决策错误、反复读取和额外模型轮次而更差。

论文成立取决于这一权衡能否被测量、方法是否优于强基线，以及结论能否推广到项目之外。

## 2. 当前实现提供了哪些研究基础

| 已检查的实现 | 代码依据 | 对研究的作用 | 尚不能推出的结论 |
|---|---|---|---|
| 编译后的生产者—消费者许可、字段许可、run/step/channel 预算 | [manifest.py](../../apps/agentOS/src/components/communicator/manifest.py)、[broker.py](../../apps/agentOS/src/components/communicator/broker.py) | 固定信息访问边界，使不同读取策略可比较 | 权限规则本身不构成新的选择算法 |
| 预取与运行中补读共用 Broker | [broker.py](../../apps/agentOS/src/components/communicator/broker.py)、[reader.py](../../apps/agentOS/src/components/communicator/reader.py)、[node_runner.py](../../apps/agentOS/src/components/executor/node_runner.py) | 可以在相同执行链路替换预取和补读策略 | 当前默认行为不一定稀疏；没有配置小范围 prefetch 时可能读取全部授权字段 |
| list_sources、read、read_page；显式启用嵌套路径读取 | [context_read.py](../../apps/agentOS/src/adapters/tool/context_read.py) | 已有可供模型选择字段、页面、子树的工具接口 | 能调用工具不代表模型能可靠判断缺什么信息 |
| 原字段投递，分页保留剩余内容 | [broker.py](../../apps/agentOS/src/components/communicator/broker.py) | 可以研究可回溯的精确读取与摘要的差别 | 分页可重建不等于模型已读全，也不等于最终答案完整 |
| sourceData 按生产步骤保留字段；data 为兼容扁平投影 | [contracts.py](../../apps/agentOS/src/components/communicator/contracts.py)、[README.md](../../apps/agentOS/src/components/communicator/README.md) | 可构造同名字段冲突、多来源归属实验 | 保留来源不代表模型正确使用来源；data 仍可能发生覆盖 |
| 生产、消费及交互记录；Trace 不复制通信正文 | [service.py](../../apps/agentOS/src/components/communicator/service.py)、[provenance.py](../../apps/agentOS/src/components/communicator/provenance.py) | 支持分析实际读取过程 | 读过一项证据不等于答案受到它的因果影响，也不等于证据真实 |
| 读取操作身份、预算快照、引用队列与确认 | [broker.py](../../apps/agentOS/src/components/communicator/broker.py)、[reliable.py](../../apps/agentOS/src/components/communicator/reliable.py) | 可用于重试、恢复和重复计费实验 | 不足以宣称整个系统具备端到端 exactly-once 语义 |

注意当前实现中的细节：`assemble_context()` 使用 `requested or declared`，因此空 prefetch 列表不会自然产生“零正文预取”。实验如需要只给目录、不预取正文，必须先定义明确的策略入口并验证实际模型输入，不能靠配置空列表假定已经实现。

`estimate_tokens()` 按规范文本长度估算，当前约为 `round(len(text) / 3.2)`。内部预算和 `savingRatio` 可用于诊断，但论文成本必须依据实际 tokenizer、模型请求和服务 usage 独立计算。正文是否在扁平输入、来源输入或多轮提示中重复出现，也要计入。

## 3. 三个候选论文方向

| 方向 | 核心研究问题 | 需要增加的主要研究工作 | 初步判断 |
|---|---|---|---|
| A：预算下的按需证据获取 | 哪些字段、哪个来源、哪一页值得接着读？何时停止？ | 明确读取策略、强检索基线、实际成本核算、质量—成本曲线 | 推荐首篇，已有接口最接近可实验状态 |
| B：多来源通信中的证据保真 | 扁平合并、摘要和分来源投递如何影响冲突识别、事实保持和归属？ | 公开可复现的冲突与遗漏任务、答案到证据的标注、来源使用评测 | 可先作为 A 的压力测试；若发现独立规律，再形成单独研究 |
| C：图修订和恢复后的通信一致性 | 重试、版本变化和局部恢复时，如何避免陈旧上下文、遗漏和重复读取？ | 精确状态语义、故障模型、执行轨迹对照、故障注入 | 更偏系统研究；涉及 Planner/Executor 边界，投入更大 |

三个方向可以共享基础设施，但单独成文需要各自的问题、方法和主要证据。不能仅按通信器的模块拆成多篇。

## 4. 推荐首篇的贡献结构

工作标题：

**Budgeted Evidence Acquisition for LLM Multi-Agent Workflows**

中文：**面向大语言模型多智能体工作流的预算约束证据获取**。

标题暂时描述研究对象，不提前承诺效果。论文可以争取形成三项贡献：

1. **问题定义**：在固定协作图和授权边界内，把接收方的上下文构建定义为序贯证据获取，操作单位是来源、字段、路径和页面。
2. **读取方法**：设计能根据缺失证据、已读内容与剩余预算决定下一次读取和停止的策略，与现有 Broker 执行机制衔接。
3. **可复现实证**：在不同任务、信息规模与预算下，评估质量、实际总成本、证据覆盖和故障边界；公开任务生成规则与读取轨迹格式。

其中第二项是方法论文的关键缺口。Broker、访问控制、来源记录和分页都是实验基础，是否构成系统贡献要由与既有系统的差异及评估证明。若新的读取策略不能优于合理的静态检索，应该根据结果改写为实证分析，或转向来源保真研究。

### 4.1 问题形式化

固定协作图为 G。上游产物 O 保存在 Value Store，A 表示既定访问许可。消费者在第 t 轮只观察任务、授权目录、已交付证据和剩余预算，形成状态 h_t。

策略选择读取动作 a_t = (producer, field, path, cursor, page_size)，或选择停止。每个动作必须满足 A；读取结果更新 h_t。最终输出 y 由任务评测器计算质量 Q(y)。

可以研究最大化期望任务质量、同时限制通信读取预算和总模型成本的问题。读取预算与总模型成本分别报告：额外规划轮次、工具返回值、历史重传、摘要模型调用都会影响后者。不要把估算 token 称作信息熵，也不要把普通预算约束包装成信息论定理。

### 4.2 方法从简单、可解释的版本起步

先实现三个可以独立比较的读取策略：

- **静态相关性选择**：按任务对字段或片段做 BM25/向量排序，在预算内读取。它是必须认真调优的强基线。
- **模型自主补读**：模型调用现有通信工具，自行选择内容与停止。它检验现有能力，不自动算新算法。
- **基于缺失证据的补读**：维护已获得的事实、未解决的任务要求和候选来源；优先读取预计能解决关键缺口且成本较低的内容，并显式处理重复与冲突。

第三种是待验证的候选方法。初版可以通过可审计规则和模型选择实现，随后再判断是否需要训练策略。不能把模型自评分当作已校准的信息增益或成功概率；只有验证集上有效的评分才值得进入方法。

停止策略也需要对照：预算耗尽、固定轮数、模型自行停止，以及按任务要求检查证据覆盖后停止。只读得少、答得少不是有效节省。

## 5. 实验怎么设计才有说服力

### 5.1 先区分两层实验

**读取策略隔离实验**：冻结上游产物、消费者角色和图，只改变下游获得信息的方式。这样可以确定收益是否来自通信策略。预先标清冻结产物的生成成本，不把免费上游当作真实总成本。

**完整工作流实验**：所有 Agent 实际执行，测量包含生产、选择、补读、推理、重试的端到端成本与质量。若仅做第一层，论文结论应限制在消费者的证据获取阶段。

### 5.2 任务选择

| 任务族 | 具体作用 | 客观评测 |
|---|---|---|
| 多跳、多来源问答 | 测试跨来源依赖与缺失证据补读 | 答案正确率、支持证据覆盖；可考虑 HotpotQA、MuSiQue 等公开任务，先确认版本和许可 |
| 文档与表格联合判断 | 测试小字段读取、精确数字、日期、例外条款 | 确定性答案或可执行检查；业务任务只能作为补充 |
| 可控通信压力任务 | 改变干扰比例、关键事实位置、同名字段、嵌套深度、冲突和正文长度 | 生成器保留答案及必要证据，评测时使用；策略与提示不可访问标注 |

首轮先用小样本开发集检查链路和失败模式，再依据差异与方差估计正式测试规模。正式结果至少覆盖两个任务族和两种模型配置；任务族、模板及文档来源要隔离，不能让同一模板的改写同时进入训练和测试。

### 5.3 对照组

同一图、模型、角色、授权集合和任务下比较：

1. 全量投递授权上游信息。
2. 固定字段或固定长度预取。
3. 固定预算摘要；摘要生成成本计入。
4. BM25/向量检索选取字段或片段。
5. 模型自主调用通信工具。
6. 候选的缺失证据驱动补读策略。

LLMLingua 等压缩方法可作为补充，需要提供合法来源边界和同等调参机会。后续补查通信剪枝与自适应通信论文，再决定最直接的可复现对手。

全量投递超出模型窗口时应记录不可执行，另设明确的窗口受限基线，不能暗中截断后继续称为“全量”。接收方选择与图剪枝解决的问题不同，首轮固定图；联合优化留作扩展。

### 5.4 关键指标

- **任务质量**：准确率、任务成功率、可执行验收结果。自动判分优先；需要模型评审时固定规则并抽样核查。
- **真实成本**：各次请求的输入/输出 token、缓存 token、选择与摘要开销、重试成本、总调用数及实际时延。Broker 交付量另列。
- **证据使用**：必要证据召回、无关读取比例、来源归属正确率、冲突识别率、答案中无支持断言比例。
- **读取行为**：首次上下文大小、补读次数、重复读取量、停止时仍缺失的必要证据、预算失败率。

主要结果应展示预算变化下的质量—成本曲线，比较达到相近质量时的成本，以及相近成本时的质量。若主张“质量不下降”，需提前确定有实际意义的非劣界并报告区间，不能用不显著差异替代非劣证明。

同任务配对比较；按独立任务或任务族计算置信区间，报告随机种子、重复方式和失败样本。页面不是独立样本。最终样本量由先导实验与目标效应确定。

### 5.5 消融与压力条件

- 去掉分来源表示，改用扁平字段，判断收益是否来自来源保留。
- 去掉补读，只保留预取，判断适应性价值。
- 只用通用 read 工具、去掉候选策略，检验算法增量。
- 改变页面大小和停止规则，识别省 token 是否被轮次开销抵消。
- 逐步增加干扰、证据分散程度、字段冲突和任务深度。
- 在授权内加入错误或冲突材料，检查读取量减少是否损伤交叉核验。

权限拒绝和恢复正确性可以另做确定性测试。访问控制限制读取范围，但不能据此声称解决了提示注入、数据外泄或差分隐私问题。目录、字段名和大小等元数据也有其暴露边界。

## 6. 文献定位：已确认什么、还缺什么

2026-11-24 从以下 arXiv 原始摘要页核对了标题和摘要。以下是背景定位，尚未逐篇核查全文和代码。

| 文献 | 与本选题的关系 | 需要避免的重复表述 |
|---|---|---|
| [ChatDev](https://arxiv.org/abs/2307.07924) | 多角色语言通信与软件开发协作 | “让 Agent 通过沟通协作”已有成熟先例 |
| [MetaGPT](https://arxiv.org/abs/2308.00352) | SOP、角色分工和中间产物验证 | 不能把结构化工作流或产物交接本身当作新概念 |
| [AutoGen](https://arxiv.org/abs/2308.08155) | 可编程多 Agent 会话与工具协作 | 需要区分通用协作框架与具体证据获取机制 |
| [MemGPT](https://arxiv.org/abs/2310.08560) | 有限上下文下的分层数据移动与控制流 | “正文外置、按需取回”本身不足以证明原创性 |
| [LLMLingua](https://arxiv.org/abs/2310.05736) | 预算控制与提示压缩 | 应比较成本和质量，不能假定摘要/压缩必然损伤任务 |
| [A Survey of AI Agent Protocols](https://arxiv.org/abs/2504.16736) | 上下文协议与 Agent 间协议分类 | 协议互通和运行期证据选择不是同一个研究问题 |
| [Agent Interoperability Protocols Survey](https://arxiv.org/abs/2505.02279) | MCP、ACP、A2A、ANP 的互操作比较 | 通信器尚不是已证明具有外部生态兼容性的新互操作标准 |

仓库已有的通信文献以综述为主，尚不足以完成创新性论证。下一步应优先检索并核查：

- 多智能体通信剪枝与自适应消息选择：AgentPrune、AgentDropout 等检索线索。
- 共享上下文、KV 或隐表示通信：KVComm 等检索线索，确认其实际问题设置。
- 接收方驱动的检索、工具读取、共享工作区与长上下文管理。
- provenance-aware context、evidence-preserving communication、budgeted information acquisition。
- 2025—2026 年与上述问题直接相关的方法与系统，以及相应公开实现。

本轮 arXiv API、OpenAlex 和部分 arXiv 关键词搜索遇到 429 或超时；精确 arXiv 摘要页可访问。上述检索线索未核查到可靠元数据的部分，不列为已确认参考文献。当前不能断言“现有工作没有研究接收方按需读取”，也不能把三种常见机制的组合直接判断为首次提出。

后续逐篇建立比较矩阵：信息选择发生在发送端还是接收端；选择单位是边、消息、字段还是片段；能否补读原文；是否训练；是否保留来源；是否包含额外决策开销；在何种任务上验证。

## 7. 与项目完善同步推进的顺序

### 阶段一：得到可信的实验底座

明确预取策略及其默认行为，接通真实请求的成本采集，冻结可回放任务、上游产物和图，确保模型的所有信息入口均可追踪。先验证样例中真正少读了哪些内容、有无其他输入绕过通信器重复提供答案。

产出：现状与基线记录、实验配置和第一批读取轨迹。

### 阶段二：用最小对照决定是否继续该选题

运行全量、静态检索、摘要和自主补读，分析哪些任务确实需要适应性读取，再实现缺失证据驱动的候选策略。开发集用于调参和失败分析，独立测试集用于最终判断。

推进依据：相对强静态检索与通用工具调用，出现稳定且可解释的质量—成本优势。若只在人工构造的特殊字段任务上有效，需要缩小结论或调整方向。

### 阶段三：扩大证据并开始正式写作

补齐最邻近工作，确定比较对象；扩展模型和任务，完成消融、区间和失败分析。随后按“问题→方法→对照→结果→边界”写正文。arXiv 可用作预印本平台，但不等于同行评审录用；会议或期刊定位应由实际贡献决定。

暂不预设 Nature 系列目标，也不承诺会议档次。该题更直接面向 AI/NLP 的多智能体与上下文管理研究读者；如结果主要体现可靠性与恢复机制，则考虑系统研究受众。

## 8. 推荐论文结构与评审问题

建议结构：Introduction；Related Work；Problem Setup；Evidence Acquisition Policy；Experimental Setup；Results and Ablations；Limitations and Failure Analysis；Conclusion。

最需要提前回答的评审问题是：

1. 相比已有工具检索、共享存储和长上下文管理，新机制究竟是什么？
2. 提升来自新读取策略、分来源表示，还是更多模型调用？
3. 相比调优后的静态检索，哪些任务需要自适应？
4. 算入所有选择、重复提示和摘要开销后，是否仍节省成本？
5. 任务和字段是否专为该实现设计，换任务或模型是否仍成立？
6. 少读时缺少了哪些证据，模型是否会提前停止或输出无依据结论？
