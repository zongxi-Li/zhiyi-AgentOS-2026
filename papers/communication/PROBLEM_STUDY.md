# 通信器的问题调研：从已有方法到可验证研究问题

日期：2026-11-25。目标已确认：结合项目，先完成一篇扎实的方法或系统论文。

## 1. 结论与推荐定位

不建议继续用“接收方按需读取上游信息”作为完整的论文贡献。AOD、MSS-Complement、LTS、AgentFugue和SCH已经分别覆盖需求驱动、证据集合选择、原文按需读取和历史证据恢复。[P03](REFERENCES.md#p03)—[P08](REFERENCES.md#p08)

建议先研究这个更具体的问题：

> 当上下游Agent通过有许可、有预算、支持分页的产物引用协作时，下游能否区分“已取得一些相关信息”与“已取得支撑当前决定的充分、有效证据”，并以可接受的总开销弥补差距？

这是一个**候选问题**。本轮文献提供了动机与强对照，并未证明该组合条件下存在无人研究的空白。应先验证失败是否真实、频繁且不能被普通工具调用和已有方法轻易解决。

工作题目可暂定为：

**Evidence Sufficiency under Budgeted Multi-Agent Communication**  
**受预算约束的多智能体通信中的证据完备性**。

## 2. 项目真实基础与研究缺口

以下是2026-11-25对当前文件的定向核查。没有将历史设计文档当作当前已完成能力，也没有在本轮重跑上一轮的102项功能测试。

| 当前基础 | 依据 | 对研究有什么帮助 | 仍需测量或定义什么 |
|---|---|---|---|
| 根据生产者、消费者、字段和run判断能否读 | [manifest.py](../../apps/agentOS/src/components/communicator/manifest.py)、[broker.py](../../apps/agentOS/src/components/communicator/broker.py) | 确定合法信息域 | 合法域里缺证据，与证据在合法域外，是两类不同情形 |
| 预取与补读共用Broker | `assemble_context()`、[reader.py](../../apps/agentOS/src/components/communicator/reader.py) | 可固定执行链路更换策略 | 默认预取是否已经把关键信息全部给出，是否还有其他输入泄漏 |
| 支持字段、路径和分页读取 | `read_reference_page()`、[context_read.py](../../apps/agentOS/src/adapters/tool/context_read.py) | 可研究细粒度获取 | 完成某页、某子树、某字段和任务证据覆盖不能混为一谈 |
| 保留sourceData和evidenceRefs | [contracts.py](../../apps/agentOS/src/components/communicator/contracts.py) | 多来源归属可回溯 | 来源可追踪不代表没有冲突，也不代表断言被其蕴含 |
| 预算计数与读取操作身份 | Broker的`usage_snapshot()`等 | 可分析重试与逻辑交付 | 逻辑操作去重不等于模型没有重新付费处理同一段文本 |
| token长度估算 | `estimate_tokens()` | 可作内部预算信号 | 真实token、重复提示、缓存、选择器调用和时延要单独采集 |

两个实验前必须处理的配置细节：

1. `assemble_context()`中存在`requested or declared`，空的prefetch列表不等于零正文预取。目录优先策略应明确实现或选择可验证的入口。
2. 工具返回的`complete`对带入站cursor的请求不会自动表达“累计所有页面均已读完”。它描述当前返回范围，不能直接作全程覆盖账本或证据充分性标签。是否沿全部游标读完、是否遗漏其他分支，应由实验采集和决策状态分别判断。

这两点是研究设计约束，不是本轮提出的生产缺陷修复请求。

## 3. 四种“完整”应当分别建模

```mermaid
flowchart LR
    A[可访问：引用与字段获许可] --> B[交付完整：指定范围无遗漏]
    B --> C[证据充分：当前决定的要求被覆盖]
    C --> D[使用正确：结论或行动确由证据支持]
    D --> E[任务成功：验收条件达成]
```

箭头表示检查顺序，不表示逻辑保证：交付完整不保证证据充分，证据充分也不保证Agent推理正确。对某些任务，即使缺少外部证据也可能靠参数知识答对，因此最终正确同样不能倒推证据链完整。[P07](REFERENCES.md#p07)、[P08](REFERENCES.md#p08)、[P22](REFERENCES.md#p22)、[P26](REFERENCES.md#p26)

还应单独记录**版本有效性**：旧证据可能内容完整但已不适用于当前产物或当前决定。SCH已研究修订后恢复；我们的潜在增量必须落实到跨Agent产物版本、读取范围或控制机制的具体区别，不能只重复“版本重要”。

## 4. 三个候选研究问题

### RQ1：局部读取会怎样影响证据集合完备性？

**文献依据。** MSS-Complement说明必要证据往往是集合而非独立相关片段；Silo-Bench区分收集不足和整合失败；上下文压缩综述区分选择、保留和之后访问等失败环节。[P07](REFERENCES.md#p07)、[P22](REFERENCES.md#p22)、[P32](REFERENCES.md#p32)

**具体问题。** 相同内容分别以完整源单元、字段、跨页子树交付时，下游会不会把局部命中当作全局充分？反例可以是：前页满足主规则，后页含必要例外；两个来源分别提供互相依赖的条件；只读最新摘要但遗漏生效日期。

**候选假设H1。** 在需要多项联合证据、跨页或跨来源的任务上，仅按相关性挑选和自主补读，比显式追踪当前证据要求的策略更容易提前作出无支持结论。

**需要反驳自己的实验。** 给普通ReAct读取工具同等目录、范围信息和停止提示；给MSS式集合选择同等候选与预算。如果它们即可解决，则“增加状态字段”不值得包装成新方法。

### RQ2：跨来源与版本变化会造成什么独立困难？

**文献依据。** PACT关注可靠的行动状态交接，SCH恢复原支持证据，provenance研究区分支持关系和执行关系。已有工作并未让“保存来源”成为空白。[P06](REFERENCES.md#p06)、[P08](REFERENCES.md#p08)、[P30](REFERENCES.md#p30)、[P31](REFERENCES.md#p31)

**具体问题。** 当多个生产者同名字段冲突、产物被新版本替代、读取一半后发生修订时，下游是否沿用陈旧结论？元数据中的来源／版本／范围是否在实际提示和模型行为中被正确使用？

**候选假设H2。** 单独保留来源不足以避免陈旧或不完整证据被继续使用；需要把读取范围与产物版本绑定，并在受影响决定继续执行前重新检查证据要求。

**独立性要求。** 若收益完全来自修复字符串覆盖或检查一个版本号，它首先是工程正确性改进。系统论文还需可复用的语义、故障模型、跨任务实验和与移植SCH等方法的对照。

### RQ3：获取更少正文，何时真正降低任务总成本？

**文献依据。** AOD显式以任务和成本训练通信门控；MSS-Complement存在小交付上下文与较大选择开销的权衡；Beyond Token Savings研究token、缓存、计费和时延的偏离。[P03](REFERENCES.md#p03)、[P07](REFERENCES.md#p07)、[P25](REFERENCES.md#p25)

**具体问题。** 页面越小是否导致更多模型回合和重复历史？维护缺口或来源状态的开销何时被节省抵消？固定检索与自适应获取在哪些信息密度和任务深度下分别占优？

**候选假设H3。** 细粒度自适应的价值依赖信息分散度、任务要求与模型调用开销，不存在越细越好的普遍结论。

成本分析可作为RQ1／RQ2的方法评估；“我们也测总成本”本身不是新研究贡献。

补充检索也发现了医疗工具证据准入CIEG、跨组织消息离线问责，以及Agent共识测量工作。因此，不应将“证据准入”“有回执可审计”或“共识不等于正确”单独表述为新概念。本轮仅核对这3篇摘要，具体边界见[补充文献](SEARCH_LOG.md#supplementary)。[S01](REFERENCES.md#s01)、[S02](REFERENCES.md#s02)、[S03](REFERENCES.md#s03)

## 5. 候选机制：先用可移植、可反驳的最小版本

可以探索一个明确区分**任务要求**与**读取状态**的接收方控制器：

- 任务要求层记录当前决定尚需哪些事实、条件或互补证据；允许多组替代证据，避免把唯一标注答案当作唯一合法支持。
- 读取层记录产物来源、版本、字段／路径、已交付范围和是否仍有未读页面；将`unread`、`partial`、`read`、`blocked`、`stale`作为候选操作状态。
- 选择层在合法集合内决定下一次读什么；可从普通检索、MSS式集合选择或规则实现开始，不预设必须训练新模型。
- 决策层区分继续读、继续任务、报告证据不足；不把模型自评当作已证明的充分性证书。

这些是**待研究的设计要素**，当前没有作为新功能落地。状态名称、来源账本和版本绑定本身不保证语义正确。训练或模型调用的必要性，应该由强基线失败模式来决定。

## 6. 最小诊断实验

### 6.1 两个层次，逐步扩大

第一层冻结上游产物、图和下游决定，只改信息交付和读取策略。这可定位通信的因果影响。第二层才让完整多Agent工作流执行，观察上游产物和下游行为互相影响后的真实结果。

初轮建议24—40个开发实例、一个模型、四种策略、两档预算，作为链路和错误分析的先导实验；不是正式论文样本量，也不用于宣布统计优势。正式测试规模按先导方差、任务族和目标效应确定，再增加模型和随机重复。

### 6.2 三组任务

| 任务组 | 目的 | 构造与控制 |
|---|---|---|
| 分片多跳问答 | 不同生产者持有互补事实 | 基于HotpotQA／MuSiQue，公开分配规则；禁止每个Agent均获得全部支持文档 |
| 分页条件与例外判断 | 识别局部命中、全局缺失 | 可生成规则、数值、日期和例外，提供确定性答案及多组合法证据 |
| 修订与冲突 | 测量过期证据和来源误用 | 固定何时更新产物、哪些决定受影响；严格区分已发布信息与未来信息 |

HotpotQA／MuSiQue是问答资源，不是天然的多Agent通信基准。Silo-Bench可提供真实信息分片与确定性验收的评测设计；其算法任务也可能把主要瓶颈转向计算，所以需按失败类型分层报告。[P22](REFERENCES.md#p22)、[P28](REFERENCES.md#p28)、[P29](REFERENCES.md#p29)

### 6.3 四个先导策略与后续强基线

先导阶段用全量授权输入、静态BM25／向量检索、通用ReAct补读、显式证据要求／读取状态策略。四者使用同一图、模型、产物、许可与总预算，禁止给候选策略额外真值。

若先导显示值得继续，加入PACT式交接、MSS-Complement式状态条件集合选择、SCH式状态与证据恢复；并根据任务增加AOD式需求请求。对外声称“复现”前，应核对作者实现和配置。移植或简化实现统一标为**适配基线**，不能直接沿用作者原结果名义。

### 6.4 指标与关键对照

| 层面 | 必测指标 | 关键解释 |
|---|---|---|
| 任务 | 准确率／成功率、拒答覆盖率 | 避免通过大量拒答制造可靠性提升 |
| 证据 | 必要组覆盖、完整集合恢复、支持充分性 | 可借鉴SERBench；不要把它重命名成原创指标 |
| 来源 | 来源归属、版本有效率、跨来源冲突识别 | 引用存在不等于引用支持 |
| 读取 | 交付范围、漏页、重复读取、错误提前停止 | 每页、每路径和累计覆盖分别记录 |
| 成本 | 全部模型调用、输入／输出／缓存token、工具与选择开销、实际时延 | 同时报告逻辑交付与物理重复处理 |

建议报告两个诊断量，并明确它们是本项目的操作性定义：一是**证据未充分时继续作出结论的比例**，二是**证据已充分但仍整合错误的比例**。二者需要隐藏评测标注或独立核查，不能从模型自评分中直接生成真值。

重要对照包括无证据作答、理想必要证据、去掉一组必要证据、仅增加来源／完整性元数据、来源打乱、版本更新，以及相同选择调用预算。理想证据只作诊断上界，不作为可部署策略；全量输入若超窗应记录不可执行，不能暗中截断。

## 7. 信息与资源公平性

对照方法必须在同样的授权集合内操作。若某任务必要事实被权限禁止，正确行为是识别无法充分完成或报告受限，而不是通过放宽候选方法权限制造优势；若连必要事实存在与否都不可知，也不能要求控制器凭空证明缺失。

选择器使用的字段目录、大小、路径和版本元数据应计入可见信息与成本。标注证据、未来版本、上游未完成动作、最终答案不能泄漏给策略。任务划分按文档来源／模板／仓库隔离，不能只随机切分同一模板的改写。

引用哈希、访问控制和事件日志能帮助约束与核验数据流程，不能据此宣称解决提示注入、隐私保护、语义蕴含或端到端exactly-once。

## 8. 如何决定第一篇走方法还是系统

**方法路线成立的条件：** 在许可、表示、图和预算相同的情况下，新选择或停止策略对强检索、通用工具调用和适配的最近邻仍有稳定增量，且差异能由消融定位。

**系统路线成立的条件：** 跨来源、分页和版本语义形成可复用接口与正确性边界，在多个模型和任务上改善可恢复性或减少具体故障，并完整计入系统开销。

**应当转向或收缩的信号：**

- 普通工具调用加明确提示就消除了大多数错误。
- 收集完整证据后仍大量失败，说明主要问题在推理整合或验收。
- 收益只来自修复字段覆盖、关闭重复输入等一次性缺陷。
- 选择器成本高于节省，且质量没有足够改善。
- 只有为接口定制的合成任务有效，公开任务或其他模型不成立。

本轮推荐先做RQ1诊断，同时记录RQ3成本，再据失败轨迹决定是否投入RQ2的版本与恢复机制。这样既能完善项目，也能避免在与近邻工作高度重叠的设计上过早投入。
