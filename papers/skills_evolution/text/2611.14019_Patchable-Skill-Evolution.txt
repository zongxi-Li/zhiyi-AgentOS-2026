A.6   Case Study
In Table 5, we present a qualitative case study to
illustrate how PASE enables more precise skill evo-
lution by separating descriptive knowledge from ex-
ecutable procedural logic. The task requires extract-
ing two-digit month codes from spreadsheet strings,
retrieving their corresponding month names from
a reference table, and writing the results into des-
ignated cells. The text-only baseline, Trace2Skill,
captures the general task-solving procedure but in-
troduces potentially misleading rules during skill
evolution. Specifically, it suggests allowing prefix
matching when exact matches are unavailable and
inferring month names directly from numeric codes
when lookup fails. Although these rules appear
reasonable, they may lead to incorrect matches or
outputs inconsistent with the reference table, such
as generating “September” instead of the expected
“SEP”. Furthermore, mixing these execution details
with descriptive guidance makes it difficult to iso-
late and repair the underlying logic.
   In contrast, PASE separates the two forms of
knowledge into a natural-language skill document
and an associated executable program. The skill
document preserves high-level task guidance and
explicitly emphasizes the reference table as the au-
thoritative source, while the program implements
precise string extraction and exact lookup opera-
tions. Through programmatic patches, PASE can
directly refine the execution logic without modify-
ing unrelated descriptive knowledge. Meanwhile,
textual patches can independently improve task-
level guidance without disrupting the program im-
plementation. This case demonstrates that decou-
pling descriptive knowledge from procedural logic
facilitates more targeted and reliable skill updates,
reducing the risk of introducing ambiguous or con-
flicting execution rules during skill evolution.

 Proposer Agent Prompt
You are a Skill Proposer Agent for an LLM agent that solves spreadsheet tasks.
Your job is to explore the current skills, historical proposed patches, and multiple agent execution trajectories,
identify why tasks succeed or fail, and propose a skill update patch.

## Tools Available

Use only these four tools:
- `read_trajectory(traj_id, steps)`: reads selected steps from one trajectory and returns raw actions and observations.
- `read_skill(skill_name)`: reads one current skill's complete Markdown document and linked program.
- `read_ patch(patch_id)`: reads the full content of a historical patch.
- `finish(patch)`: submits the final patch.

## Workflow

1. Read multiple trajectories with `read_trajectory` to inspect relevant steps, analyze the agent's actions, and
diagnose the causes of success and failure.
2. Use `read_skill` to inspect the relevant skill and linked program. Use `read_patch` to inspect relevant historical
proposed patches to refine your result before finalizing the patch.
3. After read enough information, submit exactly one update patch through `finish`.

## Your Input

1. Trajectory: multiple agent execution trajectories. Each trajectory contains task instruction and number of steps.
2. Skill: a skill document linked with a program.
  - skill: Markdown guidance with YAML frontmatter, When to Apply and Rules sections. Skills with a program also
include a Program section with parameter descriptions and calling examples.
  - program: one executable function that encodes core procedural logic of the skill; empty if absent. The program
should be a reusable, parameterized function, with task-dependent inputs and settings passed as arguments rather
than hardcoded in the implementation.
3. Historical patches: Records of skill patches proposed in previous evolution iterations.

## finish() Proposal Format

For creating a new skill:
- "operation": ”create"
- "name": new skill name (snake_case)
- "skill": full Markdown with YAML frontmatter (name, description), `## When to Apply`, and `## Rules`, followed by
`## Program` if this skill has a program.
- "program": one executable function that encodes core procedural logic of the skill

For deleting a existing skill:
- "operation": "delete"
- "name": the name of an existing skill; its Markdown and program are removed.

For repairing a skill:
- "operation": "repair"
- "name": the name of an existing skill.
- “skill” : a list of line-level edits, each edit is {“line”: 1, “operator”: “+/-", "content": "text"}
- "program": a list of line-level edits, each edit is {"line": 1, "operator": "+/-", "content": "code"}

`line` is one-based. For an existing component, `+` inserts content at the specified line and `-` removes the specified
existing line. Apply multiple edits sequentially; use a deletion followed by an insertion to replace a line.

## Rules

1. Ground each proposal in actual actions evidence. Review relevant historical proposed patches, including adopted
improvements and rejected attempts, to avoid repeating patches without new evidence.
2. Prioritize experience supported by multiple trajectories. If the trajectories have different root causes, address the
one you judge most important and actionable.
3. Keep skills concise and usable from the task input alone. The resulting skill must not depend on answer.xlsx or
hardcode sampled answers.
4. Preserve useful guidance in the current skills. When new evidence conflicts with existing guidance, distinguish
their applicable conditions and refine the relevant rules. Correct unsupported or incorrect guidance while preserving
useful behavior; avoid blindly replacing existing content.
5. Programs are optional. If a skill is too general or cannot be meaningfully expressed as an executable function, keep
it Markdown-only.
6. A program implements a skill’s core logic. Use `create` to add a new skill when a newly identified pattern defines a
distinct capability. Avoid indiscriminately expanding existing skills.
