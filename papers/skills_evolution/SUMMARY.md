# 从一次执行到可复用能力：Skills 自进化、技能图与生命周期治理

整理日期：2026-11-18。本专题收录 **27 篇 PDF、687 页**，覆盖技能抽象、检索、局部修订、程序库学习、训练与技能共演化，以及关系图和长期退化。完整来源、版本与全文见 [论文索引](README.md)，实际方法选读页码见 [阅读日志](citations/reading-log.json)。本文是项目导向的文献综合与实现建议，未运行论文模型或外部代码。

建议把 Skills 自进化定义为：依据可追溯的执行证据，提出可复用技能的新版本，验证适用范围和贡献，再决定将哪个版本供未来任务调用。生成一份 SKILL.md 只是候选构造的一步；复用收益、失败边界、版本依赖与淘汰机制决定其是否形成持续能力。

## 1. 技能不是一种单一对象

文献中相同的 skill 一词，可能对应五种不同资产。

| 对象 | 内容 | 更新方式 | 适合验证的指标 |
|---|---|---|---|
| 经验笔记 | 某次失败及启示 | 增补与纠正 | 来源真实性、召回相关性 |
| 自然语言技能 | 条件、步骤、验收、例外 | 文档补丁 | 新任务成功、遵循率、误用率 |
| 技能包 | 文档、脚本、资源和依赖 | 包版本、测试和发布 | 可执行性、接口、依赖兼容 |
| 程序库抽象 | DSL 函数、工具或可调用子程序 | 合成、压缩与重构 | 行为等价、复用及搜索成本 |
| 权重内化能力 | 参数中的策略和行为 | SFT/RL 等训练 | 泛化、遗忘、训练开销 |

上述资产可以协作，但不能混报。例如，冻结基础模型并更新外部技能，并不代表完全没有训练；路由器或技能生成器也可能训练。模型能够背诵某个流程，也不代表系统已经有可审计的技能包。[图演化综述](../graph_evolution/SUMMARY.md)进一步区分技能关系图、任务执行图和候选版本血缘图。

## 2. 起点：从轨迹中学会“怎样复用”

### 2.1 Voyager：可执行技能、反馈和课程共同作用

[Voyager](2305.16291_Voyager.pdf)在 Minecraft 中结合自动课程、迭代代码生成与技能库。迭代过程利用执行反馈、错误消息和自验证信息修订程序，成功程序进入可复用技能库；任务描述检索技能描述的 embedding，再返回相应代码，论文方法包含 Top-5 检索。

基础 LLM 无需因此微调；能力增长主要表现为可执行程序和探索经验的积累。但其环境给出特定可执行接口和反馈，不能将 Minecraft 的成功检验直接等同于开放业务任务验收。

对项目可借鉴三个条件：候选有明确 callable 或操作序列，调用后存在可观察结果，复用时能找到对应来源和版本。一次命令退出码为 0，不足以证明业务目标达成；例如报告生成成功还需验证内容和证据，数据清洗成功还需检查约束及损失。

### 2.2 Agent Workflow Memory：把具体轨迹抽象为子任务

[Agent Workflow Memory](2409.07429_Agent-Workflow-Memory.pdf)从执行经历提炼可复用工作流，将具体值抽象成变量，让未来任务参考子任务模式。它区分离线预先形成的固定记忆和在线随任务序列更新的记忆。在线更新在任务 t 完成后才供后续任务使用，因此测试顺序和可用历史都会影响结果。

其在线成功判断含模型 judge，不能将 judge 判定直接当作不可争议的真值。对 Kinlin，建议抽象时保留成功证据及反例，将“在哪些条件下有效”与步骤一起存储。验证时采用时间切分，禁止后续任务的信息回流到较早任务；并报告 cold-start、随着经验增长的性能和长序列退化。

轨迹参数化还要区分可变槽位与不可随意替换的条件。用户名、文件路径可变，不代表目标系统、权限和数据保留规则都能替换。抽象器应输出槽位类型、约束和来源，避免把一次特定环境下的绕行变成普遍操作。

### 2.3 从工具制作到程序库压缩

[LLMs as Tool Makers](2305.17126_LLMs-as-Tool-Makers.pdf)将较强的工具制作模型和较轻的使用模型分工，通过缓存和后续调用摊薄构造成本。本轮以摘要筛选为主；落地时必须进一步核查真实执行验证，不能把“生成函数”当作完成工具注册。

[DreamCoder](2006.08381_DreamCoder.pdf)以 wake-sleep 程序学习发展 DSL 库和神经搜索机制，属于程序归纳路线。[LILO](2310.19791_LILO.pdf)结合语言模型合成、Stitch 压缩与文档化，说明库学习还需要可读的抽象名称和解释。LILO 本轮只选读相关原理页，未完成整体实现核查。

这两类工作提示：技能库不应只增不减，相似程序可以提炼共享抽象，稳定抽象能减少未来搜索。但 DSL 中成立的压缩不能直接推广到有外部副作用的任意业务代码。合并前应证明接口、权限和执行语义兼容，而不是只看文本相似度。

## 3. 文档、代码和参数分别如何进化

### 3.1 DGM 与 SICA：自修改的是 Agent 实现

[Darwin Gödel Machine](2505.22954_Darwin-Godel-Machine.pdf)冻结基础模型，修改 Agent 的代码实现并维护多样 archive，从不同分支继续探索。特别需要区分 archive 入库与生产采用：能编译、保持自编辑能力等条件可能让一个子代进入 archive，不要求所有入库子代都立即胜过父代。

这对项目的启示是允许失败探索存在于研究档案，但只有通过发布门槛的版本才进入默认运行。[SICA](2504.15228_SICA.pdf)同样涉及编码 Agent 的自改进，本轮为摘要筛选与全文归档，不能据此声称已经全面审查其自修改约束。

### 3.2 SkillRL：技能库与策略共同训练

[SkillRL](2602.08234_SkillRL.pdf)保留基础执行的成败轨迹，通过 teacher 抽象成技能，构建 general 与 task-specific SkillBank，并包含 cold-start SFT 和 GRPO，使策略与技能库共同改进。它不是仅更新 Markdown 的训练免费方案。

[AgentEvolver](2511.10395_AgentEvolver.pdf)也包含任务生成、经验探索和奖励归因等训练环节。本轮摘要级证据支持将其归入训练与经验共同演化，而不足以据此配置一个可靠的本地训练流水线。

在项目早期，外部技能版本化与冻结模型更容易检验：先证明检索和技能内容对任务有增益，再决定是否训练小型路由器或基础策略。若直接引入 RL，必须分别报告训练数据、采样预算、模型更新和外部技能变化的贡献。

### 3.3 同名 SkillFlow 的两条路线

[SkillFlow 2025](2504.06188_SkillFlow-Retrieval.pdf)关注可扩展且高效的技能检索；[SkillFlow 2026](2605.14089_SkillFlow-Evolution.pdf)关注 flow-driven recursive skill evolution，包含可训练 supervisor、动态库和冻结 executor，涉及流匹配及反向策略等机制。两篇不是同一文件的不同版本，也不能用其中一篇的检索结论替另一篇的演化机制背书。本文对两篇均以摘要定位为主，训练细节需要后续专项选读。

## 4. 局部补丁和技能库管理比整库重写更可控

### 4.1 PASE：把修改变成有边界的 patch

[Program-Aided Patchable Skill Evolution](2611.14019_Patchable-Skill-Evolution.pdf)，简称 PASE，组织自然语言技能及可选程序配对，利用成功和失败轨迹生成 CREATE、REPAIR、DELETE 等补丁，并保留修改历史。其候选在 heldout 上严格优于既有版本时才接受。

局部 patch 能明确“改了哪个条件、哪一步或哪段程序”，减少整份重写时丢失有效经验的问题。它也便于对比、回滚和审查。但在同一 heldout 上不断选择，观察分数严格增长不代表真实泛化能力单调增长；样本噪声与适应过拟合仍存在。详见图综述中的独立确认机制。

Kinlin 可以将技能操作限制为增加前置条件、修订某步、补验收、添加失效条件或变更程序引用。patch 应指向 base skill checksum 和局部位置，并说明支持与反对的轨迹；若 base 已更新，则拒绝静默覆盖，重新生成或显式合并。

### 4.2 SELM：检索、使用证据与生命周期分开

[SELM](2610.24630_Selm.pdf)保持目标模型冻结，以相关性和 EMA 历史 utility 辅助检索，并按类别 Map-Reduce 整理库；更新操作包括 ADD、EDIT、UPVOTE、DOWNVOTE、DELETE，另有 graveyard 保存退出活跃库的条目。置信度与实际任务效用是不同信号，不应混成一个分数。

一个关键限制是：某次任务共同检索了 5 个技能并成功，平均 reward 不能直接当作每个技能的因果贡献。它们可能互相替代，可能只有 1 个被实际使用，也可能全部无效。适合先记录 observedUtility 和 attributionMethod，而不是给全部技能同步累计“成功证明”。

低频也不意味着无用。专业领域或高风险恢复技能本来就少调用；可将其移入 dormant 索引，保留显式召回和保护任务，而不是按使用频率永久删除。

### 4.3 TrackRL：用对照估计技能是否有用

[Trackable Skill Library Lifecycle Management](2610.25126_Skill-Library-Lifecycle.pdf)在 GRPO 分组内，对技能进行独立 Bernoulli 随机注入，利用同任务处理组与对照组估计 utility 和 mastery，并据此管理孵化、保留、退役和有害移除。

相比共同检索后的平均 reward，这种干预更接近贡献估计，但仍依赖随机化、样本量及技能交互等条件。多个技能组合可能出现互补或冲突，因此单技能边际效果不覆盖所有组合。论文训练中的随机注入也不意味着生产中可以随机撤掉必需的授权、合规或安全操作。

建议在隔离回放中做同任务有/无技能对照，固定其他检索和执行设置；对高风险技能保留强制基础规则。若使用观察数据，只报告相关性，不将其写成已识别的因果效果。[EvoGuard](2611.06444_EvoGuard.pdf)以学习到的 pairwise selector 降低选择成本，但预测比较仍需检查标签来源、独立切分和分布漂移，不能永久替代真实任务审计。

## 5. 技能关系图：分类、组合与执行依赖各有语义

[SkillNet](2603.04448_SkillNet.pdf)把技能组织为 taxonomy、relation 和 package 等层次，关系包括 similar_to、belong_to、compose_with、depend_on。相似不表示可互换；同属一类不表示必须先后执行；可组合不代表双方存在前置依赖。系统应为每种关系单独定义使用规则。

该文用多维评价描述技能，但模型评分不是正式安全证明。当前版本摘要和正文关于资源规模的口径有差异，本文不选一个数字当确定事实；真正可借鉴的是关系语义、技能包和评价维度。

[AgentSkillOS](2603.02176_AgentSkillOS.pdf)区分 capability tree 的发现/检索，与当前任务所需 skill DAG 的编排。这与项目的“两张图”设计高度相关：静态目录帮助找能力，运行图规定实际依赖。其按使用频率控制活跃规模等策略可降低上下文开销，但不能据此认定低频技能质量低。其任务评测和模型成对判定也不能直接当作所有业务成果的绝对真值。

[Memento-Skills](2603.18743_Memento-Skills.pdf)以结构化 Markdown、读取/写入反思循环组织技能，基础 LLM 冻结，但 router 可以训练。因此准确表述应是“基础模型冻结”，而不是“整个系统完全无可训练参数”。其理论结论依赖特定过程及假设，不能推广成任意文档修改都保证单调提升。

检索层建议采用混合召回：关键词与能力标签保障确定性，embedding 提供语义近邻，版本与权限过滤排除不可用项，再以相关性、近期证据和 token 预算重排。把稀有高价值技能作为受保护集合，不用统一频率阈值清除。每次任务记录召回候选、过滤理由、最终注入和实际使用，才能研究“没找到”和“找到了却不奏效”的差别。

## 6. 任务图与程序记忆：SEPM 的桥接意义

[SEPM](2610.14515_SEPM-Task-Graphs.pdf)将任务前置依赖图、shared blackboard 和程序记忆放在同一框架中。共享状态强调 verified 状态与来源，程序记忆支持 create、refine、specialize、retire，warning 带触发条件；私有推理仍可留在本地。

这个方向有助于解决两类记忆脱节：只有文字经验却没有明确执行依赖，或只有图却没有解释为什么这样执行。不过运行时为当前任务修复依赖，与把经验抽象成未来 procedure 版本仍是两项不同操作。blackboard 上某字段变为 verified，必须能回到真实验证器和证据，而不能由 Agent 自称已核验。

对 Kinlin，图步骤可引用不可变的 skillId + version，skill package 指定输入输出和前置条件。技能升级后先检查哪些图版本受影响；默认冻结历史 Run 引用，只在新图版本中采用新技能。这样才能定位收益来自图、技能、检索还是模型变化。

## 7. 新近工作、外部知识和长期风险

以下为摘要筛选后下载的扩展方向，尚不能当成已复核实现。

| 工作 | 与项目相关的切入点 | 进一步验证问题 |
|---|---|---|
| [EvoSkill-S1](2611.22610_EvoSkill-S1.pdf) | 遗传式算子与可训练演化器 | 训练和选择成本、跨任务泛化 |
| [MultiEvoSkill](2610.34260_MultiEvoSkill.pdf) | 结构化多 Agent 生成技能 | 额外协作是否胜过同预算单生成器 |
| [Skills GitHub 实证研究](2611.04456_Skills-GitHub-Empirical.pdf) | 真实技能修改与维护行为 | 仓库样本代表性；流行度是否混淆质量 |
| [Skill Dreaming](2610.36188_Skill-Dreaming.pdf) | 从验证过的 PR 流提取仓库经验 | 时间拆分、未来 PR 泄漏和测试变化 |
| [Anything2Skill](2606.09316_Anything2Skill.pdf) | 外部知识编译为技能 | 来源、前置条件、禁忌和执行许可 |
| [TRACE](2608.22793_TRACE-Skill-Bank.pdf) | 一致性与能力边界记忆 | 限制是否经真实执行验证 |
| [SkillWeaver](2504.07079_SkillWeaver.pdf) | Web Agent 发现和打磨技能 | 网站漂移、登录状态与可回放性 |

[When Experience Becomes a Backdoor](2611.10542_Experience-Backdoor.pdf)讨论通过任务经历污染演化过程，令正常更新机制固化后门。它说明：来源不可信的指令，不会因为被抽象进技能而获得授权。项目应将来源内容、候选建议和用户/系统授权分开保存；文档中的操作描述只有进入已授权任务、通过依赖和权限检查后才可能执行。

长期更新还需要处理经验过时、工具升级和能力遗忘。旧技能不能只因“新版本更近”就退役；新技能也不能只因比旧版本在当前任务族更好就全面替换。应保留固定历史能力参考集、近期时间窗口和少数稀有任务的保护集合，分别观察改进与退化。

## 8. Kinlin 当前状态与优先补齐项

本轮核查 [SkillEvolutionService](../../apps/agentOS/src/components/evolution/skill_service.py)、[演化合同](../../apps/agentOS/src/contracts/evolution.py)、[Run 投影](../../apps/agentOS/src/components/evolution/integration/trajectory.py)及 [Evolution 组件说明](../../apps/agentOS/src/components/evolution/README.md)。说明文档的旧分析与后附 2026-11-18 实施结果应区分阅读。

当前 evaluate_trajectory、abstract_skill、propose_lifecycle_change、select_for_task 四个技能服务方法均为 NotImplementedError。candidate/verified/deprecated/retired 生命周期和 ADD/MERGE/SPLIT/RETIRE/PATCH 等动作已有合同，但合同存在不等于聚类、抽象、检索和治理算法已经实现。

Run 到 Trajectory 的投影已有真实引用和 provenance；source_skill_ids 虽在合同中出现，当前投影没有填充，不能据此宣称已有完整技能调用归因。当前质量评分主要来自完成状态，效率来自错误步骤比例，novelty 固定 0；Run 集成中的 memory_token_budget=768 提议仍为固定示例。以上都不是学习到的技能效用和动态预算优化。

已有 policy 原子发布、CAS、回执、幂等和回滚机制可作为工程参照；图演化也已有受限候选编排。但它们尚未构成技能库自动进化能力。最先需要补齐的是真实 skill/version 使用事件与任务验收，随后才能评估候选究竟在何处有用。

## 9. 推荐闭环：外部技能先验证，训练后置

第一阶段只构建只读技能检索基线。采用人工种子技能、不可变版本与明确合同，记录候选召回、选择、注入、实际使用和输出证据。比较不注入、关键词检索、embedding 检索及混合检索，统一 token 和工具预算，先回答“给系统技能是否真的有帮助”。

第二阶段实现 evidence → abstract → candidate。聚合同任务族的成功与失败轨迹，抽取共享前提、变量槽位、步骤、验收、已知反例和失效条件；保留工具版本与来源引用，去除无关隐私内容。先支持 ADD 和 PATCH，MERGE/SPLIT/RETIRE 需要额外证明，不急于一次实现所有动作。生成的 artifact 和脚本只能进入候选区。

第三阶段以最小对照检验增益。固定图版本、模型、检索器与环境，比较 base skill、candidate、无该技能三种条件；有交互时增加预先约定的组合消融。离线实验先建立贡献估计，不把所有共同检索技能平均分功。按任务族报告成功、质量、成本、负面迁移、错误适用和检索开销。

第四阶段采用版本化发布和生命周期。schema、程序测试、权限和依赖检查通过后，冻结候选进入独立确认；保护旧能力，使用真实授权与 CAS 发布。退役应先停止默认召回、保存历史版本和替代关系，允许在受控条件下恢复。当前 Run 不热替换已绑定的技能。联合流程、状态机与验收见 [实现计划](../EVOLUTION_IMPLEMENTATION_PLAN.md)。

第五阶段在稳定外部收益基础上研究路由训练、在线 bandit 或 RL。每一种训练都需要独立数据划分和基线，同时计算技能制作成本是否被未来复用摊薄。可尝试按新增任务收益、检索命中和反例覆盖安排更新，但不能让生成器无限重试直至碰巧通过同一验证集。

项目近期最有价值的成果，应是一项可证明的复用：某个经过来源核验的技能局部补丁，在新的任务上提高质量或降低成本，保持历史能力，并能准确追溯它被哪些图和 Run 使用。技能数量增长只是这个闭环的副产品。
