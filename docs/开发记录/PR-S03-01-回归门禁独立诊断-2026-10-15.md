## 3. 失败测试的真实调用链与 deadline 状态机

失败用例：`tests/adapters/test_model_runtime_streaming.py::test_private_provider_activity_keeps_stream_alive_until_public_json_arrives`（该测试于 2026-09-14 提交 `af2ea0ca` 引入，早于 S02-02/S02-03/S03-01 全部阶段）。

真实调用链：

- 测试构造 `_ThinkingAdapter`（继承同文件 `_ClosingStreamingAdapter`），其 `astream` 迭代器先执行 4 轮 `await asyncio.sleep(0.01)` 后各 yield 一个 `eventType="activity"` 的 `ModelStreamEvent`，随后立即 yield `delta`（`'{"answer":"ok"}'`）与 `completed`。
- 消费入口为 `RegisteredModelRuntime.stream_generate_json`（`src/adapters/model_runtime.py:385`），参数 `ttft_timeout=0.02, idle_timeout=0.03, total_timeout=0.2`。
- 每轮循环：先算 `total_left`（锚点 `started`，超时抛 `MODEL_TOTAL_TIMEOUT`）；再选窗口——`provider_active`（收到过任意 activity/delta）置位前用 `ttft_timeout` 且锚点为 `started`，置位后用 `idle_timeout` 且锚点为 `last_activity`；`activity_left <= 0` 在循环头抛 `"model stream activity deadline exceeded"`（`model_runtime.py:529-531`）。
- 随后 `await self._wait_for(anext(iterator), min(total_left, activity_left))`（`:533`）。`_wait_for` 默认为 `asyncio.wait_for`（`:702`），超时同样抛 `"model stream activity deadline exceeded"`（`:536-538`）。循环头检查与 wait_for 守卫是同一 deadline 的两道防线。
- `activity` 事件置 `provider_active=True` 并刷新 `last_activity`（idle 锚点），但不置 `first`；`delta` 事件才置 `first=True`。错误码归类 `MODEL_TTFT_TIMEOUT if not first else MODEL_IDLE_TIMEOUT`——因此纯 activity 流中的任何活动截止超时都归入 TTFT 码。
- 异常从 `stream_generate_json` 抛出，经测试的 `asyncio.run(collect())` 直达断言处，无其他包装层。

两处可能的失败点（消息相同）：循环头 `activity_left <= 0`（等待前检查）或 `wait_for` 的 `asyncio.TimeoutError`（等待期间守卫）。上轮对失败的描述（"在 `asyncio.sleep(0.01)` 等待 provider activity 时被截止期取消"）与本轮复现取得的完整 traceback 一致：异常链经 `CancelledError`（wait_for 超时取消 `anext`）→ `StructuredGenerationError`，即失败发生在等待期间守卫。

## 5. 全量运行与单文件运行的实际差异

行为差异**不需要**"前序测试遗留任务/线程/事件循环状态互相干扰"这类污染假设来解释：

- 该测试单次执行在干净进程中即有 5-20% 的固有失败概率（实验 2/3/6）；上轮"两次全量失败 + 一次单文件通过（8 项）"本身就是对这个概率的多次独立采样，落在同一模型内。
- 全量上下文的作用是**放大器而非必要条件**：1500 项测试运行后的进程内状态（线程池、堆体积、GC 频度）与实验 7 的模拟负载同构，把唤醒延迟 >20ms 的概率从 ~10% 推到 ~80%，使全量运行中的失败接近必然。这解释了为何上轮两次全量连续失败、而单文件复跑通过——同一枚硬币在不同负载下的两种采样。
- 未发现、也无需假设跨测试的 fixture、provider 注册表或事件循环状态串扰；该测试每次 `asyncio.run` 新建事件循环，适配器与注册表均为局部对象。

## 6. 已证实的根因

**测试机制缺陷（已证实）：fixture 用真实 wall-clock `asyncio.sleep(0.01)` 表达"provider 活动 10ms 后到达"这一题设。Windows 默认计时粒度（系统时钟中断 ~15.625ms，Proactor 事件循环定时唤醒受其支配）下，10ms 定时器的实际唤醒延迟近似均匀分布于 [10, ~25.6]ms：其中越过 20ms TTFT 窗口的份额即失败率（实测空载 5-20%，负载 ~80%）。失败时 provider 首个 activity 事件在 TTFT 窗口内从未到达（`events_reached=0`），生产运行时按 fail-closed 语义报 `MODEL_TTFT_TIMEOUT`——这是设计要求的正确行为，不是缺陷。idle 窗口（30ms）与 total 窗口（200ms）在该测试时间线下从未被触发（40 次复刻中通过侧最大事件间隔 25.9ms，总时长 ~62ms）。**

三个类别的划分：架构缺陷——无；测试机制缺陷——上述一项，已修复；环境问题——Windows 默认计时粒度是缺陷暴露的物理条件与放大器，不是独立根因（若把它当根因，等于承认该测试在任何默认 Windows 环境下都不可判定）。

## 7. 最小修复与对抗证据

修复只改 `tests/adapters/test_model_runtime_streaming.py` 中该测试的 fixture（+31/-2 行），生产代码零改动：

- 构造 runtime 时注入 `clock=fake_clock`（字典承载的虚拟时钟）与 `wait_for=clocked_wait_for`（以注入时钟执行 `wait_for` 超时契约：awaitable 完成后若虚拟时间越过 deadline 则抛 `asyncio.TimeoutError`）——两个都是 `RegisteredModelRuntime` 公开确定性钩子，先例即 `test_model_runtime.py:329`。
- fixture 迭代器将 `await asyncio.sleep(0.01)` 改为 `await asyncio.sleep(0)`（保留事件循环交错性质）+ `clock_state["now"] += 0.01`（与原题设完全一致的 10ms 虚拟节奏；delta/completed 紧随第 4 个 activity，同原测试）。
- **deadline 数值（0.02/0.03/0.2）、事件序列、全部断言、测试名一字未动。**

修复过程中的一个中间缺陷被对抗验证抓住并修正：首版替身 `immediate_wait_for` 直接 await 不判超时，对抗实验（虚拟步长改为 0.03 > TTFT 0.02）显示测试仍通过——因为循环头检查发生在等待之前，`anext` 内部的时钟推进永远不会被复查，TTFT 判定被实质削弱。这正是任务书禁止的"削弱门禁"，因此改为 `clocked_wait_for` 虚拟化 wait_for 的超时契约后，对抗实验如预期失败。该反复本身是可证伪性方法生效的证据。

修复后验证（全部在最终源码上）：

| 验证 | 结果 |
| --- | --- |
| 单用例独跑 ×50 | **50/50 通过** |
| 可证伪矩阵（真实 runtime + 注入时钟，驱动越界虚拟时间线） | baseline 4×10ms 通过（final_clock=0.04）；首个事件 30ms > TTFT → `MODEL_TTFT_TIMEOUT`；事件间隔 40ms > idle → 抛活动截止异常；累计 25×10ms > total → 抛活动截止异常（total 经 `min(total_left, activity_left)` 传导进 wait_for 守卫；code 归类为 TTFT 是 activity 流中 `first` 恒 False 的既有生产语义）。**证明修复后的测试仍真实执行生产 deadline 状态机，不是永真** |

### 8.1 插曲：第一次全量的并发互斥用例失败与负载归因

第一次全量（20:09，较正常基线 8:52–9:49 慢一倍以上）唯一失败是 `tests/runtime/test_cancellation_and_execution_exclusivity.py::test_concurrent_checkpoint_resume_allows_exactly_one_executor`，失败点 `tests/runtime/test_cancellation_and_execution_exclusivity.py:250` 的 `asyncio.wait_for(gated.arrived.wait(), timeout=5)` 超时——审批恢复链 5 秒内未到达收尾闸门。诊断过程与证据：

1. **无固有缺陷**：上轮独立审计两次全量（正常速度）该用例均通过；失败后单文件复跑 3 passed。
2. **背景负载确认**：失败时段机器上存在并行会话的 python 进程（累计 389+ CPU 分钟、2.8–6GB 且持续增长的堆、约 1.2 核持续占用）。按纪律未触碰该进程。
3. **负载高峰期复现**：进程内 `pytest.main` 连续 4/4 失败（16–18s，另两个用例也在超时边缘）；不经 pytest 的独立复刻脚本连续 5/5 失败，且 phase1（首步执行至 WAITING_REVIEW）耗时 2.3s（正常亚秒级），`calls=['bootstrap','deliver']` 证明恢复链已实际到达闸门、`arrived` 已置位，是整体执行被负载拖慢逾一个数量级后击穿 5s wall-clock 防线，而非互斥语义失效。
4. **排除入口差异**：负载缓解后 A/B 交替实验（命令行 `python -m pytest` 与进程内 `pytest.main` 各 2 轮）全部 3 passed（4.2–4.4s），推翻"pytest 入口差异"假设，锁定真实变量为时间上的背景负载波动。
5. **与本轮修复无因果路径**：本轮唯一改动是 `tests/adapters/` 下一个测试函数的局部 fixture（局部对象、无模块级状态），被测生产代码字节未动。
6. **定性**：环境负载问题（并行会话进程负载高峰击穿既有 wall-clock 防线），非测试机制缺陷（空载与轻载下稳定通过），非生产缺陷（负载缓解后全量通过），非 S03-01 物化关联。按项目既有纪律（全量终验须空载顺序执行），在负载缓解窗口重跑全量取得 1540/1540 通过。该用例本身不做任何修改。
