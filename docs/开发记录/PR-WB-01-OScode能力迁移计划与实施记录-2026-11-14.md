# Workbench 复用 OScode 已验证能力：迁移计划与实施记录

日期：2026-11-14。授权：先形成计划书，再按顺序实施。OScode 保持当前业务行为；Workbench 延续现有 Mission / Run、审批、检查点与模型注册表。

## 目标与现状

优先解决用户能感受到的状态更新滞后、生成时反复重绘和等待原因不清晰。复用已有模块，按 Workbench 的任务身份接入，不另建工具执行器或任务管理系统。

源码核对发现：主工作区已通过 Mission 投影版本及 SSE 更新；Copilot 仍每 3 秒读取状态，后台/终态采用其他轮询间隔。Copilot 对话的活动正文每次更新都会重新解析整段 Markdown。Run 的实时输出已有部分缓存与帧合并，但 Copilot 对话未使用 OScode 的流式合并能力，且公开进展事件没有完整进入对话界面。

## 第 1 批实施顺序

1. 为 Copilot 对话、任务权限及规划补充输入的持久写入接通现有 Mission 版本失效机制；将主工作区已经接收的版本传给 Copilot，移除定时状态轮询，合并连续版本更新，处理忙碌期间的新版本。
2. 提取并复用流式批处理能力，控制事件在结构边界立即 flush；避免后台页面依赖 animation frame 才能结束。缓存已完成消息的 Markdown，稳定输出块。
3. 将已有规划模型启动、活动、重试及完成事件映射为明确的 Copilot 进展，记录真实请求/尝试与首段正文耗时。浏览器观察和服务端计时分别标注；无对应计时或 usage 时保持未知。
4. 执行相关 Python 存储/规划/流式回归、前端状态/流式/组件测试和类型检查；共享模块若改动则回归 OScode 使用方。

## 验证方式与约束

- 使用隔离数据库、离线供应商、模拟 SSE 及独立测试页面，不重放真实用户任务。
- 事件更新必须处理身份不匹配、重复版本、请求中再收到版本、访问拒绝、切换 Run、KeepAlive、终态及 SSE 重连。
- 审批按钮和操作仍由服务端能力、选中 Run、预览版本和用户确认共同约束，展示优化不能授予执行权限。
- 本次不为验证主动请求付费模型；不在用户有执行或草稿时刷新页面、重启服务。
- 验收数据区分已有 OScode 证据与本次 Workbench 结果，不承诺尚未测量的端到端提速。

## 实施记录

### 第 1 批完成

- Runtime 原数据库的 Mission 投影版本补上 `task_copilot_permissions`、`run_copilot_exchanges`、`run_planning_inputs` 三类写入。变更在源事务中递增版本，重复无变化权限写入不递增；不会修改执行 Run 的业务 revision。
- MissionWorkspace 将已取得的投影版本传给 Copilot，不增加第二条 Mission SSE。Copilot 移除定时轮询，150 ms 合并连续版本；读取过程中再收到新版本会补读，生成期间延后到当前操作安全结束。临时读取失败最多重试两次；鉴权拒绝后停止自动读取。切换 Run、KeepAlive、隐藏/恢复与卸载均有回归覆盖。
- Copilot 对话和 Run / Planner 文本复用 OScode 的 `createStreamBatcher`，沿用 16 ms / 4096 字符 / 128 事件边界；状态、审批、失败、重试和终态前立即刷新。移除 Run 文本对 animation frame 的完成依赖，最后一个订阅释放时清理批处理器。
- Copilot 活动正文复用 `ChatTranscriptBlock`；已完成消息按身份与原文缓存 Markdown，状态刷新和新回复不重新解析旧消息。
- 现有 Planner 事件映射成准备、等待模型、接收、重试、校验阶段。每次生成尝试具有独立身份，实际模型启动事件携带请求身份；同步和流式入口共用一次公开进度投影。只提取供用户阅读的 content，结构化 action 和内部推理缓冲不作为正文展示。
- `latencyMs`、`responseTimings.firstContentMs`、`responseTimings.contextPreparationMs` 和已观察到的 `providerRequest` 与已验证回复一起保存。contextPreparationMs 包含模型启动前的准备与串行等待；firstContentMs 是本次服务端操作首次形成可展示正文的时间；latencyMs 截止回复验证完成，不包含数据库提交和浏览器绘制。没有连接/TLS/浏览器数据时不补造对应指标。历史回复不回填虚构耗时。

### 第 2 批：公开展示快照与重连

- 原 SQLiteWorkflowStore 增加 `run_runtime_display` 表。每个 Run 一份有界展示投影，不建立逐 Token 日志、执行账本或恢复调度器。最多保留 32 个调用分组、256 个压缩展示事件和 262,144 个公开文字字符；每个当前原始结构缓冲最多 65,536 字符，仅存于进程内。旧展示允许淘汰，正式证据仍由原输出、Trace 和检查点负责。
- Broker 在订阅注册与快照基线之间使用同一发布锁；首次连接、断线重连和服务重建均先发 `runtime.display.snapshot`，再接增量。Run 序号从持久快照恢复；前端按新基线重建展示，拒绝错 Run、已退役尝试及终态后的晚到片段。已完成任务也会读取一次基线，服务端随后关闭连接，不开启轮询或计时器。
- 模型结构文本只在 Broker 内提取公开叙述。实时及持久展示使用累计 `publicText`；不持久化原始结构缓冲、模型私有推理、工具参数、action 或 completion.data。现有结构化结果仍在原内部交接链使用。
- 公开文字按 16 ms / 4096 字符边界合并，结构、完成、失败、快照读取前刷新尾部。正常流式阶段每 250 ms 做展示检查点，结构边界即时提交；正常关闭会补刷。突然终止或数据库不可用时，最近未提交的尾部可能丢失，不能等同于永久逐 Token 日志，也不能补造部署前未采集的历史片段。
- 慢订阅者显式断开并用快照恢复，不在丢字后继续伪装完整流。发布顺序与跨线程的订阅所属事件循环一致；数据库检查点写入不持有跨 Run 广播锁，最多等待 250 ms，不把显示写入失败升级为执行失败。序号 CAS 拒绝旧刷新覆盖，删除 Run 后不能被晚到刷新复活。
- 展示检查点不递增 Run 业务 revision 或 Mission 投影版本，也不唤醒 Mission 读取者，避免每段文字重新查询整个工作区。

### 第 3 批：按 Workbench 边界使用工作预算与统一用量

- 同步、流式、节点、规划/Copilot 及工具回合共用 `resolve_request_budget` 和已有的最终 wire 请求计量。没有冻结预算时，只从精确 provider/model 能力中的窗口和实际输出额度推导；能力未知时保持未配置。冻结预算不能放大真实窗口，也不能少预留实际输出额度；不以本次工作预算降低输出或思考强度。
- 软工作预算独立于硬窗口，支持成对冻结的 trigger/target。可推导路由沿用独立上下文核心的相对 85% / 65% 输入额度策略，没有移植某个 GLM 的固定阈值。指标明确是 `json-characters-div-3.2.v1` 估算，不伪称精确分词或供应商用量。
- Workbench 的当前规划输入、审批条件、失败事实、材料和证据引用不能视为可任意摘要的旧聊天。普通请求超过软预算时保留保护输入并记录状态；超过硬预算在发出请求前拒绝。只有原有材料 workset 边界可以让软预算触发现有确定性分片，沿用绝对材料范围、map/reduce、结果持久化与“工具已经执行则禁止重新分片重复副作用”的保护。
- 未引入额外摘要模型调用、Node 子进程或 OScode 会话数据库；现有无损上下文去重、memory/prefetch 和补读合同继续工作。target 是分片目标与诊断，不承诺固定规则开销很大时一定达到目标。无法安全缩小的请求保持明确失败/重新规划边界。
- 规划和 Copilot 共用原 Run Trace 的 `MODEL_CALLED` 入口，正常与已观测失败尝试都记录安全元数据。没有第二套 Copilot 用量表或聊天分页累计统计。失败回复不保存为成功对话，其已观测消耗仍保留；成功操作回放不会重复调用模型或增加调用记录。
- 对话的最近四轮只投递正文、来源、方案和收据，不把时延、模型统计和重复配置送回模型。界面把“最近一次上下文输入”和“累计已观测 Token”分开，显示实测/估算/未知及未返回用量的调用数；不会把累计消耗当作当前上下文，也不把缺失 usage 当成实测零。

### 第 4 批：测量后保留 urllib 实现

新增可重复执行的离线脚本 `ops/scripts/measure_workbench_transport.py`，不读取密钥、不发 DNS/网络或模型请求，只输出数值及 CA/代理是否配置的布尔值。证据：`.tmp-tests/workbench-transport-20261114.json`。

7 次采样中，标准 HTTPSConnection 构造首次 **24.655 ms**、后续中位 **21.691 ms**；验证 SSLContext 首次 **23.566 ms**、后续中位 **23.143 ms**；urllib opener 首次 **23.084 ms**、后续中位 **22.751 ms**；合成 19k 字符输入的请求准备首次 **0.240 ms**、后续中位 **0.055 ms**。这不是 TLS 握手、供应商等待或完整首字延迟，也不测量线上代理/CA 性能。

本轮没有足够收益证据支撑新增证书缓存或替换 HTTP 库，因此保留 urllib、环境代理、证书/主机验证、密钥轮换与取消后的响应关闭机制；后续若真实请求测出 DNS、代理、握手或连接复用问题，再针对该段验证，不将 OScode/httpx 的秒级结果直接套用。
