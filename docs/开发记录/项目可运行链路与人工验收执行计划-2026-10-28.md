## 2. 从第一性原理推导最小闭环

用户购买的能力是：把目标和材料变成可信、可取得的结果。成立至少需要六个条件：

1. **输入确定**：目标、约束、材料、审核模式与所属用户持久化，历史 Run 的执行依据固定。
2. **权限明确**：登录身份可信；正式图、许可与启动命令属于同一 Mission / Run；未显式启动不得执行。
3. **执行真实**：规划与业务节点确实调用选定 Provider，节点按既有 Runtime 推进。
4. **过程可控**：能看见执行进度、等待审核、失败和取消；观察断线不能重复提交任务。
5. **结果可信**：最终交付来自正式引用；需要审核时批准前不得公开；下载字节和 Manifest 一致。
6. **状态持久**：刷新、重登录、完成后重启服务可读取原结果，不重复执行。

因此优先级由闭环的必要依赖决定，不按代码规模或功能数量排列。扩充 Pack、分布式部署、任意控制图、更多模型和正式发布冻结，不是首次本地人工验收的必要条件。

实际请求与执行链：

```text
浏览器正常登录
  → Spring Security：JWT + sid + 持久会话
  → Java Gateway：可信用户转发 + 内部服务认证
  → Python Mission / Run：固定语义依据与执行范围
  → PlanningCommit：正式规划接受
  → Materialization → Activation（暂停）→ Handoff → Permit
  → 用户显式 Dispatch → 应用 Coordinator
  → 唯一 ExecutionRuntime → Native Scheduler / NodeRunner → Provider
  → Checkpoint / Review / 审计 / 内容存储
  → 正式 final 引用 → 浏览器阅读 / 下载

观察：Java SSE → 前端事件展示；持久 Run 查询负责状态校准。
```

不增加第二个 Scheduler、第二套运行状态机或前端假暂停来连接这条链。

## 4. 真正影响本轮交付的缺口

### 4.1 标准部署没有接入正式链开关——优先解决

本次用实际 Windows 三文件 Compose + `.env.windows` 执行 `config --format json`，解析后确认以下四项都没有传入 ai-service：

```text
AGENTOS_MISSION_SEMANTIC_CONVERGENCE
AGENTOS_C2_EXECUTION_AUTHORITIES
AGENTOS_C2_EXECUTION_DISPATCH
AGENTOS_ALLOW_LEGACY_MISSION_INTENT
```

前三项在 Runtime 中默认 false。仅把值写进宿主 `.env` 不会让容器自动得到未在 Compose 中映射的环境变量。由此可确认：当前标准启动路径不会启用目标正式链；不能推导所有旧功能都不可运行。

验收环境目标为前三项 true、Legacy false，并验证实际生效值。保留开关依赖检查，不能靠关闭 Authority 或开启 Legacy 绕过。

### 4.2 显式升级已有实现，但未形成可复用的启动前步骤

`scripts/upgrade_agentos_c2_schema.py` 与 `upgrade_agentos_dispatch_schema.py` 已存在；Windows `up.ps1` 是 preflight→build→compose up，未调用它们。AI 镜像也未复制根 `scripts/`，开发挂载未映射该目录。因此容器里直接照抄宿主升级命令没有完整路径保证。

应提供同一数据卷上的明确维护入口：先只读检查；需要时显式安装 C2（workflow/checkpoint/identity），再安装 Dispatch version 1；随后只校验并启动 Runtime。不要在应用 lifespan 隐式升级，也不要用宿主错误路径创建另一套空库。

Java V11 与 Python 的显式升级是两条不同路径：前者遵守现有 Flyway，后者保持运维显式执行。两者都要留回执。

### 4.3 真实运行环境当前不在线

本次 Docker named pipe 不存在，未取得容器清单。当前 `.env.windows` 的实际 Web 入口是 `127.0.0.1:9050`，不是 README 示例 8080。历史 18089/19089 验收入口不代表当前在线；10-27 决定已记录两个临时验收栈拆除。

启动前先恢复 Docker Desktop 并清点现有卷和部署 ID。按已确认方案使用现有 `kinlin-win-p1-001` 配置、数据与 Secret，显式升级既有库；不做备份，不重建数据库，不操作 `kinlin-win-p1-002`。

### 4.4 最新认证改造缺少当前全栈浏览器验收

10-26 的完整业务闭环早于 10-27 的 sid/V11/SSE 改造。后者有测试证据，但不能自动拼成“最新源码已经由真实用户验收”。需要在同一个当前版本环境里贯穿验证。

登出是撤销会话、停止受保护事件交付；**不是取消任务**。任务取消使用正式取消操作。人工验收必须区分两者。

### 4.5 模型输出存在受支持范围

10-26 记录过真实 Provider 生成当前不支持的控制图，并被 `CONTROL_BARRIER_BLOCKED` 拒绝。它证明边界生效，也说明不能承诺任意自然语言任务都能执行。

首轮选择小型、无外部副作用、明确文档输出的任务；不强求固定节点数。若仍失败，保存实际规划、错误码与引用，定位为能力范围、Provider、绑定或产品提示问题；限制修复次数，不无限改提示词直到“看起来成功”。

### 4.6 测试入口有证据清理副作用

`apps/agent/tests/conftest.py:45-55` 在导入时遍历 `.tmp-tests` 并删除超过 24 小时的条目；这不只是清理本次测试创建的文件。为保护既有证据，本轮未运行这些 Python 测试。后续定向回归应在独立 checkout/worktree 的独立临时目录执行，或先修成仅清理本次拥有的资源，并明确核对全部数据库/Chroma 路径。

## 6. 人工验收脚本

建议主任务：为一次班级科技分享会生成 Markdown 策划书，明确目标、议程、分工、风险和检查清单；材料直接写入输入，关闭联网，不执行本机命令。先做文本任务以验证系统链路，完成后再决定是否追加附件或 Legal 场景，不将其混成首次通过的前置条件。

| 步骤 | 人工动作 | 判定标准 |
| --- | --- | --- |
| 1 | 正常账号登录；进入新建 Mission，输入任务并选择“人工审核” | 能理解审核语义；创建后有真实 Mission/Run；目标与约束正确 |
| 2 | 等待规划；检查正式规划、计算图与步骤说明 | 正式规划已接受，节点能力可用；不是前端示意图或预置结果 |
| 3 | 依次准备图、激活暂停、准备交接、申请许可 | 状态与实际操作一致；获得 Permit 后业务节点仍未执行 |
| 4 | 点击“执行任务”，等待第一步完成 | 产生正式 Dispatch；可见真实模型调用与节点进度；没有重复调用 |
| 5 | 每次进入 waiting_review 后阅读结果并填写审核意见、批准 | 未批准不能继续下游；最终审核前没有公开 final；需按真实步骤次数审核 |
| 6 | 批准最终步骤，打开并下载 final.md | Run completed；正式 final 唯一、来源属于本 Run；正文符合任务，字节长度/摘要与 Manifest 一致 |
| 7 | 刷新、关闭重开、退出并重新登录后打开原 Run | 同一 Run、Dispatch 和 final 引用；内容不丢失，无再次执行 |
| 8 | 完成态下重启现有开发环境的 AI 服务，再读原结果 | 状态与引用保持；不会重新调用节点 |
| 9 | 使用另一个普通账号尝试原 Run/Artifact/SSE | 无权读取，不能看到他人正文 |
| 10 | 保持一条受保护事件流，注销其会话；再以旧凭据请求 | logout 后旧 HTTP/新 SSE 被拒；已有流按现有时限停止准入和取消；业务任务是否运行由任务状态决定 |

另开一条短 Run 验证取消或审核驳回，避免把主成功 Run 改成失败。只刷新 UI 无法充分证明幂等；需要结合 Dispatch 数量、节点调用/commit 记录验证。

验收交付包：环境清单、源码版本和有效配置摘要（去 Secret）、用户步骤记录、关键截图、脱敏请求/错误码、Mission/Run/Graph/Permit/Dispatch/final 引用、模型名称与调用计量、下载长度与 SHA-256、重登录/重启复查记录、人工意见。不要归档 Token、API Key、密码或完整敏感提示词。
