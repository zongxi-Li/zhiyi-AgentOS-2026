# OScode 运行中上下文占用刷新

## 问题与根因

长用户轮次包含许多模型调用和后台命令输出轮询。原有 `usage` 只在整轮成功结束后发出；中间的 `model_context` 事件仅携带请求字节数，前端正确地没有把字节当 Token，却因此持续展示上轮用量。任务若中断，整轮末尾的 usage 不会发出，历史中的本轮单次用量也会缺失。

累计 Token 是全部已结算调用的总消耗，上下文占用是最近一次模型调用的输入加输出；两者不能混用，也不应把上下文百分比设计成只增不减。

## 修改

- `ObservableChatModel` 在供应商的每次响应返回真实 usage 时，立即沿现有进展队列发送 `model_context`，measurement 为 provider-usage，携带该次 prompt/completion 和 attempt/turn，不等待整轮结束。已有压缩 usage anchor 回调保持。
- 不发送伪造的累计 usage，不将运行时间、请求字节或 UTF-8 上界转成供应商 Token。无实际统计时继续保留最近一次值；该值不是逐字更新的直播计数。
- Store 按该次输入加输出更新窗口占用；后续 request-bytes 事件只更新请求体大小，不清空已测用量。压缩后较小的单次用量可以降低占用。
- 后端持久保存 last_input_tokens / last_output_tokens，确保重连或恢复历史时仍能显示运行中最后已测用量。恢复历史时支持尚未产生整轮累计 inputTokens 的回复。
- 最近工作输入卡同时接收实际 prompt 用量，和保守工作集预算保持区别。protocolSession 由真实运行上下文提供，不从 usage 存在与否推断。
- 提示文案明确为最近模型调用，工具执行期间保留最近统计。

## 验证与边界

真实 SDK + 离线供应商流回归：第一次工具调用 prompt/completion=100/10 时，第二次请求仍被门闩阻塞，客户端已经收到容量事件；释放后收到第二次 240/12，整轮正常结束。没有额外调用真实付费模型。

前端流测试在同一个未结束请求内依次收到 201000、250500、40100，验证增长、压缩后下降、请求字节不覆盖用量、未伪造累计 Token。后端测试覆盖未 done 时的用量持久保存。

最终 Python 模型流/协议相关 28 项通过；前端流 22 项、历史 11 项、ChatView 44 项通过，相邻压缩测试此前 9 项通过，前端类型检查通过；后端投影 6 项通过，构建通过。历史恢复新增用例验证任务在整轮累计用量产生前失败时，仍恢复最后单次模型占用 250500，而不是丢失统计或仅恢复输入 250000。

本轮只读检查发现用户长轮次已记录为 failed，工作上下文包含 COMPACTION_VALIDATION_FAILED、failed_passthrough、接近硬边界的保守输入估计。该压缩问题与统计刷新缺口是两件事；本修改没有声称修复压缩失败，也没有将保守字节数伪报为真实 Token。没有重跑失败任务或重放其命令。

本修改不热替换正在执行的 Python 生成器，不刷新用户运行中的桌面页面。现有任务中的旧统计不能通过修改源码补回供应商未转发的历史 usage。

## 历史回退导致更新服务后仍显示旧 20%

后续核对当前页面发现第二个独立缺陷：loadHistory 向前寻找 lastWithUsage，把较早成功轮次的 207793 Token 直接恢复为当前窗口占用，而末尾两个 failed 回复均没有实际用量。仅更新服务不能消除此回退。

现在历史恢复只把最新回复自己的用量作为当前值；失败/取消发生在本轮统计前时清除当前占用，snapshot 同样不保留旧值。UI 显式区分“当前上下文（未测量）”与“上次已测 … Token（历史值）”，缺乏当前实测时不绘制百分比或进度条，保留容量信息和全部历史记录。

前端相关 79 项测试及类型检查通过。已在原桌面对话实测 contextUsedTokens=null、34 条消息保留，当前卡片不再显示 20%，而将 208k 标为历史值；刷新前保留输入草稿。用户后续切换至另一对话后，截图再次验证相同未知/历史区分，没有为验证切回或重跑任何对话。截图位于 output/playwright/context-current-measurement.png。
