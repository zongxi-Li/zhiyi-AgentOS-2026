## 3. 独立发现、失败证据和修复

### P1-1：暂停态普通保存可改写规划和执行事实（已修复）

FIX 绑定了图、包及 graphActivation，但未绑定其他 Run 事实。新增合法 RuntimeRunRecord 的 13 类变更均未抛错：taskPlan 正文/版本、taskBindings、steps、attempt、输出、步骤 running、完成集合、活动集合、outputRefs、checkpointId、execution_scope、bindingRequirements。确认日志 `before.log` 后，修正无关测试 fixture 的 `confirm.log` 稳定得到 **13 failed / 7 passed，38.01s**。追加 Workflow/domain/engine 与伪造 Run completed 四例，也均能写回（`identity-before.log` 中四个真实 DID NOT RAISE）。

修复仅在 `graph_activation_store.py:110` 的同 Activation 普通写入分支，把完整 execution_state、steps、scope、Workflow/domain/engine、完成/活动集合及当前节点钉在已持久 Run；拒绝新增 completed/superseded 声明。仍允许合法诊断、操作员 input 更新、失败/取消等生命周期处理。首次 v1→v2 写入仍由服务完整 `_verify` 与原 Safe-Cut 保证，不伪造或清空前缀。原 40 项 FIX 验证目标完整保留。

保护锚点是同事务此前的正式 Run，不是防恶意管理员重写该行的签名。重读同一损坏正文不能凭空证明真实收据；S03-02B 必须重新验证独立执行事实。

### P1-2：完整物化来源身份没有与接受事实重比对（已修复）

`_verify` 重验 graph_revision 和 Blueprint hash，但未比较 materialization.commitmentFingerprint/proofFingerprint/sources。保持完整包、typed Record 和行 checksum 合法，仅改变以上三者，prepare 仍错误 ACTIVATION_PREPARED。修正 frozen model fixture 后 `identity-confirm.log` 为 **3 failed / 31 deselected，14.45s**。这组模拟持久化来源不一致，不宣称客户端能直接写 Journal 或攻破 SHA-256。

`runtime/graph_activation.py:88` 增加实际 graph Record 的 content_fingerprint、SafeCutProof 指纹和完整 Frozen Sources 的比较；prepare 与 commit 最终写事务均复用。没有重编译包、降低来源校验或改变冻结合同。

### P1-3：真实已执行前缀的 Planner wait 无法激活（已修复）

复用 S03-01 独立的完整初始通信合同 fixture，通过真实 Runtime 执行 A 并写收据，B/C pending，接受/物化新增 D。prepare 成功，但 commit 脱开 v1 checkpoint 后仍保存 WAITING_REVIEW，被原 `validate_run_state` 拒绝：`waiting_review ACG run has no checkpoint`，事务完整回滚。`prefix-before.log` 与带异常定位的 `prefix-confirm.log` 均为 **1 failed / 20 deselected**（前者 7.61s）。不是错误 fixture，也不是“控制图不支持”。

`_activated_run` 对被替代的 Planner review 使用原状态机 WAITING_REVIEW→RETRYING，phase=RECOVERY，显式等待已验证交接；保留旧 planningLoop/review 历史、旧 Checkpoint 引用和全部收据。RETRYING 本身不是许可，持久 Head 仍阻止任何调度。未放宽 WAITING_REVIEW/Checkpoint 合同。

### P1-4：普通取消导致 Identity 包身份冲突（已修复）

在有效 ACTIVATED_PAUSED 上先保存诊断，再走真实 cancel，Workflow 已落取消，但 flush outbox 报 `immutable Run metadata changed: compiledPackageId`；`expanded.log` **1 failed / 26 passed，96.25s**。根因是 v2 Run snapshot 的包元数据试图经普通生命周期对账覆盖 Identity 的不可变 v1 包身份。

`runtime/v2/reconciliation.py:278` 对持久激活链先做共享 Head 验证；只处理生命周期投影，剔除四个包身份字段，保持原 Identity 包与图，不做 v2 执行身份迁移。Identity 源 Run 缺失时拒绝，且检查发生在 on_run_prepared 之前，不能用恢复隐式新建 v2 Identity。独立测试断言取消成功、旧包身份不变、无 Agent 调用，以及缺失 Identity 不会进入准备入口。没有修改 Identity immutable 规则或提前实现 S03-02B。

### P1-5：Head 故障后旧快照可抹掉剩余激活证据（已修复）

保留激活前合法 v1 Run，激活为 v2 后模拟 Head 行丢失或 Head 表丢失，再通过正常 save_run 写旧快照。原无 Head 兼容分支只检查传入快照，故旧 worker 可以覆盖仍带 graphActivation 的正式 Run，连剩余持久激活标记一起抹除；两项均 DID NOT RAISE，`missinghead-before.log` **2 failed / 38 deselected，8.41s**。故障注入只破坏 Head，没有修改 Run；真正的危险写入走正常生产 Store。

`graph_activation_store.py:55` 在无 Head 分支检查此前持久 Run 的激活标记：此前曾有标记则拒绝丢失 Head 的降级保存。无标记的真实旧库仍兼容。没有新增历史状态、Schema 或管理员修复机制；同时销毁全部历史证据的管理员攻击仍不在本合同内。

### P1-6：真实启动恢复与批量 Identity 补建未识别暂停交接（已修复）

把 A/B/C/D 的新进程恢复从仅 `_recover_pending_planning_transitions` 推进到实际 `close_orphaned_runs`，通用恢复会重写 planningLoop.restartPending；新事实保护会正确拒绝此写，但导致启动恢复抛 ValueError。`startup-before.log` 中该项是真实失败；同组批量 Identity 初版调用了不存在的 reconcile 方法是 fixture 错误，不算生产问题。

另排空 outbox，模拟源 Identity 缺失，调用真实 `reconcile_workflow_store`。原批量扫描直接进入 on_run_prepared，试图以 paused v2 图补建身份；修正方法名和 list_outbox 参数后，`bulk-before.log` 得到 **1 failed / 40 deselected，4.87s**（禁止隐式准备的探针触发）。前一版仅测待处理事件、因 failed aggregate 跳过批量扫描而通过，不能作为该路径已安全的证据。

`runtime/runtime_recovery.py:215` 对存在激活标记的 Run，在独立 SQLite 快照中执行完整 Head 校验，确认后保留交接状态，不当作孤儿或旧 Planner 轮次重驱动；authority 未装配也不降级。`reconciliation.py:107` 在缺失 Identity 的批量补建前拒绝激活标记，不调用准备入口。没有复原空 Checkpoint、发许可或改动执行器；扩展后的真实新进程场景验证恢复后 Run/所有外部数据库保持。

### P1-7：跨进程旧投影覆盖可掩盖在途外部工作（已修复）

前六类修复后曾取得 41/395/1035/1650 全绿，但尾项核查仍发现：把 prepared 收据纳入冻结来源后，来源重验会认定其稳定，Safe-Cut 仅保护节点语义，不拒绝这笔未结算工作。单独临时 Runtime 探针实际获得 ACCEPTED→MATERIALIZED_INACTIVE→ACTIVATED_PAUSED；这不是完成证据。

随后真实 spawn 反例 `test_stale_projection_cannot_activate_over_inflight_external_agent`：A 进入 Agent，已有 running/绑定与 prepared 收据，暂停在外部写入前；B 用普通 SQLiteWorkflowStore 保存此前的合法 v1 快照（无 Head 时可覆盖活动投影），再接受独立 D、物化并激活。所有冻结来源都含同一 prepared 收据。B 实际提交 v2 后释放 A，A **真实写出带 PID 的外部文件并调用 Agent**，最后 Run 写回才被 Head 拒绝。`inflight-before.log` **1 failed / 41 deselected，4.52s**，明确证实“写回拒绝”不能阻止跨版本副作用。没有原始 SQL 伪造 Run/receipt 或减少任何验证。

最小修复分为两道：

- `support/run_execution_fence.py:34` 为同一规范化 Workflow DB 路径＋Run ID 提供非阻塞 OS 文件互斥：Windows 为 msvcrt 一字节锁，POSIX 为 flock。`_claim_acg_execution` 在读取 Head **前**获得互斥，通过 ExitStack 转移到本次执行生命周期，finally 释放；Activation.prepare/commit 在来源校验和写事务期间获得同一互斥。文件不可用时 fail-closed，忙时结构化 CONTROL_BARRIER_BLOCKED。真实生产执行漏斗都经过它，不能仅靠文档声明单进程。
- `_verify` 捕获收据后复用原来源重验，再拒绝任何非 committed 收据。即使旧进程死亡使 OS 自动释放互斥，prepared/未知工作也不能被误判为静止；不清除收据、不伪造完成。捕获位于原重验之前，原有“物化后新增收据应报 STALE_STRATEGY”测试语义不变。

它只补齐既有执行槽与激活临界区的互斥，不新增 Permit、Attempt 合同、数据库事实、租约续期/过期权威或 Scheduler。单字节辅助文件位于 Workflow DB 目录，不含规划正文；运行中禁止删除/替换它们，否则会破坏互斥身份。它不是跨机器租约，也不能撤销已经派发的远程副作用。完整 S03-02B 执行许可与 Attempt Fence 仍未实现。

修复后在途反例拒绝激活，A 只在原 v1 下完成；新增无活 worker 但存在 prepared 收据的反例也拒绝。与原 69 项激活/FIX 合跑 **112 passed，121.85s**。本轮自己的“认领后尚未落盘”诊断用例加强为要求 B 拒绝激活（不再只验证 A 事后被拒绝）；原有两个测试文件和断言均未修改。最终全部四组重新执行，旧 1650 全绿仅作为中间证据。

`_claim_acg_execution`:1113 在 RunLock 内先取得 OS 互斥，再用单 SQLite 读快照验证 Head；有 Head 一律拒绝，没有可选 authority 也拒绝；MemoryWorkflowStore 仅允许无 authority/激活投影的旧路径。错误 Store 的 AttributeError、缺失 schema 的投影冲突、悬空 Head 等均不进入 Agent；错误分类尚可改善，但没有降级许可。`_release_execution_slot`:1838 同时关闭执行生命周期中的互斥句柄。

**真实进程实验**使用 multiprocessing spawn、新 Runtime、独立 SQLite 连接和 Event 同步，PID 均与父进程不同：

1. 子进程 A 通过真实执行认领后停住，B 即使看不到进程内槽，也因 OS 互斥拒绝激活；释放 A 后仅原 v1 Agent 正常执行，无新 Head。
2. A 的 nodes_scheduled/running 已持久化后停住，同样拒绝激活；释放 A 后 Agent A 真实调用并写带 PID 的外部文件，原图正常完成。
3. 两个独立子进程同时 commit：一个 ACTIVATED_PAUSED，另一个重放或忙时拒绝；原 Key 最终对账为同一 activationId，只有一个正式 Head。
4. A 在途且 B 普通旧快照覆盖其运行投影时，P1-7 修复前真实跨版本副作用已复现；最终 prepare 被 OS 互斥拒绝，无 Head，A 在 v1 下正常完成。
5. 原测试的激活先成功、旧快照随后执行路径仍拒绝，Agent 不调用。进程死亡后的句柄释放由三个实际 os._exit 切口检验；无活 worker 的 prepared 收据仍单独拒绝，不把锁空闲当作副作用已完成。

单靠 nodes_scheduled 落盘和事后拒绝写回的论证已被 P1-7 证伪。最终以真实 OS 互斥阻止执行体与激活临界区重叠，并以未结算收据防御进程死亡后的外部工作不确定性；两者均由实际入口落实。已验证同机、同 Workflow SQLite、当前正式 Runtime 漏斗下的跨进程交接防线；不宣称任意外部 worker、混合旧二进制、不遵守互斥的代码、跨机器租约或数据库备份分叉已经安全。没有用文档中的单进程假设替代实现。

## 5. Checkpoint、故障及恢复

真实 A/B/C/D 测试保证：A 的 WorkflowStep、完成集合、输出与收据原样；B/C/D pending；同一个 Run ID、包 runId 对应源 Run；v1 Checkpoint 原始数据库 dump 不变，v2 checkpointId=None、supersededCheckpointId 精确指旧头。除 Workflow ledger 外的全部 fixture SQLite dump 在激活前后和新进程恢复后相等（含 ValueStore、Checkpoint、Identity、Memory、审计、内容与来源数据库）；新增 D 无执行许可和调用。

新进程重建 authority 后从持久表读取，依次运行 pending transition 恢复和实际 close_orphaned_runs，恢复不调用 Planner、Binder、SemanticRevision.prepare；执行入口拒绝 no execution permit，Run 图和执行历史保持。旧 v1 checkpoint 原样保留，不能作为 v2 正式恢复点。原测试另验证实际 resume/审核和旧快照写入拒绝。

故障覆盖：原准备幂等；新增真实子进程在准备 INSERT 前、INSERT 后但 COMMIT 前直接 os._exit，重新连接均无 preparation/Head、Run 仍 v1；准备 COMMIT 后退出可原 Key 找回唯一 PREPARED。四个独立提交断点在 Journal UPDATE 后、Head INSERT 后、Run UPSERT 后、COMMIT 前注入异常，全部恢复为原 durable dump；解除故障后原 Key 可提交。原测试的真实 conn.commit 后 ACK 丢失，通过新 Store 原 Key 对账，不重新执行或生成第二个 Head。

最终只有 v1 未激活（可以保留 PREPARED）或 Head/Journal/Run 一致的 v2 paused；没有测试支持第三种可执行半提交态。未做机器断电、磁盘损坏或 OS 强杀所有数据库组合实验，os._exit 不等于物理断电保证。

外部副作用探针是测试 Agent 经正式调用链执行的实际文件 IO，不是线上 LLM/远程业务 Provider 验收；没有调用生产外部系统。这里证明进程时序、持久化与调用栅栏，不外推为生产 E2E 通过。

## 6. 不变量和保留限制

| 项 | 结论与边界 |
| --- | --- |
| 唯一版本权威与同库原子性 | CONFIRMED：当前 Head + Journal + Run 同一个 Workflow SQLite 写事务、唯一约束和最终 COMMIT；进程锁不是跨进程 CAS |
| 完整包与来源绑定 | 入场部分 VIOLATED；修复后 CONFIRMED：物化记录完整接受身份重验，暂停事实写保护；不声称摘要是签名 |
| 无许可不执行 | 入场/中间跨进程路径 VIOLATED；修复后 CONFIRMED（现有正式无控制 DAG 路径）：公开执行漏斗、OS 互斥、未结算收据拒绝及持久 Head 防线；普通审核与恢复无许可权威 |
| 已执行前缀与恢复 | 入场 Planner wait 激活 VIOLATED；修复后真实 A/B/C/D 与独立进程验证；旧 Checkpoint 不伪装为 v2 |
| 生命周期/Identity | 入场取消报错；修复后只更新旧 Identity 生命周期，不隐式迁移新包；缺 Identity 拒绝 |
| 跨库联合原子与分布式执行许可 | NOT PROVIDED：Workflow 与 values/Checkpoint/Identity/目录/权限非联合事务；最后来源检查之后仍有窗口。已提供同机 OS 互斥，未提供跨机器持久租约、授权许可或 Attempt Fence |

保留的 P2：互斥忙时需原 Key 重试对账；错误 Store 等异常分类；完整包/Run 多次解析与哈希（普通保存线性成本）；BEGIN IMMEDIATE 内重验会持有全库写锁，同 Mission 外也受影响，5 秒 SQLite timeout 可能安全拒绝；没有大包/多 Mission 性能基准与硬截止期。同步校验没有可抢占 deadline。

GraphProvider 有节点/边/收据数量等政策上限，但部分列表先完整读取再计数，不能把它当作 SQL 读取量或内存分配的硬上限；尚无全部跨库收据正文的聚合字节预算实验。不以测试小图的耗时宣称最坏延时有界。互斥不持有 Workflow SQLite 写事务执行 Agent；只有最终激活重验/写入持全库写锁。

OS 互斥必须使用可写、同一规范化的 Workflow DB 目录；无可用锁时拒绝，不能回退为内存锁。每个 Run 保留一个小辅助文件，未实现在线清理，禁止在 worker 存活期间 unlink/替换；它不保存规划或执行事实。本轮实际验证 Windows NTFS/MSVCRT，POSIX 分支、多主机/网络文件系统和滚动混合版本未实测。现有 default-off authority 未接入生产装配，不把该限制写成“所有部署模式已支持”。后续部署必须确保所有生产执行入口使用当前协议，不能保留忽略互斥的旧 worker。

**连续版本的实际限制**：虽然 `_head_state` 有 activeVersion==sourceVersion 的分支，但 `_competition` 在 prepare 时对任意现有 Head 直接 STALE_GRAPH，因此不能据此宣称任意长度激活序列已经可用。原实施记录的该项外推不成立。本轮仅验收首次 v1→v2、无控制 DAG；控制图和 v2→v3 的正式准备/执行交接都留给后续显式合同，不为了扩大范围提前开放。

跨库最后窗口仍需 S03-02B 重新验证，不得用本轮 ACCEPT、历史 ACTIVATED_PAUSED 或原 Key 历史回执授权执行。默认装配未开启新 authority；没有新增“支持多实例交接”的运行模式声明或文档替代性部署约束。

历史同名 activation-dag-v1 记录不能推定经过本轮 OS 互斥或未结算收据检查；不回写或美化旧记录。S03-02B 必须从当前事实重新建立授权证据，不能靠策略字符串或重放回执继承执行许可。

## 8. S03-02B 最小可信交接合同

1. 以 durable activationId/materializationId/sourceCommitId、Head 的 Mission/Run/Graph/activeGraphVersion、完整 Package/checksum、proof/commitmentFingerprint 和 supersededCheckpointId 为输入，逐项比对完整正文；历史回执只证明过去提交，不授权当前状态。
2. 显式 Permit Authority 定义版本化许可记录、授权状态迁移和撤销。当前精确 `activation_projection` 与有 Head 一律拒绝是有效安全边界；后续必须新增可验证状态转换，不能删除防线或只把 executionPermit 字典改成非空。
3. 重验最新执行前缀、真实收据、审核与控制历史、全部祖先与 Compiler 依赖、当前权限/Basis/scope/Identity/来源、操作员输入和取消。迁移 v2 Checkpoint 必须保留真实 A 输出及收据身份，原子或可恢复地绑定当前 Head，不能简单改旧 checkpoint.graphVersion。
4. 显式处理 Identity 的 v1 不可变包/图身份与 v2 正式执行身份交接；本轮仅允许生命周期对账，不能把它当作完成了执行身份迁移。处理 planningLoop v1 Observation 的换代、恢复和过期消息。
5. READY Attempt、资源绑定、收据和许可必须绑定 Run/GraphVersion/Head/attempt generation；旧 attempt、迟到结果、旧 permit 均 fail-closed。在实际外部调用前验证，不以返回时 Run 保存失败代替副作用保护。
6. 在宣称多实例交接前建立并验证持久执行占用/租约与 Attempt Fence，明确崩溃释放、续租、撤销和跨数据库最后窗口的处理。继续复用单一 Scheduler/ResourceBinder，不新增调度或资源权威。
