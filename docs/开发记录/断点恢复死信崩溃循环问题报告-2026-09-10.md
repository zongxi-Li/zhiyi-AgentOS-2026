# 断点恢复（断点继续运行）产毒死信 → ai-service 启动崩溃循环 — 问题报告

- **报告日期**：2026-09-10（运维诊断会话出具；断点恢复功能代码归 runtime v2 开发会话所有，本会话未改动任何相关代码）
- **涉事对象**：run_b1bf757c84b2 / mission_a0efa9c4e492（企业级安全审计任务，38 节点）
- **触发操作**：用户在界面上正常使用「断点继续运行」功能（两轮：9-10 12:54 与 16:26）
- **严重级**：最高——单条死信可让 ai-service 每次启动即崩，全应用 Chat/Agent 接口 503，需手工清库才能恢复

---

## 一、结论

断点恢复功能本身可用，但其发射的 lifecycle 事件**编号方案与身份投影的校验合同不一致**：运行时按 **step（ACG 节点）自己的计数器**编 attempt 号（`workflow_runtime.py:1556`），而投影侧 `ensure_attempt` 按 **(run_id, task_id) 维度**要求编号从 1 连续（`repositories.py:1374-1384`）。恢复一个已有投影历史的 step 时，两套计数必然错位，事件被一致性校验拒绝变成**死信**；死信滞留 outbox 后，ai-service **每次启动的 lifespan flush 撞到死信即 raise**（`workflow_runtime.py:1818-1819`），进入无限崩溃循环，外在表现就是全应用 Chat 报 `HTTP 503`。

当前状态机只有 pending/applied/failed 三态、消费轮只跳过 applied（`reconciliation.py:186`），**没有任何死信跳过或告警机制**，因此死信一旦产生就无法自愈。

## 三、根因分析（代码锚点）

**发射侧**（runtime，step 级计数）`apps/agentOS/src/runtime/workflow_runtime.py`：

```python
# :1556  execute() 内，每次调度 step 时现算编号
attempt_number = max(step.attempt, step.retry_count) + 1
attempt_key = f"{step_id}:{attempt_number}:{loop_key}"
attempt_id = str(attempts.setdefault(attempt_key, new_attempt_id()))

# :1645-1663  三个事件一起发（attempt.ensured / resource.bound / step.started）
self._lifecycle_event(f"attempt.ensured:{attempt_id}", "attempt.ensured", run.run_id,
    {"runId": ..., "stepId": step_id, "attemptId": attempt_id,
     "attemptNumber": attempt_number})
```

问题点有两个：
1. `step.attempt / step.retry_count` 是 **run payload 里的 step 级计数器**，与投影侧 (run_id, task_id) 的既有编号**没有任何对账**。恢复轮里 step_19 的计数器已涨到 3（+1=4），而它的 task 在投影里只有 #1。
2. `attemptIds` 这个 executionState 字典以 `step_id:编号:loop` 为键做幂等（`setdefault`），但**断点恢复重建 executionState 后键会丢**，于是同一个 (step, #1) 第二次恢复时生成了全新 attemptId（step_20 的冲突即由此而来）。

**校验侧**（投影，task 级连续）`apps/agentOS/src/storage/v2/repositories.py:1345-1384` `ensure_attempt`：

```python
rows = SELECT * FROM attempts WHERE run_id=? AND task_id=? ORDER BY attempt_number
expected = attempt_number or (len(rows) + 1)
if 已有 expected 号的行:
    if attempt_id 不一致: raise "Attempt number already uses a different attemptId"  # :1381
    return 既有行  # 幂等重放
if expected != len(rows) + 1: raise "Attempt number is not contiguous"  # :1384
```

这个合同本身是自洽的（重放同事件会命中幂等分支），但它假设**发射方给的编号始终与投影记录连续衔接**——首轮执行（一切从 #1 开始）满足，恢复轮不满足。

**消费与启动侧**：

- 重放入口 `identity_projection.py:1432-1435` 把 payload 里的 attemptNumber 原样传给 ensure_attempt，冲突即 `IdentityConflictError` → 事件标 failed。
- 启动 flush `workflow_runtime.py:1810-1819`（coordinator.startup → `_flush_identity_outbox`）：`if report.failures: raise RuntimeError(...)`——**历史死信直接卡死进程启动**。
- `reconciliation.py:186` 只跳过 APPLIED 状态；failed 每轮必重试，无死信旁路、无告警。

**为什么 12:54 那轮能跑通、16:26 那轮崩**：12:54 恢复时目标 step 的投影历史可以以 #1 衔接（前次 attempt 未落投影或计数器未被复用），编号恰好连续；16:26 恢复时 step 计数器已涨到 3+（+1=4），投影却只认到 #1，错位暴露。**即：只要对"投影里已有 attempt 历史"的 step 发起断点恢复，就必然产毒。**

## 四、复现条件

1. 跑一个 mission，让某个节点失败使 run → failed（该 step 的 task 在投影 attempts 表留有记录）；
2. 对该 run 发起断点恢复，使恢复路径重新调度该 step；
3. 发射的 attempt.ensured 编号 ≠ 投影既有条数+1，或 #1 被新 attemptId 重放 → 死信；
4. **任意一次** ai-service 重启（up -d、崩溃、宿主机重启均可）→ 启动 flush raise → 崩溃循环 → 全应用 503。

## 五、修复建议（按优先级；具体方案归功能会话定夺）

**P1 — 服务可用性兜底（建议先行，改动最小）**
`_flush_identity_outbox` 遇 `report.failures` 不再 raise：ERROR 日志 + 计数/告警后放行启动，failed 事件留在 outbox 待修复后重放。理由：投影缺几行可由对账机制修复，而"一条死信毒死整个服务"的故障面完全不成比例——本次事故两次都是它把 Chat 打成 503。

**P2 — 统一编号合同（根治产毒）**
二选一：
- 发射侧不再自带编号：attempt.ensured 的 attemptNumber 交给投影侧 `ensure_attempt` 自动分配（`repositories.py:1374` 已支持 `attempt_number=None → len(rows)+1`），幂等键改用 attempt_id（需在 ensure_attempt 增加"同 attempt_id 直接返回既有行"分支）；
- 或恢复路径发射前先查投影既有编号再拼 next，弃用 `step.attempt/step.retry_count` 现算值。核心原则：**step 级计数器与 task 级连续编号必须二选一，不能两套并存**。

**P3 — 恢复路径幂等**
断点恢复重建 executionState 时保留 `attemptIds` 映射（或 ensure_attempt 以 attempt_id 为幂等键），避免同一 (step, #1) 在第二次恢复时换新 attemptId。

**P4 — 死信旁路与毒 run 隔离**
消费侧对连续 N 次失败的事件转入死信旁路（新增状态或旁路表）并告警，不再每轮无条件重试；对反复产毒的 run 给隔离标记，阻断其继续发射事件。
