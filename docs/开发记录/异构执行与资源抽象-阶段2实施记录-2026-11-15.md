## 1. 交付范围

第二阶段完成定义、注册实例及资源事实的区分，增加 AgentPool 事实与生命周期接口，并在现有本地执行链中核对精确注册代次。

| 对象 | 职责与事实归属 |
| --- | --- |
| AgentDefinition | 不可变的能力、权限、模型配置、执行模式和来源声明快照 |
| AgentRegistrationRef | Registry 启动 epoch、instanceId、逻辑 agentId、generation、定义摘要及作者版本 |

Step、TaskPlan、ACG、ExecutionBinding 与 ExecutionPermit 合同保持原有结构。已有 `contracts/task.py.AgentInstance` 继续作为任务内统计记录；新视图命名为 `RegisteredAgentInstance`。

## 2. 定义与注册身份

主要入口：

- [声明与注册引用](../../apps/agentOS/src/contracts/agents.py)。
- [Profile/调用上下文兼容扩展](../../apps/agentOS/service/agents/base.py)。
- [实现注册表](../../apps/agentOS/service/agents/registry.py)。

### 2.1 三种身份分别表达

- `agentId` 沿用逻辑身份及 scope。
- `definitionVersion` 是作者显式声明的版本。旧 Profile 默认 `None`，不会从插件版本、模型版本或时间戳推造。
- `generation` 区分同一实例槽位内发布的实现代次；同一版本可以有多个实例，也可以替换实现产生新 generation。

声明采用 frozen 模型，能力、Skill、Tool 使用 tuple。定义摘要由规范化 JSON 的 SHA256 计算。同一逻辑所有者与 Registry epoch 中，显式作者版本不能发布不同内容；即使原实例已删除，仍保留版本和所有者约束。启动装配阶段的来源 stamping 单独受首次注册和未绑定条件约束。

`executionMode` 区分 unspecified、stateless、stateful。旧 Agent 默认为 unspecified，不推断它无状态；这个字段目前是声明事实，不产生实例隔离或容量分配保证。

### 2.2 旧 API 与多实例兼容

- `register(agent) -> None`、`resolve()`、`resolve_by_id()` 保持返回原 BaseAgent 对象。
- `all()` 仍表示默认逻辑 Agent；`registrations()` 才是全部当前实例清单。
- 首个实例成为逻辑 Agent 的默认实例；增加其他实例不切换默认值。删除默认实例后不自动选择其他实例，需要显式登记激活默认槽位。
- 同对象、同声明重复注册幂等；替换对象或发布变化后的声明产生新代次。
- `expected_generation` 校验当前仍存在的注册记录，删除后的迟到替换不能复活它。
- 保留已用 generation 计数。Registry 重建后使用新 epoch，防止数值同为 generation=1 时复用旧身份。
- 同一实现对象不能登记成多个实例；同一逻辑 ID 的领域、名称和来源所有者不能通过另一个实例或删除后重登记被接管。
- 逻辑禁用不会被换对象、新实例、新版本或注销重建隐式清除；`set_enabled()` 是明确恢复入口。直接设置旧 Profile.enabled=False 的效果也被保留。

Pack 的来源 stamping 收敛到启动装配方法 `stamp_plugin()`，随后发布新的不可变快照。已经产生精确绑定后不能再走该装配入口。这仍是启动路径，未把现有 Pack loader 变成运行中热安装协议。

## 3. 资源事实与生命周期

主要入口：[AgentPool](../../apps/agentOS/service/agents/pool.py)、[ResourcePlane](../../apps/agentOS/src/components/resource/application/resource_plane.py)、[RuntimeStore](../../apps/agentOS/src/components/resource/infrastructure/runtime_store.py)。

### 3.1 复用现有资源存储

RuntimeProfile 增加 `AGENT_INSTANCE` 类型、`agentRegistration`、`hostRuntimeId` 和 `draining`，继续使用已有的内存/SQLite RuntimeStore 与 HealthStore，无新的 busy 或占用账本。

每个完整注册引用对应独立的 SHA256 资源 ID，因此不同 generation、不同 Registry epoch 的资源及健康记录互不覆盖。实例关联已登记的执行后端，继承创建时的 Node、placement、trust、owner 快照；视图同时回读当前 host、Node 和 host health，避免把旧快照当成当前宿主状态。

`synchronize()` 只创建缺失事实，不覆盖已管理的容量、enabled、draining 或健康。首次并发创建使用 Store 的原子唯一登记，失败方读取胜方状态，保留胜方在期间所做的管理变更。

`update()` 使用 expected_version 与整份 expected_profile CAS；内存实现处于同一个锁内，SQLite 实现处于同一个事务内。容量变化同时更新资源 Profile 与已有 Snapshot。通用 Runtime 启停、容量入口如果作用于实例，也经过实例版本更新路径。

旧 Runtime JSON 可以按默认值加载；默认新增字段不会改变旧远程 Runtime 的登记幂等指纹。请求签名仍覆盖原始 body，未放宽签名或凭据检查。

### 3.2 正交状态和代次保护

- 注册不自动证明存活，初始健康为 UNKNOWN；实例 heartbeat 与 host heartbeat 独立。
- heartbeat 不清除实例 disabled 或 draining，也不恢复逻辑 Agent 的禁用。
- capacity 是声明容量，不是剩余槽位。Pool 不提供 in_use、acquire、release 或执行队列。
- Pool 的迟到 heartbeat、update、unregister 会核对当前 ref。即使检查之后发生换代，旧写入也只会落在旧资源命名空间。
- scoped Pool 是只读视图；已知实例 ID 不能绕过逻辑 scope，嵌套 scope 只能收缩。
- unregister 保留资源与健康历史，不自动关闭 Python 对象或推断已经排空。

内存与 SQLite 使用同一组生命周期测试。SQLite 重开后保留旧 ref、容量与 draining，健康 TTL 使用持久化 UTC 时间；新 Registry epoch 的当前实例不会继承旧记录的 healthy。

### 3.3 先发布事实，再激活新实现

Pool 的注册入口在 Registry 发布临界区中调用受限的资源事实发布器，事实写入成功后才切换当前实现。这个回调只做本地资源元数据写入，不启动外部进程或进行模型调用。

写入前失败、提交后丢失确认都会保留原来的当前实现。已预留的 generation 不重复使用；可能留下的资源事实属于未激活引用，不进入 Pool 当前实例视图，后续重试使用更大的 generation。

直接使用旧 Registry.register() 的调用方仍可登记逻辑实现；准备和 READY 路径会在使用之前同步对应事实。动态 Provisioner 的安装、启动及失败补偿仍属于阶段 5。

## 4. 真实调用边界

修改 [ACG 执行服务](../../apps/agentOS/src/runtime/acg_execution.py)、[NodeRunner](../../apps/agentOS/src/components/executor/node_runner.py) 和 [调用适配器](../../apps/agentOS/src/adapters/agent_invocation.py)：

1. READY 确定本地 Agent 后捕获精确注册 ref，并确认其资源事实已投影。
2. NodeRunner 将 ref 放进当前调用的 AgentRunContext。
3. Adapter 在真实调用前核对 ref、scope、启用状态、能力、定义快照及实现对象身份。
4. 发现过期 ref、对象被替换或声明未登记即变动时，拒绝调用，继续使用现有可信 not-invoked 证明。

真实回归在 `node.started` 时替换同 ID 实现：旧对象和替代对象均未执行该过期尝试，未生成其成功产物；随后新准备的 Run 可以使用替代对象正常完成。

此处保证选择不会静默漂移。检查之后的跨线程绝对截止、跨进程恢复、持久化 Attempt/Binding/Permit generation fencing 尚属下一阶段。已进入 `run()` 的调用不被取消。

运行中升级应使用新 BaseAgent 对象。同对象原地修改 Profile 后重登记仅能让后续精确解析辨别代次，无法隔离已经进入 run() 的代码继续读取同一对象配置。

## 5. 阶段边界

AgentPool 现在可以回答“有哪些声明和当前注册实例、各实例关联什么环境、资源与健康状态如何”。当前图的具体分配仍走原来的聚合执行后端。

为防止半接入，本阶段 Binder 对 AGENT_INSTANCE 无条件给出 `AGENT_INSTANCE_NOT_SCHEDULABLE`；普通候选枚举同样排除它，即使指定该实例 ID 和 kind，也不会获得租约。

实例 enabled/draining/capacity 现为后续实例调度消费的资源事实，尚未替换旧聚合路径的准入与计容规则。不能据此声称已经实现每个 Step 的异构实例匹配、同实例争用、排空完成或共享模型 quota。

Registry 的定义历史、所有者、逻辑启停和代次是进程内事实；SQLite 持久化的是资源投影与健康。新 epoch 不自动认领旧 ref，也不自动把旧实例管理策略搬到新创建的实例。定义控制面的持久化策略、动态注册授权与历史回收需在后续控制面建设中明确。

## 8. 阶段 3 追记：本地实例分配（2026-11-15）

READY 现在把当前 scope 内可调用的实例交给现有 Binder：实例满足能力、逻辑启用、enabled/draining 和健康约束，宿主满足环境、信任、地域及资源策略。角色提示影响偏好，忙碌实例可由其他合格实例承接；通用 Runtime 候选仍不把 AGENT_INSTANCE 当作独立执行端点。

一次执行同时持有宿主与实例租约，沿用原 LeaseCoordinator；预留未完成时统一补偿，期间没有进入外部执行。它是顺序预留加失败补偿，不是新的多资源原子事务，也没有增加 busy 账本。原 KeepAlive 续期两份租约，正常结束一并释放；原有 UNKNOWN 分类保留两份租约至既有 TTL 并隔离实例，普通已结束异常不被一概升级为 UNKNOWN。

ExecutionBinding 增加可选的 agentRegistration、agentLeaseId、agentLeaseVersion；resourceId 仍表示宿主。相同 Attempt 在没有执行 WAL 时只能恢复原注册身份和仍有效的租约；失效后需要新的 Attempt。绑定先持久化再调用，调用入口复核当前注册、租约和准入状态。已提交结果复用原 NodeRunner 重放，不要求历史 Agent 继续在线；遗留 prepared 调用要求显式核对，不能换代后自动重跑。

Identity 与 Handoff 复用绑定的统一元数据投影，Permit 和恢复核对同一注册及租约身份；没有新增数据库表或修改 Step/TaskPlan/ACG。旧已提交绑定仍可读取；没有精确实例身份的旧本地在途 Attempt 明确要求恢复处理，不会被静默升级成另一份实例绑定。

## 9. 阶段 4 追记：模型需求与共享配额（2026-11-15）

### 9.1 已接通的执行路径

- 复用 `ModelDemand`：能力描述符可声明 `modelDemand`，规划输入把它冻结到 `resourcePlan.models`；手工构图也可使用 `ModelRequirementSpec(stepId, demand)`。Step、TaskPlan 和图执行器不变。
- 编译为 `BindingRule.modelDemand`，再由 `execution_requirements_for()` 生成 `ExecutionRequirement.model`。需求进入 blueprintHash/package checksum 和现有重建比较；语义修订保留未改变 Step 的模型需求，为改变的 Step 重新生成。重复或未知 Step 的声明会被拒绝。
- 未声明需求仍保持旧语义；无需求时两个新增字段不输出，因此旧图/包不会仅因补默认值而改变哈希。使用第四阶段修改前真实源码生成的 artifact 验证：新代码加载、重编译后 blueprintHash 和 package checksum 均保持一致。
- READY 仍由 Binder 选择具体实例、宿主和模型端点。明确声明的模型需求不满足时不会回退到 Agent Profile 默认模型。新绑定的模型路由与 quota 进入 Identity 元数据，Permit 与恢复核验同一份绑定。

### 9.2 配额语义与配置

`ModelEndpointProfile.quota` 和冻结的 `ModelEndpointBinding.quota` 复用同一 `ModelQuotaPolicy`，包括 `scope`、`maxConcurrency`、可选 `requestsPerMinute`、`tokensPerMinute`。多个端点配置相同 scope 即共享配额；同 scope 的冲突策略被拒绝，不能通过切换 Agent、Run 或端点别名扩大额度。修改策略需要显式切换配额域或受控迁移，当前不提供在线改额。

并发占用继续使用既有 LeaseCoordinator；RPM/TPM 使用独立的窗口账本，具有内存与 Redis 实现。Redis 沿用已装配协调器的 client/namespace，以 Lua 原子裁决并使用服务端时间；不可用时不回退为另一份本地额度。内存模式只在共享同一个协调器的执行服务间协调，SQLite 目录本身不代表分布式配额。

配额在实际模型适配器尝试入口申请，不在 READY 时按整个 Step 持有。候选切换、重试、工具调用回合与续写均重新计额；同步和流式请求走同一入口。并发租约正常/异常/取消后释放；RPM 保留到开始后 60 秒。TPM 预留输入字节估算加有上限的输出额度，取得供应商 usage 后按实际用量结算并保留到结算后 60 秒；超预估形成债务，缺失用量保留原预留，不能把估算显示成实际 token。配置 TPM 而输出无上限时明确拒绝。

流式完成、异常和主动关闭都会同步关闭底层 iterator 并结算；容量排队不消耗供应商 TTFT/idle 窗口。适配器内部的本地预检失败或收到 started 即关闭、但缺乏可靠未调用证明的情况仍保守占额；这里是准入配额，不是供应商账单核算。金额预算未纳入本阶段。旧 `BindingRule.maxConcurrency` 元数据也不作为新的 quota 权威，实例容量仍来自注册资源事实，模型容量来自明确配置的 quota。

应用现有 `AGENTOS_MODELS` 每项可增加：

```json
"quota": {"scope": "provider:account-a", "maxConcurrency": 2, "requestsPerMinute": 30, "tokensPerMinute": 100000}
```

应用装配将其投影到模型端点；旧 Profile/default route 解析到已配置 quota 的路由时同样受限，无法通过兼容回退跳过配额。原有进程内 gate 继续保留为底层保护。Tool 的按操作授权、租约与 WAL 机制直接复用；Skill 是实现声明，不按目录条目另占一份运行槽位。

当前远程 Step 协议没有携带并执行模型路由/配额的保证，因此 ACG 本地候选映射下，声明模型需求的 Step 不会被分给这种远程 Backend（候选原因 `MODEL_DEMAND_UNSUPPORTED_REMOTE`）；无模型需求的既有远程路径保留。跨 Worker 模型授权协议与自动装配不在阶段 4 承诺内。

### 9.3 可直接运行的实测入口

新增 `ops/scripts/heterogeneous_execution_trial.py`。手工注册需求评审、交付评审两种 Agent，实现两个并行 Step，分别审查内置的短材料；模型端点共享 quota scope。脚本沿正式 ExecutionRuntime/AgentRegistry/Binder/ACG/审计与提交链运行，使用隔离的 SQLite 状态目录。

从仓库根运行，先使用现有格式配置模型（替换实际供应商、模型、兼容 API 地址和密钥）：

```powershell

$env:AGENTOS_MODELS='[{"capabilityId":"model.trial","provider":"实际供应商","models":["实际模型"],"baseUrl":"https://实际兼容API地址/v1","apiKeyEnv":"TRIAL_MODEL_API_KEY","version":"1.0.0"}]'
py -3 ops/scripts/heterogeneous_execution_trial.py --dry-run
```

## 10. 阶段 5 追记：受控动态供给（2026-11-15）

### 10.1 已接通的供给与执行链

新增 `service/agents/provisioning.py`，复用现有 `InstallationJob`、JobStore、AgentRegistry、AgentPool、ResourcePlane 与 LeaseCoordinator。没有新增数据库表、执行器、调度器、busy 账本或 Step/ACG 字段。生产装配直接使用 `runtime_binding_service.agent_pool`。

应用启动时用受信 callable 登记 `AgentTemplate`，冻结现有 AgentDefinition、每模板动态副本上限（默认 8，不含启动实例）、可选依赖资源 ID 和健康检查。请求仅提供 templateId / idempotencyKey。默认开放 NativeGeneralAgent；Workspace Pack 已加载时还开放 WorkspaceDeveloper。只为新对象补齐已冻结的 Pack 来源字段，随后核对完整定义；不会覆盖或提升工厂返回对象的能力声明。

供给流程为：模板与逻辑准入检查 → 构造新对象 → 身份与定义核验 → disabled 注册 → 依赖/可选健康检查 → 本地存活心跳 → enabled 发布 → 全局宿主刷新 → RUNNING。这里的心跳只证明本地实例存活；不代表已调用真实模型或工具。具体模型、工具权限与租约仍由既有执行链检查。

动态副本复用原 logical agentId、definition digest/version 和插件来源，因此在 Run scope 冻结之后也能进入该逻辑 Agent 原本获准的候选集；没有向旧 Run 增加新的逻辑角色或权限。READY 继续由原 Binder 选择精确实例与宿主，并沿原租约、Binding、Identity、Permit、提交和审计链执行。

### 10.2 生命周期、失败与重启

创建请求按 local + templateId + idempotencyKey 确定唯一 job；同键不重复构造。达到模板上限会拒绝新建；停止但未回收、以及失败后仍保留资源的实例继续占该上限。

工厂返回种子或已注册对象时，在修改配置、登记或清理之前拒绝。注册、发布和 JobStore 的 ACK 不确定时先读回：完整 RUNNING 事实可确认成功；其余情况先禁用并 draining。只有确认无活跃租约、无 UNKNOWN 且撤销成功后，才清理本次新建对象。注册前事实已写入的孤儿投影按本请求 instanceId、registry epoch 和 definition digest 精确定位补偿。

stop 先 disabled + draining，不取消已在途的调用，也不直接释放其租约。uninstall 复查协调器真实占用；活跃租约存在时保留实例，释放后才能撤销 Registry 与 ResourcePlane 事实。FAILED 允许进入 UNINSTALLING，以复用同一状态机处理失败实例的清理。Marketplace 将 Agent 作业委托给 Provisioner，避免把 Python 对象交给进程 launcher 停止。

UNKNOWN 现在在实例 metadata 持久化 `outcomeUnknown=true`，同时 disabled/draining；TTL 结束或健康心跳不会清除它。重新启用、解除 draining 和卸载均要求先处理 UNKNOWN。此阶段不提供自动对账或清除 UNKNOWN 的操作。

持久化作业不会使旧 registry epoch 的 Python 对象复活。重启后的旧 RUNNING 作业在实例查询中显示 callable=false、reconciliationRequired=true；同键创建返回冲突，要求显式核对，不自动重建或声称可调用。

全局宿主投影现在根据全部本地实例事实聚合，排除其他宿主、disabled、draining 与 UNKNOWN，采用实例当前 capacity；Run scope 仅过滤候选，不再改变共享宿主容量。停止和卸载后聚合能力/容量同步回落。
