## 2. 真实入口与权威边界

正式入口是 `WorkflowRuntime.prepare_graph_handoff(activation_id, idempotency_key)`（`apps/agentOS/src/runtime/workflow_runtime.py:1176-1186`），进入唯一 `GraphHandoffAuthority.prepare`（`apps/agentOS/src/runtime/graph_handoff.py:389-437`）。Authority 只能显式启用，构造时要求现有 Activation Authority、Planning Commit Authority、同一权威 Workflow SQLite 和分离的 Checkpoint SQLite（`graph_handoff.py:41-60`）。调用者仅提交服务端 Activation ID 与幂等键，不能提交候选图、Checkpoint 正文、身份或权限。

`prepare` 先取同 Run 进程锁和 OS 文件执行 fence，再在事务外构建完整候选并校验；开启 Workflow `BEGIN IMMEDIATE` 后重验并写入唯一 STAGING intent；释放 Workflow 写锁后写分离的 staged Checkpoint；最后再次开启 Workflow 事务，核对完整 stage、重验来源并把 Journal 确认为 `STATE_PREPARED`。相关阶段见 `graph_handoff.py:389-429`。事务外计算不会持有 Workflow 写事务，但最终一次完整重验和候选相等比较发生在 Workflow 写事务内。

候选仅由已接受的最新 Graph Revision、Materialization、原 Run 与其既有 Checkpoint 推导。代码校验 source/parent/revision 链、Mission、basis/provenance、proposal 与 Safe-Cut 摘要、当前 Mission revision、nextPlan/bindings/candidate graph 与当前 Compiler package（`graph_handoff.py:77-115`）；随后经现有 `SemanticRevisionService._validate_bindings`、当前 principal 授权、Identity 当前记录与原 Plan/Graph 核对（约 `:116-148`）。没有引入第二个 DAG Compiler。

前缀验证比较 Run 投影和正式 Checkpoint，读取当前 Review、执行收据、ExecutionValueStore、Identity Attempt/StepExecution/ExecutionOrigin、资源绑定和审计决策、输出/上下文/记忆/trace/provenance（约 `:149-340`）。完成前缀须依赖闭合，未完成节点必须保持 pristine pending；失败、skip、retry 或含糊副作用不能被当成完成。编译器推导边也参与闭合判定。

唯一持久写入是 Workflow SQLite 的 `graph_handoffs` Journal 和分离 Checkpoint SQLite 的 `staged_graph_checkpoints` 正文；约束包括 idempotency key、activation ID、handoff ID 的唯一键（`apps/agentOS/src/support/stores/graph_handoff_store.py:14-20`）。两库之间不是联合事务：先写可恢复 STAGING，再写 stage，再确认 PREPARED，崩溃可能留下待重驱动 intent/orphan stage，但普通恢复不得消费它。

`STATE_PREPARED` 不是执行许可。正式 Run 保持 `ACTIVATED_PAUSED`，`_claim_acg_execution` 在缺少 Permit 时拒绝运行（`workflow_runtime.py:1114-1141`）。普通 Checkpoint 路径读写正式 checkpoint 表，不读取 staged 表；`close_orphaned_runs` 和 v2 reconciliation 对 `graphActivation` Run 提前退出/跳过（`runtime_recovery.py:210-215`、`v2/reconciliation.py:106,279`）。新表没有被 Scheduler、Executor、Binder 或 SemanticRevisionService 接入，普通 Review approval 不会把 staged package 提升成正式图。

## 3. 独立发现并修复的 P1

### P1：Receipt 的 allow 决策引用可被替换

构造真实已完成前缀后，插入同 Run、同 step 的第二个有效 allow 决策，把持久 receipt 的 `auditDecisionRef` 换成该决策；随后走正常接受和 handoff 路径。修复前 Authority 返回 `STATE_PREPARED`，违反 receipt 必须证明实际提交节点审计事实的合同。复现记录：`tmp/S03-02B1-independent-audit-before.log`，**1 failed / 5.42s**。

最小修复是在执行记录和 receipt 身份条件中加入 `node.audit_ref == receipt.auditDecisionRef`，再由既有 decision store 验证该确切引用为 allow（`graph_handoff.py:255-263,323-324`）。永久测试 `test_receipt_decision_ref_must_match_committed_execution_audit_ref` 保留该反例，当前必须拒绝。

### P1：Identity ExecutionBinding 资源可与 Run 资源绑定分离

在真实 Identity 数据库中把成功 Attempt 的 ExecutionBinding.resource_id 改为另一资源，保留合法 schema/FK，并在攻击状态上完成规划接受；修复前得到 `STATE_PREPARED`。复现记录：`tmp/S03-02B1-identity-binding-before.log`，**1 failed / 5.78s**。

修复从当前 Run 的 `executionBindings` 解析冻结 Runtime binding，逐项比对 Run/step/attempt、`resourceBindings`、唯一 scheduling decision、Identity resource 与 metadata，并限制 agent 身份为运行时逻辑 Agent 或既有 embedded-resource 表示（`graph_handoff.py:282-318`）。嵌入式 Agent 的实际生命周期允许 `Identity.agent_id` 暂存 Runtime resource ID，而 Run 的 `logicalAgents` 保存稳定注册 ID；修复保留这两个已有合法表示，不接受任意第三值。永久测试 `test_identity_execution_binding_must_match_runtime_attempt_binding` 保留反例。

两条失败日志是修复前证据，随后针对原有成功路径和两条攻击测试得到 **3 passed in 12.10s**；最终 handoff 定向集再次完整通过 **67 passed**。

## 5. 并发、故障与恢复

- 同一 Activation 的同 key 重放由完整候选比较返回幂等结果；不同 key 由 Activation 唯一性拒绝，不能生成第二份有效 Journal。另有双进程同连接/不同 key 竞争、SQLite 唯一约束及 ACK 丢失类既有测试。约束而非 Python 进程锁承担最终单机持久化唯一性。
- intent 写入前失败不留下成功记录；intent 后、stage 写入后、确认前失败留下不可执行的 STAGING 和可能的 stage；确认提交后 ACK 丢失可按原 key 读回。恢复必须使用原 key 重驱动，另一 key fail closed。两个数据库不可能一起原子回滚，恢复依赖可验证的幂等阶段，不把 orphan stage 当成正式 Checkpoint。
- 运行时 RunLock、活动 execution slot 检查及文件 fence 共同阻止 handoff 与同机节点执行重叠；最终候选会重读 Run、Checkpoint、收据、Review、权限/Identity 等来源。操作员输入、取消或来源改变若发生于可见的重验前会导致拒绝。不同数据库的最后一次权威读取后发生变化仍有竞态，必须由未来 Permit/激活事务再次重验，不能依赖本次 PREPARED。
- 取消、Run 终态、未授权 principal、过期图/plan/Identity、待审核控制状态以及未闭合的已完成前缀均按拒绝处理。控制图修订保持 fail closed；本轮没有放宽 safe-cut。

## 7. S03-02B2 严格前置条件

`STATE_PREPARED`、历史幂等回执和普通 Review approval 均不构成 Permit。B2 激活前至少应重新确认：当前 Activation/正式 GraphVersion 与 accepted Revision 链；Run 仍在原执行状态、取消与操作员输入未变；完整 source Checkpoint/head 与运行收据；当前 principal、能力 scope、Identity snapshot 和 Runtime binding；全部 staged 内容、摘要、编译策略版本及来源引用。准备过程之后 Run 可以继续变化，故 B2 必须对变化 fail closed，并建立绑定 `(Run, Activation, GraphVersion, staged Checkpoint identity, attempt generation)` 的正式 Permit/代际 fence。
