## 修复与真实调用链

### 同事务完整绑定

`SQLiteWorkflowStore.save_run → BEGIN IMMEDIATE → _upsert_run → validate_activation_run(conn, run) → UPSERT → COMMIT`。

共享验证函数位于 `support/stores/graph_activation_store.py`。使用调用方传入的同一连接读取 Head、typed Activation Record、typed Materialization Record 和旧 Run：

1. 校验 Journal checksum 与全部索引列；复用原合同校验物化包内容摘要、身份、版本与状态。
2. 交叉绑定 Run/Mission/Graph/Activation/Materialization/sourceCommit、源及候选版本、packageChecksum、commitmentFingerprint、proofFingerprint。
3. 完整 Run 蓝图的 `stable_checksum` 必须等于物化包 `blueprint_hash`；Run 的完整 CompiledACGPackage 必须等于不可变物化包，四个编译投影字段不能冲突。
4. execution_state 的 Graph 身份必须与 Head 一致；版本拒绝布尔值等类型混淆。
5. graphActivation 必须与服务端 `activation_projection` 精确相等，包括键集合、身份、两个版本、`ACTIVATED_PAUSED` 和 `executionPermit=None`。不提供任何许可扩展后门。
6. 首次激活时，Head 已在本事务更新、旧 Run 行仍是 v1：supersededCheckpointId 以旧 Run 的 checkpointId 为准。后续普通写回以已持久化的同 Activation 投影为准，不能任意改写。既有激活构造本身正确保留了 Checkpoint，本轮未改动该构造。

无 Head 且无激活投影的历史 Run 保持兼容，包括未部署激活 schema 的旧库。有投影却缺 Head 也拒绝。存在 Head 时缺失或损坏 Journal/物化证据统一 fail-closed。没有引入新的持久化列、索引或第二套图权威。

### 执行栅栏与竞争

`_execute_acg → _claim_acg_execution → RunLock → 单一 SQLite 只读事务中的 Head/Journal/Run 验证 → 无 Head 才认领执行槽`。

Head 存在即拒绝执行，无须依赖可选 Run 字典或进程内 activation authority 装配。正常 paused 和损坏证据都不能到达 Agent。

原有 MemoryWorkflowStore 没有 SQLite 接口、也不能持有正式激活 Head：仅在无 activation authority、无激活投影时沿用旧执行行为；携带任一激活身份时拒绝。SQLite 后端始终读取正式 Head，不能通过卸载 authority 改走内存兼容分支。

执行入口的权威读取与认领槽在同一 RunLock 内；激活 `_verify` 在相同锁序下检查 `_active_execution_slots`。执行已占槽则激活拒绝，激活先提交则旧快照执行拒绝。重试/后继 Run 循环再次认领槽也必须重走该栅栏，防止循环内绕过。

这是同 Runtime 的执行入口竞争保护；跨连接的旧快照**持久化**保护仍由同 SQLite 写事务保证，不把 RunLock 或进程内执行槽宣称为跨进程 CAS。

### 对账

`commit → _head_state` 在同一只读 SQLite 快照内读取并验证 Head、Journal、物化和 Run。最终写事务中的对账复用其现有连接，不开启嵌套事务。损坏证据不能包装为 IDEMPOTENT_REPLAY。保留 Journal/Head/Run 同一写事务提交及 ACK 丢失原 key 对账语义。
