# 异构执行与资源抽象：复用审查

- 审查日期：2026-11-15（Asia/Shanghai）。
- 代码基线：`0bf8b898`，结合当前工作区源码。
- 目标：在既定 Step 与 ACG 语义上，补齐异构 Agent、资源管理和运行时绑定。
- 方法：沿生产调用链读代码，检索真实消费者，执行现有测试，并使用内存适配器验证关键边界。

## 1. 建设结论

现有系统已经具有执行内核、Agent 调用合同、异构适配边界、资源平面、单资源租约、执行许可、上下文、审计和提交恢复。这轮适合在既有权威链上做增量扩展。

主要新增内容应集中在：可调度 Agent 实例与注册版本、实例资格与容量、必要资源的组合预留、配额管理，以及这些事实进入现有绑定/许可/投影/恢复链。不能把“新增 AgentPool”理解为重建 Step、另建计算图执行器或另建资源状态中心。

本轮补充两点此前概述不够完整的事实：

1. 规划期已有 Agent 候选评分。`CognitiveRouter.candidates_for()` 使用领域、能力语义、`binding_priority` 和登记顺序；缺少的是运行期实例资格与实时占用调度，而不是完全没有 Agent 匹配。
2. 正式工作区工具已经按操作使用 ResourceBinder 申请租约，并具备续租、WAL、审批后授权复核、执行收据和 UNKNOWN 隔离。不能把 Tool 侧视为只有接口、完全没有资源占用机制。

依据：[规划路由](../../apps/agentOS/src/components/planner/cognitive_router.py#L119)、[正式工具操作](../../apps/agent/app/tools/formal_workspace.py#L128)。

## 2. 需要优先处理的审查发现

以下区分“当前可复现行为”“建设前置条件”和“新增能力”，不把尚未承诺的热更新、联合预留功能直接当作现有生产故障。

### F1 / P1：Runtime 总容量不能保证单个 Agent 的容量

**状态：当前行为已复现；是 AgentPool 建设的直接前置问题。**

`register_embedded_agents_runtime()` 将逻辑 Agent 的能力取并集、容量相加，登记为单个 `runtime:embedded-agents`。`ResourceBinder.bind_ready()` 只对选中 Runtime 的 ID 和 capacity 申请一个槽位。具体 Agent 在 Runtime 分配后才解析。

内存验证结果：

```json
{"agentCapacity":1,"runtimeCapacity":2,"allocated":["allocated","allocated"],"resolvedAgents":["analyst","analyst"]}
```

场景中 analyst 和 writer 的 capacity 都为 1；两个 analysis Step 均分配成功，均解析到 analyst。Writer 的空闲容量不能等同于 analyst 的可用容量。

**建议复用：** 保留现有 Runtime 账本与 LeaseCoordinator；增加可识别的执行实例/槽位占用，明确 Agent 定义本身是否允许并发复用。AgentPool 不应另建 `busy` 标志作为第二份容量权威。

依据：[能力与容量聚合](../../apps/agentOS/src/components/resource/runtime/embedded_runtime.py#L29)、[单 Runtime 申请](../../apps/agentOS/src/components/resource/scheduler/binder.py#L429)。

### F2 / P1：READY 路径重新构造模型 wrapper，使同模型的并发闸门分裂

**状态：完整执行链已复现。**

`_build_runner()` 原本按模型绑定缓存 `GuardedModelRuntime`，注释也要求同模型共享闸门。但 READY 包装器选定模型后再次调用 `_model_runtime_from_binding()` 并覆盖该 Step 的 wrapper；该方法每次创建新的 `GuardedModelRuntime`，其 semaphore 在构造时独立创建。

验证使用真实 `ExecutionRuntime → ACG → READY Binder → NodeRunner → RegisteredModelRuntime`，模型 Provider 为无网络的内存适配器；两个无依赖 Step 使用同一 Provider/model，Agent capacity 为 2：

```json
{"configuredModelMaxConcurrency":1,"observedProviderMaxConcurrency":2,"runStatus":"completed"}
```

这表明现有 wrapper 内的并发保护不能直接当作“模型资源级统一配额”复用。

**建议复用：** 保留 GuardedModelRuntime 的重试、超时及调用保护；将共享 gate 的生命周期与实际端点/凭据/配额作用域对齐，由依赖装配或资源控制器持有。可参考 GuardedToolRuntime 在 scoped/bind_context 时显式传递同一 gate 的做法。仅在单次 runner 构建时缓存 wrapper，不足以覆盖 READY 路径，也不等于跨 Run/进程配额。

依据：[构建时共享](../../apps/agentOS/src/runtime/acg_execution.py#L1289)、[READY 覆盖](../../apps/agentOS/src/runtime/acg_execution.py#L735)、[重新构造 wrapper](../../apps/agentOS/src/runtime/acg_execution.py#L1849)、[模型 gate](../../apps/agentOS/src/adapters/guarded_model.py#L62)、[工具 gate 共享](../../apps/agentOS/src/adapters/guarded_tool.py#L92)。

### F3 / P1：Agent 级准入尚未落实，角色提示可以命中能力不符的 Agent

**状态：解析器与执行服务方法级验证已复现；未声称普通规划必然产生此类输入。**

`AgentRegistry.resolve()` 名称命中后直接返回，只检查 scope，不检查该 Agent 是否 enabled、是否具备请求 capability。`_resolve_embedded_agent()` 根据角色提示/名称解析时也没有传入能力约束。Runtime 层的能力检查面向所有 Agent 的能力并集，不能替代具体 Agent 的资格验证。

验证结果：

```json
{"required":"analysis","selected":"writer","selectedCapabilities":["writing"]}
{"resolveReturnedEnabled":false,"projectedCapabilities":["agent:disabled","analysis","exec.agents"],"projectedRuntimeEnabled":true}
```

第二个验证说明 disabled Agent 仍能从 registry 解析，其能力仍投影到 enabled 的聚合 Runtime。`binding_priority` 在规划路由中已有消费者，但 runtime registry 本身不实施该排序；`capacity` 也没有成为 Agent 级占用约束。

**建议复用：** 复用 AgentProfile、领域/scope 规则与现有 ResourceBinder 的“先硬过滤、后评分”结构；在实例候选层校验全部必需能力、启用/健康、版本和环境兼容。角色名称只能影响合格候选的偏好，不能覆盖硬约束。

依据：[名称命中路径](../../apps/agentOS/service/agents/registry.py#L29)、[运行时角色解析](../../apps/agentOS/src/runtime/acg_execution.py#L419)、[Runtime 硬过滤](../../apps/agentOS/src/components/resource/scheduler/binder.py#L107)。

### F4 / P1：当前注册和调用方式不能直接升级为热注册或精确实例绑定

**状态：替换与调用边界已复现；在开放动态注册之前必须明确语义。**

`AgentRegistry.register()` 按 `(domain, name)` 直接覆盖对象；scoped view 只冻结允许的逻辑 ID，仍引用活 registry。`AgentInvocationAdapter.invoke(context, agent=selected)` 收到具体对象后，又提取逻辑 ID 并 `resolve_by_id()`，因此不保证执行的是调度时选中的对象。

验证顺序：选中旧对象 → 建立 scoped view → 登记同名同 ID 新对象 → 向 invoke 传入旧对象。结果：

```json
{"scheduledObject":"old","actuallyInvoked":"new","scopeStillContainsId":true}
```

现有 scope 限制仍有价值，但它固定的是允许集合，不是实现版本快照。该验证不等于证明跨租户越权。

**建议复用：** 继续保留 registry 与 invocation adapter；为注册项增加明确 generation/version 和生命周期，在绑定中固定执行实现/实例身份。调用前核验精确绑定，同时保留实时撤销策略。旧实现进入 draining 后，可停止接新任务而不静默改写在途 Attempt。

通用 `CapabilityRegistry` 已有 RLock、manifest 校验、确定性指纹和冲突拒绝，优先复用其规则；但同 manifest 重复登记保留旧 entry，也不能把重复 register 视为已完成代码热更新。插件 register_pack 是启动装配路径，整包暂存/校验/发布仍需另行设计。

依据：[覆盖注册](../../apps/agentOS/service/agents/registry.py#L21)、[scoped 活视图](../../apps/agentOS/service/agents/registry.py#L85)、[调用前再解析](../../apps/agentOS/src/adapters/agent_invocation.py#L53)、[通用注册器](../../apps/agentOS/src/adapters/registry.py#L34)、[插件装配](../../apps/agentOS/src/support/packs/registry.py#L122)。

### F5 / P2：模型需求和并发声明已有合同，但不能按字段存在判断已经接入主链

**状态：静态调用链确认的接线缺口。**

- `ModelDemand` 和 `ExecutionRequirement.model` 已存在，Binder 也支持模型端点选择。
- 正常 `execution_requirements_for()` 只生成 capabilities、runtimeKinds、domain、agentRole 和 policyMetadata，没有构造 ModelDemand。
- 模型执行可回退到 AgentProfile/default model；它不等价于按 Step 的模型特性/上下文要求选端点。
- `BindingRule.maxConcurrency` 被抄入 `policyMetadata`，当前 Binder 不据此实施 Agent 级并发限制。

**建议复用：** 补需求生产者和从权威编译结果/运行策略到执行需求的传递，不另定义同义 ModelRequirement。涉及需求扩展时，同步更新 immutable package、requirements 重建比较及来源验证；不能只修改 Run 字典，否则激活路径会把它认作需求漂移。

依据：[ModelDemand](../../apps/agentOS/src/contracts/resource/resource.py#L268)、[需求生成](../../apps/agentOS/src/runtime/binding.py#L27)、[权威需求比较](../../apps/agentOS/src/runtime/binding.py#L52)、[模型回退](../../apps/agentOS/src/runtime/acg_execution.py#L1744)。

### F6 / P2：现有单资源租约值得复用，组合预留与配额需要新语义

**状态：新增能力边界。**

LeaseCoordinator 已支持单资源原子申请、身份幂等、TTL、续期和释放。InMemory 用 RLock，Redis 使用 Lua；生产装配在配置 Redis 后使用相应协调器，无 Redis 时仍是本地协调，不能据 SQLite 目录持久化推导分布式容量安全。

当前接口没有多资源 bundle；并发槽位也不是 RPM/TPM、Token 或金额预算。应分别定义：

- 必须同时占用的 Agent/Runtime 等资源的组合预留及失败补偿/回收；
- 按窗口或消耗计量的 quota；
- 工具操作按实际调用申请，沿用正式工具已有机制；
- 租约续期修订版本与持有者更替 fencing epoch 的区别；
- 新实例/租约身份在调用与提交边界的校验，以及 UNKNOWN 结果的隔离。

现有资源 release 入口只接收 lease_id；若后续暴露给跨进程 Worker，需要增加所有权校验或等效服务端授权，不能直接下放内部接口。现有 lease ID 终态不可复用，不能仅凭此断言必然发生 ABA。

依据：[LeaseCoordinator](../../apps/agentOS/src/components/resource/scheduler/leases.py#L129)、[内存租约](../../apps/agentOS/src/components/resource/scheduler/leases.py#L154)、[Redis 租约](../../apps/agentOS/src/components/resource/scheduler/leases.py#L274)、[生产装配](../../apps/agent/app/execution/wiring.py#L445)、[UNKNOWN 处理与清理](../../apps/agentOS/src/runtime/acg_execution.py#L870)。

## 4. 存在定义不等于可以直接接入

### 4.1 旧 AgentInstance 不是池实例

`contracts/task.py:101` 已有 AgentInstance，但它是 task 内的运行记录，状态为 pending/running/success/failed，字段偏向 modelName、tokenUsage、executionCount。全量检索未发现生产调用方将其用于池分配。

不宜直接把它当作具有 runtimeId、health、capacity、draining、generation 的可租用实例，也不宜不经辨析再建一个完全同名的权威模型。应先决定迁移、明确命名或保留为统计投影。

### 4.2 两个 ExecutionBinding 职责不同

- `contracts/resource/resource.py:330`：Scheduler 的真实执行资源绑定。
- `domain/identity_graph/bindings.py:62`：Identity 中关联 Attempt、节点、资源、Agent、模型的投影。
- `runtime/identity_projection.py:1233`：把前者写入后者，拒绝同 Attempt 的矛盾身份。

本轮应扩展这条既有映射，不因类名相同就删掉其中之一，也不另建第三套 BindingPlan 真源。新增实例/版本信息需要同步覆盖事件、持久化、许可、handoff 和恢复检查。

### 4.3 各种“能力目录”不是同一个东西

- Planning CapabilityCatalog 描述规划语义与输入输出要求；
- CapabilityRegistry 保存可调用适配器与 manifest；
- ResourcePlane 保存部署、可用性与资源事实；
- AgentPool 应提供实例候选和占用视图。

可以统一查询和关联，但不应把规划语义、执行代码、心跳和租约全部塞进一个无类型大字典。`support/skills/registry.py` 当前只有模块说明，也不能据文件名把它算成可复用技能池实现。

## 5. 必须沿用的运行不变量

1. TaskPlan 继续禁止具体执行身份；复用当前 Step 和 ACG，而不是再造 Step 合同。
2. ACG 负责依赖/控制就绪，Scheduler 消费 READY 工作；池实例不拥有另一份图状态。
3. ResourcePlane 维持资源事实权威，占用由既有协调器扩展；Registry 不自持独立 busy 账本。
4. 一次 Attempt 的绑定可追溯且不可被热注册静默改写；换执行主体使用新 Attempt 或明确的恢复协议。
5. Permit 初次签发可许可候选范围；最终 dispatch 和真实调用前继续校验完整绑定与撤销情况。
6. Graph generation、Attempt 身份、输入引用和提交身份保留。已提交结果重放不依赖原实例仍在线，也不应重新调用 Agent。
7. 结果 UNKNOWN 不可直接释放后重跑；复用现有 WAL、隔离和对账恢复规则。
8. 审计拒绝不发布输出/共享记忆，人工审核结果沿现有提交链处理。
9. 当前图会并发启动一轮 READY Step、逐个提交结果，但下一轮推进仍有屏障。实例调度与移除轮次屏障应分别验收。

依据：[TaskPlan 边界](../../apps/agentOS/src/contracts/planning.py#L14)、[调用前 Permit](../../apps/agentOS/src/runtime/execution_permit.py#L511)、[Identity 投影](../../apps/agentOS/src/runtime/identity_projection.py#L1233)、[图推进](../../apps/agentOS/src/components/executor/graph.py#L516)、[提交重放](../../apps/agentOS/src/components/executor/node_runner.py#L161)。

## 6. 建议的最小增量

### 第一批：先把现有机制变成可信的实例分配基础

- 修复共享模型 gate 在 READY 阶段被拆分的问题，并增加真正经过 READY 路径的并发回归。
- 补 Agent 候选的硬资格校验，使名称/角色偏好无法绕过能力与启用状态。
- 固定注册 generation 与绑定实现身份，明确逻辑定义、无状态调用会话、有状态执行实例。
- 在现有协调器和 ResourcePlane 扩展 Agent 槽位计容，覆盖同实例争用。

### 第二批：贯通绑定与资源需求

- 扩展已有 ExecutionBinding 与 Identity 投影，携带实例和定义版本；审视历史记录兼容。
- 补模型需求生产者；相关需求进入编译/策略的权威来源和重建校验。
- 对确需同时占用的资源实现组合预留，对调用型 Tool 沿用按操作申请。
- 增加独立 quota 计量/预留/结算接口；复用既有模型和工具调用保护。
- 把新身份、租约拥有者代次接入 Permit、提交、取消和恢复。

### 第三批：按需实例化与控制面扩展

- 利用现有注册校验与 Marketplace 生命周期模式实现 Registrar / Factory / Provisioner。
- 新实例继承已授权定义的 scope；新增定义或扩大权限必须受控。
- 先支持已有模板/实现与已登记资源的组装，再考虑更多框架和部署协议。
- 异步交付队列只在异步审计、跨进程交付有实际需求时接入既有提交链。

## 7. 本轮验证与限制

### 7.1 现有测试

| 测试组 | 本轮结果 |
| --- | --- |
| Resource / Scheduler 全目录，Agent invocation、compatibility、framework、guards、远程执行与模型适配，binding authority | 234 passed |
| Runtime 资源/模型绑定、Permit/Permit audit、scoped optional dependencies、架构门禁 | 61 passed，7 failed |
| Unified tools / AuditedToolRuntime | 45 passed，1 条已有 Pydantic 弃用警告 |
| 合计（最终有效调用） | 340 passed，7 failed |

Permit 组从 `apps/agentOS` 作为工作目录运行，环境为 `PYTHONPATH=src;.`、`PYTHONIOENCODING=utf-8`，解释器为本机 `py -3`（Python 3.14）。此前从仓库根运行会让子进程 fixture 无法导入 test_react_loop；纠正工作目录后重跑，最终统计不包含该次导入错误。

7 个失败需要保留为建设前的测试基线事项：

- 3 个 Permit 用例在预期的权限/需求校验之前，被 `runtime event Run store identity mismatch` 拦住；涉及 live event broker 的 Run/store 绑定和复制数据库的测试 fixture。
- 2 个 transport retry 用例没有观测到预期的 Agent adapter 调用；它们会吞掉 ValueError，当前未独立归因，不能据此断言 Permit 被绕过。
- 1 个门禁因为 `apps/local-runtime` 目录存在而失败。`git ls-files apps/local-runtime` 为空，现场可见旧 pycache/pytest cache；目录存在本身不能证明退役源码复活。
- 1 个门禁因为 Marketplace 的受控 launcher 导入 subprocess 而失败；需要核对已实现的安装控制面与原生执行宿主规则边界，不能直接删断言掩盖问题。

另外，调度依赖门禁仍扫描旧的 `components/scheduler` 路径，资源权威门禁只扫描 resource 根层文件。新增代码进入当前分层前，应更新检查覆盖范围，而不是把当前通过视为覆盖完整。

### 7.2 额外行为验证

使用内存 Store/Provider/Agent，无真实供应商请求，验证了五个边界：

1. 聚合 Runtime 分配两个 analysis Step，但单 analyst capacity=1。
2. 完整双 READY Step 执行时，模型并发上限 1，实际并发 2。
3. 角色提示命中不具备 analysis 的 writer。
4. disabled Agent 仍可解析并投影到启用的聚合 Runtime。
5. 同 ID 覆盖注册后，传入旧 Agent 对象的 invocation 实际调用新对象。

这些验证用于确认审查发现，并未向生产源码加入修复。Redis 测试使用仓库已有测试替身/脚本检查，本轮未进行真实多进程 Redis 压测、远程跨主机执行演练或完整全仓回归。

### 7.3 实施时优先增加的回归

- 两个 Step 争用同一独占实例时不超配，不相关实例仍可并行。
- 同模型端点的多个 READY Step/多个 Run 按资源作用域共享额度。
- 不合格/disabled Agent 不因名称或角色偏好被选中。
- 调度后同 ID 换实现，旧 Attempt 不静默漂移；撤销策略仍生效。
- 部分资源预留失败、等待中取消、绑定持久化前后崩溃能够回收/恢复。
- 旧持有者迟到结果不覆盖新 Attempt；合法续租不改变执行身份。
- 已提交结果在实例离线后仍可重放；UNKNOWN 不被误判成可安全重试。
- 新实例/版本信息贯穿 Runtime binding、事件、Identity、Permit、handoff 与 recovery。
