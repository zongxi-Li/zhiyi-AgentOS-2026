## 0. 执行摘要

**总体结论：先落实 S00 语义权威的最小纵向闭环，再连接 S01/S07，随后落地 S02/S03/S09 的安全执行边界。** 当前有大量有效基础设施，不能重构成第二套 Mission、Run、Graph、Memory 或调度引擎。首轮 PR 建议聚焦 **Mission Semantic Commit 的单库原子性、CAS、Commit History、Outbox、有效快照查询**。先不改 Planner 算法、不接 Progressive ACG、不动本地 Runtime 的能力权限。

**最重要的五项事实**：

1. 当前 `RuntimeMissionRecord` 已有基本任务身份、标题、领域、意图、输入、运行状态；**不包含 Mission 层正式语义修订与决策列表**。
2. 当前 `SQLiteWorkflowStore` 有 `tasks/runs`、`lifecycle_outbox`、Run Summary、事务保存及部分防重复；`save_mission()` 对 JSON 执行无条件 UPSERT，更新时仍使用名为 `mission.created` 的快照事件；它**不是** S00 的 Semantic Commit/CAS/Outbox。
3. 当前 Planner 有 `TaskPlan`、`TaskPlanPatch`、运行观察与 safe/quiescent planning boundary；`SemanticRevisionService` 创建 Successor Run 时清空新 Run 执行列表和 Checkpoint。**Work Receipt 跨 Run 安全继承尚未闭环**。
4. 当前 `MemoryService` 有 metadata 先过滤、BM25/Vector/RRF、向量失败时 lexical fallback、PhaseCapsule；`ContextAssembler` 有字段白名单、graphVersion、inputRevision、证据引用。**当前认知 Overlay、来源失效签名、Critical-First 和版本化 Capsule 未形成正式闭环**。
5. 当前授权与审计有 `AuditedToolRuntime`、独立 Policy Decision Store，远程资源调用发送 Idempotency-Key。但**通用 Effect Intent/UNKNOWN Reconciliation/Compensation Ledger** 不是这些现有字段的直接等价物。

### 2.1 已有 Outbox 的复用原则

`lifecycle_outbox` 为现有 Mission/Run 生命周期消息传递机制，保留原事件、原消费者和现有去重行为。S00 需要的是 **Semantic Aggregate + Semantic Commit History + Semantic Outbox 的同一事务写入语义**。建议在同一个 SQLiteWorkflowStore 数据库中新增**边界明确的语义表和写入端口**，而非再启动另一套数据库服务器或独立 Mission 运行时。能否复用 `lifecycle_outbox` 的物理表，应先证明事件类型、消费者幂等及事务边界兼容；即使共表，也必须区分 `mission.created` 与 `mission.semantic.committed`，不能直接把当前快照 outbox 称为正式语义历史。

### 2.2 为什么不能从现有 Replacement Run 开始做 Progressive ACG

源码在构造后继 Run 时将 `steps`、`checkpoints`、`trace`、`completedStepIds` 清空；虽有图补丁、生命周期和 IdentityV2 关联，但“目标 Run 中已完成依赖能由旧 Work Receipt 合法满足、Executor 不再派发且未知外部副作用不重放”还需新的持久化合同及复用校验。因此 **Successor Run 已存在 ≠ ADR-0008 R1 已实现**。

### 2.3 代码现状与测试执行的区分

本轮已确认对应已有测试文件：`tests/support/test_workflow_store_contract.py`、`tests/support/stores/test_lifecycle_outbox_boundary.py`、`tests/runtime/test_graph_patch.py`、`tests/runtime/test_semantic_patch.py`、`tests/runtime/test_planning_loop.py`、`tests/components/memory/test_hybrid_capsule.py`、`tests/components/communicator/test_execution_context.py`。**这些是测试入口和现有覆盖证据，不是本轮运行通过的证明。** 远端 GitHub 无法替代用户本地尚未提交的工作区；所有最终实施 PR 必须在用户本地分支重新审计并跑测试。

## 3. 目标架构的最小纵向链路

```text
User / API creates Mission
  → existing ExecutionRuntime.create_mission
  → MissionManager / WorkflowStore (existing operational record)
  → S00 SemanticStore.bootstrap_if_absent(missionId, initialGoal)
  → S00 MissionSemanticAggregate(revision=1)
  → S00 effective_snapshot(missionId, revision, watermark)
  → S01 Planner / S07 (initially read-only shadow consumer)
  → S02 Proposal→PlanningCommit (later PR)
  → S03 MaterializedGraph→ACTIVE (later PR)
  → S04/S06 dispatch (only after guards)
  → Receipt / Evidence refs → S00 Cognitive Projection
```

**关键：** 不要先插入一个具有全量规划图和 Run 状态的“第二 Mission JSON”，也不要在首次 PR 修改 ACGGraphCompiler 的唯一权威。首条可验收闭环以持久化语义修订为终点：**创建 → 修改正式语义 → 旧版本 CAS 冲突 → 查询快照 → 重启再查 → 审计提交历史**。

### 4.2 PR-S00-02：Mission 启动接入 + EffectiveSnapshot / 只读兼容投影

- 将 S00 初始语义主体接入 **已有** `ExecutionRuntime.create_mission → MissionManager → WorkflowStore` 唯一创建链，避免接口旁路。
- `get_effective_snapshot(missionId, expectedAtLeastRevision?)` 返回 **仅正式认知的快照**；SourceProjection 后续再按水位加载 Run/Artifact/Resource，不能伪装跨数据库强一致。
- 新旧 Mission 兼容：只在首次访问/显式迁移时进行幂等 bootstrap（规则需写明来源、schemaVersion、legacyFlag）；已存在语义主体禁止用 `RuntimeMissionRecord.input` 全量覆盖。
- 只读 shadow 模式：在当前 Mission / Workspace 链路中旁路比对新旧认知，不先替换执行输入；逐步引入仪表/日志，避免泄露敏感源正文。

验收：已有旧任务列表/新建/归档/删除兼容；新旧 API 和 Run 不变；重启一致；观察版本水位可读；shadow 不改变 Planner 结果与 Token 支出。

- `CognitiveProjectionBuilder` 只读 S02/S03/S05/S07/S10 的可用 refs 与各领域水位，缺失返回 `STALE_SOURCE / INCOMPLETE_VIEW` 而不是补造状态。
- 保留现有 Run/Step `PolicyDecision` 审计存储语义，不能当成 Mission 用户决定覆盖表。

验收：A 被 B supersede 后只把 B 当现行决定；审查/产物局部决定不会覆盖整个 Mission；已确认事实撤销保留历史；水位落后标记为 stale；不因 resource heartbeat 增加 MissionRevision。

### 4.4 PR-S07-01：SourceDependency / DerivedStateSignature + Snapshot Overlay（依赖 S00-02/03）

验收：旧决定不覆盖新决定、越权记忆 0、无关 Mission 修订不导致全量刷新、旧包兼容但不被误判为可跨版本复用。

### 4.5 PR-S07-02：ExactSource & Critical-First Budget；PR-S07-03：Capsule 版本化（独立后续）

### 4.6 PR-S02-01：Planning Commit / Semantic Patch 正式承诺权威（依赖 S00）

- 保留 `TaskPlan` / `TaskPlanPatch` 与唯一的 `TaskPlanTopologyCompiler`；在现有 `RuntimePlanningCoordinator.boundary()` 形成**Proposal → S02 Commit** 的权威收敛。

- D4 safe-cut 在 HTN primitive 工作与已知依赖上建立 horizon；未知前提/分支截止；调度资源暂不可用时 WAIT/REBIND，不撤销原 Commit。

验收：重复 proposal 不生成重复 Commit；非安全前沿或冲突 CAS 拒绝；实际图物化前可查询 `COMMITTED_NOT_MATERIALIZED`；不支持的 patch 不持久化。

### 4.7 PR-S03-01：Materialize + Activate / Dispatch Fence（依赖 S02）

- 使用既有 ACGGraphCompiler 编译并冻结 Graph Package；独立持久化 MaterializationReceipt、Graph Hash 与 `ACTIVE` 指针，通过 CAS/activationEpoch 更新。
- Scheduler/Executor 只对 ACTIVE Graph 派发；重复 Outbox 投递按 `commitId` 幂等返回；materialized≠active 不派发。
- 先兼容**现有 Full ACG** 模式，完整安全闭环通过后才缩小到 Committed Horizon；减少物化的节点必须有真实计数证明，避免把 Full ACG 改名 Progressive ACG。

验收：Materialize 成功但 Activate 失败不派发、激活 CAS 冲突旧图仍有效、断电后 Outbox 对账收敛、已启动节点前缀不变。

### 4.8 PR-S09-01：Effect/UNKNOWN 最小防重复（必须早于跨 Run 自动继承）

- **不要关闭已有审批、命令白名单和隔离机制。** 复用 `AuditedToolRuntime` 和 ResourceExecutionAdapter 作为受管动作入口；先为 1–2 种真正可控的外部动作实现 Action 级 EffectIntent、状态 CAS、Request Fingerprint、未知结果 WAIT/RECONCILE。
- 相同 effectKey 在不同 Run/GraphVersion 下保持稳定；HTTP Header 只有 Provider 真实支持时才宣称远端去重；无查询/Key 期限过期不盲重发。OPAQUE shell/backend 未受管路径必须标注“无保证”。
- E3 Compensation 可在 V1.5 以后扩充，不要第一轮实现全部补偿业务。

验收：ACK 丢失后不重复外部效果；两个 Worker 同 Key 不能双派发；Provider 没有去重能力时进入 UNKNOWN/用户确认；重启不自动重放不可逆动作。

### 4.9 PR-S03-02：Logical Work Ledger + V1 Successor Run 安全继承

- 稳定 `(missionId, semanticTaskKey, executionGeneration)`；`InheritedWorkReference` 指回源 Run Receipt；不拷贝源 Trace、完成时间或 Side Effect 状态。
- Checkpoint/运行栈以新 Run 冷启动；ReuseAdmission 校验输入/合同/ACL/证据与 Effect Receipt；不符合条件时 REUSE_CONFLICT/NEEDS_REPLAN，绝不默默重跑。
- 现有 `semantic_revision.py` 的全清空策略须受新机制保护，并有跨 Run 源测试；目标投影标明 `INHERITED`（视图）而不是 R2 已执行。

验收：A/B 在 R1 完成，R2 只引用 A/B，新增 D 执行；原外部动作计数不增加；R1/R2 重启对账一致。

## 7. 发布门禁、风险和回滚要求

| 关口 | 必须提供的证据 | 阻断条件 |
|---|---|---|
| Schema | 全新 DB 初始化、既有 DB 迁移、备份/回滚说明 | 迁移覆盖旧任务/历史或破坏 IdentityV2 |
| 单库原子性 | CAS 冲突、重复提交、异常注入、进程重启 | Aggregate 与 History/Outbox 不一致 |
| 领域权威 | 唯一 Mission Semantic Writer、S02/S03 只读 refs | 多处可写正式状态或跨域更新假装原子 |
| 语义质量 | A→B supersedes 保留旧历史；事实准入可追溯 | 历史 Memory 覆盖当前决定 |
| 执行边界 | 未 ACTIVE 不 Dispatch、UNKNOWN 不自动重放 | 新 Graph/Successor 产生双派发 |
| 安全隔离 | 既有 Approval/Local Runtime/Scope/ACL E2E | 提升不透明 Backend 的效果保证或放宽授权 |
| 回归 | 固定基线、差异清单、原有关键测试结果 | 提交成功但 Run/Frontend/Artifact 行为回归 |

**回滚要点**：在 SQLite schema 中采用向前兼容 additive migration 和保留旧读取路径；回退功能开关不应删除新的语义历史或让旧客户端以过时数据覆盖正式状态。数据回滚与代码回滚不同，前者必须有明确的人工/备份策略。S02/S03 新图切换需要 ACTIVE 指针 CAS、旧来源可追溯；不得回放外部 Effect。
