# PR-S00-03：Mission 正式语义创建与编辑入口

日期：2026-10-11。基线 `ea1fc6ba`，`master`，开始时工作区与暂存区干净；单一 worktree。已阅读 S00-01、S00-02A、S00-02B，并按当前代码核实。未提交、推送、部署、修改开关或升级业务数据库。

## 根因与实际修改

原 `agentos_v2.create_mission` 只创建旧 Mission，然后立即 `prepare_run`。没有公开初始化提交，严格模式在 `MissionSemanticResolver.freeze` 拒绝 UNINITIALIZED；失败后只有 Run 级幂等查找，没有 Mission 创建阶段的恢复锚点。Workspace 只能显示语义，没有写入入口。Java 创建 DTO 也拒绝新的字段。

现在的调用链：可信内部认证上下文 → 显式创建合同验证 → WorkflowStore 原子创建/重放 Mission → 既有 Identity 创建投影重放 → 原 MissionSemanticService 初始化提交 → prepare_run 冻结 Basis → 原子首次 Run 保存/重放 → 原 Coordinator.submit。

- `contracts/mission_semantic.py` 抽取共享 Content、Edit Request；不复制提交实现。
- Mission JSON 增加可选 `creationKey`、`creationFingerprint`，旧数据缺省为 None。
- WorkflowStore 增加 `create_mission_once`、`save_prepared_run_once`。SQLite 使用既有表、`BEGIN IMMEDIATE` 与原生命周期 Outbox；Memory 使用既有锁与回滚快照。不是第二套语义提交或状态管理器。
- Runtime/MissionManager 接入上述首次保存；生成 Mission/Run 身份仍用原身份分配入口。
- Python API、Java Mission 网关、TS 合同与 API、Workbench 创建请求构造器、CreateMissionView、MissionEditor、EditorGroup、MissionWorkspaceView 完成接入。
- MissionEditor 保持文档设计，增加目标与逐条约束编辑；保留 constraintId/sourceRefs。未初始化旧 Mission 的表单为空，必须用户显式填写；不从 title/Identity goal 自动填入正式事实。保存后刷新 Workspace，并保留所选历史 Run。
- 创建失败保留同一完整请求和 clientRequestId；编辑失败保留同一 operationId/body，409 要求刷新版本后重新编辑。已发送创建请求的附件不因失败响应被前端自动删除，避免破坏已绑定 Mission。

## 对外合同

Java 根路径 `/api/agentos/v2`，Python 路由根路径 `/agentos/v2`；原上游前缀仍由网关处理。

创建 `POST /missions` 新增可选字段：

```json
{
  "title": "显示标题",
  "clientRequestId": "create-unique-1",
  "semantics": {
    "objective": "显式正式目标",
    "constraints": [{"constraintId": "c1", "text": "显式约束", "sourceRefs": []}],
    "sourceRefs": []
  }
}
```

严格模式要求 semantics；显式语义创建要求非空 clientRequestId。初始化 operationId 为 `create:<现有服务端幂等键>`，expectedMissionRevision=0，复用原 Receipt。202 响应继续使用原 MissionResponse。

`POST /missions/{missionId}/semantics` 为完整替换 Objective/Constraints/sourceRefs：

```json
{
  "operationId": "edit-unique-1",
  "expectedMissionRevision": 1,
  "objective": "新的目标",
  "constraints": [],
  "sourceRefs": []
}
```

COMMITTED/NO_OP 返回 200 与原 SemanticOperationResult；REVISION_CONFLICT/OPERATION_CONFLICT 返回 409 与同一结果合同。调整 expectedMissionRevision 或内容后的 CAS 重试必须使用新 operationId；网络/存储失败重试保持原请求。身份、tenant、Mission ID 来自可信上下文和路径，不接受请求声明身份或冻结 Basis。

读取入口：`GET /missions/{missionId}/semantics`、`GET .../semantics/commits`（items 包装）、`GET .../semantics/receipts/{operationId}`。所有入口重新授权；软删除隐藏公开语义命令、历史与回执，内部保留原历史。提交或创建中断返回可重试错误，不伪造成功提交。

## 保证边界与权衡

1. 同一创建键/指纹返回同一个 Mission；不同请求返回冲突。原子首次 Run 保存防止两个请求竞争时产生重复 Run，且返回已存在快照，不覆盖其 Basis、执行状态或结果。
2. 原语义事务继续原子保存 State/Commit/Receipt/Semantic Outbox。首次 Mission 写入与生命周期 Outbox 同库原子；Run 初次保存沿用原生命周期事件生成规则。
3. Workflow 与 Identity 不是跨库 ACID。失败后需重发相同完整请求，逐步恢复；已提交语义不被补偿删除。Runtime 重建后恢复已有待提交 Run 已验证。没有新增后台自动扫描创建任务或新的跨进程执行租约。
4. Mission 提交与 Run 冻结之间仍有时间窗口；Run 保存的是 prepare 时读取的已提交版本，不宣称创建提交与 Run Capture 是一个事务。之后修改 Mission 不改旧 Run、TaskPlan 或已执行结果，也不自动重新规划旧 Run。
5. 开关关闭时仍走旧创建/执行路径，不产生正式语义；新版创建表单发送显式 semantics 也不会偷偷启用开关。已有无 Basis Run 不回填。缺省旧创建请求指纹保持原序列化合同。
6. 新字段只在已有 JSON payload 中保存，不增加 DDL 或业务数据迁移。启用仍要求事先独立安装 S00-01 schema；本次只在临时测试库显式安装。
7. 创建锚点和幂等 Run 查找使用现有表的 JSON 查询；大规模索引优化可后续显式迁移。物理 purge 会移除对应锚点，沿用原生命周期边界，不提供永久请求键 tombstone。
8. 浏览器创建重试缓存限于当前创建页面；跨页面/刷新后的自动草稿恢复与全局待创建队列未实现。服务端恢复要求客户端保留并重发 clientRequestId/body。执行中断后的 Run 恢复仍遵循现有 Runtime 恢复策略。
