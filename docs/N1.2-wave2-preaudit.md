## D：Feedback 统计与 POST 回执

### 端点与当前实现

| 端点 | Java 响应类型 | 数据来源 |
|---|---|---|
| GET `/api/feedback/user/{userId}/statistics` | `UserFeedbackService.FeedbackStatistics`（Service 内部类） | countByUserId + AVG(rating) + findByUserId 两次分组统计 |
| GET `/api/feedback/statistics` | `UserFeedbackService.GlobalFeedbackStatistics` | count + countByFeedbackType 分组 + AVG(rating) |
| POST `/api/feedback` | `Map<String,Object>` = {message:"反馈已提交", feedbackId} | createFeedback（情绪自动判定，第一波未动） |

### 字段清单（当前 wire）

- FeedbackStatistics：userId(UUID)、totalFeedbacks(long)、averageRating(double)、feedbackTypeCount(**Map<String,Long> 动态键**)、sentimentCount(**Map<String,Long> 动态键**，仅 positive/negative/neutral 三值但键集动态)。
- GlobalFeedbackStatistics：totalFeedbacks、averageRating、feedbackTypeCount(动态键)。
- 动态键来源：`UserFeedback.feedbackType` 为自由 String 列（length=50，注释建议 quality/relevance/helpfulness/other 但**无枚举/无校验**，POST body 直接透传），自定义分类是真实输入而非假设。
- 空统计现状：无数据时 totalFeedbacks=0、averageRating=0.0（Service 把 null AVG 改写为 0.0——注意这是**既有行为**：null → 0.0 的"伪造零值"在投影时必须原样保持还是显式区分，需要批内决策并记录）、两个 count Map 为空 Map（`{}` 非 null）。

### 消费者

**零前端消费者**（services/api 无 feedback 声明、全仓无 `/api/feedback` 引用；第一波已复核）。后端无其他调用方（仅 Controller 使用）。

### 兼容冲突评估

**无阻断冲突**。wire 形状变化（Map → typed 列表）没有任何现有消费者受影响。设计要点：分类计数用 `List<CategoryCountQuery(String type, long count)>` 承载动态键（保序：按计数降序或键字典序需批内定案并写入迁移记录）；自定义分类不能丢失（typed 列表天然逐键保留）；averageRating 保留既有 0.0 语义并在 DTO 注释说明；POST 回执单独评估（两个 String 字段，typed ReceiptQuery 成本极低）。

## E：Mission Workspace

### 端点与调用链

GET `/api/agentos/v2/missions/{missionId}/workspace?runId=`：AgentOsObservationController#getMissionWorkspace（Map 透传）→ Python `agentos_v2.py#get_mission_workspace`（identity `MissionWorkspaceProjector` + workflow_store 运行状态合并 + deferred-run 回退构造 + TASK entry 的 outputRef/outputSummary 注入）。

### 字段清单（Python wire，`exclude_none=True`）

信封：mission、activeRun?、activeGraph?、runs[]、entries[]、graphNodes[]、inputAttachments[]、diagnostics[]。

- **mission** = 完整 Mission 领域模型：missionId、**userId**、goal、description、**metadata(dict)**、createdAt、updatedAt、status。mission.metadata 前端零读取（WorkspaceMission TS 声明但视图未用）；userId 属 owner 身份（详情/列表批先例=删）。
- **activeRun/runs[]** = WorkspaceRunSummary：runId、status、parentRunId?、sourceRunId?、createdAt、completedAt?、isActive（注释明确"never embeds execution state"——已是干净投影）。
- **activeGraph** = `dict[str, Any]`（动态），TS 侧声明为 GraphProjection（nodes/edges）。**前端重度消费**：MissionWorkspaceView、EditorGroup、RunProgressEditor（blueprint、edges、拓扑图全走它）。与第一波已有 `GraphProjectionMapper`/`GraphQuery` 投影（847e0183 批）对应——E 批应复用而非新造；需在批内核对 Python workspace 的 activeGraph 键与 `/runs/{id}/graph` 的图 wire 是否同构。
- **entries[]** = WorkspaceEntry：约 35 个显式键（entryId/kind/name/group/title/parentEntryId/displayOrder/semanticTaskKey/artifactKey/taskId/logicalRole/objective/dependencyKeys/attemptCount/latestAttemptId/artifactCount/artifactId/contentRef/artifactType/mediaType/checksum/attemptId/acgNodeId/disposition/sourceRunId/identityQuality/createdAt/runId/status/blueprintId/graphId/graphVersion/parentRunId/completedAt/isActive/content/**metadata(dict)**)。三个生产来源：TASK entry metadata={runtimeStatus,parentTaskId}；ARTIFACT entry metadata=**dict(artifact.metadata) 全量**（含 logicalRole 及其他生产者键——需在批内枚举 artifact.metadata 的全部写入者）；路由再向 TASK entry 注入 metadata.outputRef/outputSummary。
- **graphNodes[]** = WorkspaceGraphNode（9 键，全部公开导航字段）。
- **inputAttachments[]** = InputAttachment model_dump，已 exclude {owner_user_id, owner_tenant_id, **storage_key**}（上游已做一轮脱敏，Java 侧需白名单对齐 TS `InputAttachment` 类型）。
- **diagnostics[]** = {code,message,severity(info|warning),details(dict)}；details 动态（PLANNING_PROJECTION_PENDING 注入 runtimeStatus/lifecyclePhase/errorCode）。

### 消费者（前端实读证据）

- MissionWorkspaceView.vue + components/workspace/*（RuntimeInspector、TaskEditor、EditorGroup、RunProgressEditor）。
- **entry.metadata 前端实读键：`outputRef`**（RuntimeInspector.vue:254、TaskEditor.vue:69-70）。outputSummary 在 workspace 视图未直接读 entry.metadata.outputSummary（相关读取来自 ACG 视图的 step state，另一数据源）；runtimeStatus/parentTaskId 未发现读取。→ 白名单最小集 = outputRef；outputSummary 属路由刻意注入的展示摘要，建议保留并记录依据。
- mission.metadata、mission.userId：零读取。
- diagnostics.details：动态 dict，前端 severity 只用 info/warning（TS 声明含 error 但 Python 仅产出 info/warning）。

### 兼容冲突评估

1. **entries[].metadata 是动态 dict**：白名单化（outputRef/outputSummary/runtimeStatus/parentTaskId + artifact.metadata 待枚举）与"保持已有 wire 形状"可并存——未被读的键删除前需按"每个删除字段有内部数据或无公共消费依据"留证。**artifact.metadata 全量透传是唯一需要深挖的点**：须枚举 RunArtifact 写入 metadata 的所有生产者（logicalRole 已提升为 entry 一等字段）才能定白名单；如发现 binding/provenance 类内部键，删除即安全，如发现前端间接依赖（如 TaskEditor 的 artifacts.value[].metadata.outputRef——注意该读取对象是 entry 列表）则保留。
2. **activeGraph 是 dict 透传**：符合"复用已有 Graph 投影"路径，GraphQuery 已是 typed 闭包；若两处图 wire 不同构（workspace 的 activeGraph 可能含 blueprint 专有键），需在批内给出差异表。
3. 生成正文（entry.content 虚拟文档）为用户可见正文，禁止投影层清洗；内部控制数据只可能经 metadata 混入，正文本身按"公开文档内容"处理。
4. 错误路径已走既有 QueryError 规则（同 detail/history/list）。

## F：Artifact 元数据（列表/详情/fragments）

### 端点与当前实现

| 端点 | Java | Python wire |
|---|---|---|
| GET `/runs/{runId}/artifacts` | Map 透传 | {runId, items[], total}；identity 命中时 items=project_identity_artifact 合并投影，否则 ContentManifest model_dump |
| GET `/runs/{runId}/artifacts/{manifestId}` | Map 透传 | **三模型合并 dict**：ContentManifest(10 键) + Artifact(16 键) + RunArtifactBinding(9 键) 平铺 + manifestId 覆盖 |
| GET `/runs/{runId}/artifacts/{manifestId}/fragments` | Map 透传 | {manifest(=详情), items[], nextCursor}；items=ContentFragmentRef(10 键)+content(UTF-8 decode) |
| GET `.../download` | `ResponseEntity<byte[]>`（二进制+Content-Disposition） | 字节流 |

### 字段清单要点

- 详情合并平铺键（三模型 + 覆盖）：manifestId、kind、ownerType、ownerId、mediaType、checksum、byteLength、fragmentCount、estimatedTokens、chunkingVersion、sealed、createdAt(manifest)、artifactId、missionId、originRunId、taskId、semanticTaskKey、artifactKey、acgNodeId、producerAttemptId、name、artifactType、contentRef、checksum/artifact 侧、createdAt(artifact，**与 manifest.createdAt 同名冲突——合并时后者覆盖前者**，现状行为须保留或显式定案)、metadata(artifact 动态 dict)、bindingId、runId、disposition、sourceRunId、createdAt(binding，第三次同名覆盖)。
- **内部键候选**：ownerType/ownerId（存储归属）、bindingId（内部绑定标识）、chunkingVersion（内部版本）、verificationStatus/sourceRefs/constraintRefs（fragments 溯源内部引用）——计划第 6 节要求隔离物理存储路径/凭据/binding；**未发现物理路径字段**（storage_key 已在 manifest 层不存在，inputAttachments 侧已被上游 exclude）。
- fragments：cursor/pageSize 定位 + nextCursor 翻页 + 顺序（sequence），Mapper 不得重写。

### 消费者（前端实读证据）

- **列表端点 `/artifacts`：前端零调用**（services/api 无 listArtifacts；全仓无引用）。
- **fragments 端点：前端零调用**（getArtifactContent 改走 /download blob 流式拼装，注释明确"avoids one JSON request per fragment page"）。
- **详情端点：ArtifactEditor.vue**（getArtifactDetail；实读 mediaType、manifestId、byteLength，spec 佐证；TS ArtifactDetail 声明约 19 键）。
- **download：getArtifactContent/downloadArtifact（blob）**——二进制输出属计划明确豁免，不改实现。
- `/outputs/{outputRef}` 与 `/legacy-outputs` 属第三波 H 批，不在 F 范围。

### 兼容冲突评估

1. **"禁止动态容器"与"保持 wire 形状"的真实冲突点在详情端点**：现状是三模型平铺合并（含 createdAt 三重同名覆盖的顺序语义）。typed DTO 若按计划"三种 typed 输出"拆开（manifest/artifact/binding 嵌套），会改变平铺形状——唯一活跃消费者 ArtifactEditor 只读 3 键且详情端点有消费，**嵌套化是 wire 破坏性变化，存在真实消费者**。可行方案：(a) 保持平铺键集做 typed record（同名覆盖顺序显式固定并测试）；(b) 与前端同步改（跨端两笔提交）。按计划"先明确消费者兼容迁移方案"，建议 (a) 起步并在批内登记 createdAt 覆盖语义。
2. 列表/fragments 无消费者 → 自由度最大，但 fragments 的 cursor/顺序契约仍须按计划逐字保留（零消费者≠可重写定位语义，公共契约不变）。
3. artifact.metadata（详情内）动态 dict 同 E 的枚举需求。
