# SAFE阶段交付：Qwen2 双角色 KV 逐 token 续算

日期：2026-11-14。范围：在既有 Qwen2 FP32/eager 无 KV 基线上，为 prefix 和 suffix 增加独立进程内缓存句柄，并检查真实模型逐 token decode 数值。该阶段不实现网络、认证、云端 API、完整会话装配或差分隐私。

## 实现

- 使用 Transformers `4.46.3` 的 `DynamicCache`，不自定义或序列化 KV 格式。
- prefix 缓存 embedding 后本机层的 K/V；suffix 缓存云端层的 K/V。两个 runner 各自创建随机不透明句柄，句柄绑定调用方提供的 session ID。
- prompt prefill 只允许填充空缓存；decode 必须从当前缓存长度继续，逐 token 更新 `cache_position`、RoPE 位置与 causal mask。
- prefill/decode 输入受 manifest 的 `max_context` 限制；非法 token、shape、非有限激活、错会话句柄、乱序和已释放句柄均拒绝。
- 释放幂等，并等待同一句柄的前向完成后清空缓存张量。runner 关闭会释放其所有本地句柄。
- 原有不带句柄的 `prefill` 保留为无 KV 数值基线；原文和 token ID 仍只交给 prefix，跨角色边界只有激活数据。

## 验证

环境：仓库锁定的 Windows x64 / CPython 3.10、Torch `2.11.0+cpu`、Transformers `4.46.3`、CPU FP32/eager；使用本机已存在、revision 固定的 `Qwen/Qwen2.5-0.5B-Instruct` 权重和角色制品，无网络下载。

- 合成 Qwen2：prefix/suffix 的 prompt prefill 以及3个连续 token decode，逐步对照完整模型，全部 logits 通过 `atol=1e-5, rtol=1e-4`，greedy 一致。
- 真实模型：20条合成中英文输入，每条16个 logits/decode 检查，共320步；使用完整模型自己的 `DynamicCache` 作为 oracle，greedy `320/320` 一致，最大绝对误差为 `0`，使用 `atol=1e-5, rtol=1e-4`。端到端脚本总耗时约41.8秒，包含加载模型和tokenizer；该数值不是纯推理延迟或性能对照结论。
- 另有诊断显示，把 split KV 与“每步无KV全序列重算”直接比较时，真实模型最大绝对差约 `3.72e-5`，但 greedy 仍全部一致。这是缓存和全序列计算的矩阵形状/浮点归约差异，不能与同缓存 oracle 的正确性混为一谈；无KV基线报告继续单独保留。
- 真实模型 prefill 的最大绝对误差为 `0`，两条样本均 greedy 一致。
- 模型测试：`python -B -m pytest tests/safe/models/test_qwen_prefill.py -q -p no:cacheprovider`，`12 passed`。
- safe 测试：`python -B -m pytest tests/safe -q -p no:cacheprovider`，`54 passed`；模型分区回归 `4 passed`。

## 边界和后续

这证明固定 CPU FP32/eager 配置下单进程中两个独立角色的 KV 数值续算。它没有验证两台机器之间的传输、签名/nonce、云端 owner 授权、runner 崩溃恢复、并发取消、OOM 清理或吞吐提升。Qwen2 的动态缓存每步会拼接 K/V 张量，本次也没有形成性能基准；性能优化须在正确性报告之外单独测量。

下一步先把 prefill/decode 与会话 step、采样回执串为可注入用例，确保计算成功后回执提交失败会使两端会话都终止并释放缓存；再实现受认证的远端 suffix transport。完整20条样本×32 token、真实网络和故障注入仍是 P3/P2 后续验收。
