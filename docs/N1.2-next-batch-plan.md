# N1.2 后续批次操作计划

日期：2026-10-01。本次仅修正已交付批次，以下内容是后续执行指南，尚未实施。

## 1. 下一批：收口 Search 的 Message 查询出口

原因：历史查询已经采用 MessageQuery，但 Search 两个出口仍返回同一个 Message Entity，可能携带 role_context 等内部 metadata。复用现有白名单 Mapper 即可关闭这一旁路，变更范围最小。

范围仅限 SearchController 的 GET `/search/messages`、GET `/search/all-messages`、相关测试与守卫登记、迁移记录。不创建新的 DTO、空 Application Service；不修改 SearchService、Repository 或数据库查询。

操作顺序：

1. 核对 HEAD、全部工作区修改和现有调用方。当前前端 API 声明在 `apps/frontend/src/services/api/search.ts`；执行时重新检查实际消费者，逐项记录旧字段、新字段、消费位置。若发现依赖被排除的 metadata，先给出具体冲突，不能直接扩展历史白名单。
2. 两个成功响应改为 `ResponseEntity<List<MessageQuery>>`，对既有 Service 结果调用 `MessageProjectionMapper.toQuery`。contextId 缺省时仍返回空列表；现有关键词匹配、结果顺序、跨会话 200 条上限、身份获取、属主检查、400/404 与错误格式保持。
3. 同步删除这两条 Entity 例外，并把 Search 两个 handler 纳入严格输出检查。已有 Message 全局禁令保持；不能把例外换一个名字继续保留。
4. 增加 Controller 契约测试：有/无 contextId、空结果、关键词匹配、返回顺序、未认证、他人会话；验证跨会话查询仍传递当前认证身份与原关键词。敏感请求头不能替换当前身份。
5. 响应序列化确认 DTO 与 15 键白名单、正文完整、时间格式、异常数值 null 策略。复用已有 Mapper 边界测试，不复制同一套数值测试。
6. 运行相关测试及后端 `mvn clean test`。核对 API 层无 Entity/内部 metadata；重建 backend 后以既有会话进行授权范围内的查询验收，避免创造新的 Runtime Run。若有活跃前端消费者，验证真实搜索流程；没有消费者则如实记录 API 验收，不虚构 UI 验收。
7. 显式暂存该批文件，检查 staged diff 后提交 `projection(search): close message query entity exceptions`，不 push。Controller 迁移与删除例外同笔提交，避免中间提交被守卫判失败。完成后保存审计证据，按第四节的波次安排继续。

交付证据：提交号、字段兼容表、相关及全量测试结果、部署/实际 API 验收结果、例外集合变为零的证据、工作区剩余并行改动。回滚按提交依赖倒序，不放宽守卫。

## 2. 再下一批：Feedback 输出边界

先单独审计 UserFeedbackController 的 GET `/api/feedback/user/{userId}`、`/user/{userId}/statistics`、`/statistics`，以及 POST `/api/feedback` 的响应回执。查询目前分别返回 UserFeedback Entity 与 Service 内嵌统计对象。

DTO 显式声明字段，Mapper 只读现有结果；不改提交反馈命令、sentiment 计算、评级计算或权限。统计包含动态分类计数 Map，应先核对生产键与消费者；自定义分类不能静默丢失。可设计 typed 分类计数列表，但若改变 wire 形状，必须先明确消费者兼容迁移方案，不能套用 Role 自由 JSON 例外。

先迁移反馈列表，再迁移统计/回执；每笔提交保持编译测试通过并同步收紧对应守卫。新增 Entity 禁令、统计字段闭包与空统计契约测试，避免为纯构造 DTO 添加重复测试。

## 3. 随后回到 Workbench 核心查询

优先审计 AgentOSMissionController 的 GET `/api/agentos/v2/missions` 与 AgentOsObservationController 的 GET `/api/agentos/v2/missions/{missionId}/workspace`。它们当前仍透传 Map。

沿 Java Controller → Client → Python API → 查询模型核对实际字段与前端读取；复用已有 Mission/Run/Graph 投影。Workspace 要明确文档、目录、图与 Artifact 引用的输出白名单，尤其检查生成文本中是否嵌入内部 metadata，不能只把原始 JSON 包装为 String。

列表与 Workspace 分批设计、分批迁移、分别浏览器验收。Runtime/Entity/Python wire model → 纯 Mapper → Stable DTO 仅用于输出；不得改 Runtime Kernel、Python domain model、Scheduler、Checkpoint Store、数据库、权限或业务流程。Trace/Memory/Provenance/Resource Usage 与动态 `/ai/**`、SSE 留到后续独立批次。

## 5. 第一波的具体实施要求

### B：Feedback 列表

只读 UserFeedbackService 的既有结果，显式声明 id、用户/会话/消息/角色引用以及反馈内容、类型、评分、情绪和时间等实际公共字段；最终字段集合由当前 Entity 与消费者核对确定，不能凭本计划猜测 wire 名。

禁止顺手修改 URL 中 userId 的权限语义、反馈写入或情绪判断。测试通过原身份链路核对 Service 实参与当前状态码，安全或权限历史问题另行登记。成功响应、错误响应与空列表分别验证。该批不扩大到 Service 的统计内部类。

建议提交：`projection(feedback): migrate feedback list query responses`，Controller、DTO、Mapper 与对应守卫同笔落地。

### C：Mission 列表

沿现有 AgentOsClient 调用读取 Python wire 数据，Mapper 只做输出适配。复用已存在的 Mission 字段规则，保留标识、标题、公开状态、时间及消费者确实使用的摘要；核对真实列表 envelope、分页信息、空列表与归档过滤。不得把 metadata/constraints 全量打包为 Map 或 JSON String，也不能将内部 TaskPlan、binding 或 checkpoint 加入列表项。

上游非 2xx 的 status 与错误 JSON 必须走已有错误规则；不要把错误响应当作成功列表解析，亦不把异常数据伪造成零、成功或空列表。沿用现有 QueryResponse/QueryError 方案时补对应契约测试。

建议提交：`projection(mission): migrate mission list query responses`。使用既有 Missions 页面核对列表、分页/过滤和进入详情流程；没有真实数据时如实登记验收未完成。

## 6. 第二、三波需要先解决的边界

- Artifact：保留公开 id、文件名、媒体类型、大小、校验值与合法引用；是否公开来源摘要须依据消费者。禁止暴露物理存储路径、存储凭据、原始 binding 或完整内部 provenance。fragments 的 cursor、pageSize、顺序、文本不能被 Mapper 擅自重写。`download` 维持二进制输出，不改存储与下载实现。
- Workspace：公开文档内容与内部配置要按来源区分，不能为了清除字段而删改用户正文。系统生成说明若嵌入控制面数据，应先评估消费者与查询层可行性，禁止改 Runtime 内容生成业务来配合投影。
- Trace/Memory：定义事件 id、类别、时间、公开摘要与公开引用；禁止 raw event 整体 model dump，禁止把调度器状态或原始提示词放入通用 payload。任意用户文本不能简单用敏感词过滤替代字段白名单。
- Provenance：输出公开 Artifact/Run/任务引用关系；隔离底层路径、binding 与完整运行上下文。公开关系不足时记录字段需求，不透传内部对象。
- Checkpoints：路径保持，但公共输出只能是恢复点标识、时间、公开状态等经审计允许的摘要，不能返回内部 checkpoint 数据。若消费者正在读取内部内容，应记录冲突并先给出兼容设计；不删接口，不改 Checkpoint Store。
- Resource：区分目录/健康观察与实际文件内容读取，保持当前授权与可访问路径逻辑。资源查询 DTO 不参与资源注册、执行绑定或缓存状态维护。
- SSE 与动态代理：先盘点事件名称、顺序、完成/错误/取消语义、断线行为及消费者。稳定事件采用独立 typed event DTO；二进制 `Resource`/`byte[]` 与 typed SSE 容器可作为明确豁免。不能只把 Flux 的元素命名为 Event 就豁免其内部动态 payload。

## 7. 所有批次共用的执行与验收规则

1. 每批开始重新核对 HEAD、工作区与消费者；不覆盖 Landing 等并行改动，不将两份既有未跟踪审计/计划文档顺带入库。
2. 写清 endpoint → Controller → Service/Gateway → Client/Python wire → Mapper → DTO → frontend consumer。每个删除字段有内部数据或无公共消费依据，每个兼容变化有旧/新字段表。
3. DTO 显式字段，不继承内部模型，不使用 Map/Object/JsonNode、copyProperties 或 convertValue。Mapper 不调用 Repository、Service、Runtime，不写缓存或状态。
4. 每笔代码提交运行相关测试；批次收尾执行 backend `mvn clean test`。前端受影响时跑相关测试、类型检查与生产构建；没有前端改动时不为凑证据重复全量构建。纯文档提交做 diff 检查即可。
5. 测试优先验证真实风险：响应闭包、敏感字段不可达、错误格式、身份与 Service 实参、数据顺序/分页、缺失与异常类型、消费者读取。复用公共边界测试，不为每个 DTO getter 或构造赋值重复造测试。
6. 完成批次代码后重建 backend 并验收实际 API；有活跃 UI 消费者时执行真实浏览器流程。优先用既有数据，避免产生有费用或副作用的新 Run。构建/单元测试与实际部署/浏览器结果分别报告。
7. 守卫以实际 handler、完整方法和路由、返回类型闭包为依据。逐批登记迁移完成的严格 handler；未来待迁移项必须精确登记，不能扩大 controller 级豁免。Role 的可扩展配置例外保持原槽位。
8. 显式路径暂存，执行 `git diff --cached --check` 并核对暂存清单；不 push。提交间依赖写进迁移记录，回滚倒序并只指定仍存在的测试。

每波交付统一报告：各批提交号、接口清单、字段兼容/删除依据、守卫覆盖与剩余例外、测试通过/失败/未执行、部署和浏览器证据、遗留问题、工作区并行改动，以及下一波是否具备实施条件。不能将第一波通过写成 N1.2 全部完成。
