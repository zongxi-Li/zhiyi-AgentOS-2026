## 一、批次 A：Search 两个 Message 查询出口

### 端点与调用链

| 端点 | Controller → Service | 旧响应 | 新响应 |
|---|---|---|---|
| GET `/search/messages?keyword=&contextId=` | SearchController#searchMessages → ChatService#getHistory(contextId, userId) 内存过滤 | `List<Message>` Entity（含全量 metadata jsonb） | `List<MessageQuery>`（复用既有 Mapper） |
| GET `/search/all-messages?keyword=` | SearchController#searchAllMessages → SearchService#searchMessages(userId, keyword)（200 条上限在 Service） | `List<Message>` Entity | `List<MessageQuery>` |

### 字段兼容表

行级字段与 GET `/chat/history` 迁移完全一致（id、conversationId、role、content、messageType、fileUrl、metadata、createdAt；metadata 15 键白名单 + 精确数值策略原样复用，未复制新的数值测试）。变化仅一点：搜索出口不再可能携带 role_context/sources 等内部 metadata 键。

### 消费者核对

前端 `apps/frontend/src/services/api/search.ts` 声明了 searchMessages/searchAllMessages，但全仓 grep 确认**零调用**（无任何视图/store 引用 searchApi）。因此本批**只做真实 API 验收，无 UI 验收**（如计划第 1.6 条要求，不虚构）。

### 行为保持

contextId 缺省/空串 → 空列表且不触碰两个 Service；关键词大小写不敏感包含匹配；结果顺序 = Service 返回顺序；未认证 → 400（单元测试覆盖；经网关时 JWT 过滤层先回 401，为部署层既有行为）；身份只认 SecurityContext（X-User-Id 已被 SensitiveIdentityHeaderFilter 剥离，StrippedIdentityHeaderBoundaryTest 既有覆盖 + 新测试在投影语境复证）。
