## 三、metadata 白名单依据

**方法**：先枚举三个持久化生产者写入的全部键，再对照历史链路唯一消费者 `stores/chat.ts loadHistory` 实际读取的键，取交集；生产但无历史消费者的键不再进入响应（仍照旧持久化，不影响写入链路）。

**生产者**（apps/backend/src/main/java/com/kinlin/ai/service/）：

- ChatService.sendMessage（非流式）：role_context、confidence、tokens_used、sources、reasoning_path
- ChatStreamPersistenceService.StreamCapture（流式）：inputTokens、reasoningTokens、outputTokens、totalTokens、latencyMs、requestedModel、effectiveModel、requestedThinkingMode、effectiveThinkingMode、effectiveReasoningEffort、resolutionReasons、toolsUsed、thinkingEnabled、fallbackUsed、toolExecutions（callId/toolName/status/durationMs/inputSummary/outputSummary/sourceRefs/errorCode）、sources（citationId/title/filename/url/snippet/provider/retrievedAt）、executionSummary（stage/status/description）、reasoningPhaseMs
- AgentConversationPersistenceService：agent_mode

**白名单（15 键，全部有 loadHistory 消费证据）**：

confidence、tokens_used（@JsonProperty 保留蛇形名）、totalTokens、effectiveModel、model_info（遗留兼容键，loadHistory:794 fallback 读取）、requestedThinkingMode、effectiveThinkingMode、effectiveReasoningEffort、reasoningPhaseMs、inputTokens、reasoningTokens、outputTokens、latencyMs、thinkingEnabled、executionSummary（typed `ExecutionStageQuery{stage,status,description}`，三值皆 String）。

**排除键与理由**（仍持久化，仅不再出现在历史响应）：

- role_context：完整角色上下文（含 system_prompt），典型内部数据；无前端历史读取。
- sources、reasoning_path：loadHistory 不映射；MessageBubble 的 sources/reasoningPath 仅来自实时 POST /chat/text 与 SSE 响应，不来自历史接口。
- agent_mode、toolExecutions、toolsUsed、fallbackUsed、resolutionReasons、requestedModel：无历史消费者；SSE 实时链路消费的是流事件 data，不经过本接口。

**类型策略**：数值键做精确整型映射——固定宽度整型直取；BigInteger/BigDecimal 走 `longValueExact()`（小数或越界抛 ArithmeticException → 置 null）；float/double 仅在有限、数学整数且落在 long 范围内时取值，否则置 null。confidence 为 Double，仅要求有限（NaN/Infinity → null，防止 Jackson 把非有限数写成 `"Infinity"` 字符串）。字符串/布尔键要求精确类型；类型不符的值按"缺省"处理（该字段为 null），不臆造、不抛错——这些字段在前端全部经可选链读取，省略与 null 行为等价。metadata 为 null/空 Map 时投影为 null。

**结论**：未发现保留业务流程依赖被排除键的情况，无需要上报的冲突样例；未扩散 Role 自由 JSON 例外（MessageMetadataQuery 为显式字段 record，无 Map/Object/JsonNode）。

## 四、DTO 实现约束的落实

- DTO 显式声明字段，不引用 Entity 与 Entity 内嵌枚举（MessageRoleQuery/MessageTypeQuery 为公共枚举，按 name 映射，wire 值不变）。
- 无 Map、Object、JsonNode、copyProperties、convertValue、通用 JSON 树；无把内部 JSON stringify 藏入 String。
- Mapper 仅读取既有结果构造 DTO：不查库、不调 Service/Repository/Runtime、不写缓存、不改 Entity（守卫测试按源码扫描强制）。
- 认证身份获取（AuthenticatedUser）、owner 校验（requireUserId/ResourceNotFoundException 语义）、workspaceMode 过滤、消息顺序、时间格式、正文与 fileUrl 行为全部保持。

## 五、统一守卫（QueryProjectionArchitectureTest，批次 3）

- Conversation/Message Entity 加入全局禁令（含嵌套，同 User/Role 既有规则）。
- 严格输出检查（禁 Map/Object/JsonNode/开放序列化等）针对已迁移 handler：ConversationController 全部、ChatController#getHistory；UserController/RoleController 维持既有严格。
- 负例扩展：List\<Conversation\>、List\<Message\>、嵌套 Message 的 record、Map<String,Object> metadata 容器，均在同一守卫函数上断言抛错，未复制第二套守卫。
- 例外登记制（修正批收紧）：`SearchController#searchMessages`、`SearchController#searchAllMessages` 仍返回 `ResponseEntity<List<Message>>`（不在本批 5 个接口范围内，待其独立批次）。例外不是按名跳过：每条例外钉住**精确的 GET 路由与返回类型全名**，handler 迁移成 DTO（例外失效）、改返回其他 Entity（例外扩大）、改路由/改 HTTP 方法均会 FAIL；例外 handler 内仍执行 User/Role/Conversation Entity 禁令。守卫另断言登记集合与实际存活 handler 严格相等，防止静默漂移与过期残留。负例 `registeredExceptionsRejectExpansionStalenessAndRouteDrift` 固化这三类失效方式。

## 八、回滚说明（依赖倒序，非任意单笔 revert）

四笔提交存在依赖关系：守卫提交 `abc5b564` 禁止 Conversation/Message Entity 出现在任何 Controller 响应闭包中，因此**在保留守卫的前提下单独 revert `b2fb16ad` 或 `c758be0e` 必然使守卫 FAIL**——这是守卫按设计工作，不是可以绕过的障碍；不得通过删除守卫、放宽禁令或扩大例外登记来实现"独立回滚"。修正批（守卫例外登记制与数值精确化）在守卫之上，同样依赖 `abc5b564` 先行回滚。

正确回滚顺序与复验步骤（依赖倒序，每步后必须复验）：

1. `git revert <修正批提交>`（若有）→ 复验：`mvn test -Dtest=QueryProjectionArchitectureTest,MessageProjectionSerializationTest`。
2. `git revert abc5b564`（守卫）→ 复验：守卫测试回退为 User/Role 版本仍须通过（`mvn test -Dtest=QueryProjectionArchitectureTest`）。
3. `git revert c758be0e`（chat history，GET /chat/history 回到 Entity 响应）→ 复验：`mvn test -Dtest=ChatProjectionControllerTest,ChatControllerTest`（此时 ChatProjectionControllerTest 若仍断言 DTO 需一并回退，属同笔提交内容）。
4. `git revert b2fb16ad`（conversation，四接口回到 Entity/Map 响应）→ 复验：`mvn test -Dtest=ConversationProjectionControllerTest,ConversationServiceTest`。

任一步守卫或契约测试失败，说明回滚顺序错误或漏回滚依赖，应恢复该步而不是修改守卫。全量回滚完成后 `mvn clean test` 应恢复基线全绿。前后端契约方面：所有 DTO 的 JSON 形状与旧响应按字段逐一对齐，唯一语义变化是历史 metadata 不再包含未消费的内部键（前端无可达读取路径）与数值键不再接受非精确值（缺省为 null），回滚后旧形状即恢复。
