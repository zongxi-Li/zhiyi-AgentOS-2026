# 动态并发与统一数据源设计

> 日期：2026-09-06
> 背景：mission_6f817aea5352 三次运行全部失败（模型供应商 429 限流），且三次 Run 在任务工作台只显示两次。本文给出两个问题的根因定位与设计方案。
> 关联：`ops/scripts/backfill_identity_runs.py`（存量数据补账，已执行）；执行期模型超时 120s 见 `agent/app/execution/model_runtime.py`。

## 一、现状与根因（证据）

### 1.1 并发链路现状

一次 ACG 节点的模型调用自外向内经过四层：

```
执行器超步（executor/graph.py:447 astream）
  └─ 节点任务 asyncio.Task，整组并行，无节点级重试
      └─ GuardedModelRuntime（runtime/workflow_runtime.py:2346，ACG 绑定路径）
           retries=2, retry_delay_seconds=1.0（固定）, max_concurrency=AGENTOS_MODEL_MAX_CONCURRENCY
           └─ RegisteredModelRuntime（adapters/model_runtime.py）
                只在多候选适配器间 failover，不做时间退避
                └─ OpenAI 兼容适配器 → HttpJsonTransport（adapters/http_transport.py:294）
                     429 → MODEL_RATE_LIMITED，丢弃 Retry-After 等响应头
```

两个并发口互不知晓：

| 环节 | 环境变量 | 默认 | 语义 |
| --- | --- | --- | --- |
| 模型信号量 | `AGENTOS_MODEL_MAX_CONCURRENCY` | 4（`.env.windows` 当前 2） | 单实例在途模型调用上限（`_CallGate`） |
| ACG 节点线程池 | `AGENTOS_ACG_MODEL_MAX_CONCURRENCY` | 2 | `GatewayStructuredGenerationRuntime` 的工作线程数 |

### 1.2 本次失败的根因

事故链（ai-service 日志 2026-09-06）：

1. 10:50:54 run_2f27adbcd271 发起；10:56:17 `POST /api/paas/v4/reader → 500`（GLM web reader 旁路工具，无独立退避）。
2. 10:59:43 主模型流式调用收到 `429 Too Many Requests`。
3. 429 在 GuardedModelRuntime 层属可重试码（`_RETRYABLE_CODES`），但重试预算是 **2 次 × 固定 1s/2s 退避**，三次尝试在约 3 秒内打完；GLM 侧限流窗口是分钟级，重试全灭。
4. 节点抛出异常后，执行器超步按 fail-fast 语义取消同批 4 个兄弟节点（`executor/graph.py:485-527`），整个 run 判失败：`ACGSuperstepError: failed=native_general_agent_12, cancelled=...`。

结论：**静态并发 + 秒级固定退避，扛不住分钟级供应商限流窗口；且限流被当成节点失败向上传播，放大为整组取消**。

### 1.3 三次 Run 只显示两次的根因

Run 列表存在两个数据源：

- **运行时存储** `workflows.sqlite3.runs`：所有 Run 的权威执行记录（全局运行索引、`GET /runs` 读这里）。
- **身份图投影** `identity_v2.sqlite3.workflow_runs_v2`：任务工作台（workspace）、任务历史（`GET /missions/{id}/runs`）的权威读模型。

正常链路：`save_run` 写运行时行 + outbox 事件 → `_flush_identity_outbox`（workflow_runtime.py:1458）由 `IdentityProjectionReconciler` 消费事件写入身份图。

缺口：`start()` 中 `if is_acg and not defer_acg_planning: _flush_identity_outbox()` —— **延迟规划的重跑跳过投影 flush**；且该场景下 Run 若在规划编译完成前失败（run_d937396b3438 即如此：manual_rerun + planningDeferred，14:54 因 "TaskPlan contains capabilities without an Agent binding" 失败），**连一条 outbox 事件都不会产生**。对账器（reconciliation.py:217）只能重放已有事件，无事件即无自愈。于是运行时 3 条、身份图 2 条，工作台永远少显示一条。

## 二、方案 A：动态并发（模型调用层）

### 2.1 目标

- 429 不再放大为节点失败：把供应商限流当作**容量信号**而非错误。
- 并发度随供应商反馈自适应，无需人工盯着改 `AGENTOS_MODEL_MAX_CONCURRENCY`。
- 静态配置保留为硬上限（`max`），动态窗口 `[floor, max]`。

### 2.2 核心设计：AdaptiveCallGate（改造 `_CallGate`）

在 `adapters/guarded_model.py` 内演进 `_CallGate` → `AdaptiveCallGate`，保持"同一实例内限流、不同模型实例不互相阻塞"的既有语义：

```
状态：in_flight(当前并发许可数), floor, max, success_streak, cooldown_until

成功路径（调用完成且非 429）:
    success_streak += 1
    每 连续 K 次成功（默认 K=8）: in_flight = min(in_flight + 1, max)   # 加性增

429 路径:
    in_flight = max(floor, max(1, in_flight // 2))                      # 乘性减
    cooldown_until = now + backoff
    backoff 退避序列: 2s → 4s → 8s → … → 上限 60s（指数 + 抖动 ±20%）
    若响应带 Retry-After: cooldown_until = now + max(Retry-After, 1s)    # 见 2.3

许可发放:
    acquire 前: if now < cooldown_until: sleep(cooldown_until - now)
    之后按 in_flight 信号量发放
```

要点：

1. **退避预算与重试预算解耦**。现状 retries=2、delay=1s 固定；改为 429 专用退避（2s 起步、×2、60s 封顶、带抖动），重试次数上调为可配置 `AGENTOS_MODEL_RATE_LIMIT_RETRIES`（默认 5）。分钟级限流窗口需要的是"等得起"，不是"试得多"。
2. **闸门状态全局生效**。`cooldown_until` 对所有等待许可的调用共享，避免重试风暴（N 个节点各自重试等于放大 N 倍压力——这正是本次 cancelled=4 的诱因之一）。
3. **floor 保护**。`AGENTOS_MODEL_CONCURRENCY_FLOOR`（默认 1）：连续 429 也不许把并发压到 0，防止活锁。
4. **可观测**。闸门每次乘性减/加性增发一条结构化日志（当前并发、触发原因），并暴露到 run 的 audit（`safe_audit_keys` 已有通道）。

### 2.3 传输层配合：保留 Retry-After

`HttpJsonTransport._code_for_status` 只返回错误码。在抛出 `HttpTransportError` 时附带 `retry_after_seconds`（解析 `Retry-After` 头，秒数或 HTTP-date 均支持；解析失败置 None），`openai_runtime.astream/invoke` 透传到 `ModelInvocationError`，GuardedModelRuntime 读取。GLM/DeepSeek/DashScope 均遵循该头，这是最便宜的容量信号源。

### 2.4 超步语义配合：限流 ≠ 节点失败

`executor/graph.py` 超步失败处理保持 fail-fast 不变（业务异常仍整组取消），但要求节点异常在到达执行器之前已被 GuardedModelRuntime 的退避重试耗尽。为兜底"重试耗尽时恰逢长限流窗口"的场景，增加执行器级最后手段：

- 节点异常若 `cause.code == "MODEL_RATE_LIMITED"` 且该节点本 run 内未经历过限流重试耗尽（幂等键不变），执行器可将该步骤**重新入队一次**（计入 `recoveryCount`，沿用既有恢复通道）而非立即判失败。
- 重新入队全 run 生命周期最多 1 次（`AGENTOS_ACG_RATE_LIMIT_REQUEUE`，默认 1，0 关闭），防止无限循环计费。

### 2.5 旁路工具（web search / reader）独立预算

GLM web reader 500 / search 调用是辅助增强，不应拖垮主链路：

- 为 web 工具调用建立独立小预算闸门（独立信号量 + 3 次退避重试），与主模型闸门分离。
- 预算耗尽或最终失败时**降级**：AgentOutput 标注 `webSearchUnavailable: true`，节点继续执行（提示词已要求仅在有证据时引用，降级不产生幻觉引用）。

### 2.6 配置汇总

| 环境变量 | 默认 | 说明 |
| --- | --- | --- |
| `AGENTOS_MODEL_MAX_CONCURRENCY` | 4 | 动态窗口硬上限（保持现状语义） |
| `AGENTOS_MODEL_CONCURRENCY_FLOOR` | 1 | 乘性减的下限 |
| `AGENTOS_MODEL_RATE_LIMIT_RETRIES` | 5 | 429 重试次数 |
| `AGENTOS_MODEL_RATE_LIMIT_BACKOFF_INITIAL_SECONDS` | 2 | 退避初值 |
| `AGENTOS_MODEL_RATE_LIMIT_BACKOFF_MAX_SECONDS` | 60 | 退避封顶 |
| `AGENTOS_ACG_RATE_LIMIT_REQUEUE` | 1 | 执行器级限流重入队次数 |
| `AGENTOS_ACG_MODEL_MAX_CONCURRENCY` | 2 | 线程池工作线程（保持不变，需 ≥ 上限才有意义） |

`.env.windows` 推荐初值：`AGENTOS_MODEL_MAX_CONCURRENCY=2`、`FLOOR=1`，其余默认——并发 2 起步，429 时自动降到 1 并进入分钟级等待，不再崩 run。

## 三、方案 B：统一数据源（Run 可见性）

### 3.1 目标

任何一条进入运行时存储的 Run，必然出现在身份图投影中；**身份图是所有面向用户的 Run 列表的唯一权威**，运行时存储只做执行态与事件溯源。

### 3.2 缺口闭环：注册即投影

现状缺口在"Run 注册（含延迟规划重跑）到规划物料就绪之间"没有任何投影事件。补齐原则：**注册即投影，物料后补**。

1. **新增 `run.registered` 事件**：`start()` 在 `save_run(run)` 之后无条件发出（含 `defer_acg_planning` 分支），payload 只含身份图建行所需最小字段（runId、missionId、workflowId、status、createdAt、parentRunId/sourceRunId/rerunReason）。
2. **投影适配器新增 `on_run_registered`**：身份图 `workflow_runs_v2` 建行。`blueprint_id` 当前 NOT NULL + FK，两个选择：
   - **推荐（短期）**：schema 迁移把 `blueprint_id` 放宽为 NULL 可空（保留 FK），未规划 Run 建空行；workspace 投影器对 `blueprint_id IS NULL` 的选中 Run 走现有 `PLAN_SNAPSHOT_UNRESOLVED` 降级路径（已验证该诊断路径存在且可用）。
   - 备选：允许继承父 Run 蓝图建行（本次补账脚本的做法），但语义上"重跑可能换蓝图"，会造成误导性外键，不建议固化为机制。
3. **规划物料事件照旧升级**：`run.prepared`/`run.snapshot` 到达时按现有 `missing_before → on_run_prepared` 逻辑补齐蓝图/任务计划关联，幂等。
4. **flush 条件修正**：`start()` 的 flush 判断从 `not defer_acg_planning` 改为无条件（消费 `run.registered` 成本极低），消除"注册后进程即死则事件永不消费"的窗口——flush 内联消费与事件写入同进程，崩溃窗口收敛为"save_run 已提交、flush 未执行"，由 3.4 的启动对账兜底。

### 3.3 读路径统一

- `GET /missions/{id}/runs`、workspace 投影：已读身份图，保持不变。
- 全局 `GET /runs`（运行时 store）：**改为读身份图**（或聚合身份图 + 运行时活跃 Run），使聊天页"最近运行"、全局索引、工作台三处口径一致。前端 `bootstrap()` 的一致性校验（workflowRuns.ts:243）即可成立。
- 过渡期：全局列表实现"身份图全量 + 运行时独有（active）Run 合并"，迁移完成后移除合并逻辑。

### 3.4 自愈：启动对账扩展

`IdentityProjectionReconciler` 增加一个**无事件修复通道**（现有 `_consume_execution_outbox` 只能重放事件）：

- 启动时（及每次 reconcile 周期）扫描运行时 `runs` 表中**终态且身份图缺失**的 Run，走与 `run.prepared` 相同的投影路径；无规划物料的 Run 按 3.2 的空行规则落库。
- 该通道同时消化存量缺口（本次 `ops/scripts/backfill_identity_runs.py` 已手工补 1 条；其余 32 条因蓝图来源不可解析仍缺口，属于更早的历史数据，修复通道会以同样保守的规则处理：能解析则补，不能则跳过并计入 report.failures 供排查）。
- 对账幂等：以 run_id 为主键判存，重复执行无副作用。

### 3.5 一致性验收口径

红绿可验证的判据（沿用全链路验收习惯）：

1. 造一个 deferred-planning 重跑并令其在规划期失败（如恢复 run_d937 的 "capabilities without an Agent binding" 场景）→ 任务工作台 Run 列表必须出现该 Run。
2. 任一 Run 运行中重启 ai-service → 重启后 60s 内（启动对账）三处列表（工作台 / 任务历史 / 全局索引）Run 数一致。
3. `GET /missions/{id}/runs` 返回条数 == `GET /runs?…` 中该 mission 的条数（CI 可断言）。
