# 跨操作系统兼容开发方案

日期：2026-11-26。性质：下一阶段开发设计与验收依据，尚未实施。

## 1. 目标与范围

在现有 Windows 原生持久栈基础上，逐步支持 Windows、Linux、macOS，保持同一套 Vue 前端、TypeScript Backend、Python AgentOS、Hands 和通信／持久化合同。操作系统适配只处理路径、凭据、依赖、进程、终端与桌面集成，不新增业务执行器、身份系统或数据库权威。

按三个交付层次分别验收：

1. **开发与测试**：在目标平台安装依赖、构建并运行适用测试。
2. **本地持久运行**：首次初始化、重复启动、状态查询、停止及崩溃恢复，保留身份和数据。
3. **桌面发行**：真实桌面、终端、安装、升级与卸载验证。

三个层次不能互相替代。Linux 上构建前端成功，不代表完整服务或桌面已支持；WSL 和虚拟路径测试也不替代宿主平台原生验收。本阶段沿用原生部署方向，容器不作为兼容性的前提。

## 2. 支持矩阵与推进顺序

下表中的 Linux/macOS 版本为建议的首轮验收基线，正式发布时再根据 Electron、Python 和依赖支持范围冻结最低系统版本。

| 目标 | 架构与系统基线 | 当前证据 | 本阶段目标 |
|---|---|---|---|
| Windows | Windows 11 x64 | 已有 N03、DPAPI、Memurai、Electron/ConPTY 实现及阶段验证；安装升级仍需发行验收 | 保持现有 Home、启动入口与权限边界兼容 |
| Linux 服务 | Ubuntu 24.04 LTS x64 | CI配置含Ubuntu前端／后端检查；未完成整栈原生验收 | 优先支持无桌面的完整持久栈 |
| Linux 桌面 | Ubuntu 24.04 LTS x64，X11与Wayland分别记录 | 尚无完整产品验收 | 随后支持Electron、PTY与用户级桌面入口 |
| macOS | macOS 15或更新的验收机器，Apple Silicon arm64 | 尚无完整产品验收 | 支持持久栈、Keychain、Electron与zsh终端 |
| 扩展架构 | Linux arm64、macOS x64、Windows arm64 | 本轮未核验 | 首轮不承诺发行；具备实机及依赖证据后单列验收 |

建议顺序为 Windows 回归与公共逻辑抽离 → Linux 服务 → Linux 桌面 → macOS arm64 → 各平台发行。可并行收集依赖可用性，但每个平台的运行承诺必须有独立证据。

版本权威仍为根目录[.python-version](../../.python-version)与[.node-version](../../.node-version)：当前分别为Python 3.14和Node 24.22.1。平台差异不应产生未经批准的Python／Node版本漂移。

## 4. 方案选择与职责边界

| 方案 | 优点 | 代价与适用判断 |
|---|---|---|
| **公共编排＋平台适配，推荐** | 身份、数据、健康、回滚共用；平台行为可以独立测试 | 需先拆开Windows工具调用与公共状态逻辑 |
| 各平台复制一套完整启动器 | 单个平台首次接通较快 | 重复维护身份、端口、恢复逻辑，后续容易漂移 |
| 要求所有系统通过同一容器入口 | 环境一致性较强 | 不覆盖本机PTY、桌面权限和凭据，与当前原生交付方向不匹配 |

建议的新增目录如下，均为**规划路径，当前尚不存在**：

```text
ops/scripts/infra/native/
  cli.py                 # 统一命令解析及结构化结果
  lifecycle.py           # 依赖就绪、启动、状态、关闭与失败回滚
  home.py                # Home布局、格式兼容与身份绑定
  capabilities.py        # 平台与依赖能力发现
  platform/
    base.py              # 技术接口与结果类型
    windows.py           # 复用现有DPAPI、ACL与进程管理
    linux.py             # POSIX进程、XDG路径、Secret Service适配
    macos.py             # POSIX进程、Keychain与macOS路径
ops/scripts/infra/tests/
  test_native_home.py
  test_native_capabilities.py
  test_native_lifecycle.py
```

Python统一启动器管理应用服务生命周期；Node侧继续使用现有Electron、Terminal与Hands实现，通过其配置／协议对接。不要为了统一语言而重写这些组件。

平台接口按责任暴露：`resolve_paths()`、`credential_store`、`restrict_permissions()`、`spawn_owned()`、`inspect_identity()`、`terminate_owned_tree()`、`discover_dependencies()`。公共模块不直接导入Win32模块，操作系统模块仅在对应平台装配。

进程身份至少包含PID、启动时间及所属Home／服务标识；停止前重新核对。平台模块不得因某端口占用而终止未知进程，也不能用“kill所有python/node”完成回收。

## 5. 路径、身份与持久数据

### 5.1 目录策略

| 项目 | Windows | Linux | macOS |
|---|---|---|---|
| 默认数据位置 | 保留`%LOCALAPPDATA%/ZhiyiNative/default` | `${XDG_DATA_HOME:-$HOME/.local/share}/zhiyi/default` | `~/Library/Application Support/Zhiyi/default` |
| 缓存默认位置 | 应用本地缓存目录 | `${XDG_CACHE_HOME:-$HOME/.cache}/zhiyi` | `~/Library/Caches/Zhiyi` |
| 临时文件 | 平台temp下的本次运行目录 | 同左，受限权限 | 同左，受限权限 |

显式Home优先于默认值。现有`KINLIN_NATIVE_HOME`兼容接口保留；新命令只提供一个明确的`--home`参数。路径应按宿主解析并检查真实路径、符号链接与目录归属；持久状态中的绝对路径不能从Windows直接照搬到POSIX。

应用安装目录可只读；数据库、上传、日志、缓存和凭据不得写入应用包／asar。数据默认在本地磁盘；网络共享和同步盘暂不进入支持承诺，锁与SQLite语义需要另外验收。

### 5.2 数据及身份兼容

- 保留原有LocalIdentity、actorId、legacyUserId和环境绑定校验；跨平台不重新实现用户身份。
- Windows旧Home读取不变；新增平台采用明确版本的环境格式。格式升级先校验、备份，再原子提交；`up`不能暗中轮换身份、重建数据库或重新应用历史迁移。
- 多Home隔离端口、凭据、PID与数据库。默认端口仍来自`runtime-defaults.json`，已有端口偏移规则继续复用。
- 跨OS搬迁通过明确的导出／导入流程：PostgreSQL使用逻辑备份；SQLite停写后备份或使用其备份接口；上传材料核对摘要；目标平台重新封装凭据。不要直接复制PostgreSQL数据目录或DPAPI密文。
- 本阶段优先保证各平台本地运行。任意方向的跨OS迁移只有完成独立迁移验收后才声明支持。

## 6. 凭据、依赖与平台能力

### 6.1 凭据存储

Windows沿用当前用户DPAPI；macOS使用用户Keychain；Linux桌面优先Secret Service。无桌面的Linux可能没有可用钥匙环，必须在`doctor/init`阶段明确报告。

无钥匙环时，首轮无界面验收可采用显式注入凭据，限制到必要服务，并明确不提供自动持久化。无人值守持久凭据方案需单独定义密钥来源和解锁方式；不得自动回退明文、把解密密钥与密文放在同一目录，或扩大继承环境变量。

POSIX敏感目录以0700、文件以0600为目标，并检查实际owner与权限；Windows维持受限ACL。真实权限由适配器检测，失败时中止初始化。日志、命令行、诊断结果与终端子进程不得包含服务凭据。

### 6.2 依赖与锁

保留当前`.in`作为约束权威，迁移过程中保留Windows旧锁入口。先为Linux x64和macOS arm64分别生成Python3.14锁及开发锁，核查全部传递依赖与wheel可用性；不能只从Windows锁中删掉`pywin32`就宣称可安装。

新增锁建议命名为`requirements.<os>-<arch>-py314.lock`，开发锁同维度配套，并以对应运行锁约束共享依赖。生成工具及版本必须固定，更新`check_repository_hygiene.py`的核对范围。每个目标平台执行带哈希、仅二进制的安装和`pip check`；缺wheel时明确列出阻塞依赖，评估版本调整或独立可选能力。

`package-lock.json`保持各包现有权威；`node-pty`等原生模块在目标平台重新安装或构建，不能跨OS复制`node_modules`。纯逻辑测试可设置`ELECTRON_SKIP_BINARY_DOWNLOAD=1`，真实桌面测试必须安装对应Electron二进制。

数据库首轮优先“发现并使用已安装依赖”：Windows保持PostgreSQL／Memurai；Linux/macOS使用经过合同验证的PostgreSQL及Redis兼容服务。记录二进制路径、版本、架构和启动方式。Memurai兼容不代表可忽略命令、过期、持久化与认证差异。

开发阶段可使用系统包管理器准备依赖，但启动器不自动提升权限、注册系统服务或接管已有实例。发行阶段的自带依赖需单独处理许可证、架构和平台可重定位性。

### 6.3 能力发现与降级

输出建议结构：`os`、`arch`、`runtimeVersions`、`credentialStore`、`dependencies`、`capabilities`、`blockingReasons`；禁止输出密钥。能力区分`available/unavailable/blocked`并给出可行动的原因。

Linux无图形会话可以正常运行服务，但桌面能力不可用；钥匙环不可用应阻止相应持久凭据能力；PTY不满足要求则明确禁用交互终端。不能把缺能力伪装成空成功或通过吞异常继续运行。

## 7. 进程、Shell、文件和桌面

**进程生命周期。** Windows复用现有归属核验和进程树机制；POSIX创建应用所属进程组／会话，先请求优雅退出，再对已核实归属的进程组升级终止。验证启动失败回滚、PID复用、父进程崩溃、子进程脱离以及重复down。只停止启动器拥有的服务，外部数据库只关闭连接。

**终端。** 在现有Terminal服务中补充POSIX的HOME、USER、LOGNAME、SHELL、TMPDIR、LANG／LC_CTYPE等必要环境，保持密钥隔离；PATH查找按平台处理大小写和分隔符。Linux支持已安装bash，macOS优先用户合法zsh，启动前核验可执行文件。Shell选择仍由服务端profile白名单控制，网页不得传任意可执行路径。

实际测试交互输入、中文、窗口缩放、Ctrl+C、后台子进程、关闭标签与退出回收。登录Shell可能读取用户配置，不能因此把全部环境变量透传。用户终端与AI的Hands工具执行继续分离，授权不互通。

**文件工作区。** 使用Path／Node path，不拼固定反斜杠。覆盖中文与空格、大小写差异、Unicode规范化、只读目录、长路径、symlink／junction越界和重命名。规范化后仍需验证工作区边界；不要只做字符串前缀比较。写入保持临时文件＋原子替换，分别验证文件占用、权限和跨文件系统行为。

**桌面。** Electron只管窗口和原生交互。macOS建议关闭最后窗口后保留应用、Dock激活重新打开窗口；显式退出时回收所属PTY与LSP。Windows/Linux关闭语义保持现有行为，背景服务的停止仍由运行器控制。不同平台快捷键使用Ctrl／Cmd映射；托盘不可用时提供菜单和窗口入口。

Linux分别记录X11与Wayland的窗口、托盘、输入法和文件选择器行为。macOS不为普通终端默认申请辅助功能或录屏权限；只有真实产品能力需要时才增加权限流程。

## 8. 分阶段开发与交付

每阶段形成独立可评审变更，先补可复现失败用例，再实施，最后附本机／CI证据。这里是路线级开发文档；单个阶段进入实施前按当前源码进一步拆分任务和测试。

| 阶段 | 主要文件或组件 | 交付物 | 准入／完成条件 |
|---|---|---|---|
| CP-00 基线 | 当前Windows启动器、依赖锁、两份workflow、现有测试 | 平台依赖与接口清单、Windows回归记录 | 修复后的workflow通过actionlint；记录Windows功能结果，不能用语法校验替代功能 |
| CP-01 公共运行器 | 规划的`infra/native/`、现有`windows/native/`、运行器测试 | 路径／能力／凭据／进程接口，Windows薄入口 | 原Home原身份重复启停；普通用户运行；未知进程不受影响 |
| CP-02 Linux服务 | Linux适配、平台锁、应用与Backend、Hands | 无桌面的init/up/status/down与恢复 | 新用户环境完成安装、准备、健康与故障恢复，且Windows无回退 |
| CP-03 终端与桌面 | Terminal sessions、Electron main／dev、工作区与PTY测试 | Linux桌面与真实PTY；POSIX路径用例 | 中文／Shell／Ctrl+C／回收通过；图形会话类型与限制记录完整 |
| CP-04 macOS | macOS适配、Keychain、arm64锁、Electron生命周期 | Apple Silicon原生开发与持久栈 | 不经Rosetta的安装与运行；Keychain和Dock／退出实机验收 |
| CP-05 三平台CI | application-ci、backend-ci、hygiene与测试分组 | 平台矩阵、产物与失败诊断 | 必需用例真实执行；平台跳过可见；不把全跳过视为通过 |
| CP-06 发行 | electron-builder、portable装配、更新与备份文档 | Windows/Linux/macOS独立制品和发布清单 | 各目标实机安装、升级、卸载、权限、数据保留验证 |

不要在CP-00阶段直接将全部Windows测试放进三平台矩阵：先区分公共合同、平台实现和真实集成，再扩大运行范围。另一方面，不能长期通过skip隐藏跨平台必需能力。

## 9. CI与验收设计

现有Python内核、应用测试及npm脚本作为检查入口继续复用：

```text
python -m pytest --rootdir=. -c apps/agentOS/pytest.ini TEST/tests -n 4 --dist loadscope -q
python -m pytest --rootdir=. -c apps/agentOS/pytest.ini apps/agent/tests -n 4 --dist loadscope -q
python -m pytest --rootdir=. -c apps/agentOS/pytest.ini ops/scripts/infra/tests -q
python ops/scripts/infra/check_repository_hygiene.py
```

这些是**当前命令入口**，不是承诺在Linux/macOS上当前即可全通过。各npm包在自身目录执行`npm ci`、已有typecheck、build和test脚本；前端分别build:web与build:electron。平台依赖安装完成后才执行适用检查。

CI分四组：

1. 公共逻辑与合同：Windows、Ubuntu、macOS各自运行；固定Python／Node与平台架构。
2. 平台集成：DPAPI／ACL／ConPTY、Secret Service／POSIX、Keychain／arm64分别归对应平台。
3. 整栈冒烟：使用独立临时Home、随机端口／偏移和测试凭据，完成健康检查、一次文件任务、通信来源、SSE、重启恢复与清理；真实模型调用作为独立可选作业，不能阻塞普通PR。
4. 桌面与发行：各OS原生构建；无头GUI只覆盖自动化部分，输入法、托盘、安装签名和系统弹窗仍需实机记录。

测试标记建议新增`platform_windows/platform_linux/platform_macos/native_integration/desktop_smoke`，不是当前已实现配置。收集结果附执行数、跳过数及原因。必需平台用例无运行证据时发布状态为阻塞。

工作流新增时保留含冒号命令的块标量，提交前运行`actionlint`，避免再次出现推送后因YAML解析失败而完全没有运行测试。

### 验收场景

| 场景 | 三平台共同要求 |
|---|---|
| 首次初始化／第二次up | 不重复创建身份、重建库、轮换已有凭据 |
| 目录含中文、空格及只读安装目录 | 启动与文件操作正确，运行数据进入Home |
| 陌生进程占用端口 | 拒绝并说明原因，不终止该进程 |
| 单服务崩溃／整栈异常退出 | 状态可信；只恢复所属实例；不重复提交业务结果 |
| 数据持久化 | PostgreSQL、SQLite、附件和Run／证据引用重启后可用 |
| 文件与路径越界 | 对symlink、junction和路径穿越保持相同授权边界 |
| 终端退出 | 仅回收所属会话与子进程，无残留、不误杀 |
| 预算与通信 | 相同任务输入保持字段许可、来源、分页和预算语义一致 |
| 升级与回退 | 失败可定位；保留Home；无损回退需与schema版本兼容 |

## 10. 发行与完成标准

Windows先维持x64 NSIS；Linux先选定一种主发行物再验证，不能假定AppImage覆盖全部发行版；macOS先独立arm64应用包，再加入签名、公证与安装包。不同CPU和OS独立构建原生依赖，制品命名包含版本、OS、架构和摘要。

macOS签名／公证凭据与Linux／Windows发行凭据只进入受控发行作业；普通构建可以生成明确标识的未签名测试制品。未签名可运行不代表已满足用户安装分发要求。升级／卸载默认保留用户数据，删除数据必须是独立明确操作。

平台从“实验”升级为“支持”至少需要：依赖可重复安装、适用合同与平台集成测试、独立Home整栈冒烟、真实桌面记录（如声明桌面支持）、发行安装升级记录（如声明可发行）。将结果、环境和已知限制写入同一支持矩阵后，再更新根README能力表述。
