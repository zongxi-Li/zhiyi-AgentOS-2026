# 端边云资源注册中心详细设计

## 1 设计说明

### 1.1 编制目的

资源注册中心是 AgentOS 执行内核中负责资源事实管理和执行资源分配的基础部件。本文用于说明该部件的总体结构、数据模型、运行流程、关键算法、接口约束、安全机制以及与 Runtime 的集成方式，为代码实现、联调测试和后续验收提供统一依据。

本文所述设计以当前 Node/Agent 两张主账本的实现为基础。旧 Resource 账本在迁移期间继续承担兼容查询和历史运行适配职责，但不再作为新调度、健康判断、凭据管理或租约分配的主数据源。

### 1.2 设计范围

资源注册中心管理以下对象和行为：

1. 执行节点的静态能力、部署位置和运行状态；
2. Agent 的能力声明、节点约束和运行状态；
3. 节点登记、凭据签发、签名心跳和健康判定；
4. Agent 与 Node 的联合筛选和执行绑定；
5. 面向具体执行尝试的租约申请、释放和过期回收；
6. 本地执行、远程执行与旧 Resource 接口之间的兼容关系。

工作流依赖、任务语义、图结构、条件分支和业务重试不属于资源注册中心的职责，由 Planner、Executor 和 ExecutionRuntime 负责。

### 1.3 术语约定

| 术语 | 定义 |
|---|---|
| Node | 真实承载执行的设备、进程或远程服务节点 |
| Agent | 提供一种或多种执行能力的逻辑角色 |
| Profile | 资源的静态画像，描述稳定能力和治理属性 |
| Snapshot | 资源的动态快照，描述当前负载、心跳和健康状态 |
| Binding | 某次执行尝试选定的 Agent/Node 配对 |
| Lease | 在限定时间内占用资源容量的使用凭证 |
| 真源 | 系统中唯一允许写入并作为决策依据的数据来源 |
| 兼容投影 | 将新账本数据转换为旧接口所需字段的只读视图 |

## 2 建设背景与设计目标

### 2.1 原有模型的问题

早期资源模型使用单一 `ResourceProfile` 和 `ResourceSnapshot` 表，通过 `resourceType` 区分 Agent、工作节点、模型服务、工具服务等多种对象。这种模型在资源类型较少、执行范围局限于单进程时可以工作，但在端边云协同场景下存在三个结构性问题：

第一，Agent 与执行节点的职责被混在同一对象中，无法表达“同一个 Agent 可以部署到多个节点”以及“同一个节点可以承载多个 Agent”的关系。第二，资源的静态能力、动态健康和执行凭据容易在多个服务中重复维护，导致状态来源不一致。第三，租约只绑定 `resourceId`，无法准确约束 Agent 与 Node 组合的并发容量，也无法在跨进程场景下可靠防止重复占用。

### 2.2 设计目标

本次重构确立以下目标：

- 以 Node 和 Agent 作为两个独立的主账本对象；
- 以 SQLite Store 保存持久化画像、快照、凭据和 nonce；
- 以 `(agentId, nodeId)` 作为新执行绑定的完整身份；
- 将步骤约束、Agent 约束和 Node 状态纳入同一调度决策；
- 通过 Redis Lua/CAS 或等价的原子协调机制避免并发超卖；
- 通过签名、时间窗、nonce 和严格递增序号保护远程观察接口；
- 在不破坏历史运行和旧 API 的前提下逐步退出旧 Resource 真源。

### 2.3 设计原则

资源注册中心遵循“事实与决策分离、静态与动态分离、身份与位置分离、兼容与主路径分离”的原则。

资源器记录资源事实并提供可用性判断，但不解释任务语义；Profile 描述稳定属性，Snapshot 描述瞬时状态；Agent 表达能力和使用约束，Node 表达承载条件和运行位置；旧字段可以继续返回，但不得反向成为新路径的写入源。

## 3 总体架构

### 3.1 逻辑结构

```text
                    +-----------------------+
                    |      ExecutionRuntime |
                    +-----------+-----------+
                                |
                         BindingRequirement
                                |
                    +-----------v-----------+
                    | TwoLayerScheduler    |
                    | Agent/Node 联合调度   |
                    +-----+-------------+---+
                          |             |
                    +-----v-----+ +-----v-----+
                    | AgentService| | NodeService|
                    +-----+-----+ +-----+-----+
                          |             |
                    +-----v-----+ +-----v-----+
                    | AgentStore | | NodeStore  |
                    | SQLite     | | SQLite     |
                    +-----------+ +-----+-----+
                                          |
                               +----------v----------+
                               | LeaseCoordinator    |
                               | Redis / InMemory    |
                               +---------------------+
```

Runtime 在准备阶段生成冻结的 `BindingRequirement`，调度器根据 Agent 和 Node 两张账本得到合法配对；执行阶段凭配对申请租约，随后由本地 Agent 或 Node Adapter 完成执行。旧 Resource API 位于兼容边界；迁移期间仍可服务旧登记、旧观察和历史运行，但不得向新调度提供主决策数据。

### 3.2 组件职责

| 组件 | 主要职责 | 持久化/状态要求 |
|---|---|---|
| `NodeStore` | Node 画像、快照、凭据、nonce 的存取 | SQLite 持久化，版本 CAS |
| `AgentStore` | Agent 画像、快照的存取 | SQLite 持久化，版本 CAS |
| `NodeService` | Node 登记、凭据校验、心跳、健康查询 | 统一 Node 写入口 |
| `AgentService` | Agent 登记、状态上报、能力候选查询 | 统一 Agent 写入口 |
| `AgentDirectory` | 将进程内 Agent 写入 Agent 主账本 | 只做登记投影 |
| `TwoLayerSchedulerService` | 联合筛选、评分、租约创建 | 不修改工作流语义 |
| `LeaseCoordinator` | 原子占用、释放、过期处理 | 生产使用 Redis |
| `NodeExecutionAdapter` | 调用远程执行节点 | 从 NodeService 获取凭据 |
| Legacy Resource Facade | 旧资源字段和接口兼容 | 只读投影和历史适配 |

### 3.3 主数据关系

Node 与 Agent 之间不建立静态一对一关系。Agent 的 `allowedNodeIds` 是调度白名单，AgentSnapshot 的 `nodeId` 是当前运行位置；前者表达策略，后者表达事实。一次具体执行的关系由租约和 Runtime 的 `nodeAgentBindings` 保存。当前实现以 `nodes`、`agents` 两个主表承载两个主账本，并在 Node 侧增加凭据表和 nonce 表；“两张表”指两个逻辑主账本，不要求画像和快照必须拆成四张物理表。

## 4 数据模型设计

### 4.1 NodeProfile

NodeProfile 保存节点的稳定属性，主要字段如下：

| 字段 | 含义 |
|---|---|
| `nodeId` | 节点唯一标识 |
| `nodeType` | `worker`、`model`、`embedding`、`tool` 或 `mcp` |
| `deploymentTier` | `local`、`terminal`、`edge` 或 `cloud` |
| `cpuCores`、`memoryMb` | CPU 和内存能力 |
| `gpuType`、`gpuMemoryMb` | GPU 类型和显存 |
| `modelIds` | 节点可承载或直连的模型集合 |
| `privacyLevel`、`dataZone` | 数据处理等级和驻留区域 |
| `costPerUnit` | 单位执行成本 |
| `ownerScope` | 节点归属范围 |
| `executionEndpoint` | 远程执行地址及凭据引用 |
| `labels`、`metadata` | 查询标签和厂商扩展字段 |
| `enabled`、`version` | 是否接受新任务及画像版本 |

`modelIds` 必须作为显式字段存在，不能仅存放在 `metadata` 中，否则调度器无法对模型约束进行稳定校验和审计。

### 4.2 NodeSnapshot

NodeSnapshot 保存节点当前运行事实：

```text
nodeId
observationSequence
observedAt / lastHeartbeat
cpuUtilization / gpuUtilization
availableMemoryMb / queuedTasks
latencyMs
healthStatus
consecutiveFailures
metrics
```

`observationSequence` 是节点侧生成的单调递增序号。服务端拒绝小于或等于当前值的观察，保证迟到数据不能覆盖较新的状态。

### 4.3 AgentProfile

AgentProfile 描述逻辑能力和使用约束：

```text
agentId
capabilities
requiredModelIds
requiredGpuMemoryMb
minPrivacyLevel
allowedNodeIds
labels / metadata
enabled / version
```

`capabilities` 表示 Agent 可以执行的能力集合，包含能力标签和 skill 标识。`requiredModelIds`、`requiredGpuMemoryMb`、`minPrivacyLevel` 表示 Agent 自身的最低运行要求。调度时这些要求与步骤要求取交集，不允许步骤约束放宽 Agent 的安全条件。

### 4.4 AgentSnapshot

AgentSnapshot 保存 Agent 的动态状态：

```text
agentId
observationSequence / observedAt
state: idle | busy
nodeId / currentStepId
successRate / avgLatencyMs / avgTokens
healthStatus / metrics
```

本地 Agent 由应用注册和运行时状态更新维持；远程 Agent 可通过事件或心跳更新。只有处于允许状态且能力集合满足步骤要求的 Agent 才能进入候选集。

### 4.5 BindingRequirement 与 ExecutionBinding

`BindingRequirement` 是 Runtime 为一个步骤冻结的资源要求，包含能力、资源类型、部署层、数据区、owner、标签、成本、延迟、隐私等级、模型和显存等字段。

`ExecutionBinding` 是一次具体尝试的选择结果，至少包含：

```text
bindingId, runId, stepId, attemptId
resourceId, resourceType, snapshotVersion, boundAt
metadata(agentId, nodeId, scoreFactors, effectiveRequirements)
```

新路径通过 metadata 和关联租约记录完整保存 `agentId`、`nodeId`；`resourceId` 仅用于旧状态和旧接口兼容。

### 4.6 ResourceLease

新租约包含以下身份和生命周期字段：

```text
leaseId
resourceId       # 兼容字段，生产路径等于 nodeId
agentId
nodeId
runId / stepId / attemptId
slotCount
status: active | released | expired
createdAt / expiresAt
```

租约状态变化必须单向进行。处于 `released` 或 `expired` 的租约不可重新用于执行，也不能再次贡献活动槽位。

## 5 持久化与一致性设计

### 5.1 Store 结构

NodeStore 和 AgentStore 分别保存画像和快照。当前实现将同一账本对象的画像与快照序列化保存在主表中，以版本字段实现快照并发控制；NodeStore 另设凭据表和 nonce 表。默认应用使用 SQLite Store，测试和单进程场景可使用 InMemory Store。

应用启动时由 `wiring.py` 创建：

```text
AGENTOS_NODE_DB  -> data/nodes.sqlite3
AGENTOS_AGENT_DB -> data/agents.sqlite3
```

Store 对外暴露登记、查询和带 `expected_version` 的更新方法，Service 不绕过 Store 直接操作数据库。

### 5.2 乐观并发控制

画像和快照更新采用版本号 CAS。请求提交时携带读取到的版本号；数据库只在版本匹配时写入新状态并递增版本。若版本不匹配，服务返回冲突，调用方重新读取后决定是否重试。

这种设计解决了两个问题：一是多个 Runtime 进程同时刷新心跳时不会发生静默覆盖；二是调度器可以在绑定前确认自己读取的快照版本，避免使用明显过期的节点状态。

### 5.3 真源和投影

目标状态下，写入路径只允许进入 NodeService、AgentService 和 LeaseCoordinator。旧 ResourceService 只读取新账本并生成旧字段，不再保存另一套健康、容量、凭据或租约状态。当前迁移实现仍保留部分旧登记和旧观察接口，属于待收敛的兼容写路径，不得作为新调度依据。

兼容映射规则如下：

| 旧资源类型 | 新主对象 | 旧 ID 的语义 |
|---|---|---|
| `agent`、`skill` | Agent | `agentId` |
| `worker`、`model`、`embedding`、`tool`、`mcp` | Node | `nodeId` |

当旧 `resourceId` 无法唯一映射时，系统必须返回明确错误，不得猜测为本地 Agent 或绕过租约直接执行。

## 6 Node 登记、认证与健康管理

### 6.1 节点登记

本地 Node 由应用启动时登记；远程 Node 调用 `/nodes/register` 登记。远程登记必须满足：部署层不能为 `local`、必须声明 `ownerScope`、必须提供非本地执行端点。

登记成功后，服务端生成节点凭据。凭据明文只在登记响应中返回一次，Store 保存凭据摘要和加密密文，不保存可直接读取的明文密钥。

### 6.2 观察请求签名

远程节点调用：

```text
POST /nodes/{id}/observation
```

请求头：

```text
X-Node-Credential-Id
X-Node-Timestamp
X-Node-Nonce
X-Node-Signature
```

签名原文由以下五部分按换行拼接：

```text
HTTP_METHOD
PATH
TIMESTAMP
NONCE
SHA256(BODY)
```

服务端校验顺序为：读取凭据、校验凭据 ID、校验时间窗口、校验 HMAC、原子消费 nonce、检查观测序号、执行快照 CAS 更新、刷新健康投影。任何校验失败均不得改变快照。

### 6.3 心跳状态更新

NodeService 的 `observe_remote` 接收 CPU 利用率、GPU 利用率、可用内存、排队任务数、延迟、时间戳和观测序号。服务端根据负载和最近心跳更新快照，并将失败次数传递给健康监视器。

当前健康状态包括 `online`、`busy`、`overloaded`、`stale` 和 `offline`。调度器拒绝陈旧或离线节点；远程执行错误会通过 NodeService 写回失败状态，而不是只修改旧 Resource 健康对象。

## 7 Agent/Node 联合调度

### 7.1 调度输入

调度输入由步骤约束和账本状态共同组成：

```text
步骤要求：capabilities、modelIds、gpuMemory、privacy、nodeType、tier、dataZone...
Agent画像：capabilities、requiredModelIds、requiredGpuMemory、minPrivacy、allowedNodeIds
Agent快照：state、successRate、metrics
Node画像：modelIds、gpuMemory、privacy、endpoint、capacity、labels
Node快照：health、load、queue、latency、available slots
```

### 7.2 联合筛选过程

`TwoLayerSchedulerService.schedule()` 不是先独立选择 Agent，再独立选择 Node，而是枚举合法的 `(Agent, Node)` 配对：

1. 从 AgentStore 中筛选已启用、能力完整且状态可接受的 Agent。
2. 计算步骤模型要求与 Agent 模型要求的并集。
3. 计算步骤显存要求与 Agent 显存要求的最大值。
4. 计算步骤隐私等级与 Agent 最低隐私等级中更严格的等级。
5. 遍历 NodeStore，只保留满足 Agent 节点白名单的节点。
6. 校验节点模型、显存、隐私、健康、类型和部署层。
7. 对通过硬约束的配对计算分数并选取最优结果。

当前 `TwoLayerSchedulerService.schedule()` 已实际执行的联合硬约束包括：Agent 启用状态、能力集合、忙闲状态、Agent 白名单、步骤与 Agent 的模型要求合并、步骤与 Agent 的显存要求取最大值、隐私等级取更严格值、Node 白名单、节点类型、节点模型、节点显存以及节点健康状态。`BindingRequirement` 中的部署层、数据区、owner、标签、成本、延迟和远程执行开关已经进入合同模型，但尚未全部接入 `schedule_ready()` 的硬约束判断；在迁移完成前，这些字段属于设计约束而非已完全生效的运行时隔离条件。

Agent 白名单为空表示不限制节点；非空时，白名单之外的节点即使资源条件更好也不能被选中。若没有合法配对，返回 `NO_ELIGIBLE_RESOURCE`，不得回退到未授权资源。

### 7.3 评分规则

评分采用“硬约束过滤、软约束排序”的两阶段策略。Agent 侧主要使用成功率和当前运行状态，Node 侧主要使用可靠性、可用容量、负载、延迟和成本。组合分数按固定权重计算，并将 Agent 分数和 Node 分数写入审计信息。

同分时按照 `agentId`、`nodeId` 升序选择，保证相同账本状态和相同约束下的结果稳定、可复现、可测试。

### 7.4 READY 节点分配

Runtime 进入 READY 步骤后，调用 `schedule_ready()`。该方法根据冻结的 `BindingRequirement` 读取 Agent/Node 偏好，再申请租约。租约创建成功后才返回 `ExecutionBinding`；若候选存在但容量不足，返回 `NO_CAPACITY`，Runtime 在限定时间内等待或产生调度超时。

## 8 租约与并发控制

### 8.1 租约语义

租约表示某个执行尝试在有限时间内占用一个 Agent/Node 配对的容量。租约与 `runId`、`stepId`、`attemptId` 关联，具备创建时间、过期时间和状态。租约不等同于任务完成状态，任务完成后必须显式释放。

### 8.2 内存协调器

InMemoryLeaseCoordinator 使用进程锁保护租约字典，按 `(agentId, nodeId)` 计算活动槽位，并在申请、释放和查询时清理过期租约。它用于单元测试和单进程开发，不承担生产环境的跨进程协调责任。

### 8.3 Redis 协调器

生产环境使用 RedisLeaseCoordinator。一次申请通过 Lua 脚本完成：

1. 清理已过期租约；
2. 判断 `leaseId` 是否已存在，保证重试幂等；
3. 汇总同一 `(agentId, nodeId)` 的活动槽位；
4. 校验容量上限；
5. 以 `SET NX` 写入租约主体并设置 TTL；
6. 写入租约索引、槽位记录和过期集合。

任一步骤不满足条件时都不产生新的活动占用。租约重试返回原租约，释放操作删除主体和配对槽位索引，TTL 到期后由后续事务回收残留索引。

## 9 Runtime 集成设计

### 9.1 运行准备

`ExecutionRuntime._register_and_freeze_resources()` 在准备阶段完成 Agent 登记和步骤绑定：

1. 通过 `AgentDirectory` 将进程内 Agent 写入 AgentStore；
2. 根据 BindingManifest 生成步骤级 `BindingRequirement`；
3. 调用 TwoLayerSchedulerService 选择合法配对；
4. 保存 `nodeAgentBindings`，记录 `agentId`、`nodeId` 和兼容 `resourceId`；
5. 为旧调用方生成 `resourceBindings` 投影。

绑定一旦冻结，执行阶段不能根据全局 Agent 注册表重新选择其他 Agent。

### 9.2 执行与适配器

带有 Node 绑定的步骤在 READY 阶段由 TwoLayerSchedulerService 重新申请租约，并由 `_node_execution_adapter()` 创建 Node Adapter。远程适配器从 NodeProfile 读取端点，从 NodeService 读取签名凭据；本地执行继续使用进程内 Agent。

旧 Resource 调度器只用于未包含 Node 绑定的历史运行或兼容路径。新账本调度失败时，Runtime 不得静默使用旧 Resource 候选替代新配对。

### 9.3 失败处理

远程执行产生 `ResourceExecutionError` 时，Runtime 更新 Node 失败计数和健康状态，写入失败事件，并在 finally 路径释放当前租约。恢复器根据失败绑定和新的节点状态决定是否重新调度，资源器不直接改变工作流拓扑。

## 10 接口与配置

### 10.1 当前接口

| 接口 | 作用 | 数据源 |
|---|---|---|
| `POST /nodes/register` | 登记远程 Node 并签发凭据 | NodeService |
| `POST /nodes/{id}/observation` | 接收签名观察和心跳 | NodeService |
| `GET /nodes` | 查询 Node 画像与状态 | NodeStore |
| `GET /agents` | 查询 Agent 画像与状态 | AgentStore |
| 旧 `/resources` 查询及部分登记、观察接口 | 兼容既有调用方 | 迁移期兼容路径，非新调度真源 |

### 10.2 运行配置

| 配置项 | 用途 |
|---|---|
| `AGENTOS_NODE_DB` | Node SQLite 数据库 |
| `AGENTOS_AGENT_DB` | Agent SQLite 数据库 |
| `AGENTOS_RESOURCE_CREDENTIAL_KEY` | 远程 Node 凭据加密密钥 |
| `AGENTOS_COORDINATION_REDIS_URL` | Redis 租约协调地址 |

生产环境必须设置凭据加密密钥。未配置 Redis 时使用内存租约协调器，只适合单进程开发和测试，不适合多实例部署。

## 11 安全与可靠性设计

### 11.1 认证安全

Node 观察请求采用 HMAC 签名，凭据不通过日志、画像或普通 API 返回。时间戳限制请求有效窗口，nonce 防止请求重放，观测序号防止旧状态覆盖新状态。

### 11.2 数据一致性

画像和快照使用版本 CAS；远程观察按序号和版本双重校验；租约使用 Redis 原子脚本；Runtime 在绑定、事件和租约记录中保存同一 attempt identity。以上机制共同保证资源事实、调度结果和执行尝试之间可追溯。

### 11.3 失败隔离

Node 健康异常只影响资源候选资格，不直接修改工作流语义。租约过期只回收容量，不自动伪造执行成功。旧兼容路径与新主路径分离，防止旧表状态污染新调度结果。

## 12 验证方案与实现状态

### 12.1 验证内容

资源器测试应覆盖：

- Node/Agent SQLite Store 重启后画像、快照、凭据和 nonce 可恢复；
- 注册、签名观察、时间窗、nonce 重放和严格递增序号；
- Agent 白名单、模型、显存、隐私和 Node 健康联合筛选；
- 相同租约幂等重试、配对容量限制、释放和过期回收；
- Runtime 的 Node 绑定、远程 Adapter、失败状态回写和旧字段投影；
- 旧 API 查询结果与新账本事实一致。

### 12.2 当前实现

当前代码已经实现 Node/Agent SQLite 持久化、远程 Node 登记、签名观察、nonce 防重放、严格递增序号、Agent/Node 核心约束联合调度、Redis/Lua 原子租约、Node Adapter 和 Runtime 接线。旧 Resource 仍作为兼容门面存在，并保留部分旧登记、旧观察和历史运行适配路径。部署层、数据区、owner、标签、成本、延迟及远程执行开关等步骤约束尚未全部纳入新调度器的实际筛选逻辑。

### 12.3 后续完善

后续工作包括租约续期、租户和任务级配额、完整的陈旧/离线事件广播、前端和 Java 网关迁移，以及旧表和兼容门面的最终删除。删除旧实现前必须确认新接口无旧表写入、历史运行可恢复、兼容投影不再承担主路径决策，并完成多进程并发超卖验证。
