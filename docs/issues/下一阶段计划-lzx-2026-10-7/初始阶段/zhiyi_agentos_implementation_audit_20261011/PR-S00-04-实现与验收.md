## 根因及组件边界

`runtime/workflow_runtime.py:prepare_run` 已冻结 `MissionIntentBasis`；S00-03 的 `/missions/{mission_id}/semantics` 已通过 `MissionSemanticService.commit` 更新当前 Mission。二者之间没有版本差异观察或持久化用户选择。

`runtime/semantic_revision.py:SemanticRevisionService.prepare` 服务的是 WAITING_REVIEW 屏障上的 TaskPlan/Graph 补丁，它要求持久化检查点及无活动节点，并继承旧 Basis。它不能冒充 Mission Revision 切换服务。直接把新目标写进旧 Run 的 TaskPlan、ACG 或节点上下文，会破坏冻结执行依据。

因此选择现有取消和后继 Run 路径，重新准备整个 Run，而不在旧图上替换 Mission 目标。没有新增语义影响 LLM，也没有新增 Mission、Run、Graph 管理器。

## 实现合同

### 版本观察

`GET /agentos/v2/missions/{mission_id}/runs/{run_id}/revision`

- `CURRENT`：正式 Basis 来源 Revision 等于当前 Mission Revision。
- `REVISION_CHANGED`：正式 Basis 与当前 Revision 不同。
- `LEGACY_UNBOUND`：不存在正式 Basis，或使用明确标记的旧输入/标题 Basis；来源 Revision 为 0。不自动提升旧事实。
- 同时返回具体 Mission、Run、来源/目标 Revision、Run 状态、`impact=NOT_ANALYZED`、已保存决定。
- `decisionStatus` 区分 UNDECIDED、CONTINUE_SELECTED、REPLAN_REQUESTED、DECISION_STALE、SUCCESSOR_CREATED；后继 Run 存在时提供 `successorRunId`。版本差异本身不会因“继续”被伪装为已证明无影响。
- 终态 Run 可以观察历史；不能以新决定改变其执行。

### 持久化用户决定

`POST /agentos/v2/missions/{mission_id}/runs/{run_id}/revision`

请求：`operationId`、`sourceRevision`、`targetRevision`、`decision=CONTINUE|REQUEST_REPLAN`。Mission/Run 取自 URL，actor/tenant 只取可信身份边界，不接受 JSON 身份字段。

`MissionSemanticService` 使用原有 Identity write 授权；同一 `MissionSemanticStore` 适配器在其现有存储边界中写入不可覆盖的决定回执。SQLite 的 `BEGIN IMMEDIATE` 同时读取 Mission State、源 Run 和既有回执；Memory 使用原有 RLock。成功回执绑定 Mission、Run、来源/目标 Revision、操作、主体和时间。

同 Run 同操作完全相同的请求重放原回执，包括后续 Mission 更新或源 Run 终止后的历史重放；不同请求或身份复用同操作返回 OPERATION_CONFLICT。新请求必须匹配冻结来源和当前目标 Revision，源 Run 必须非终态且有效。过期、CURRENT 上无差异的决定、终态新决定明确返回 409。回执没有修改 Mission Revision，也没有覆盖 Semantic Commit/Receipt。

### 显式取消及重新规划

`POST /agentos/v2/missions/{mission_id}/runs/{run_id}/revision/{operation_id}/apply`

只有保存的 REQUEST_REPLAN 可以应用，并重新检查写权限与原决定主体。用户需先使用既有 `/runs/{run_id}/cancel` 明确取消源 Run。申请本身不会取消、批准审核或改变当前执行；旧 Run 在用户取消前仍按旧依据执行。

- 未取消源 Run：409 SOURCE_NOT_CANCELLED。
- 取消已持久化但 Coordinator 任务仍活动：202 WAITING_CANCELLATION，尚未创建新 Run，可重试。
- 此操作已被较新的决定替代：409 DECISION_SUPERSEDED。
- 目标 Mission Revision 已变化：409 REVISION_CONFLICT，不悄悄选择其他版本。
- 旧 Run 已完成、失败或被 supersede：不能由此入口取消终态、替换目标；仍可走原有终态新建 Run 入口。

安全边界满足后，通过原有 `prepare_run` 创建后继 Run：沿用身份分配、parent/source Run 关系、原 workflow、reviewMode 和冻结 executionScope，重新规划，禁止继承旧 TaskPlan/ACG 包。新 Run 冻结选择的正式 Revision，保存 `missionRevisionDecision` 审计依据。原 TaskPlan/ACG/结果保持历史。

幂等键从完整持久化决定导出，不依赖进程状态。`save_prepared_run_once` 在同一存储事务中再次检查目标 Revision、源 Run 已取消且未被删除、Mission 仍有效及最新决定，随后插入新 Run 和原有 Lifecycle Outbox。冻结之后、入库之前的并发语义更新或源 Run 删除会拒绝此次准备，不留下错误版本的 Run。

创建已持久化但 Coordinator submit 失败时，同操作重试找到原后继 Run，再次 submit，不创建第二个。后继 Run 一旦创建，即使 Mission 后续变化，重放也返回原后继 Run；不能用重放重新绑定它的 Basis。

若取消后目标版本过期，原请求不再应用。用户可通过现有终态新建 Run 入口按当前语义创建新执行。成功决定与取消事实仍保留，不撤销或重写历史。

## Workspace 与兼容性

`MissionRevisionNotice.vue` 在现有 MissionEditor 内显示紧凑提示，提供继续/申请按钮。重新打开页面从服务读取决定；取消后提供按已选版本新建 Run 的操作，已创建的后继 Run 显示 ID 并通过原运行历史打开。CAS 冲突提示刷新；网络重试复用操作标识；异步旧 Run 的观察响应不会覆盖新选中 Run。

Java 网关增加同路径透明转发并编码 Mission/Run/operation 路径段，继续使用现有认证上下文转发。没有视觉重构或新的默认 LLM 请求。

SQLite 新增 `mission_revision_decisions(mission_id,run_id,operation_id,payload)`，主键 `(run_id,operation_id)`。这是现有语义存储中独立的用户决定回执，不是第二套语义提交系统。保留 v1 Semantic Commit 格式与原 schema version，作为可选能力扩展。

仅现有显式升级入口 `SQLiteWorkflowStore(path, enable_mission_semantics=True)` 的事务添加此表；普通构造及 `enable_existing_mission_semantics()` 不执行此 DDL。已有 v1 库若尚未显式增加该表，原 S00-03 语义读写仍可使用，新增决定接口返回 503；不自动升级。需要部署该能力时由既有运维流程显式升级，不在本次执行。

Feature Flag 关闭时原旧输入创建/执行路径保持兼容，新决定接口明确返回 disabled。软删除保留回执历史、隐藏公共操作；原有显式物理清除在其事务内移除被清除 Run 的决定，支持仍未安装此表的旧数据库。

## 保证边界和后续建议

当前生产装配的正式 State、决定、Runtime Run 均在同一个 WorkflowStore SQLite 数据库中；决定接受与后继首次插入有存储级事务保护。Identity 授权/投影在其他存储、Coordinator 调度在进程内，未承诺跨存储 ACID；沿用 Lifecycle Outbox 投影修复和同操作重试。重启后记录不会丢失，但此能力不新增后台自动取消/自动重规划消费者；用户重开 Workspace 后继续明确操作。

取消沿用现有协作式 Runtime 边界，不撤销已发生的工具操作，也不证明外部服务物理工作已经全部停止。此 PR 没有实现 Effect Ledger。旧运行的所有节点仍使用旧依据，后继执行使用独立的新 Run；不会在正在执行的节点内部换目标。

本轮没有执行真实浏览器端到端、真实 LLM/provider、远程工具物理退出、部署、生产升级、断电模拟或全仓所有测试。前端证据是 Vitest/jsdom 与类型检查；其既有 jsdom 网络错误日志不应当作真实浏览器成功证据。

后续建议：独立补齐两个旧 Workspace 夹具；部署前按既有流程显式增加决定表；将来 S02 Planning Commit / 单 Run 多 GraphVersion 接入时，以此次绑定的决定及后继关系作为审计输入，继续保持各阶段执行权威独立。
