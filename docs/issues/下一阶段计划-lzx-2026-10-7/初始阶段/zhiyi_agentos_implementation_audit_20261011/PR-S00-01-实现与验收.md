# PR-S00-01：Mission Semantic Core Foundation

## 范围与内部调用

本 PR 提供可独立调用的语义内核，不自动接入 Mission 创建、Planner、IdentityV2 或 Workspace API。

```text
可信认证主体 + MissionSemanticRequest
  -> MissionSemanticService（每次验证当前 read/write 授权）
  -> 同一个 MemoryWorkflowStore / SQLiteWorkflowStore
  -> Semantic State + Commit History + Receipt + 独立 Semantic Outbox
```

Service 必须注入 `authorize(principal, mission_id, action) -> bool`。仅显式 `True` 表示允许；`False`、`None` 或异常均不能授权。调用方必须根据可信认证上下文、Mission 所有者、tenant 及当前修改权限判断，不能相信请求自报身份。现有 API 的 owner/tenant 校验是后续接入依据，本 PR 不新增对外路由。Store 是与现有 WorkflowStore 相同信任级别的内部基础设施端口，不能直接暴露为未认证 API。

使用现有 Store 实例构造 Service 后，通过 `commit(principal, request)` 写入，通过 `get_effective_snapshot`、`list_commits`、`get_receipt` 授权读取。请求只接受显式 objective、constraints、sourceRefs、operationId、expectedMissionRevision 和 missionId；actor/tenant 由 Service 注入。

SQLite 默认构造保持旧行为，不自动创建 Semantic Schema。显式使用 `SQLiteWorkflowStore(path, enable_mission_semantics=True)` 才进行增量升级并启用语义接口；本次只对临时测试库启用。未启用时语义接口明确拒绝调用。Memory 无数据库迁移，直接支持语义合同。现有运行时注入未改动，部署接入与业务库升级需另行安排。

## 已实现合同

- Mission 不存在：`MISSION_NOT_FOUND`；存在但没有语义 State：`UNINITIALIZED / missionRevision=0`。读取不写入、不提取 title/input/Identity goal。
- 首次正式提交要求 expectedRevision=0，创建 revision=1。此后每次正式语义变化递增 1；不影响 runtimeRevision、planVersion 等领域版本。
- 操作为完整替换正式 Objective、Constraints 和来源引用。Objective 非空，Constraints 必须显式提供，可为空。不同 constraintId 是不同约束；文本不做语义等价推断。
- 幂等身份为 `(missionId, operationId)`。Receipt 保存原结果、指纹版本、指纹、可信 actor/tenant 和时间。
- `COMMITTED`、`NO_OP`、`REVISION_CONFLICT` 均持久化 Receipt。同请求重放原结果；不同请求返回 `OPERATION_CONFLICT`，不覆盖旧 Receipt。修改 expectedRevision 后重试必须使用新 operationId。
- No-op 只写 Receipt，不更新 State、revision、Commit 或 Outbox。版本检查先于 No-op 判断。
- sourceRefs 仅表示已记录的引用。存在引用时快照返回 `UNVERIFIED`；无引用返回 `NOT_APPLICABLE`。本 PR 不校验来源正文、可用性或真实性，不宣称完整认知投影。

## 指纹协议 v1

SHA-256 输入为 UTF-8 JSON：`ensure_ascii=False`、键排序、紧凑分隔符、禁止 NaN。

包含 fingerprintVersion=1、command=`set_semantics`、missionId、operationId、expectedMissionRevision、actorId、tenantId、objective、constraints、sourceRefs。实时权限、Token、时间和生成的 commitId 不参与。

约束按 constraintId 排序；引用去重并排序。文本保持精确内容，不进行 Unicode 折叠、空白改写或模型推断。重复 constraintId 拒绝。固定指纹样例由测试保护；未来变更必须新增协议版本并保留旧回执规则。

## SQLite 原子性与增量 Schema

复用 WorkflowStore 的数据库和连接配置：WAL、busy_timeout、synchronous=FULL。正式提交使用：

```text
BEGIN IMMEDIATE
  -> Receipt/指纹检查（先于当前 revision）
  -> Mission 存在/删除状态检查
  -> revision 检查、合法变更与 No-op 判定
  -> 首次 INSERT 或带 revision 条件的 UPDATE CAS
  -> Commit History
  -> 独立 Semantic Outbox
  -> Receipt
COMMIT
```

异常由连接事务上下文回滚。两个连接竞争同一个 revision 时，写锁串行化读判定；后到者得到持久化 REVISION_CONFLICT。同 operationId 竞争只生成一次正式提交。

显式启用时新增 `mission_semantic_schema` 记录已应用版本，v1 在独立 `BEGIN IMMEDIATE` 内创建 State、Commit、Receipt、Outbox 四表并记录版本。没有 legacy 数据回填。State 的 missionId、Receipt 的 `(missionId, operationId)`、History 的 `(missionId, revision)` 和 `(missionId, operationId)`、Outbox 的 `(missionId, revision)` 有唯一保护。没有外键级联。

升级测试只使用临时库，验证旧记录保持不变、重复启动、未知版本拒绝及 DDL 失败回滚。部署前仍需按既有运维流程备份；本次没有升级业务库。旧二进制可读取原始表，但不能对已含语义历史的数据库执行旧物理删除方法。回退代码不应删除新表；破坏性 Schema 回退不属于本 PR。

Semantic Outbox payload 只含事件/提交/Mission ID、revision、schemaVersion、时间。没有目标/约束正文、主体身份或原始 input。事件不会写入 lifecycle_outbox；本 PR 不接投递消费者，记录保持 pending。IdentityV2 使用不同数据库，授权查询、投影消费与 WorkflowStore 提交没有跨库 ACID 保证。

内存实现与语义提交相关的 Mission/Run 写入和物理清除共享 RLock；语义变更先准备新容器再发布，读取和返回结果深复制。该锁只保证当前实例内并发，不提供跨进程持久化。

## 删除及隐私边界

公开软删除行为保持现状，语义历史保留；软删除的 Mission 拒绝新的语义变更。重放仍需当前授权。

Store 物理删除最后一个 Run 且实际移除 Mission 时，在同一个 `BEGIN IMMEDIATE` 事务内显式清除 Semantic Outbox、Receipt、History、State，再清理原有任务记录。清除根据数据库是否已安装语义 Schema 判断，不依赖实例是否启用语义接口；未知已安装版本拒绝清除并回滚。尚有其他 Run 或 delete_orphan_mission=False 时保留语义记录。内存实现遵循同一合同，并在发布前准备完整清除结果。

**已知限制：Mission ID 生命周期不复用无法由现有代码严格证明。**现有 ID 采用截短 UUID 随机生成，且 MissionManager 接受显式 mission_id；数据库没有永久禁止复用记录。因此物理清除后若调用者显式复用 ID，不能保证旧 operationId 的终身去重。本 PR 不新增含敏感历史的永久 Tombstone。调用方应避免复用 ID，严格证明需后续身份策略决策。

同库清除不等于全系统隐私清除：已有 lifecycle_outbox、IdentityV2、已投递消费者及备份的数据仍遵循各自边界。特别是已有 lifecycle_outbox 的 Mission 快照可能含旧 input，本 PR 未改变其格式或保留策略。
